**Decision memo: revise before production approval.** Six replicas and the proposed API fields do not establish availability, security, or database durability. The recommendations below separate documented behavior from configuration decisions and operational prerequisites.

1. **PDB and rollout availability.** `minAvailable: 5` does not guarantee five available replicas in all three cases. Node failure is involuntary: a PDB cannot prevent it, although unavailable Pods count against the budget. During an eviction-based node drain, a correctly selected PDB constrains evictions; requests can be rejected and retried, so a drain can stall. Direct deletion bypasses this protection. Deployment rolling updates are not constrained by PDBs, although their unavailable Pods count against the budget.

   With six desired replicas, `maxUnavailable: 2` permits rollout availability to fall to four. Recommend `maxUnavailable: 0`, `maxSurge: 1`, with capacity for the surge; `maxUnavailable: 1` is also compatible with a five-replica rollout floor. Neither configuration prevents simultaneous infrastructure failure. Sources: `concepts/workloads/pods/disruptions.md:59-65,92-140`; `concepts/workloads/controllers/deployment.md:1183-1208`.

2. **Zone spreading.** Recommend a matching application `labelSelector`, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`. Correct node labels and sufficient schedulable capacity are prerequisites. Under normal three-zone placement, six replicas can distribute 2/2/2. `DoNotSchedule` prohibits placements exceeding the permitted difference between the target domain’s count and the global minimum; `ScheduleAnyway` merely prefers placements reducing skew.

   Choose hard spreading if balance outweighs replacement availability, or soft spreading if recovery capacity takes precedence. Zone loss can leave hard-constrained replacements Pending. Explicit `minDomains: 3` makes the global minimum zero when fewer than three eligible domains remain; omitting it defaults to one. Actual behavior depends on domain eligibility and surviving capacity. Constraints do not guarantee rebalancing after removal. Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:76-131,199-214,605-623`.

3. **Probes for slow startup.** Configure a startup probe with `failureThreshold × periodSeconds` covering measured worst-case initialization. Readiness and liveness probes begin only after startup succeeds. Exhausting startup failures kills the container, with restart governed by `restartPolicy`.

   Readiness should represent ability to serve useful requests, including necessary database access; failed readiness removes the Pod from Service backends without itself restarting the container. Liveness should detect unrecoverable local failure, such as deadlock. Avoid treating a temporary database outage as a reason to restart every API replica. Liveness failures trigger restart behavior, and poorly designed checks can cause cascading failures. Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:17-48,311-347`.

4. **Termination and long requests.** The grace-period countdown begins **before** `preStop`. The hook therefore consumes the same budget as application shutdown. Normally, the hook runs before the runtime sends TERM to container process 1. A still-running hook may receive a one-off two-second extension; remaining processes receive SIGKILL when shutdown time expires.

   Endpoint handling proceeds concurrently: terminating endpoints are not immediately removed, but have `ready: false`, excluding them from regular load balancing. Their `serving` condition can support draining. Thirty seconds is a default, not a request-completion guarantee. Implement TERM handling and connection draining, then size grace time for measured hook and request durations. Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:1006-1008`; `concepts/workloads/pods/pod-lifecycle.md:584-644`.

5. **Resource settings and CPU autoscaling.** CPU requests inform scheduling and provide the denominator for utilization-based HPA. A request is not a usage ceiling: spare resources can permit higher consumption. CPU limits enforce a ceiling through throttling; memory limits are enforced reactively through OOM killing, rather than CPU-style throttling. Memory over-allocation need not cause an immediate kill.

   Set measured CPU requests for all relevant containers. If some lack CPU requests, Pod CPU utilization is undefined and HPA takes no action for that metric. Account for defaulting: a limit can become the request when no request or admission default exists. Sources: `concepts/configuration/manage-resources-containers.md:15-67`; `tasks/run-application/horizontal-pod-autoscale.md:89-102`.

6. **HPA’s conservative adjustments.** HPA starts from the rounded-up replica count implied by current versus desired metrics, but sets aside missing metrics and certain not-yet-ready CPU samples. Missing metrics are treated as 100% of target for downscaling and 0% for upscaling. Not-yet-ready Pods additionally dampen prospective scale-up using 0%. A recomputed ratio that reverses direction or falls within tolerance produces no scaling.

   Default readiness-delay and CPU-initialization windows are 30 seconds and five minutes. Downscale stabilization defaults to five minutes, selecting the highest recommendation within that window. Reported utilization excludes these conservative adjustments, so observed scaling can differ from a raw calculation. Sources: `tasks/run-application/horizontal-pod-autoscale.md:135-202,204-218`.

7. **Least-privilege networking.** Establish default-deny ingress and egress for the relevant Pods, then allow only intended API callers, API-to-database traffic on required ports, DNS resolution, and identified operational dependencies. Select namespaces and workloads narrowly.

   Ingress and egress isolation are independent. Applicable policies combine additively: a broad allow remains effective despite a separate deny baseline. Pod-to-Pod connections require both source egress and destination ingress permission; reply traffic is implicitly allowed. Explicitly preserve access to the cluster DNS service. A CNI/network controller implementing NetworkPolicy is mandatory—creating objects alone provides no enforcement. Sources: `concepts/services-networking/network-policies.md:44-81`; `concepts/security/multi-tenancy.md:208-234`.

8. **Secrets.** Reject base64-encoded production credentials in Git as a protection mechanism. Base64 obscures data but does not make it secret. Kubernetes Secrets are stored unencrypted in etcd by default; enable encryption at rest, protect encryption keys, and verify encryption in storage.

   Apply least-privilege RBAC and restrict which containers receive credentials. Namespace permission to create Pods—including indirectly through Deployments—also enables reading that namespace’s Secrets, so restricting direct Secret reads alone is insufficient. Cluster encryption does not protect a separately committed Git copy; replace that distribution practice and rotate exposed credentials. Sources: `concepts/configuration/secret.md:35-49,305-307`; `tasks/administer-cluster/encrypt-data.md:415-421,534-588`.

9. **Storage retention.** Changing a StorageClass policy does not retrofit existing PVs: dynamically provisioned PVs inherit their policy, and existing PVs must be edited or patched separately. The default is `Delete`. For supporting plugins, Delete removes both the PV and underlying storage asset. Retain leaves a released PV and its data after PVC deletion, requiring manual reclamation.

   PVC deletion differs from StatefulSet deletion or scaling. StatefulSet claim retention defaults to Retain; optional `whenDeleted` and `whenScaled` policies can delete template-created PVCs after the corresponding Pods. The documented feature-gate prerequisites must be satisfied. Recommend explicit retention and inspection of every database PV. Sources: `concepts/storage/storage-classes.md:126-135`; `concepts/storage/persistent-volumes.md:185-210`; `concepts/workloads/controllers/statefulset.md:387-423`.

10. **Prioritized rollout and validation checklist.**

   - **Before production:** remove exposed credentials, verify encryption/RBAC, test NetworkPolicy enforcement and DNS, and inspect existing PV reclaim policies. These address concrete exposure and deletion paths documented in answers 7–9.
   - **Before rollout:** establish measured probes and shutdown timing, explicit resource requests, working resource metrics, surge capacity, and zone-spread configuration. Keep the HPA minimum consistent with the intended six-replica baseline. Metrics Server is a separately deployed prerequisite in the usual resource-metrics setup (`tasks/run-application/horizontal-pod-autoscale.md:113-117`).
   - **Exercise failure paths:** test rolling updates, eviction-based drains, zone loss, missing metrics, database outages, long-request termination, and database restore.

   Approval still requires application or cluster evidence for at least four limits: worst-case startup/request duration, actual load-balancer draining behavior, surviving-zone capacity and scheduling, and database failover/backup recovery. The cited termination, topology, and retention mechanisms do not establish those outcomes (`concepts/workloads/pods/pod-lifecycle.md:612-639`; `concepts/scheduling-eviction/topology-spread-constraints.md:95-131,605-623`; `concepts/storage/persistent-volumes.md:185-210`).
