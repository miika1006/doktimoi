**Decision memo — revise before production approval.** The proposed fields do not establish end-to-end availability, request completion, confidentiality, or database durability. The recommendations below are configuration choices grounded solely in the supplied Kubernetes v1.32 corpus. Citations give local paths relative to the supplied workspace, followed by source line ranges.

1. **PDB and rollout availability.** `minAvailable: 5` does not guarantee five available replicas in every case. **Node failure:** involuntary disruptions cannot be prevented by PDBs, although they consume the budget. **Node drain:** eviction-based draining respects the budget and retries rejected evictions; this protection requires using the Eviction API rather than directly deleting Pods. A drain can therefore block. **Deployment update:** rolling updates count against the budget but are not constrained by it. With six desired replicas, `maxUnavailable: 2` permits rollout availability to fall to four. Choose `maxUnavailable: 1`, `maxSurge: 1`, with capacity for the surge; this makes rollout policy compatible with five available replicas, without guaranteeing protection against concurrent failures.  
   Sources: `docs/concepts/workloads/pods/disruptions.md:99–145`; `docs/concepts/workloads/controllers/deployment.md:1189–1211`.

2. **Zone distribution.** Configure a selector matching the API Pods, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, aiming for two replicas per zone. The topology key groups nodes by label value. With `DoNotSchedule`, skew bounds the difference between the target domain’s matching-Pod count and the global minimum; unsatisfiable placements remain pending. `ScheduleAnyway` instead prefers reduced skew without enforcing it. Recommend hard spreading initially, with an explicitly tested outage strategy. An unavailable zone’s treatment depends on eligible nodes, affinity, and taints—not simply the zone name. With `minDomains: 3`, fewer eligible zones makes the global minimum zero and can block replacement placement. Omitting it allows balancing across remaining eligible domains, but does not guarantee recovery capacity. Pod removal can also leave imbalance.  
   Sources: `docs/concepts/scheduling-eviction/topology-spread-constraints.md:82–130,167–185,605–619`.

3. **Probes for slow startup.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Until it succeeds, readiness and liveness probes are disabled. Use readiness to indicate ability to serve requests; failure removes the Pod from matching Service endpoints, rather than restarting the container. Use liveness for an application condition that warrants restarting, such as deadlock; avoid making a transient database outage alone trigger restart storms. Startup or liveness failure at the configured threshold kills the container, with restart governed by its restart policy. Probe timing and application health semantics require measurement; the documentation does not establish suitable values for this API.  
   Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–347`; `docs/concepts/workloads/pods/pod-lifecycle.md:475–497`.

4. **Termination and long requests.** The grace-period countdown begins **before** `preStop`; the hook consumes that budget. The kubelet runs the hook before asking the runtime to send TERM to process 1. An overrun hook can receive a one-off two-second extension. At expiry, remaining processes receive `SIGKILL`. Endpoint processing happens concurrently with shutdown: terminating endpoints remain temporarily in EndpointSlices but have `ready: false`, excluding them from regular traffic; `serving` supports draining decisions. Thirty seconds is a default timeout, not a request-completion guarantee. Implement application draining and choose a measured budget covering the hook and outstanding work; validate traffic propagation and connection behavior.  
   Sources: `docs/reference/kubernetes-api/workload-resources/pod-v1.md:1008–1008`; `docs/concepts/workloads/pods/pod-lifecycle.md:581–639`.

5. **Resource settings and CPU autoscaling.** Set explicit, measured CPU requests for every relevant container: requests guide scheduling and provide the denominator for utilization-based HPA. A request is not a usage ceiling; spare resources can permit higher consumption. CPU limits impose throttling, potentially affecting startup and request latency. Memory limits behave differently: enforcement is reactive through OOM killing, not CPU-style throttling or guaranteed immediate termination at the boundary. If relevant CPU requests are missing, Pod utilization is undefined and HPA takes no action for that metric. Inspect effective settings: absent admission defaults, specifying a limit without a request causes Kubernetes to copy the limit into the request.  
   Sources: `docs/concepts/configuration/manage-resources-containers.md:18–66`; `docs/tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **HPA’s conservative adjustments.** HPA sets aside missing metrics and, for CPU, not-yet-ready Pods or samples preceding readiness. Its default initial-readiness delay is 30 seconds; the CPU initialization period is five minutes. Missing metrics are assumed to consume 100% of the target during downscale calculations and 0% during upscale calculations. Not-yet-ready Pods additionally dampen an otherwise indicated upscale using a 0% assumption. If recalculation reverses direction or falls within tolerance, scaling is skipped. Reported utilization can still show the unadjusted average. Default downscale stabilization selects the highest recommendation within five minutes. Consequently, scaling need not match the raw utilization ratio; startup readiness and metrics availability materially affect it.  
   Source: `docs/tasks/run-application/horizontal-pod-autoscale.md:145–218`.

7. **Least-privilege networking.** Establish default-deny ingress and egress, then allow approved callers to the API port, API egress to the database port, database ingress from API Pods, and required DNS traffic to the actual cluster resolver. Discover and test DNS destinations and ports rather than assuming a universal resolver layout. Ingress and egress isolation are independent. Policies are additive unions: an existing broad allow defeats a restrictive policy’s intent. For Pod-to-Pod communication, both source egress and destination ingress must permit the connection; allowed replies are implicit. Supporting CNI/network-policy enforcement is a prerequisite—creating policy objects alone has no effect.  
   Sources: `docs/concepts/services-networking/network-policies.md:45–81`; `docs/tasks/administer-cluster/dns-debugging-resolution.md:138–163`.

8. **Secrets and Git.** Reject base64-encoded credentials in Git as a protection mechanism: the documentation describes base64 authentication material as obscured, not secret. Enable encryption at rest for Secrets; Kubernetes otherwise stores them unencrypted in etcd. Apply least-privilege RBAC and restrict which containers receive each Secret. Also restrict Pod and Deployment creation privileges in sensitive namespaces: someone allowed to create a Pod can use that permission to read any Secret in that namespace, even without direct Secret-read permission. Encryption at rest addresses the cluster datastore, not confidentiality of repository copies; a separate credential-delivery decision is required.  
   Sources: `docs/concepts/configuration/secret.md:35–48,286–306,658–669`.

9. **Storage reclamation and workload deletion.** Do not expect changing a StorageClass policy to retrofit existing PVs. Dynamically created PVs inherit the class policy; existing PVs needing different behavior must be edited or patched individually. The default is `Delete`: with supporting plugins, reclamation removes both the PV and backing storage. `Retain` leaves the released volume and data for manual reclamation, without automatically making it available to another claim. PVC deletion initiates reclamation; StatefulSet deletion or scaling is a separate decision. StatefulSet PVC retention defaults to `Retain`, while `whenDeleted` and `whenScaled` can request PVC deletion. Verify the documented feature prerequisites. If the database uses a StatefulSet, inspect both retention and PV reclaim policies.  
   Sources: `docs/concepts/storage/storage-classes.md:126–135`; `docs/concepts/storage/persistent-volumes.md:178–210`; `docs/concepts/workloads/controllers/statefulset.md:391–423`.

10. **Prioritized rollout and validation checklist.** First, remove repository credential exposure, enforce Secret permissions, verify network enforcement, and inspect existing database PV policies. Second, implement startup/readiness/liveness behavior and graceful draining; measure startup duration, longest supported requests, CPU throttling, and memory peaks. Third, configure compatible rollout limits, zone spreading, resource requests, and HPA behavior; test drain, rollout, zone loss, and missing-metric scenarios before broad deployment. Finally, exercise database recovery and verify retained data can actually be restored into service. At least four limits remain unproven: completion of long requests before forced termination, sufficient surviving-zone capacity, CPU utilization’s suitability for application demand, and database recovery/durability. These documents specify mechanisms, not this application’s service-level outcomes.  
   Sources: `docs/concepts/workloads/pods/pod-lifecycle.md:619–639`; `docs/concepts/scheduling-eviction/topology-spread-constraints.md:605–619`; `docs/tasks/run-application/horizontal-pod-autoscale.md:183–218`; `docs/concepts/storage/persistent-volumes.md:187–210`.
