**Decision memo — revise before production approval.** The proposed settings do not establish five-replica availability, request completion, network isolation, or database durability. The recommendations below distinguish documented behavior from configuration choices and validation prerequisites. Citations use paths relative to the supplied `docs/` directory, with inclusive source line ranges.

1. **PDB protection differs across the three disruption cases.** Node failure is involuntary: a PDB cannot prevent it, although unavailable Pods count against the budget. A drain using the Eviction API respects the PDB; with six healthy replicas and `minAvailable: 5`, one eviction is permitted, and subsequent evictions can block pending recovery. Direct deletion bypasses that protection. Deployment rolling updates are not constrained by PDBs, although their unavailable Pods count against the budget. Thus `maxUnavailable: 2` permits rollout availability to fall to four.

   Recommend `maxUnavailable: 1`, `maxSurge: 1`, with capacity for the surge. This aligns rollout-controlled unavailability with the five-replica objective at six desired replicas; it does not protect against concurrent failures. Keep the HPA minimum consistent with that operating baseline. Sources: `concepts/workloads/pods/disruptions.md:99–136`; `concepts/workloads/controllers/deployment.md:1191–1211`.

2. **Spread by zone, but explicitly choose the failure tradeoff.** Use an application-matching selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`. The topology key groups nodes with identical label values into domains. Under `DoNotSchedule`, skew bounds the target domain’s matching-Pod count relative to the global minimum; violating placements remain unscheduled. `ScheduleAnyway` instead prefers placements reducing skew without making that constraint mandatory.

   For availability during zone loss, recommend `ScheduleAnyway`, accepting temporary imbalance. Strict placement with `minDomains: 3` can block replacements when fewer than three eligible domains remain because the global minimum becomes zero. Without that setting, eligibility and remaining nodes determine the result; “zone unavailable” alone does not define scheduling behavior. Even a 2/2/2 distribution leaves only four survivors after losing a zone. Spread is not continuously guaranteed after removals. Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:82–128,527–529,605–619`.

3. **Separate startup, traffic eligibility, and restart decisions.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Until it succeeds, readiness and liveness probes are disabled. Exhausting startup failures kills the container, subject to its restart policy. After startup, readiness should report ability to serve requests, including required database functionality; liveness should detect failures for which restarting is useful, rather than treating every dependency outage as a restart condition.

   Readiness failure removes the Pod from matching Service endpoints without itself restarting the container. Liveness failure kills it, with restart governed by policy. These are documented mechanisms; suitable checks and thresholds remain application choices. Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–347,349–355`; `concepts/workloads/pods/pod-lifecycle.md:479–497,521–526`.

4. **Thirty seconds is a shutdown budget, not a completion guarantee.** The grace-period countdown begins before `preStop`; the hook consumes that budget. The kubelet runs the hook before asking the runtime to send TERM to process 1. A still-running hook can receive a small, one-off two-second extension. At grace expiry, remaining processes receive SIGKILL.

   Endpoint processing happens concurrently with shutdown. Terminating endpoints are not immediately removed from EndpointSlices, but have `ready: false`; `serving` supports draining-aware consumers. Configure the application to handle termination and finish open requests, then size grace for hook time plus measured draining time. The docs do not guarantee that thirty seconds accommodates long requests or establishes instantaneous traffic convergence. Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:1006–1008`; `concepts/workloads/pods/pod-lifecycle.md:581–639`.

5. **Size resource requests and limits deliberately.** CPU requests influence scheduling and provide the denominator for utilization-based HPA; they are not CPU usage ceilings. Containers can exceed requests when resources are available. CPU limits enforce throttling, potentially slowing startup and requests. Memory limits behave differently: enforcement is reactive through OOM kills, rather than CPU-style throttling or guaranteed immediate termination at the threshold.

   Set realistic CPU requests for every relevant container. If requests are missing, Pod CPU utilization is undefined and HPA takes no action for that metric. Check effective configuration: when a limit exists without a request or admission default, Kubernetes copies the limit into the request. Sources: `concepts/configuration/manage-resources-containers.md:18–53,64–66`; `tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **HPA intentionally differs from a raw utilization ratio.** It ignores terminating Pods and discards failed Pods, setting aside missing metrics and certain not-yet-ready CPU samples. Missing metrics are conservatively treated as 100% of target for downscaling and 0% for upscaling. Not-yet-ready Pods additionally dampen scale-up by being treated as consuming 0%. If recalculation reverses direction or falls within tolerance, scaling is skipped.

   Readiness interpretation uses configurable defaults of thirty seconds for initial readiness delay and five minutes for CPU initialization. Default downscale stabilization selects the highest recommendation over five minutes. Consequently, displayed utilization, replica changes, and the naïve ratio can disagree legitimately. Validate these timings against this API’s slow startup. Source: `tasks/run-application/horizontal-pod-autoscale.md:153–218`.

7. **Replace default allow with explicit connection allowances.** First verify that the installed networking implementation enforces NetworkPolicy; creating objects alone can have no effect. Establish ingress and egress isolation, then allow approved callers to the API port, API egress to the database port, corresponding database ingress, and other demonstrated dependencies.

   Isolation is directional. Policies combine additively as a union: a broad allow cannot be overridden by adding a deny policy. Both source egress and destination ingress must permit a Pod-to-Pod connection; reply traffic is implicitly allowed. Explicitly permit DNS queries to the cluster’s actual resolver destinations and required ports/protocols, then test name resolution under isolation. Resolver details are cluster prerequisites, not established by this design. Sources: `concepts/services-networking/network-policies.md:47–81,120–137,210–259`; `concepts/services-networking/dns-pod-service.md:15–26`.

8. **Base64 is not sufficient Secret protection.** Reject base64-encoded credentials in Git: the docs describe base64 data as obscured, not secret. Enable Secret encryption at rest; Kubernetes otherwise stores Secrets unencrypted in etcd. Apply least-privilege RBAC and restrict exposure to containers that need the credentials.

   Review workload-creation permissions as well as direct Secret-reading permissions. Someone authorized to create Pods in a namespace can read its Secrets through those Pods; Deployment creation provides indirect access too. Encryption at rest therefore does not substitute for authorization controls, nor does it protect a committed Git copy. Sources: `concepts/configuration/secret.md:300–306,36–48`.

9. **Existing PVs require explicit reclaim-policy review.** Dynamically provisioned PVs inherit the StorageClass reclaim policy, defaulting to `Delete`. Do not treat a changed StorageClass setting as a retrofit: the documented remedy for already-created volumes is editing or patching the PV itself.

   After PVC deletion, `Retain` leaves the PV released with its data, requiring manual reclamation. With a supporting plugin, `Delete` removes both the PV and backing storage. StatefulSet deletion or scaling is a separate trigger: PVC retention defaults to `Retain`, while `whenDeleted` and `whenScaled` can explicitly request PVC deletion. Verify the documented feature prerequisite. Prefer explicit retention for database volumes pending an approved recovery process. Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:185–210`; `concepts/workloads/controllers/statefulset.md:391–423`.

10. **Prioritize validation before broad rollout.** First secure credentials and verify networking enforcement; inventory existing PV policies and exercise database recovery. Second configure probes, resource requests, measured termination grace, zone placement, and compatible rollout/HPA bounds. Third conduct staged rollout, drain, zone-loss, dependency-outage, missing-metrics, and long-request shutdown exercises.

   Acceptance must include application and cluster evidence for at least these limits: maximum startup duration; completion of in-flight requests; capacity after losing two zone-local replicas; actual NetworkPolicy/DNS behavior; and database restore and storage-access behavior. These documents establish mechanisms, not those workload outcomes. Relevant constraints supporting this checklist are `concepts/workloads/pods/disruptions.md:130–136`; `concepts/workloads/pods/pod-lifecycle.md:619–639`; `concepts/services-networking/network-policies.md:47–49`; `concepts/storage/persistent-volumes.md:185–210`.
