**Decision: revise before production approval.** The proposed settings do not establish five-replica availability, request completion, confidentiality, or database durability. The recommendations below distinguish Kubernetes behavior from configuration choices and validation obligations.

Citations use paths relative to the supplied `docs/` directory and original source line ranges.

1. **PDB and rollout availability.** A `minAvailable: 5` PDB cannot prevent involuntary node failure; those unavailable Pods nevertheless count against its budget. During a normal `kubectl drain`, eviction requests respect the PDB and can be rejected and retried. This constrains voluntary eviction, provided tooling uses the Eviction API; it does not guarantee five healthy replicas against simultaneous failures. Deployment rolling updates are explicitly **not constrained by PDBs**, although their unavailable Pods count against the budget.  
   Recommend `maxUnavailable: 0`, `maxSurge: 1`, with spare scheduling capacity; `maxUnavailable: 1` is also compatible with a five-of-six rollout target. The proposed value of two permits only four available replicas during rollout. These are controller rollout constraints, not protection against concurrent failures.  
   Sources: `concepts/workloads/pods/disruptions.md:92–149`; `concepts/workloads/controllers/deployment.md:1189–1211`.

2. **Zone placement.** Configure a matching application selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, aiming for two replicas per zone. Correct node labels and sufficient capacity are prerequisites. With `DoNotSchedule`, skew limits the difference between the target domain’s matching-Pod count and the global minimum across eligible domains. `ScheduleAnyway` instead prefers placements reducing skew without enforcing that bound.  
   Choose the failure tradeoff explicitly: strict spreading can leave replacements Pending when remaining placements violate skew. With `minDomains: 3`, fewer than three eligible domains makes the global minimum zero, potentially blocking replacements in already populated zones. Omitting it defaults to one; outage behavior still depends on domain eligibility. Soft spreading permits imbalance but guarantees neither capacity nor recovery. Losing one zone from a two/two/two layout immediately leaves four replicas.  
   Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:82–130,196–214`.

3. **Probes for slow startup.** Use a startup probe with `failureThreshold × periodSeconds` covering measured worst-case initialization. Until it succeeds, readiness and liveness probes are disabled. Exhausting startup failures kills the container, subject to its restart policy. After startup, readiness should test whether this instance can serve requests; failure removes its address from matching Service endpoints without itself restarting the container. Liveness should detect a condition a restart can fix, such as deadlock.  
   I recommend separate application health checks, avoiding a liveness check that restarts every API replica merely because the shared database is unavailable. Endpoint removal is documented; instantaneous cessation of all traffic or completion of existing requests is not established by these probe rules.  
   Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–347`; `concepts/workloads/pods/pod-lifecycle.md:475–497`.

4. **Termination and long requests.** The grace-period countdown starts **before** `preStop`. The kubelet runs that hook, then sends TERM/SIGTERM to container process 1; the hook therefore consumes the same shutdown budget. A still-running hook can receive a small, one-off two-second extension. Remaining processes receive SIGKILL when graceful shutdown expires.  
   Concurrently, terminating endpoints remain represented temporarily but have `ready: false`, excluding them from regular load-balancer traffic; consumers implementing draining can inspect `serving`. Thirty seconds is a default, not a request-completion guarantee. Configure the application to stop accepting work and drain existing requests, then size grace for measured hook and drain duration. Verify signal handling and actual traffic-path behavior.  
   Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:1006–1008`; `concepts/workloads/pods/pod-lifecycle.md:584–640`.

5. **Resource requests and limits.** CPU requests inform scheduling and provide the denominator for utilization-based HPA; they are not usage ceilings. A container can exceed its request when resources are available. CPU limits enforce throttling, which can extend request latency. Memory limits instead lead to reactive OOM killing under memory pressure; exceeding a limit need not cause immediate termination.  
   Set realistic CPU requests for every relevant container, plus measured CPU and memory limits. Missing relevant requests make Pod CPU utilization undefined, so HPA cannot act on that metric. Check admitted configuration: when a limit exists without a request or admission default, Kubernetes copies that limit into the request.  
   Sources: `concepts/configuration/manage-resources-containers.md:15–67`; `tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **HPA’s conservative adjustments.** HPA starts from the current-to-target metric ratio but sets aside missing metrics and, for CPU, not-yet-ready Pods or measurements preceding readiness. Missing metrics are conservatively assumed to be 100% of target for downscaling and zero for upscaling. Not-yet-ready Pods are assumed to consume zero when assessing an otherwise indicated upscale. If recalculation reverses direction or falls within tolerance, scaling is skipped.  
   Default readiness-delay and CPU-initialization windows are 30 seconds and five minutes respectively. Default downscale stabilization selects the highest recommendation within five minutes. Consequently, scaling can differ from the raw ratio and from displayed average utilization, which excludes these adjustments. Validate startup behavior and metrics delivery under load.  
   Sources: `tasks/run-application/horizontal-pod-autoscale.md:129–218`.

7. **Least-privilege networking.** Replace default allow with policies selecting the intended Pods and isolating both ingress and egress. Add narrowly scoped permissions for approved callers to the API, API-to-database connections on the required port, DNS resolution, and other demonstrated dependencies. DNS destinations and required transport details must be confirmed in this cluster.  
   Isolation is independent in each direction. Policies are additive unions: an allow-all policy cannot be overridden by adding a restrictive one. Both source egress and destination ingress must allow a Pod-to-Pod connection; replies to allowed connections are implicitly permitted. A NetworkPolicy-capable CNI/controller is a prerequisite—creating policy objects alone can have no effect. Test allowed and forbidden connections.  
   Sources: `concepts/services-networking/network-policies.md:44–82`; `concepts/security/multi-tenancy.md:376–380`.

8. **Secrets.** Base64 is reversible encoding, not confidentiality; reject base64-only Secret manifests in Git. Kubernetes Secrets are stored unencrypted in etcd by default. Enable encryption at rest, enforce least-privilege RBAC, and expose each Secret only to containers needing it. At-rest encryption does not protect an independently committed Git copy.  
   Audit workload-creation permissions as well as direct Secret access: someone allowed to create Pods in a namespace can read its Secrets through those Pods, including indirectly through Deployment creation. Validate encryption in stored data rather than assuming a configuration declaration proves it works.  
   Sources: `concepts/configuration/secret.md:35–51,303–307`; `tasks/administer-cluster/encrypt-data.md:534–588`.

9. **Storage lifecycle.** Dynamically provisioned PVs inherit their StorageClass reclaim policy at creation; the default is `Delete`. Changing the class is not a retroactive update to existing PVs: inspect and patch those PVs individually. `Retain` leaves a released PV and its data for manual reclamation after PVC deletion. With a supporting plugin, `Delete` removes both the PV and backing storage asset.  
   PVC deletion differs from StatefulSet deletion or scaling. StatefulSet claim retention defaults to `Retain`; explicit `whenDeleted` or `whenScaled: Delete` can delete affected template-created PVCs, after which PV reclaim behavior matters. Verify the documented feature-gate prerequisite. Recommend explicit retention for database storage, alongside independently tested recovery.  
   Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:179–213`; `concepts/workloads/controllers/statefulset.md:387–422`.

10. **Prioritized rollout and validation checklist.**

   - **First, protect credentials and data:** remove base64-only Git storage, verify encryption and RBAC, inspect existing PV policies, and test database restoration.
   - **Then configure lifecycle and capacity:** implement probes and draining; measure resource requests, startup time, and shutdown duration; reserve surge capacity and choose an explicit HPA minimum consistent with the availability objective.
   - **Before rollout, verify infrastructure:** check zone labels and outage placement behavior, metrics availability, and CNI enforcement; exercise DNS and database access under restrictive policies.
   - **Release progressively:** test rollout, drain, node failure, and zone loss while observing ready replicas, errors, latency, throttling, OOM events, and HPA decisions.

   At least four limits remain application or cluster validation obligations: maximum drain time, spare-zone capacity, policy enforcement along the actual network path, and database recovery/durability. Neither PDBs nor dynamic provisioning establishes them.  
   Sources: `concepts/workloads/pods/disruptions.md:106–142`; `concepts/workloads/pods/pod-lifecycle.md:612–640`; `concepts/services-networking/network-policies.md:44–82`; `concepts/storage/persistent-volumes.md:179–213`.
