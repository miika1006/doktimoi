**Decision memo — revise before production approval**

The proposed configuration does not establish five-replica availability, graceful completion of long requests, or database durability. Approve deployment only after the following changes and validation. Citations below identify local paths relative to the supplied `docs/` directory, with source line ranges.

1. **PDB protection depends on the disruption.** During **node failure**, `minAvailable: 5` cannot guarantee five available replicas: involuntary disruptions cannot be prevented, although they count against the budget. During **node drain**, tools using the Eviction API respect the PDB; with six healthy selected Pods, one voluntary eviction is permitted, and subsequent evictions may wait. Direct deletion bypasses that protection. During a **Deployment rolling update**, the controller is not constrained by the PDB, although unavailable rollout Pods count against it. [Sources: `concepts/workloads/pods/disruptions.md:105–135`; `tasks/run-application/configure-pdb.md:148–161`.]

   Replace `maxUnavailable: 2`, which permits rollout availability to fall to four, with `maxUnavailable: 1` and explicit `maxSurge: 1`. This aligns the rollout’s permitted unavailability with five of six replicas; it is not protection against simultaneous failures. Reserve surge capacity and keep the autoscaling floor consistent with the six-replica baseline. [Source: `concepts/workloads/controllers/deployment.md:1183–1211`.]

2. **Spread replicas deliberately across zones.** Recommend a Pod topology constraint selecting the API’s Pods, using `topologyKey: topology.kubernetes.io/zone`, `maxSkew: 1`, and `DoNotSchedule`. Verify consistent node labels. `topologyKey` groups nodes with equal label values into domains. With `DoNotSchedule`, skew measures the target domain’s matching-Pod count against the global minimum; violating placements remain unscheduled. `ScheduleAnyway` instead expresses a preference to reduce skew and permits imbalance. Six replicas can therefore target a two-per-zone layout, subject to scheduling prerequisites. [Source: `concepts/scheduling-eviction/topology-spread-constraints.md:76–132,203–211`.]

   Zone loss exposes a tradeoff. If fewer than three domains remain eligible and `minDomains: 3` is configured, the global minimum becomes zero, potentially blocking replacements in populated surviving zones. Without it, the default is one, allowing balancing among remaining eligible domains. Actual behavior depends on eligibility and capacity; unavailable does not automatically mean excluded. Two-per-zone placement also leaves only four replicas immediately after losing a zone. [Source: same document, lines 95–124.]

3. **Use three probes with distinct purposes.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Liveness and readiness probes do not begin until startup succeeds. Exhausting startup failures kills the container, with restart governed by `restartPolicy`. Readiness should represent ability to accept requests, including necessary database access; failing readiness removes the Pod from Service backends without itself restarting the container. Liveness should detect unrecoverable failure, such as deadlock; avoid making a transient database outage a restart trigger. These endpoint semantics are application choices requiring validation. [Source: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:16–41,311–347`.]

4. **Thirty seconds does not guarantee completed requests.** The grace-period countdown starts **before** `preStop`, so the hook consumes the same shutdown budget. The kubelet runs the hook, then requests container termination, normally sending SIGTERM to process 1; an image’s configured stop signal may differ. A still-running hook can receive a one-off two-second extension. Remaining processes receive SIGKILL when the shutdown allowance expires. [Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:1006–1008`; `concepts/workloads/pods/pod-lifecycle.md:559–610,636–640`.]

   Endpoint handling proceeds concurrently: terminating endpoints remain represented temporarily but have `ready: false`, excluding regular traffic; `serving` supports draining-aware consumers. This does not prove existing requests finish or routing changes propagate within an application-specific deadline. Implement draining and choose a measured grace period covering hook execution and outstanding requests. [Source: `concepts/workloads/pods/pod-lifecycle.md:612–632`.]

5. **Requests, limits, and HPA serve different purposes.** CPU requests inform placement: the scheduler checks aggregate requests against node capacity. A request is not a usage ceiling; containers may use spare resources. CPU limits enforce throttling, which can affect latency. Memory limits are enforced reactively through OOM kills, rather than CPU-style throttling; exceeding a memory limit need not cause an immediate kill. Measure and configure both requests and limits accordingly. [Source: `concepts/configuration/manage-resources-containers.md:27–65,230–241`.]

   CPU-utilization HPA measures usage relative to requests. If relevant requests are missing from some containers, Pod utilization is undefined and HPA takes no action for that metric. Check effective admitted requests: Kubernetes can copy a limit into an omitted request. [Sources: `tasks/run-application/horizontal-pod-autoscale.md:89–102`; `concepts/configuration/manage-resources-containers.md:62–65`.]

6. **HPA deliberately moderates the raw ratio.** Its baseline calculation rounds up current replicas multiplied by current/desired metrics, with a default 10% tolerance. It ignores terminating Pods, discards failed Pods, and sets aside missing metrics and certain CPU samples from not-yet-ready Pods. [Source: `tasks/run-application/horizontal-pod-autoscale.md:129–165`.]

   Missing metrics are conservatively assumed to equal 100% of target for downscaling and 0% for upscaling. Not-yet-ready Pods also count as 0% when moderating a proposed upscale. If recalculation reverses direction or falls within tolerance, scaling stops. Default readiness-delay and CPU-initialization windows are 30 seconds and five minutes. Downscaling selects the highest recommendation within the default five-minute stabilization window. Reported utilization excludes these adjustments, explaining apparent discrepancies with actual scaling. [Source: same document, lines 167–218.]

7. **Replace default allow with explicit communication permissions.** Establish ingress and egress isolation, then permit approved callers to the API port, API egress to the database port, database ingress from API Pods, and required DNS access. Use specific namespace and Pod selectors. DNS allowance is necessary when applications depend on name resolution; verify the cluster’s actual resolver arrangement. [Sources: `concepts/services-networking/network-policies.md:51–81,234–243`; `concepts/security/multi-tenancy.md:215–223`.]

   Directions are isolated independently. Policies are additive unions, so a broad allow policy cannot be overridden by a restrictive one. Both source egress and destination ingress must permit a connection; replies are implicitly allowed. NetworkPolicy is not absolute isolation, including documented node-traffic exceptions. A supporting network plugin/controller is a prerequisite: creating policy objects alone has no effect. [Source: `concepts/services-networking/network-policies.md:35–81`.]

8. **Base64 is insufficient protection.** Reject base64-only Secrets in Git: the documentation explicitly describes base64 content as obscured, not secret. Enable Secret encryption at rest; Secrets otherwise reside unencrypted in etcd. Apply least-privilege RBAC and restrict which containers receive credentials. API-store encryption does not protect a separate Git copy. [Source: `concepts/configuration/secret.md:35–47,286–306`.]

   Restrict workload-creation permissions too. Someone allowed to create Pods—or a Deployment—in a namespace can read its Secrets through those workloads. RBAC that denies direct Secret reads therefore does not alone close this access path. [Source: same document, lines 36–40.]

9. **Reclamation belongs to each PV.** Dynamically provisioned PVs inherit the StorageClass reclaim policy, defaulting to `Delete`. Changing the class is not a retroactive update to existing PVs; inspect and patch those PVs individually. `Retain` leaves the released PV and data requiring manual reclamation after PVC deletion. For supporting plugins, `Delete` removes both the PV object and backing storage. [Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:185–210`.]

   StatefulSet deletion/scaling is a separate trigger: default PVC retention is `Retain`. Optional `whenDeleted` and `whenScaled: Delete` remove affected template-created PVCs after Pods terminate, then PV reclamation applies. Verify the documented `StatefulSetAutoDeletePVC` prerequisite. Dynamic provisioning alone establishes neither database replication nor recovery. [Source: `concepts/workloads/controllers/statefulset.md:387–422`.]

10. **Prioritize validation before rollout.**

   - **First:** remove exposed credential handling, enforce RBAC/encryption and tested network policies, and verify existing PV reclaim settings and database recovery procedures.
   - **Next:** configure requests, probes, draining, topology constraints, and the compatible rollout strategy; reserve replacement and surge capacity.
   - **Finally:** stage a rolling update, Eviction-API drain, zone-loss exercise, long-request shutdown, and HPA load test; inspect readiness, endpoints, throttling, metrics, and PVC/PV outcomes.

   These checks follow the documented mechanisms above, especially `disruptions.md:105–135`, `pod-lifecycle.md:559–640`, and `horizontal-pod-autoscale.md:129–218`. Outstanding validation limits include application startup bounds, request-draining duration, surviving-zone capacity, network-plugin enforcement, and database recovery. None is guaranteed merely by configuring the corresponding Kubernetes fields.
