**Decision memo — revise before production approval.** The proposed fields do not collectively guarantee availability, request completion, isolation, or database durability. The following recommendations distinguish documented behavior from choices requiring validation. Citations are local paths relative to the supplied corpus directory.

1. **The PDB does not guarantee five available replicas in all three cases.** Node failure is involuntary: PDBs cannot prevent it, although unavailable Pods count against the budget. During a drain using the Eviction API, `minAvailable: 5` limits permitted evictions; with six healthy replicas, one can be evicted before further evictions must wait. This depends on matching selectors and eviction-respecting tooling, not direct deletion. Deployment rolling updates are explicitly unconstrained by PDBs.  
   **Recommendation:** replace `maxUnavailable: 2`, which permits four available replicas at six desired, with `maxUnavailable: 1, maxSurge: 1`; prefer `maxUnavailable: 0, maxSurge: 1` when spare capacity permits. These constrain rollout behavior, not simultaneous infrastructure failures.  
   Sources: `docs/concepts/workloads/pods/disruptions.md:99–136`; `docs/concepts/workloads/controllers/deployment.md:1189–1211`.

2. **Spread across zones, while explicitly choosing the outage tradeoff.** Use the API’s label selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, targeting two replicas per zone. `topologyKey` groups equally labeled nodes into domains. With `DoNotSchedule`, skew limits the difference between the target domain’s matching Pod count and the global minimum; violating placements remain unscheduled. `ScheduleAnyway` instead prefers reduced skew without enforcing it.  
   Recommend hard spreading if balanced placement takes precedence; choose soft spreading if replacement capacity during zone loss takes precedence. An unavailable zone does not imply one universal scheduling outcome: node visibility, taints, eligibility, and `minDomains` matter. With `minDomains: 3` and fewer than three eligible domains, the global minimum becomes zero, potentially blocking replacements. Removed Pods can leave an imbalance; spread constraints do not continuously guarantee balance.  
   Sources: `docs/concepts/scheduling-eviction/topology-spread-constraints.md:82–130,179–189,527–529,605–619`.

3. **Use startup protection, readiness for traffic, and liveness for recovery.** Configure a startup probe with a failure budget covering measured worst-case startup. Until it succeeds, readiness and liveness probes are disabled. Readiness should test whether this instance can serve requests, including required dependencies where appropriate; failed readiness removes its address from matching Service endpoints without itself restarting the container. Liveness should detect application failure that restarting can resolve, rather than treating every database outage as a restart trigger. Consecutive startup or liveness failures reaching `failureThreshold` trigger container restart behavior. Probe thresholds are configuration choices, not proof that the application is healthy.  
   Sources: `docs/concepts/workloads/pods/pod-lifecycle.md:479–497,512–526,544–557`; `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:398–420`.

4. **Thirty seconds is not a request-completion guarantee.** The grace-period deadline is established before local shutdown; `preStop` executes before TERM and consumes that same budget. The kubelet requests a one-off two-second extension if the hook remains running at expiry. It then asks the runtime to send TERM to the container’s main process; remaining processes receive SIGKILL when graceful termination expires. Endpoint processing happens concurrently, rather than after the hook: terminating endpoints remain represented temporarily, with `ready: false`, excluding them from regular traffic; `serving` supports draining decisions.  
   Implement application shutdown handling and choose a grace period covering hook execution and measured request draining. The docs do not establish instantaneous propagation through this production traffic path or completion of arbitrary long requests.  
   Source: `docs/concepts/workloads/pods/pod-lifecycle.md:580–639`.

5. **Resource sizing determines both placement and autoscaling meaning.** CPU requests inform scheduling and define the denominator for utilization-based HPA; they are not CPU ceilings. Containers can exceed requests when resources permit. CPU limits enforce throttling, whereas memory limits are enforced reactively through OOM kills, not equivalent throttling or guaranteed immediate termination at the boundary. Set explicit, measured requests for every relevant container and test limits against startup and request latency. If relevant CPU requests are missing, Pod CPU utilization is undefined and HPA cannot act on that metric. Inspect admitted specifications: absent requests can inherit limits when no other default applies.  
   Sources: `docs/concepts/configuration/manage-resources-containers.md:18–53,64–66`; `docs/tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **HPA deliberately differs from the raw utilization ratio.** Its starting calculation is the rounded-up replica count multiplied by current/desired metrics, with default tolerance of 0.1. Missing metrics and initializing CPU measurements are set aside. For missing metrics, recalculation assumes 100% of target during downscale and 0% during upscale; not-yet-ready Pods additionally count as 0% when evaluating upscale. These assumptions dampen changes. A reversed direction or ratio within tolerance cancels scaling. Readiness classification uses configurable windows, defaulting to 30 seconds and a five-minute CPU initialization period. Downscale stabilization separately selects the highest recommendation within the default five-minute window. HPA status can show the original average despite these adjustments. A working resource metrics API, usually supplied by separately deployed Metrics Server, is prerequisite.  
   Source: `docs/tasks/run-application/horizontal-pod-autoscale.md:114–118,132–218`.

7. **Replace default allow with explicit connection permissions.** Select all application Pods with default-deny ingress and egress policies, then allow approved callers to the API port, API egress to database destinations and ports, and database ingress from API Pods. Ingress and egress isolation are independent; a Pod-to-Pod connection needs permission at both ends. Policies are additive unions, so a broad existing allow policy defeats intended restriction; reply traffic is implicitly allowed. Permit DNS egress to the actual cluster resolver, including its required protocols—the documented DNS Service example exposes UDP and TCP port 53. Confirm topology and test resolution. NetworkPolicy requires an enforcing CNI/network plugin; creating policy objects alone has no effect.  
   Sources: `docs/concepts/services-networking/network-policies.md:45–81,210–259`; `docs/tasks/administer-cluster/dns-debugging-resolution.md:155–169`.

8. **Base64 does not protect Secrets in Git.** It encodes data; the docs explicitly describe a base64 authentication value as obscured, not secret. Reject committed plaintext-equivalent credentials and use a controlled delivery mechanism. Enable Secret encryption at rest: etcd storage is unencrypted by default. Apply least-privilege RBAC and restrict which containers receive each Secret. Review workload-creation privileges as well as direct Secret permissions: someone authorized to create Pods—or indirectly create them through Deployments—can read namespace Secrets through those workloads. Encryption at rest addresses stored cluster data; it does not establish protection for encoded copies in a repository.  
   Source: `docs/concepts/configuration/secret.md:35–48,306,455–456`.

9. **Reclaim behavior belongs to each PV.** Changing the StorageClass policy does not retroactively rewrite existing PV policies; inspect and edit existing PVs separately. Dynamically provisioned PVs inherit the class policy, defaulting to `Delete`. After PVC deletion releases a volume, `Retain` preserves the PV and data for manual reclamation; supported `Delete` implementations remove both the PV and backing storage. PVC deletion is distinct from StatefulSet deletion or scale-down: StatefulSet PVC retention defaults to `Retain`, with separate configurable `whenDeleted` and `whenScaled` policies. The documented feature prerequisites must be satisfied before relying on those controls. Recommend explicit retention choices for database claims, backed by restore testing.  
   Sources: `docs/concepts/storage/storage-classes.md:126–135`; `docs/concepts/storage/persistent-volumes.md:180–210`; `docs/concepts/workloads/controllers/statefulset.md:389–423`.

10. **Prioritize rollout evidence as follows.** First, remove credential exposure, verify encryption/RBAC, confirm enforcing networking, and inspect actual PV and StatefulSet retention policies. Second, measure startup, resource consumption, and shutdown; configure probes, requests, grace periods, topology constraints, and a compatible rollout strategy. Third, exercise node drain, node/zone failure, rolling updates, missing metrics, database interruption, denied connections, DNS resolution, and storage recovery before production rollout. These tests follow the distinct mechanisms documented above, particularly eviction limits, concurrent termination, HPA damping, and reclaim behavior.  
    At least four limits remain unproven: whether four surviving replicas can carry load after losing a two-replica zone; whether long requests drain before shutdown; whether CPU utilization predicts demand and database connection pressure; and whether database/storage recovery meets durability and recovery objectives. Field availability establishes none of those application-specific outcomes.  
    Sources: `docs/concepts/workloads/pods/disruptions.md:130–136`; `docs/concepts/workloads/pods/pod-lifecycle.md:612–639`; `docs/tasks/run-application/horizontal-pod-autoscale.md:183–218`; `docs/concepts/storage/persistent-volumes.md:180–210`.
