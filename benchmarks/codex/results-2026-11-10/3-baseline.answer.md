**Decision: revise before production approval.** The proposed fields do not establish five-replica availability, request completion, network isolation, or database durability. The recommendations below distinguish Kubernetes behavior from choices requiring validation. Citations identify local paths and inclusive source line ranges.

1. **PDB and rollout availability.** Node failure is involuntary: the PDB cannot prevent it, although unavailable Pods consume the budget. During node drain, `minAvailable: 5` constrains eviction through the Eviction API; with six healthy replicas, one eviction is permitted before replacement availability is needed. This depends on tools respecting that API; direct deletion bypasses protection. Deployment rolling updates are not constrained by PDBs. Thus, `maxUnavailable: 2` permits rollout availability to fall to four. Recommend `maxUnavailable: 0`, `maxSurge: 1`, with capacity for the surge; `maxUnavailable: 1` also matches a five-of-six rollout floor. Neither configuration protects against simultaneous failures. Sources: `docs/concepts/workloads/pods/disruptions.md:99–136`; `docs/concepts/workloads/controllers/deployment.md:1189–1211`.

2. **Zone placement.** Configure a selector matching the API Pods, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, aiming for two replicas per zone. The topology key groups nodes by label value. With `DoNotSchedule`, skew limits the target domain’s count relative to the global minimum; violating placements remain unscheduled. `ScheduleAnyway` prefers reduced skew but permits imbalance. Recommend the latter if replacement capacity during an outage takes priority over strict balance. Zone unavailability does not imply automatic successful redistribution: eligibility, remaining capacity, and constraints matter. With strict scheduling and `minDomains: 3`, fewer than three eligible domains makes the global minimum zero and can block replacements. Domains are discovered from existing nodes; removal of Pods can also leave imbalance. Sources: `docs/concepts/scheduling-eviction/topology-spread-constraints.md:82–130,527–529,605–619`.

3. **Slow-start probes.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Readiness and liveness remain disabled until startup succeeds. Readiness should test ability to serve requests, including database availability if it is a strict dependency; liveness should test application health independently so database failure does not itself trigger restarts. Failed readiness removes the Pod from matching Service endpoints without restarting its container. Consecutive startup or liveness failures reaching the configured threshold trigger container termination/restart under the restart policy. These mechanisms do not establish instantaneous traffic withdrawal. Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–318,412–422`; `docs/concepts/workloads/pods/pod-lifecycle.md:479–497,512–528`.

4. **Termination and long requests.** The grace-period clock begins **before** `preStop`; the hook consumes that budget. Normally, the hook runs before the runtime sends TERM to the container’s main process. An unfinished hook can receive a one-off two-second extension. Endpoint processing happens concurrently: terminating EndpointSlice entries are not immediately removed, but have `ready: false` for regular traffic; `serving` supports draining decisions. At grace expiry, remaining processes receive SIGKILL. Thirty seconds therefore does not guarantee request completion. Choose a budget covering hook execution and measured draining, implement signal handling, and test open connections through the actual traffic path. Sources: `docs/reference/kubernetes-api/workload-resources/pod-v1.md:1006–1008`; `docs/concepts/workloads/pods/pod-lifecycle.md:591–639`.

5. **Resources and CPU utilization.** CPU requests inform scheduling and resource allocation; they are not usage ceilings. Containers may exceed requests when capacity permits. CPU limits enforce a ceiling through throttling, which must be considered when measuring request latency. Memory limits use reactive OOM termination rather than CPU-style throttling; exceeding a limit need not cause an immediate kill. Set measured requests for every relevant container: utilization-based HPA divides usage by requests, and missing relevant requests leave Pod utilization undefined, preventing action for that metric. Check effective admitted values: a limit can become the request when no request or admission default exists. Sources: `docs/concepts/configuration/manage-resources-containers.md:18–53,64–66`; `docs/tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **HPA’s conservative calculation.** The initial recommendation is the rounded-up product of current replicas and the current/target metric ratio, with default tolerance 0.1. Missing metrics are set aside, then conservatively assumed to equal 100% of target for downscaling and 0% for upscaling. Not-yet-ready CPU Pods are also set aside; potential upscaling treats them as consuming 0%, damping expansion. Default readiness-delay and CPU-initialization windows are 30 seconds and five minutes. If recalculation reverses direction or falls within tolerance, scaling stops. Downscaling selects the highest recommendation within the default five-minute stabilization window. Reported utilization excludes these adjustments, so it need not explain the final replica change by itself. Source: `docs/tasks/run-application/horizontal-pod-autoscale.md:132–218`.

7. **Least-privilege networking.** First verify that the installed CNI/network-policy implementation enforces NetworkPolicy; objects alone have no effect. Establish default-deny ingress and egress, then allow authorized callers to the API port, API egress to the database port, corresponding database ingress, and required DNS access. Identify the actual resolver; the documented DNS Service exposes UDP and TCP port 53. Ingress and egress isolation are independent. Policies are additive unions, so a broad existing allow remains effective despite a default-deny policy. Both source egress and destination ingress must permit a Pod-to-Pod connection; reply traffic is implicitly allowed. Validate allowed and forbidden paths. Sources: `docs/concepts/services-networking/network-policies.md:45–81,254–262`; `docs/tasks/administer-cluster/dns-debugging-resolution.md:158–173`.

8. **Secrets.** Reject base64-encoded credentials in Git as a protection strategy: the docs describe base64 credentials as obscured, not secret. Kubernetes Secrets are stored unencrypted in etcd by default. Enable encryption at rest and rewrite existing Secrets so the configuration applies to stored objects; this does not protect Git copies. Apply least-privilege RBAC and restrict which containers receive credentials. Restrict workload creation too: permission to create Pods, including indirectly through Deployments, permits reading any Secret in that namespace. Secret-read restrictions alone are therefore insufficient. Sources: `docs/concepts/configuration/secret.md:35–48,306`; `docs/tasks/administer-cluster/encrypt-data.md:593–607`.

9. **Storage lifecycle.** Changing a StorageClass policy does not retroactively change existing PV policies; inspect and edit those PVs individually. Dynamically provisioned PVs inherit the class policy, defaulting to `Delete`. After PVC deletion, `Retain` preserves the released PV and data for manual reclamation; supported `Delete` implementations remove both PV and backing storage. In-use PVC protection delays removal, rather than canceling deletion. StatefulSet deletion/scaling is a separate decision: template PVCs default to retention, while `whenDeleted` and `whenScaled` can request deletion, subject to the documented feature prerequisite. Subsequent storage reclamation follows the PV policy. Recommend explicit retention for database volumes pending a reviewed recovery process. Sources: `docs/concepts/storage/storage-classes.md:126–135`; `docs/concepts/storage/persistent-volumes.md:123–135,178–210`; `docs/concepts/workloads/controllers/statefulset.md:387–423`.

10. **Prioritized rollout and validation.** First remove the Git-secret approach, configure encryption/RBAC, verify existing PV policies, and establish tested database recovery. Second verify policy enforcement and deploy narrowly scoped network allowances. Third measure startup and shutdown, configure probes/resources, and reserve surge and surviving-zone capacity. Finally exercise rolling updates, eviction-based drains, node/zone loss, missing HPA metrics, and scale-down before broad rollout.

    Acceptance must include at least these limits the documents do not establish: application request completion within the grace period; adequate throughput and replacement capacity after zone loss; actual CNI/DNS enforcement; and database recovery or cross-zone storage accessibility. Also validate CPU utilization as a useful demand signal and availability of the resource metrics API, usually supplied by separately deployed Metrics Server. These tests address the documented termination deadline, scheduling limitations, enforcement prerequisite, and storage lifecycle—not guarantees of application safety. Sources: `docs/concepts/workloads/pods/pod-lifecycle.md:619–639`; `docs/concepts/scheduling-eviction/topology-spread-constraints.md:605–619`; `docs/concepts/services-networking/network-policies.md:45–49`; `docs/concepts/storage/persistent-volumes.md:178–210`; `docs/tasks/run-application/horizontal-pod-autoscale.md:89–118`.
