**Decision memo — revise before production**

The proposed configuration does not establish five-replica availability or safe handling of long requests and database data. Adopt the changes below, then validate application behavior and cluster prerequisites. All citations refer to local files beneath the supplied `docs/` directory; recommendations are configuration choices, not additional Kubernetes guarantees.

1. **PDB: three distinct cases.** Node failure is involuntary: a PDB cannot prevent it, although unavailable Pods count against the budget. During node drain, eviction requests respect the PDB and may be rejected and retried; this constrains budget-respecting evictions, rather than guaranteeing five healthy replicas despite concurrent failures. Direct deletion bypasses that protection. Deployment rolling updates count against the budget but are **not constrained by it**. Thus, `maxUnavailable: 2` permits rollout availability to fall to four. Recommend `maxUnavailable: 0`, `maxSurge: 1`, with capacity for the surge; `maxUnavailable: 1` also aligns with a five-of-six objective. Neither protects against simultaneous failures.  
   Sources: `concepts/workloads/pods/disruptions.md:92–140`; `concepts/workloads/controllers/deployment.md:1183–1209`.

2. **Spread explicitly across zones.** Configure a selector matching the API Pods, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`. The key groups identically labeled nodes into domains. With `DoNotSchedule`, skew limits the destination domain’s matching-Pod count relative to the global minimum; with `ScheduleAnyway`, reducing skew is a scheduling preference. Six replicas can therefore target two per zone under suitable conditions. Recommend hard spreading initially, but explicitly decide outage behavior: if fewer than three domains remain eligible, `minDomains: 3` makes the minimum zero and can block replacements. Omitting it allows balancing across remaining eligible domains; eligibility depends on affinity and taint policies. Soft spreading favors recovery flexibility. None guarantees recovery capacity or continuous balance after deletion; losing two replicas still leaves four initially.  
   Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:76–126`, `:169–194`, `:196–213`, `:605–623`.

3. **Use probes for different decisions.** Give slow initialization a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case startup. Liveness and readiness probes—and their configured delays—begin only after startup succeeds. Startup failure at its threshold triggers restart; subsequent liveness failure should identify an unrecoverable condition such as deadlock, rather than temporary database unavailability. Readiness should indicate whether this instance can serve requests, including necessary dependencies. Readiness failure leaves the container running but sets the Pod unready, removing it from Service backends. Configure thresholds against measurements: overly aggressive liveness checks can cause cascading failures under load.  
   Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:14–48`, `:311–347`, `:398–429`.

4. **Thirty seconds is a deadline, not a completion guarantee.** The grace-period countdown starts **before** `preStop`; the hook consumes that budget. Kubelet runs the hook before requesting TERM delivery to container process 1. An overrunning hook gets a small, one-off two-second extension. At grace expiry, remaining processes receive SIGKILL. Endpoint processing proceeds concurrently: terminating endpoints are not immediately removed, but have `ready: false` for regular traffic; `serving` supports draining decisions. Existing requests require application cooperation. Set grace time from measured hook duration, request duration, and draining behavior; the documents do not guarantee that thirty seconds finishes them.  
   Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:1006–1008`; `concepts/workloads/pods/pod-lifecycle.md:584–641`.

5. **Size resources before tuning CPU autoscaling.** CPU requests inform scheduling and provide the denominator for utilization-based HPA; they are not CPU ceilings. Containers may exceed requests when resources are available. CPU limits enforce throttling; memory limits can produce reactive OOM kills, rather than CPU-style throttling, and excess memory is not necessarily killed immediately. Set measured requests for every relevant container, including sidecars. If a container lacks the relevant request, Pod CPU utilization is undefined and HPA takes no action for that metric. Inspect effective requests: absent admission defaults, specifying only a limit causes Kubernetes to copy it into the request.  
   Sources: `concepts/configuration/manage-resources-containers.md:38–79`, `:230–241`; `tasks/run-application/horizontal-pod-autoscale.md:88–100`.

6. **Expect conservative HPA decisions.** The basic calculation is the ceiling of current replicas multiplied by current/desired metric value, with default tolerance 0.1. Failed Pods are discarded and deleting Pods ignored; missing metrics and certain not-yet-ready CPU samples are set aside. Recalculation assumes missing Pods consume 100% of target during downscale and 0% during upscale. Not-yet-ready Pods also dampen upscale through a zero-consumption assumption. Reversed direction or a ratio within tolerance causes no action. Default readiness-delay and CPU-initialization windows are thirty seconds and five minutes. Downscale stabilization selects the highest recommendation within five minutes by default. Consequently, displayed utilization and the raw ratio need not predict actual scaling. A working metrics API, usually separately deployed Metrics Server, is prerequisite.  
   Sources: `tasks/run-application/horizontal-pod-autoscale.md:110–218`.

7. **Replace default allow with explicit communication paths.** Apply default-deny ingress and egress, then allow intended callers to the API port, API egress to the database port, corresponding database ingress, and DNS queries to the actual resolver. Add other dependencies only when justified. Isolation is directional: a selecting policy with the relevant `policyTypes` activates restrictions for that direction. Policies are additive unions; a broad allow cannot be overridden by a later deny. Both source egress and destination ingress must permit Pod-to-Pod connections, while replies to allowed connections are implicitly permitted. Verify that the installed CNI implements NetworkPolicy; otherwise the objects are ignored. DNS destinations and permitted ports require cluster-specific validation.  
   Sources: `concepts/services-networking/network-policies.md:51–81`; `concepts/security/multi-tenancy.md:208–234`.

8. **Reject base64 Secrets in Git as protection.** Base64 obscures values but does not make them secret. Remove plaintext-equivalent credentials from versioned manifests and use a controlled secret-delivery process. Kubernetes Secrets are stored unencrypted in etcd by default: enable encryption at rest, verify stored ciphertext and API retrieval, and enforce least-privilege RBAC and container access. Restrict Pod and Deployment creation too: authorization to create Pods in a namespace can expose any Secret there, even without direct Secret-read permission. At-rest encryption does not protect a separately committed Git copy.  
   Sources: `concepts/configuration/secret.md:34–50`, `:304–307`; `tasks/administer-cluster/encrypt-data.md:534–588`.

9. **Treat PVC retention and PV reclamation separately.** Changing the StorageClass reclaim policy does not retrofit existing PVs: dynamically provisioned PVs inherit the class policy, and existing PVs require editing or patching. The default is `Delete`, which removes the PV and backing asset for supporting plugins. `Retain` leaves a released PV and its data requiring manual reclamation after PVC deletion. StatefulSet deletion or scale-down normally retains template-created PVCs; optional `whenDeleted` and `whenScaled` policies can delete them, subsequently invoking PV reclamation. The conceptual documentation requires `StatefulSetAutoDeletePVC` enabled on the API server and controller manager. This distinction applies if the database uses a StatefulSet; the API Deployment does not establish database lifecycle behavior.  
   Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:179–210`; `concepts/workloads/controllers/statefulset.md:387–424`.

10. **Prioritize rollout and validation.** First secure credentials, verify encryption/RBAC and CNI enforcement, and inspect actual database PVC/PV policies. Next measure startup, requests, resource consumption, and shutdown; implement probes, draining, and suitable grace time. Then configure spreading, surge capacity, the PDB, and HPA, choosing an autoscaling minimum consistent with the availability objective. Finally exercise rolling updates, budget-respecting drain, zone loss, missing metrics, denied network paths, and disposable storage deletion/recovery. Acceptance must validate at least these undocumented outcomes: application request completion during shutdown; sufficient surviving-zone and surge capacity; database recovery and data durability; and CPU’s usefulness as a demand signal. API acceptance guarantees none of these. Terminating Pods can also consume resources beyond the nominal surge count.  
   Sources: `concepts/workloads/controllers/deployment.md:327–332`; `concepts/workloads/pods/pod-lifecycle.md:612–641`; `concepts/scheduling-eviction/topology-spread-constraints.md:605–623`; `tasks/run-application/horizontal-pod-autoscale.md:255–281`.
