Decision: revise the design before production rollout. The proposed settings do not establish five available replicas through failures or updates, successful completion of long requests, or protection of database credentials and data. The recommendations below are configuration choices grounded in the supplied v1.32 documentation; their application-specific results require validation.

1. **PDB and rollout availability.** `minAvailable: 5` does not prevent node failure: involuntary disruptions cannot be prevented by PDBs, although they count against the budget. During a normal `kubectl drain`, eviction requests respect the PDB and can be rejected and retried; this protection depends on using the Eviction API rather than direct deletion. Deployment rolling updates are explicitly outside PDB enforcement. With six desired replicas, `maxUnavailable: 2` permits four available during an update. Recommend `maxUnavailable: 1, maxSurge: 1`, or conservatively `0/1` with sufficient spare capacity. These control rollout disruption, not simultaneous failures. Sources: [docs/concepts/workloads/pods/disruptions.md, lines 99–141](docs/concepts/workloads/pods/disruptions.md#L99-L141); [docs/concepts/workloads/controllers/deployment.md, lines 1183–1211](docs/concepts/workloads/controllers/deployment.md#L1183-L1211).

2. **Zone placement.** Configure topology spread with an API-specific `labelSelector`, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, targeting two replicas per zone. `topologyKey` groups nodes by label value. With `DoNotSchedule`, skew limits the difference between the target domain’s matching-Pod count and the global minimum; violating placements remain unscheduled. `ScheduleAnyway` instead prefers lower skew while allowing placement. Choose explicitly between strict distribution and degraded-zone scheduling flexibility. An unavailable zone does not imply automatic successful redistribution: eligibility, taints, remaining capacity, and domain discovery matter. Setting `minDomains: 3` makes the global minimum zero when fewer than three eligible domains remain, potentially blocking replacements. Without it, the default is one. Removal also need not preserve balance. Sources: [docs/concepts/scheduling-eviction/topology-spread-constraints.md, lines 82–130, 179–189, 527–529, 605–623](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L82-L130).

3. **Probes for slow startup.** Use a startup probe with a failure budget sized to measured startup time. It disables readiness and liveness probes until startup succeeds; startup failure kills the container, with restart governed by restart policy. Then use readiness to indicate whether the API can serve requests, including required database availability. Failed readiness removes the Pod from matching Service endpoints without itself restarting the container. Use liveness for an unhealthy application that needs restarting, rather than making a database outage trigger restarts across the API fleet. Probe failures follow configured thresholds; endpoint removal is not documented as instantaneous completion or cancellation of existing requests. Sources: [docs/concepts/workloads/pods/pod-lifecycle.md, lines 479–497, 512–556](docs/concepts/workloads/pods/pod-lifecycle.md#L479-L556); [docs/reference/kubernetes-api/workload-resources/pod-v1.md, lines 2176–2178](docs/reference/kubernetes-api/workload-resources/pod-v1.md#L2176-L2178).

4. **Termination and long requests.** The grace-period countdown starts **before** `preStop`. The kubelet runs that hook before asking the runtime to send TERM to the container’s main process; hook time therefore consumes the shutdown budget. An overrun can receive a one-off two-second extension. At grace expiry, remaining processes receive `SIGKILL`. Concurrently, terminating endpoints remain represented in EndpointSlices with `terminating` status and `ready: false`; `serving` supports draining decisions. Thirty seconds is a default/configuration value, not a guarantee requests finish. Implement signal handling and draining, then size grace time for hooks and measured request completion. Sources: [docs/reference/kubernetes-api/workload-resources/pod-v1.md, lines 1006–1008](docs/reference/kubernetes-api/workload-resources/pod-v1.md#L1006-L1008); [docs/concepts/workloads/pods/pod-lifecycle.md, lines 591–639](docs/concepts/workloads/pods/pod-lifecycle.md#L591-L639).

5. **Resource requests and limits.** CPU requests influence scheduling capacity and, on Linux, CPU weighting under contention; they are not CPU ceilings. Containers can exceed requests when resources permit. CPU limits impose throttling, whereas memory limits are enforced reactively through OOM killing, potentially causing restarts. Set requests from workload measurements and test limits against latency and memory peaks. CPU-utilization HPA divides usage by requests: if relevant container requests are missing, Pod utilization is undefined and HPA takes no action for that metric. Inspect effective configuration because a limit can become the request when neither an explicit request nor admission default exists. Sources: [docs/concepts/configuration/manage-resources-containers.md, lines 29–66, 230–265](docs/concepts/configuration/manage-resources-containers.md#L29-L66); [docs/tasks/run-application/horizontal-pod-autoscale.md, lines 89–102](docs/tasks/run-application/horizontal-pod-autoscale.md#L89-L102).

6. **HPA damping and stabilization.** The basic recommendation is the ceiling of current replicas multiplied by current/desired metric value. HPA sets aside missing metrics and qualifying not-yet-ready CPU samples. Missing metrics are conservatively assumed at 100% of target for downscale and 0% for upscale; not-yet-ready Pods further dampen upscale using 0%. If recalculation reverses direction or falls within tolerance, scaling stops. Default tolerance is 10%; readiness handling uses configurable defaults of 30 seconds and a five-minute CPU initialization period. Default downscale stabilization chooses the highest recommendation within five minutes. Consequently, displayed utilization and the raw ratio need not predict actual scaling. A working metrics API is a prerequisite. Sources: [docs/tasks/run-application/horizontal-pod-autoscale.md, lines 113–116, 130–218](docs/tasks/run-application/horizontal-pod-autoscale.md#L130-L218).

7. **Least-privilege networking.** Establish default-deny ingress and egress, then allow approved callers to the API port, API egress to the database port, and corresponding database ingress. Isolation applies independently in each direction. Policies combine additively: an existing allow-all policy defeats narrower restrictions. Both source egress and destination ingress must permit a connection; reply traffic is implicitly allowed. Preserve DNS egress to the actual cluster resolver, including the documented UDP/TCP 53 service pattern, and validate cluster-specific addressing. Supporting CNI/network-policy enforcement is mandatory: merely creating policy objects has no effect without an implementing controller. Sources: [docs/concepts/services-networking/network-policies.md, lines 45–81, 234–259](docs/concepts/services-networking/network-policies.md#L45-L81); [docs/tasks/administer-cluster/dns-debugging-resolution.md, lines 158–174](docs/tasks/administer-cluster/dns-debugging-resolution.md#L158-L174).

8. **Secrets protection.** Base64 is serialization, not adequate confidentiality; the docs explicitly describe encoded credentials as obscured but not secret. Reject encoded production credentials in Git. Enable encryption at rest and least-privilege RBAC, and expose credentials only to containers requiring them. Secrets are stored unencrypted in etcd by default. Restricting direct Secret reads alone is insufficient: permission to create Pods—including indirectly through Deployments—allows reading namespace Secrets through those workloads. Review workload-creation permissions alongside Secret access. Encryption at rest does not establish protection for repository copies. Sources: [docs/reference/kubernetes-api/config-and-storage-resources/secret-v1.md, lines 45–47](docs/reference/kubernetes-api/config-and-storage-resources/secret-v1.md#L45-L47); [docs/concepts/configuration/secret.md, lines 35–48, 305–307](docs/concepts/configuration/secret.md#L35-L48).

9. **Storage lifecycle.** Changing a StorageClass reclaim policy does not retroactively update existing PVs; inspect and patch those PVs individually. Dynamically provisioned PVs inherit the class policy, defaulting to `Delete`. After PVC deletion, `Retain` preserves the released PV and data for manual reclamation; supported `Delete` removes both PV and backing storage. StatefulSet deletion/scaling is a separate trigger: PVCs default to retention. Optional `whenDeleted` and `whenScaled` policies can delete template-created PVCs after affected Pods disappear, subject to the documented feature prerequisite. Those PVC deletions then expose the PV reclaim behavior. Sources: [docs/concepts/storage/storage-classes.md, lines 126–135](docs/concepts/storage/storage-classes.md#L126-L135); [docs/concepts/storage/persistent-volumes.md, lines 178–210](docs/concepts/storage/persistent-volumes.md#L178-L210); [docs/concepts/workloads/controllers/statefulset.md, lines 391–423](docs/concepts/workloads/controllers/statefulset.md#L391-L423).

10. **Prioritized rollout and validation.** First remove Git-held credentials, verify encryption/RBAC, and audit existing PV reclaim settings and database PVC retention. Next implement probes, draining, resource requests, compatible rollout settings, and explicit zone constraints. Apply tested network restrictions with DNS allowances. Finally exercise rollout, drain, node/zone loss, startup spikes, missing metrics, and storage recovery. Validate at least four unresolved limits: actual request-drain duration, remaining-zone capacity, CPU utilization’s relationship to API latency, and database recovery/data durability. The documents establish mechanisms, not those application outcomes.
