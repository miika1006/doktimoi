**Decision memo: revise before production approval.** Six replicas provide redundancy, but the proposed settings do not establish five-replica availability, request completion, credential protection, or database recovery. The recommendations below distinguish Kubernetes behavior from choices and prerequisites. Citations refer only to the supplied local documentation.

1. **The PDB provides conditional eviction protection, not a universal availability guarantee.** During node failure, involuntary disruption can take availability below five; those unavailable Pods count against the budget. During a drain using the Eviction API, `minAvailable: 5` permits one healthy replica’s eviction from six, then blocks further budget-breaking evictions. Direct deletion bypasses this protection. During Deployment updates, unavailable Pods count against the PDB, but the Deployment is not constrained by it. Thus, `maxUnavailable: 2` permits rollout availability to fall to four. Recommend `maxUnavailable: 1, maxSurge: 1`, or preferably `0, 1` with surge capacity. Neither prevents concurrent failures. Sources: `docs/concepts/workloads/pods/disruptions.md:99–136`; `docs/concepts/workloads/controllers/deployment.md:1183–1211`.

2. **Configure explicit zone spreading and choose the outage tradeoff.** Use an API label selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, targeting two replicas per zone. The topology key groups nodes by label value. With `DoNotSchedule`, skew bounds the target domain’s matching-Pod count relative to the global minimum; violating placements remain pending. `ScheduleAnyway` merely prefers placements that reduce skew. If a zone becomes unavailable, replacement scheduling depends on eligible domains, affinity, and taint policies. With `minDomains: 3`, fewer than three eligible domains makes the global minimum zero, potentially blocking replacements in populated surviving zones. Soft spreading favors recovery capacity over strict balance. Neither mode guarantees continuous balance after removals. Sources: `docs/concepts/scheduling-eviction/topology-spread-constraints.md:82–130,607–619`.

3. **Separate startup tolerance, traffic eligibility, and restart detection.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case startup. Other probes remain disabled until it succeeds; their initial-delay clocks then begin. Readiness should check whether the API can serve requests, including required database availability. Failed readiness removes the Pod from matching Service endpoints without restarting its container. Liveness should detect application failures requiring restart, rather than simply mirror database availability. Startup or liveness failure at the configured threshold triggers container restart behavior; a transient failed check alone need not. Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–347,398–422`; `docs/concepts/workloads/pods/pod-lifecycle.md:479–497,524–528`.

4. **Thirty seconds is a shutdown budget, not a request-completion guarantee.** Deletion records the grace period before local shutdown. The kubelet executes `preStop`, then requests TERM delivery to the container’s main process; hook execution consumes that same budget. A still-running hook can receive a one-off two-second extension. Remaining processes receive SIGKILL after expiry. Endpoint changes proceed concurrently: terminating endpoints remain represented temporarily, have `ready: false`, and expose `serving` for draining-aware consumers. Application code must handle shutdown and finish existing work within the configured allowance. Select grace time from measured hook duration, request duration, and traffic-draining behavior. Sources: `docs/concepts/workloads/pods/pod-lifecycle.md:567–577,581–639`.

5. **Size resource requests and limits deliberately.** CPU requests inform scheduling and CPU sharing under contention; they are not usage ceilings. CPU limits enforce throttling, which can affect long-request latency. Memory limits are enforced reactively through OOM handling, potentially killing processes rather than slowing allocation safely. Set explicit CPU requests for every relevant container: utilization-based HPA computes usage relative to requests, and missing requests leave Pod CPU utilization undefined, preventing action for that metric. Inspect admitted Pod specifications because a limit can become the request when no request or admission default exists. Sources: `docs/concepts/configuration/manage-resources-containers.md:18–66,230–263`; `docs/tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **Expect HPA decisions to differ from the raw utilization ratio.** The basic calculation rounds up current replicas multiplied by current/desired metric value. Missing metrics are initially set aside, then conservatively assumed to equal 100% of the target for downscaling and 0% for upscaling. Not-yet-ready CPU Pods are also set aside and assumed at 0% when reconsidering scale-up, damping expansion. A recomputed ratio that reverses direction or falls within tolerance produces no scaling. Default readiness-delay and CPU-initialization windows are 30 seconds and five minutes. Default downscale stabilization chooses the highest recommendation from the preceding five minutes. Metrics availability is a prerequisite; Metrics Server normally requires separate installation. Sources: `docs/tasks/run-application/horizontal-pod-autoscale.md:113–118,129–218`.

7. **Replace default allow with explicit, tested permissions.** Select workload Pods for both ingress and egress isolation, then allow approved callers to the API port, API egress to the database port, and required operational dependencies. For Pod-to-Pod communication, source egress and destination ingress must both permit the connection; permitted reply traffic is implicit. Policies are additive unions, so a broad allow policy defeats narrower restrictions regardless of order. Preserve DNS access to the actual resolver; the documented cluster DNS example exposes UDP and TCP port 53. Use appropriate namespace and Pod selectors. A NetworkPolicy-capable CNI/controller is essential: objects alone enforce nothing. Sources: `docs/concepts/services-networking/network-policies.md:45–81,144–155`; `docs/tasks/administer-cluster/dns-debugging-resolution.md:158–168`.

8. **Reject base64 Secrets in Git as credential protection.** The documentation explicitly describes base64 credentials as obscured, not secret; repository readers can recover them. Keep live credentials out of ordinary manifests committed to Git and establish a controlled delivery mechanism. Kubernetes Secrets are unencrypted in etcd by default: enable encryption at rest, apply least-privilege RBAC, and restrict exposure to necessary containers. Restrict workload creation too: permission to create Pods, including indirectly through Deployments, permits reading namespace Secrets by mounting them. Namespace separation therefore matters alongside Secret read permissions. Encryption at rest does not protect a repository copy. Sources: `docs/concepts/configuration/secret.md:35–48,305–307,658–673`.

9. **StorageClass policy changes do not repair existing PV policies.** Dynamically provisioned PVs inherit their class’s reclaim policy, defaulting to `Delete`; existing PVs needing different behavior must be edited or patched individually. With `Retain`, PVC deletion releases the PV while preserving its data for manual reclamation. With supported `Delete` implementations, reclamation removes both the PV and backing storage. StatefulSet deletion or downscaling normally retains PVCs; optional `persistentVolumeClaimRetentionPolicy` independently controls `whenDeleted` and `whenScaled`, with `Retain` defaults and documented feature prerequisites. If that policy deletes PVCs, PV reclaim behavior then determines storage disposal. Do not equate Pod removal, PVC deletion, and data deletion. Sources: `docs/concepts/storage/storage-classes.md:126–135`; `docs/concepts/storage/persistent-volumes.md:178–210`; `docs/concepts/workloads/controllers/statefulset.md:387–423`.

10. **Roll out in this priority order, with evidence gates.**
   
   - **Protect credentials and data first:** replace committed credentials, verify encryption/RBAC, inventory actual PV reclaim settings, and explicitly choose StatefulSet PVC retention. Sources: `docs/concepts/configuration/secret.md:35–48`; `docs/concepts/storage/persistent-volumes.md:203–210`.
   - **Establish lifecycle correctness:** measure startup, configure probes, implement TERM handling, and test long requests through termination. Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–347`; `docs/concepts/workloads/pods/pod-lifecycle.md:591–639`.
   - **Validate placement and scaling:** reserve surge capacity, apply compatible rollout settings, select zone-failure behavior, and exercise HPA with missing metrics and warming Pods. Sources: `docs/concepts/workloads/controllers/deployment.md:1191–1211`; `docs/tasks/run-application/horizontal-pod-autoscale.md:153–218`.
   - **Test network restrictions and recovery:** prove allowed API/database/DNS flows and denied alternatives, then rehearse drains, node loss, zone loss, and database recovery. Validate storage topology; `WaitForFirstConsumer` requires supporting drivers. Sources: `docs/concepts/services-networking/network-policies.md:45–81`; `docs/concepts/storage/storage-classes.md:173–199`.

   Approval still requires application or cluster evidence for request-completion time, probe accuracy, sufficient surviving-zone capacity, actual CNI enforcement, and database durability/recovery. These documents describe mechanisms and prerequisites; they do not establish those production outcomes.
