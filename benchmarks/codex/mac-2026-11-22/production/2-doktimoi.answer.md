**Decision memo — revise before production approval.** The proposed settings do not establish five-replica availability, safe request draining, credential confidentiality, or database durability. Approve only after the configuration changes and validation below. Citations refer to local paths beneath `docs/` in the supplied Kubernetes v1.32 corpus.

1. **PDB coverage and rolling updates.** `minAvailable: 5` limits voluntary disruptions through the Eviction API; it does not guarantee five replicas through node failure. Involuntary failures cannot be prevented by PDBs, although they count against the budget. During a normal `kubectl drain`, eviction requests respect the PDB and may be rejected and retried. Direct deletion bypasses that protection. Deployment rolling updates are explicitly not constrained by PDBs. Thus, `maxUnavailable: 2` permits rollout availability to fall to four at six desired replicas. Recommend `maxUnavailable: 0, maxSurge: 1`, with sufficient spare capacity; `maxUnavailable: 1` would also align the rollout allowance with five. Neither protects against concurrent failures.  
   Sources: `concepts/workloads/pods/disruptions.md:92–145`; `concepts/workloads/controllers/deployment.md:1189–1211`.

2. **Zone placement and zone loss.** Configure the Deployment Pod template with an application-matching selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`; verify node labels and eligible capacity. With three healthy eligible zones, this targets two replicas per zone. `topologyKey` groups nodes by label value. Under `DoNotSchedule`, skew measures the target domain’s matching-Pod count against the global minimum; violating placements remain unscheduled. `ScheduleAnyway` makes balance a preference.

   Choose failure behavior explicitly: `minDomains: 3` with a hard constraint treats the minimum as zero when fewer than three domains remain eligible, potentially blocking replacements. Without it, balancing can proceed across remaining eligible domains. An unavailable zone’s treatment depends on node eligibility and taint policies. Scheduling rules do not guarantee continued balance after removals; losing two of six replicas leaves four initially.  
   Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:48–126`, `605–623`.

3. **Probes for slow startup.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Readiness should test whether this instance can serve requests; liveness should detect an unrecoverable condition such as deadlock. A database outage should not automatically trigger restarts unless restarting actually helps—this is an application decision.

   Readiness and liveness probes, including their initial delays, begin only after startup succeeds. Repeated startup or liveness failures trigger container restart handling; readiness failure leaves the container running, marks the Pod unready, and removes it from Service backends. These are control-plane behaviors, not a documented instantaneous cutoff for every packet.  
   Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:13–48`, `311–347`, `398–429`.

4. **Termination and long requests.** The grace-period countdown starts **before** `preStop`. The kubelet runs the hook, then requests TERM delivery to process 1. Hook execution therefore consumes shutdown time; it does not add another 30 seconds. A hook still running at expiry can receive a one-off two-second extension. At grace expiry, remaining processes receive SIGKILL.

   Endpoint updates proceed concurrently with local shutdown. Terminating endpoints remain represented temporarily, carry terminating status, and normally have `ready: false`; `serving` supports consumers implementing draining. Services publishing not-ready addresses have an exception. Thirty seconds cannot guarantee completion of long requests: choose a budget covering hook execution and measured draining, and implement signal handling and connection management.  
   Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:992–1008`; `concepts/workloads/pods/pod-lifecycle.md:584–645`; `concepts/services-networking/endpoint-slices.md:91–117`.

5. **Resource requests, limits, and HPA.** CPU requests inform scheduling and provide the denominator for utilization-based HPA; they are not CPU ceilings. A container can consume resources above its request when available. CPU limits enforce a ceiling through throttling. Memory limits instead use reactive OOM killing: exceeding a limit may lead to termination when the kernel detects memory pressure, rather than immediate enforcement.

   Set deliberate CPU requests for every relevant container, and select limits from load measurements. If some containers lack CPU requests, Pod CPU utilization is undefined and HPA takes no action for that metric. Verify effective admission defaults: absent an injected request, specifying only a limit causes Kubernetes to copy it into the request.  
   Sources: `concepts/configuration/manage-resources-containers.md:27–67`, `230–241`; `tasks/run-application/horizontal-pod-autoscale.md:89–117`.

6. **HPA’s conservative adjustments.** The basic calculation is the ceiling of current replicas multiplied by current/desired metric value, with default tolerance of 0.1. HPA ignores terminating Pods, discards failed Pods, and sets missing metrics aside. For CPU, it also sets aside not-yet-ready Pods and metrics preceding readiness.

   Missing metrics are conservatively assumed at 100% of target for downscaling and 0% for upscaling. Not-yet-ready Pods further dampen scale-up using 0%. If recalculation reverses direction or enters tolerance, scaling stops. Default readiness-related windows are 30 seconds and five minutes. Downscale stabilization defaults to five minutes and selects the highest recommendation in that window. Consequently, the raw ratio—and even reported average utilization—need not predict the actual scaling action.  
   Sources: `tasks/run-application/horizontal-pod-autoscale.md:130–165`, `167–202`, `204–218`.

7. **Least-privilege networking.** Start with default-deny ingress and egress for API and database Pods. Add narrowly selected allowances for approved callers to the API port, API-to-database connections on the database port, DNS resolution, and other demonstrated dependencies. Verify actual DNS destinations and required ports in this cluster.

   Isolation is independent by direction. Policies combine additively: any broad allowance remains effective despite narrower policies. A Pod-to-Pod connection must satisfy both source egress and destination ingress; replies to permitted connections are implicitly allowed. Node-originated ingress has an explicit exception, so this is not absolute isolation. A network plugin implementing NetworkPolicy is a prerequisite; otherwise policies are ignored.  
   Sources: `concepts/services-networking/network-policies.md:51–81`, `224–252`; `concepts/security/multi-tenancy.md:208–234`.

8. **Secrets and Git.** Reject base64-encoded credentials in Git as a confidentiality mechanism. Base64 is reversible encoding; the documentation explicitly describes encoded credentials as obscured, not secret. Kubernetes Secrets are also stored unencrypted in etcd by default. Enable encryption at rest, verify stored ciphertext, apply least-privilege RBAC, and expose credentials only to containers that need them.

   Restrict Pod and workload creation permissions as well as direct Secret reads. Someone authorized to create a Pod—or indirectly a Deployment—in a namespace can use that permission to read its Secrets. Encryption at rest does not protect committed Git content or prevent authorized API retrieval.  
   Sources: `concepts/configuration/secret.md:35–48`, `299–307`, `448–463`; `tasks/administer-cluster/encrypt-data.md:575–588`.

9. **Storage reclamation and StatefulSet lifecycle.** Changing or replacing a StorageClass policy does not retroactively update existing PV policies: dynamically provisioned PVs inherit policy at creation; existing PVs require individual edits or patches. The default is `Delete`. For supporting plugins, `Delete` removes the PV and underlying storage asset. `Retain` preserves the released volume and data after PVC deletion, requiring manual reclamation.

   StatefulSet deletion or scale-down is a separate PVC-lifecycle decision: retention defaults to `Retain`. Optional `whenDeleted` and `whenScaled` policies can delete affected template-created PVCs; the conceptual documentation requires the `StatefulSetAutoDeletePVC` feature gate on API server and controller manager. PVC deletion then invokes PV reclamation. Dynamic provisioning alone establishes neither database replication nor recovery safety.  
   Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:185–210`; `concepts/workloads/controllers/statefulset.md:387–423`.

10. **Prioritized rollout and validation checklist.** First, remove exposed credentials from the delivery workflow, verify encryption/RBAC, and inspect existing PV reclaim policies before destructive operations. Second, deploy and test restrictive networking, including DNS and database connectivity. Third, configure startup/readiness/liveness, measured shutdown timing, zone spreading, and the conservative rollout strategy. Fourth, verify CPU requests and the resource metrics API, then exercise HPA under startup, missing-metric, sustained-load, and downscale conditions. Finally, rehearse drain, rollout, node failure, zone loss, and database recovery with production-like traffic.

   Approval requires application or cluster evidence for at least: worst-case startup duration; completion of long requests during shutdown; spare capacity and placement after zone loss; effective CNI enforcement; and database durability, reconnection, and recovery. These are validation requirements, not guarantees conferred by API fields.  
   Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–347`; `concepts/workloads/pods/pod-lifecycle.md:612–639`; `concepts/scheduling-eviction/topology-spread-constraints.md:605–623`; `tasks/run-application/horizontal-pod-autoscale.md:89–117`; `concepts/storage/persistent-volumes.md:185–210`.
