1. **PDB and rollout availability.** A correctly selected `minAvailable: 5` PDB constrains voluntary evictions; it cannot prevent node failures, although their unavailable Pods count against the budget. During an eviction-based `kubectl drain`, requests that violate the budget are rejected and retried, potentially blocking the drain. Direct deletion bypasses this protection. Deployment rolling updates also bypass PDB enforcement, although their unavailable Pods count against it. Thus `maxUnavailable: 2` permits the rollout to reduce six replicas to four.

   Recommend `maxUnavailable: 0`, `maxSurge: 1`, with capacity for the surge and terminating Pods. This limits rollout-induced unavailability; simultaneous failures remain possible. Keep the PDB selector aligned with the Deployment. Sources: `concepts/workloads/pods/disruptions.md:92-145`; `concepts/workloads/controllers/deployment.md:1184-1211,327-332`.

2. **Zone placement and zone loss.** Configure a matching Pod label selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`; aim for two replicas per zone. `topologyKey` identifies node-label domains. With `DoNotSchedule`, skew limits the difference between the target domain’s matching-Pod count and the global minimum. With `ScheduleAnyway`, reducing skew is a scheduling preference.

   For this API, recommend `ScheduleAnyway` when replacement capacity takes precedence over strict balance. A hard constraint can leave replacements Pending during zone loss, depending on eligible domains and capacity. Specifically, `minDomains: 3` makes the global minimum zero when fewer than three domains remain eligible, potentially blocking placement in already populated zones. Even perfect initial placement leaves only four replicas after losing one zone. Constraints govern incoming placement and do not guarantee balance after removals. Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:76-126,605-623`.

3. **Probes for slow startup.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case startup. Readiness should indicate whether the API can accept requests; liveness should detect failures that restarting can remedy, such as deadlock. Avoid making every database interruption a liveness failure.

   Startup success enables the other probes; their initial-delay clocks also wait for that success. Readiness failure makes the Pod unready and removes it from matching Service backends without restarting its container. Startup or liveness failure reaching its threshold triggers termination and restart according to restart policy. Probe selection and timing require application evidence. Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:14-48,311-347,398-429`; `concepts/workloads/pods/pod-lifecycle.md:474-498`.

4. **Termination and long requests.** The grace-period clock starts **before** `preStop`. When configured and grace is nonzero, the hook runs before the runtime is asked to send SIGTERM to process 1. Hook execution therefore consumes shutdown time. The kubelet requests a one-off two-second extension if the hook overruns; remaining processes ultimately receive SIGKILL.

   Endpoint updates proceed concurrently with local shutdown. Terminating endpoints remain visible temporarily but have `ready: false`, excluding them from regular traffic; `serving` supports consumers implementing draining. Thirty seconds is a default, not a request-completion guarantee. Implement signal handling and draining, then size grace for measured hook execution and outstanding requests. Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:1006-1008`; `concepts/workloads/pods/pod-lifecycle.md:584-644`.

5. **Resource requests, limits, and HPA.** Set explicit, measured CPU requests for every relevant container. Requests inform scheduling and provide the denominator for utilization-based CPU autoscaling. Containers may consume above requests when resources permit. CPU limits enforce throttling; memory limits can cause reactive OOM termination rather than CPU-style throttling. Memory over-allocation does not necessarily cause an immediate kill.

   Missing relevant requests make Pod CPU utilization undefined, so HPA takes no action for that metric. Inspect effective configuration: when a limit exists without a request or admission default, Kubernetes copies the limit into the request. Choose limits using workload measurements. Sources: `concepts/configuration/manage-resources-containers.md:16-67`; `tasks/run-application/horizontal-pod-autoscale.md:89-103`.

6. **HPA’s conservative calculations.** HPA begins with a rounded-up replica calculation from the current-to-target metric ratio, but applies a default 10% tolerance. It sets aside missing metrics and, for CPU, qualifying not-yet-ready Pods or samples preceding readiness. Missing metrics are conservatively treated as 100% of target during downscale and 0% during upscale. Not-yet-ready Pods further dampen upscale through a zero-consumption assumption.

   If recalculation reverses direction or enters tolerance, scaling stops. Reported utilization can still show the original average. Defaults include a 30-second initial-readiness delay, five-minute CPU initialization period, and five-minute downscale stabilization window selecting the highest recommendation. Verify the separately installed metrics API provider. Sources: `tasks/run-application/horizontal-pod-autoscale.md:113-117,129-202,213-218`.

7. **Least-privilege networking.** Establish default-deny ingress and egress, then permit intended callers to the API port, API connections to the database port, and necessary DNS traffic to the actual cluster resolver. Verify its destinations; the documented DNS Service exposes UDP and TCP port 53.

   Ingress and egress isolation are independent. Policies combine additively: a broad allow policy cannot be cancelled by adding deny policies. A Pod-to-Pod connection requires permission from both source egress and destination ingress; reply traffic is implicitly allowed. Use namespace and Pod selectors together where appropriate. Enforcement requires a supporting network plugin/controller—creating resources alone has no effect. Sources: `concepts/services-networking/network-policies.md:45-81,100-164`; `tasks/administer-cluster/dns-debugging-resolution.md:158-175`.

8. **Secrets and Git.** Reject base64-only Secrets in Git. Base64 is reversible representation: the documentation demonstrates decoding it and explicitly describes encoded credentials as obscured rather than secret. Encrypting cluster storage would not protect a readable repository copy.

   Enable and verify encryption at rest, apply least-privilege RBAC, and expose each Secret only to containers needing it. Secrets are unencrypted in etcd by default. Crucially, permission to create Pods—or indirectly Deployments—in a namespace enables access to its Secrets, so restricting direct Secret reads alone is insufficient. Sources: `concepts/configuration/secret.md:35-49,278-307,448-463`; `tasks/administer-cluster/encrypt-data.md:570-588`.

9. **Storage reclamation versus workload lifecycle.** Dynamically provisioned PVs inherit their StorageClass reclaim policy, defaulting to `Delete`. Changing the class does not revise existing PV policies; inspect and patch those PVs separately. With `Retain`, deleting a PVC leaves a released PV and its data requiring manual reclamation. With supported `Delete` provisioning, reclamation removes both the PV object and backing storage.

   StatefulSet deletion or scale-down normally retains its template-created PVCs. Optional `persistentVolumeClaimRetentionPolicy` can instead delete them for either event, after the affected Pods are deleted; the documentation requires the feature gate on the API server and controller manager. PVC retention and PV reclamation are separate decisions. Sources: `concepts/storage/storage-classes.md:126-135`; `concepts/storage/persistent-volumes.md:179-211`; `concepts/workloads/controllers/statefulset.md:387-424`.

10. **Prioritized rollout and validation checklist.** First, replace repository-held base64 credentials, verify encryption/RBAC, enforce network isolation, and audit database PV reclaim policies. These address credential exposure and destructive storage behavior identified above. Second, configure probes, measured resources, draining, revised rollout settings, and deliberate topology behavior. Third, exercise rollout, eviction-based drain, node/zone loss, and HPA recovery while observing ready replicas, endpoints, latency, restarts, and database connectivity.

    Production acceptance still requires application or cluster validation of at least these limits: worst-case startup/probe accuracy; completion of long requests during shutdown; metrics availability and CPU-target suitability; spare capacity and placement during zone failure; actual NetworkPolicy enforcement; and database recovery/data integrity. These documents describe mechanisms and prerequisites, but do not establish those outcomes for this deployment.
