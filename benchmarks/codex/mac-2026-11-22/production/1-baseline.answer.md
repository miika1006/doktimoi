Decision: revise the design before production approval. Kubernetes provides useful controls, but the proposed settings do not establish five-replica availability, completed long requests, credential confidentiality, or database recoverability. The recommendations below are configuration choices; guarantees remain conditional on the documented prerequisites.

1. **PDB and rollout availability.** `minAvailable: 5` constrains compliant voluntary evictions. During `kubectl drain`, eviction requests that would violate the budget are rejected and retried; drain can therefore block. A node failure is involuntary: PDBs cannot prevent it, although unavailable Pods count against the budget. Deployment rolling updates also bypass PDB enforcement. With six desired replicas, `maxUnavailable: 2` permits four available replicas. Recommend `maxUnavailable: 1`, `maxSurge: 1`, with spare scheduling capacity; choose zero unavailable and one surge for a stricter rollout. Neither choice guarantees availability during concurrent failures.  
   Sources: `docs/concepts/workloads/pods/disruptions.md:99–136`; `docs/concepts/workloads/controllers/deployment.md:1189–1211`.

2. **Zone placement.** Configure topology spread using `topologyKey: topology.kubernetes.io/zone`, `maxSkew: 1`, and an API-wide matching label selector. Consistent node labels and sufficient eligible capacity are prerequisites. Under `DoNotSchedule`, skew limits the target domain’s matching-Pod count relative to the global minimum; violating placements remain pending. `ScheduleAnyway` prefers reduced skew but permits imbalance. Recommend strict spreading initially, with an explicit outage decision: `minDomains: 3` makes the global minimum zero when fewer than three domains remain eligible, potentially blocking replacements. Omitting it allows balancing across remaining eligible domains, but retained unavailable-domain nodes can affect eligibility. Scheduling constraints do not restore failed replicas or guarantee balance after removals; losing a two-Pod zone leaves four available.  
   Sources: `docs/concepts/scheduling-eviction/topology-spread-constraints.md:82–130,607–623`.

3. **Probe design.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Liveness and readiness remain disabled until startup succeeds; their initial-delay clocks also begin afterward. Use readiness to indicate actual ability to serve, including required database availability; use liveness to detect an unhealthy application requiring restart. Readiness failure removes the Pod from matching Service endpoints without restarting its container. Startup or liveness failures reaching their threshold trigger container restart, subject to restart policy. These mechanisms do not establish that a particular health endpoint accurately represents application health; validate the checks under slow initialization and database outages.  
   Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–318,398–422`; `docs/concepts/workloads/pods/pod-lifecycle.md:479–497,524–528`.

4. **Termination and long requests.** The grace-period countdown begins **before** `preStop`; the hook consumes the shutdown budget. Ordinarily the hook precedes runtime delivery of SIGTERM to process 1. A still-running hook can receive a one-off two-second extension; remaining processes receive SIGKILL when shutdown expires. Container-image stop signals can alter the usual TERM signal. Endpoint processing happens concurrently: terminating endpoints are not immediately removed from EndpointSlices, but have `ready: false` for regular traffic; `serving` supports draining decisions. Thirty seconds is therefore a deadline, not a request-completion guarantee. Implement signal handling and connection draining, then size grace time for hook execution and measured remaining request duration.  
   Sources: `docs/reference/kubernetes-api/workload-resources/pod-v1.md:1006–1008`; `docs/concepts/workloads/pods/pod-lifecycle.md:572–577,591–639`.

5. **Resource sizing.** Set explicit CPU requests for every container. Requests drive scheduling and typically determine relative CPU weighting under contention; they are not usage ceilings. A container may exceed its request when resources permit. CPU limits impose throttling, potentially extending startup and request latency. Memory limits are enforced reactively through OOM killing; exceeding one does not necessarily cause an immediate kill. Size both using measurements. CPU-utilization HPA computes usage relative to CPU requests: missing relevant requests in some containers makes Pod utilization undefined, and HPA takes no action for that metric. Inspect effective defaults too: absent another defaulting mechanism, a specified limit is copied into an omitted request.  
   Sources: `docs/concepts/configuration/manage-resources-containers.md:18–66,252–263`; `docs/tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **HPA interpretation.** The raw recommendation is the ceiling of current replicas multiplied by current/desired metric value, with default tolerance 0.1. HPA sets missing metrics aside, ignores terminating Pods, discards failed Pods, and also sets aside relevant initializing/not-yet-ready CPU samples. Missing metrics are conservatively assumed at 100% of target for downscale and 0% for upscale; not-yet-ready Pods further dampen upscale at 0%. Recalculation can suppress scaling if direction reverses or falls within tolerance. Readiness heuristics default to 30 seconds and a five-minute CPU initialization period. Default downscale stabilization selects the highest recommendation within five minutes. Thus reported average utilization need not reproduce the executed scaling decision.  
   Source: `docs/tasks/run-application/horizontal-pod-autoscale.md:132–216`.

7. **Least-privilege networking.** Establish default-deny ingress and egress, then allow approved callers to the API port, API-to-database traffic on its required port, and explicitly justified dependencies. Isolation is independent per direction. Policies combine additively: a broad allow elsewhere remains effective. A Pod-to-Pod connection requires both source egress and destination ingress permission; allowed replies are implicit. Permit DNS access to the actual resolver endpoints and required protocols—the documented DNS Service exposes UDP/TCP 53—and test resolution after isolation. An enforcing CNI/controller is mandatory; creating policies alone has no effect. Validate Service address translation because policy processing relative to address rewriting is implementation-dependent.  
   Sources: `docs/concepts/services-networking/network-policies.md:45–81,196–205,210–259`; `docs/tasks/administer-cluster/dns-debugging-resolution.md:158–174`.

8. **Secret protection.** Reject base64-encoded credentials in Git as sufficient protection. The docs explicitly describe base64 authentication data as obscured, not secret; encoding the `data` field supplies representation, not confidentiality. Secrets default to unencrypted storage in etcd. Enable encryption at rest, restrict Secret access with least-privilege RBAC, and expose credentials only to containers needing them. Restrict `get`, `list`, and `watch`, since all can reveal contents. Also restrict Pod and Deployment creation: a namespace workload creator can mount its Secrets and can use service accounts in that namespace. Encryption at rest does not protect a readable Git copy; repository credential handling requires a separate protected delivery choice.  
   Sources: `docs/concepts/configuration/secret.md:35–48,305–307,453–457`; `docs/concepts/security/rbac-good-practices.md:93–108`.

9. **Storage lifecycle.** Changing the StorageClass reclaim-policy setting does not retroactively update existing PVs; inspect and explicitly patch their policies. Dynamically provisioned PVs inherit the class policy, whose default is `Delete`. With a supporting plugin, `Delete` removes both PV and backing storage after reclamation. `Retain` preserves the released volume and data for manual reclamation; it is not automatically reusable. PVC deletion initiates this lifecycle, with removal postponed while actively used. StatefulSet deletion/scaling is separate: PVC retention defaults to `Retain`; configured `whenDeleted`/`whenScaled: Delete` can delete template-created PVCs and thereby invoke their PV policies. Verify the documented feature-gate prerequisite before relying on that field.  
   Sources: `docs/concepts/storage/storage-classes.md:126–135`; `docs/concepts/storage/persistent-volumes.md:123–136,178–210`; `docs/concepts/workloads/controllers/statefulset.md:387–423`.

10. **Prioritized rollout and validation checklist.** First, remove exposed credential material from the delivery design, verify encryption/RBAC, and inventory existing PV reclaim policies. Second, establish and test network allowlists before restricting production traffic. Third, measure resources and startup, configure probes, draining, rollout limits, zone spread, and an HPA minimum consistent with the six-replica baseline. Fourth, stage rolling updates, drains, zone loss, database outages, and missing-metric scenarios; observe available replicas, EndpointSlices, pending Pods, and HPA decisions. Validate at least these unresolved limits: application request completion within grace time; sufficient surviving-zone/surge capacity; database recovery and data durability; and actual CNI enforcement. For topology-constrained storage, evaluate supported `WaitForFirstConsumer` provisioning. None of these application or cluster outcomes follows merely from field acceptance.  
    Sources: `docs/concepts/workloads/pods/pod-lifecycle.md:619–639`; `docs/concepts/configuration/manage-resources-containers.md:230–241`; `docs/concepts/services-networking/network-policies.md:45–49`; `docs/concepts/storage/storage-classes.md:173–191`; `docs/tasks/run-application/horizontal-pod-autoscale.md:29–31`.
