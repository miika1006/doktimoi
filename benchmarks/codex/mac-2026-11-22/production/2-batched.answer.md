Decision: revise the design before production approval. The supplied Kubernetes v1.32 documentation describes useful controls, but does not establish end-to-end availability, request completion, database durability, or security merely from these fields.

All source paths below are relative to the supplied `docs/` directory; citations include source line ranges.

1. **PDB and rollout availability.** `minAvailable: 5` cannot guarantee five available replicas during node failure: involuntary disruptions bypass PDB prevention, although they consume the budget. During a normal `kubectl drain`, Eviction API requests respect the PDB and retry rejected evictions; with six healthy replicas, one disruption is initially permissible. This depends on tools using eviction rather than direct deletion and cannot prevent concurrent failures. Deployment rolling updates are explicitly unrestricted by PDBs. Therefore, `maxUnavailable: 2` permits availability to fall to four. Recommend `maxUnavailable: 1`, `maxSurge: 1`, with capacity for the surge; consider `maxUnavailable: 0` for a stricter planned-update policy. Neither prevents unrelated failures. Sources: `concepts/workloads/pods/disruptions.md:99–136`; `concepts/workloads/controllers/deployment.md:1185–1211`.

2. **Zone placement.** Configure an application-wide selector with `topologyKey: topology.kubernetes.io/zone` and `maxSkew: 1`, targeting two replicas per zone under normal conditions. `topologyKey` groups nodes by equal label values. With `DoNotSchedule`, skew limits the target domain’s matching-Pod count relative to the global minimum; violating placements remain unscheduled. `ScheduleAnyway` instead prefers placements reducing skew and can sacrifice balance for schedulability. Recommend the latter if restoring replicas during zone loss takes priority over strict balance. An unavailable zone’s effect depends on eligible nodes, taints, and inclusion policies: strict constraints can block replacements. Explicit `minDomains: 3` makes the global minimum zero when fewer than three eligible domains remain, potentially preventing recovery elsewhere. Six evenly spread replicas still lose two immediately on zone failure. Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:82–130,179–189,527–529,605–619`.

3. **Probe design.** Use a startup probe with a failure budget covering measured worst-case startup; do not compensate solely by making liveness slow. Startup success enables the other probes, and their initial-delay timers begin afterward. Use readiness to express ability to serve requests, including database availability if that dependency is indispensable. Failed readiness removes the Pod from matching Service endpoints while leaving the container running. Use liveness for application failure requiring restart, independently of transient database outages. Consecutive startup or liveness failures reaching `failureThreshold` trigger container restart, subject to restart policy; readiness failures do not. Endpoint removal is documented, but instantaneous traffic cessation is not established. Sources: `concepts/workloads/pods/pod-lifecycle.md:479–497,514–557`; `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:398–422`.

4. **Termination and long requests.** The grace period covers shutdown, including `preStop`; it is not a fresh allowance beginning after the hook. The kubelet runs `preStop` before requesting TERM delivery to container process 1. A still-running hook can receive a one-off two-second extension. Containers otherwise receive TERM in arbitrary order; some runtimes honor an image’s alternative `STOPSIGNAL`. Endpoint updates happen concurrently with shutdown: terminating endpoints remain represented temporarily, have `ready: false`, and expose `serving` for draining-aware consumers. Remaining processes receive SIGKILL after expiry. Thirty seconds therefore guarantees no request completion: measure hook duration, request duration, signal handling, and routing convergence, then configure sufficient grace. Sources: `concepts/workloads/pods/pod-lifecycle.md:565–573,581–639`.

5. **Resources and CPU autoscaling.** Set explicit, measured CPU requests for every relevant container. Requests inform scheduling and establish the denominator for CPU utilization; they are not usage ceilings. Containers can exceed requests when resources are available. CPU limits enforce throttling, which can increase latency; memory limits use reactive OOM killing rather than CPU-style throttling. Memory excess need not cause immediate termination. For utilization-based HPA, missing relevant container requests leave Pod CPU utilization undefined, so the autoscaler cannot act on that metric. Account for defaulting: absent another default, specifying a limit without a request copies the limit into the request. Sources: `concepts/configuration/manage-resources-containers.md:18–53,64–66`; `tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **HPA’s conservative adjustments.** The basic desired count is the rounded-up current replica count multiplied by current/target utilization, but the default 10% tolerance can suppress changes. HPA ignores terminating Pods, discards failed Pods, and sets aside missing metrics and certain not-yet-ready CPU observations. Missing metrics are assumed at 100% of target for downscaling and 0% for upscaling. Not-yet-ready Pods additionally dampen prospective upscaling using a 0% assumption. If recomputation reverses direction or falls within tolerance, scaling stops. Default readiness and CPU-initialization windows are 30 seconds and five minutes respectively. Downscale stabilization chooses the highest recommendation over the preceding five minutes. Reported utilization excludes these conservative adjustments, explaining apparent disagreement with scaling. Sources: `tasks/run-application/horizontal-pod-autoscale.md:130–218`.

7. **Least-privilege networking.** Select all application-namespace Pods with default-deny policies explicitly covering both ingress and egress. Add narrowly scoped allowances for authorized callers to the API port, API Pods to the database port, and necessary DNS traffic. Combine namespace and Pod selectors in one peer entry when both restrictions are intended. Ingress and egress isolation are independent; policies add allowed traffic by union, so an existing broad allowance defeats restriction. A Pod-to-Pod connection requires permission at both source egress and destination ingress; replies are implicitly allowed. Permit the cluster’s actual DNS destination and transport configuration—the documented DNS Service example exposes UDP and TCP 53. Enforcement requires a supporting CNI/network-policy implementation; objects alone have no effect. Sources: `concepts/services-networking/network-policies.md:45–81,144–155,254–262`; `tasks/administer-cluster/dns-debugging-resolution.md:158–173`.

8. **Secrets.** Reject base64-only Secrets in Git: encoding is reversible, and the documentation explicitly calls encoded credentials “obscured but not secret.” Cluster encryption at rest does not protect repository copies. Enable encryption for Secrets in the API server’s backing store, verify the provider configuration, and rewrite existing objects so encryption applies to previously stored data. Apply least-privilege Secret RBAC and restrict exposure to necessary containers. Review workload-creation permissions too: permission to create Pods, including indirectly through Deployments, permits reading namespace Secrets through those workloads. Sources: `concepts/configuration/secret.md:35–48,282–286,305–307`; `tasks/administer-cluster/encrypt-data.md:53–71,590–606`.

9. **Storage lifecycle.** A StorageClass reclaim policy supplies the policy inherited by dynamically provisioned PVs; changing that provisioning configuration does not retroactively change existing PV policies. Inspect and edit existing PVs individually. The default is `Delete`. On PVC deletion, `Retain` leaves the PV released with its data, requiring manual reclamation; supported `Delete` implementations remove both PV and backing storage. StatefulSet deletion or scale-down is a separate trigger: PVC retention defaults to `Retain`. Optional `whenDeleted` and `whenScaled` policies can delete corresponding template-created PVCs after Pods, subject to the documented feature-gate prerequisite. Those PVC deletions then expose the PV’s reclaim behavior. Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:179–210`; `concepts/workloads/controllers/statefulset.md:387–423`.

10. **Prioritized rollout and validation.** First, remove repository credential exposure, verify encrypted existing Secrets and RBAC, and inspect existing database PV reclaim policies. Second, implement and test network allowances, including denied paths and DNS. Third, deploy measured resources, startup/readiness/liveness checks, graceful shutdown, zone spreading, and compatible rollout limits. Verify metrics availability—Metrics Server is a separate prerequisite—before exercising HPA. Finally, rehearse rolling updates, drains, node/zone failures, cold startup, metric gaps, and storage recovery under representative load. Explicitly validate at least these undocumented application/cluster limits: request completion within grace; five-replica throughput and database capacity; zone-loss replacement capacity; actual CNI enforcement; and database recovery/durability. The documents guarantee none of those outcomes for this design. Sources: `tasks/run-application/horizontal-pod-autoscale.md:113–118`; `concepts/configuration/manage-resources-containers.md:230–240`; `concepts/workloads/pods/disruptions.md:130–136`; `concepts/workloads/pods/pod-lifecycle.md:619–639`; `concepts/services-networking/network-policies.md:45–49`.
