Approve only after revision and validation. The proposed settings do not establish five-replica availability, safe request draining, credential confidentiality, or database durability. The following decisions distinguish documented behavior from configuration choices. Citations identify paths relative to the supplied corpus root, `docs/`, with inclusive source line ranges.

1. **PDB and rollout.** `minAvailable: 5` cannot prevent involuntary node failure; lost Pods count against its budget. During a drain using the Eviction API, the PDB restricts voluntary evictions: with six healthy replicas, one eviction is initially permissible; subsequent evictions may block until availability recovers. Direct deletion bypasses this protection. Deployment rolling updates are explicitly **not constrained by PDBs**, although their unavailable Pods count against the budget. Thus `maxUnavailable: 2` permits four available replicas. Recommend `maxUnavailable: 1, maxSurge: 1`, with capacity for the extra Pod; choose `maxUnavailable: 0` if preserving all six during controlled replacement is required. These settings do not protect against simultaneous failures. Sources: `concepts/workloads/pods/disruptions.md:99–136`; `concepts/workloads/controllers/deployment.md:1189–1211`.

2. **Zone placement.** Configure topology spread with the API’s label selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`; verify zone labels. Under `DoNotSchedule`, skew limits the incoming Pod’s domain count relative to the global minimum across eligible domains. This supports a 2/2/2 distribution when scheduling conditions permit. `ScheduleAnyway` instead prefers reduced skew while allowing violations. Decide explicitly whether balance or replacement capacity takes priority during zone loss. With `minDomains: 3`, fewer than three eligible domains makes the global minimum zero, potentially blocking replacements. Without it, the default is one, so remaining eligible domains may accept replacements; behavior depends on which nodes/domains remain eligible. Existing Pods are not automatically rebalanced after removal. Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:82–130,607–619`.

3. **Probes.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case startup. Use readiness to test ability to serve, including the database if it is a strict dependency; use liveness to detect application failure requiring restart, rather than making database unavailability itself a restart trigger. Startup disables the other probes until success; their initial-delay clocks also wait for startup success. Threshold-level startup or liveness failure triggers container termination/restart according to restart policy. Readiness failure leaves the container running but marks it unready and removes its IP from matching Service endpoints. This documents traffic eligibility, not instantaneous completion or cancellation of existing requests. Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–318,398–422`; `concepts/workloads/pods/pod-lifecycle.md:479–497,524–527`.

4. **Termination.** The grace-period countdown begins **before** `preStop`; the hook consumes that budget. After the hook, the runtime receives the instruction to send TERM to the container’s main process. A still-running hook can receive a one-off two-second extension; remaining processes receive SIGKILL when shutdown time expires. Endpoint handling proceeds concurrently, rather than after the hook: terminating endpoints remain represented temporarily, but have `ready: false` for regular traffic; `serving` supports draining-aware consumers. Thirty seconds is a default, not a request-completion guarantee. Measure hook duration, request duration, signal handling, and traffic propagation, then configure sufficient grace and application draining. Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:1006–1008`; `concepts/workloads/pods/pod-lifecycle.md:581–639`.

5. **Resource sizing.** Set explicit, measured CPU requests for every relevant container. Requests drive scheduling capacity checks and typically provide relative CPU weighting under contention; they are not consumption ceilings. A container may exceed its request when resources permit. CPU limits enforce a ceiling through throttling, potentially slowing startup and requests. Memory limits are enforced reactively through OOM handling, potentially killing processes; they are not equivalent to CPU throttling. CPU-utilization HPA divides usage by requested CPU. If relevant requests are missing from some containers, Pod CPU utilization is undefined and HPA takes no action for that metric. Requests therefore affect both placement and scaling sensitivity. Sources: `concepts/configuration/manage-resources-containers.md:27–53,230–264`; `tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **HPA adjustments.** The raw calculation is ceiling(current replicas × current/target metric), but it is only a starting point. Missing metrics are initially set aside, then conservatively assumed to equal 100% of target for downscaling and 0% for upscaling. Not-yet-ready Pods and CPU samples predating readiness are also set aside; potential upscales are dampened by assuming those Pods consume 0%. Defaults include a 30-second initial-readiness delay and five-minute CPU initialization period. If the adjusted ratio reverses direction or enters tolerance—default 0.1—scaling stops. Downscale stabilization defaults to five minutes and selects the highest recommendation in that window. Reported utilization can omit these adjustments, explaining differences between status and actual scaling. Source: `tasks/run-application/horizontal-pod-autoscale.md:135–216`.

7. **Least-privilege networking.** First verify a CNI/network controller that actually enforces NetworkPolicy; creating objects alone can have no effect. Establish namespace-wide default-deny ingress and egress, then allow identified callers to the API port, API egress to the database port, corresponding database ingress, and necessary DNS traffic to the actual cluster resolver. Validate UDP and TCP DNS requirements; the documented DNS Service exposes both on port 53. Ingress and egress isolation are independent. Policies combine additively, so remove broad existing allows: a deny policy cannot override another policy’s allowance. A Pod-to-Pod connection needs both source egress and destination ingress permission; replies to allowed connections are implicitly allowed. Sources: `concepts/services-networking/network-policies.md:45–81,115–122,216–259`; `tasks/administer-cluster/dns-debugging-resolution.md:158–168`.

8. **Secrets.** Reject base64-encoded credentials in Git as a confidentiality measure. The docs describe base64 credentials as obscured, not secret. Secrets are also unencrypted in etcd by default. Enable and verify API encryption at rest, including rewriting existing Secrets after configuration; this does not protect repository copies. Apply least-privilege RBAC and expose credentials only to containers needing them. Restrict Pod and Deployment creation privileges too: those permissions allow indirect reading of any Secret in that namespace, even without direct Secret-read permission. Namespace boundaries therefore matter. Sources: `concepts/configuration/secret.md:35–47,305–307,658–669`; `tasks/administer-cluster/encrypt-data.md:55–66,590–607`.

9. **Storage lifecycle.** Changing a StorageClass reclaim policy does not retroactively change existing PVs; inspect and explicitly patch those PVs. Dynamically provisioned PVs inherit their class’s policy, defaulting to `Delete`. After PVC deletion, `Retain` preserves the released PV and underlying data for manual reclamation; it is not immediately reusable. For supporting plugins, `Delete` removes both PV and backing storage. StatefulSet deletion/scaling is a separate PVC-retention decision: defaults retain template-created PVCs, while `whenDeleted`/`whenScaled: Delete` remove affected claims, subsequently exposing storage to PV reclaim behavior. The supplied text requires the relevant feature gate for this field. Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:178–210`; `concepts/workloads/controllers/statefulset.md:391–423`.

10. **Prioritized validation checklist.** Before production: **first**, protect credentials and data—verify encryption/RBAC, inspect existing PV policies, and exercise database restore procedures. **Second**, establish and test network isolation, including positive database/DNS tests and negative unauthorized-access tests. **Third**, deploy measured probes, resources, shutdown behavior, spread constraints, and compatible rollout settings. Exercise a rolling update, Eviction-API drain, abrupt node loss, zone loss, and HPA behavior with missing metrics.

    Acceptance still requires application/cluster evidence for at least these limits: worst-case startup; long-request completion during shutdown; CPU target suitability and database connection capacity under scaling; CNI enforcement; and storage accessibility after zone failure. Dynamic provisioning alone establishes none of these. For topology-constrained storage, consider `WaitForFirstConsumer` with a supporting driver to align provisioning with scheduling. Sources: the probe, termination, HPA, and networking ranges above; `concepts/storage/storage-classes.md:171–195`; `concepts/workloads/pods/disruptions.md:130–136`.
