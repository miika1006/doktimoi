**Decision memo: revise before production rollout.** Six replicas across three zones are a useful starting point, but the proposed settings do not establish five-replica availability, completed long requests, network isolation, or database durability. The recommendations below distinguish Kubernetes behavior from configuration choices and operational prerequisites. Citations refer exclusively to the supplied local documentation.

1. **PDB and rollout availability.** `minAvailable: 5` cannot prevent involuntary node failure; lost Pods count against the budget afterward. During an Eviction API–based node drain, the PDB restricts voluntary evictions, potentially blocking further progress until replacements become healthy. Direct deletion bypasses that protection. Deployment rolling updates count against the budget but are **not constrained by it** ([docs/concepts/workloads/pods/disruptions.md, lines 99–141](docs/concepts/workloads/pods/disruptions.md#L99-L141)).

   With six desired replicas, `maxUnavailable: 2` permits rollout availability to fall to four. Recommend `maxUnavailable: 0`, `maxSurge: 1`, with capacity for the surge Pod; `maxUnavailable: 1` is a less conservative compatible choice. These control rollout behavior, without guaranteeing protection against concurrent failures ([docs/concepts/workloads/controllers/deployment.md, lines 1189–1211](docs/concepts/workloads/controllers/deployment.md#L1189-L1211)).

2. **Zone placement and outage behavior.** Configure an API-wide matching selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`. The topology key groups nodes by label value. With `DoNotSchedule`, skew limits the target domain’s matching-Pod count relative to the global minimum; with `ScheduleAnyway`, reducing skew is a preference rather than a scheduling prohibition. Six schedulable replicas across three eligible zones can therefore reach two per zone ([docs/concepts/scheduling-eviction/topology-spread-constraints.md, lines 82–130](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L82-L130)).

   Choose the outage tradeoff explicitly. With hard spreading and `minDomains: 3`, fewer than three eligible domains makes the global minimum zero, potentially blocking replacements in surviving zones. Eligibility depends on affinity and taint policies. Soft spreading favors recovery placement but relaxes balance. Domains derive from existing nodes, and Pod removal does not guarantee continued balance. Losing a zone containing two replicas leaves four initially; spreading cannot guarantee five survivors ([same document, lines 107–126](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L107-L126), [607–623](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L607-L623)).

3. **Probes for slow startup.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. After startup succeeds, use readiness to indicate ability to accept requests and liveness to detect recoverable process failure, such as deadlock. Treat database dependency checks as an application choice: restarting every API instance during a database outage needs justification ([docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md, lines 313–347](docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md#L313-L347)).

   Startup suppresses both other probes until success; their initial delays then begin. Repeated startup or liveness failure triggers container restart, subject to restart policy. Readiness failure keeps the container running but marks it unready and removes it from matching Service endpoints, stopping normal Service selection—not guaranteeing termination of existing requests ([same document, lines 398–422](docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md#L398-L422); [docs/concepts/workloads/pods/pod-lifecycle.md, lines 479–497](docs/concepts/workloads/pods/pod-lifecycle.md#L479-L497)).

4. **Termination and long requests.** Deletion records the grace period before local shutdown begins. The kubelet runs `preStop`, then asks the runtime to send TERM to the container’s main process; hook execution consumes the same shutdown budget. A hook overrunning the deadline can receive a one-off two-second extension. Remaining processes receive SIGKILL when grace expires ([docs/concepts/workloads/pods/pod-lifecycle.md, lines 581–610](docs/concepts/workloads/pods/pod-lifecycle.md#L581-L610), [636–639](docs/concepts/workloads/pods/pod-lifecycle.md#L636-L639)).

   Endpoint updates proceed concurrently. Terminating endpoints remain temporarily in EndpointSlices with `ready: false`; `serving` supports draining-aware consumers. Thirty seconds is therefore **not a completion guarantee**. Size grace for measured hook time plus request draining, and validate signal handling and traffic propagation ([same document, lines 612–632](docs/concepts/workloads/pods/pod-lifecycle.md#L612-L632)).

5. **Resource sizing and CPU autoscaling.** Set explicit, measured CPU requests for every relevant container. Requests drive scheduling capacity checks and typically CPU weighting under contention; they do not cap consumption. CPU limits throttle execution, potentially increasing latency. Memory limits instead use reactive OOM enforcement, potentially killing a process rather than throttling memory usage ([docs/concepts/configuration/manage-resources-containers.md, lines 29–53](docs/concepts/configuration/manage-resources-containers.md#L29-L53), [230–265](docs/concepts/configuration/manage-resources-containers.md#L230-L265)).

   Utilization-based HPA calculates CPU usage relative to requests. If relevant requests are missing from some containers, Pod CPU utilization is undefined and HPA cannot act on that metric. Inspect effective admitted requests: absent requests can default from specified limits ([docs/tasks/run-application/horizontal-pod-autoscale.md, lines 89–102](docs/tasks/run-application/horizontal-pod-autoscale.md#L89-L102); [resource documentation, lines 63–66](docs/concepts/configuration/manage-resources-containers.md#L63-L66)).

6. **HPA’s conservative calculations.** HPA initially sets aside Pods with missing metrics and CPU samples from not-yet-ready Pods. Readiness classification uses configurable defaults of 30 seconds for initial readiness delay and five minutes for CPU initialization ([docs/tasks/run-application/horizontal-pod-autoscale.md, lines 153–178](docs/tasks/run-application/horizontal-pod-autoscale.md#L153-L178)).

   Missing metrics are conservatively assumed at 100% of target during downscale and 0% during upscale. Not-yet-ready Pods contribute 0% when damping upscale. Recalculation that reverses direction or falls within tolerance causes no scaling. Default tolerance is 10%; downscale stabilization selects the highest recommendation over five minutes. Thus the raw ratio—and even displayed average utilization—can differ from the final scaling decision ([same document, lines 135–147](docs/tasks/run-application/horizontal-pod-autoscale.md#L135-L147), [180–218](docs/tasks/run-application/horizontal-pod-autoscale.md#L180-L218)).

7. **Least-privilege networking.** Establish default-deny ingress and egress, then allow approved callers to the API port, API egress to the database port, and corresponding database ingress. Isolation applies independently by direction; applicable policies combine as a union, so broad allow policies must be removed. Both source egress and destination ingress must permit a connection. Allowed replies are implicit ([docs/concepts/services-networking/network-policies.md, lines 53–81](docs/concepts/services-networking/network-policies.md#L53-L81), [254–262](docs/concepts/services-networking/network-policies.md#L254-L262)).

   Explicitly allow DNS to the actual cluster resolver; the documented DNS Service exposes UDP/TCP 53 ([docs/tasks/administer-cluster/dns-debugging-resolution.md, lines 158–174](docs/tasks/administer-cluster/dns-debugging-resolution.md#L158-L174)). Supporting CNI enforcement is a prerequisite: creating policies without an implementing controller has no effect ([network-policy documentation, lines 45–49](docs/concepts/services-networking/network-policies.md#L45-L49)).

8. **Secrets protection.** Reject base64-encoded credentials in Git as a security boundary: base64 is reversible, and the documentation explicitly calls it obscuring rather than secrecy ([docs/concepts/configuration/secret.md, lines 282–307](docs/concepts/configuration/secret.md#L282-L307)).

   Enable and verify API-data encryption at rest, apply least-privilege Secret RBAC, and restrict which containers receive credentials. Secrets are unencrypted in etcd by default. Restrict workload creation too: permission to create Pods—or Deployments—can expose any Secret in that namespace. Encryption at rest does not remove that authorization risk ([same document, lines 35–48](docs/concepts/configuration/secret.md#L35-L48)).

9. **Storage deletion semantics.** Dynamically provisioned PVs inherit the StorageClass reclaim policy, defaulting to `Delete`. Changing the class does not retroactively change existing PV policies; inspect and patch those PVs individually ([docs/concepts/storage/storage-classes.md, lines 126–135](docs/concepts/storage/storage-classes.md#L126-L135); [docs/concepts/storage/persistent-volumes.md, lines 203–210](docs/concepts/storage/persistent-volumes.md#L203-L210)).

   After PVC deletion, `Retain` leaves a released PV and its data for manual reclamation; supported `Delete` implementations remove both PV and backing storage ([persistent-volume documentation, lines 180–205](docs/concepts/storage/persistent-volumes.md#L180-L205)). StatefulSet deletion/scaling defaults to retaining PVCs. Optional `whenDeleted`/`whenScaled: Delete` changes that behavior, subject to the documented feature-gate prerequisite; subsequent storage reclamation remains governed by the PV policy ([docs/concepts/workloads/controllers/statefulset.md, lines 391–423](docs/concepts/workloads/controllers/statefulset.md#L391-L423)).

10. **Prioritized rollout and validation checklist.** First protect credentials and database volumes, verifying effective RBAC, encryption, and each existing PV policy. Next verify enforcing CNI support and working resource metrics; Metrics Server is a separately deployed prerequisite in the documented common setup ([HPA documentation, lines 113–118](docs/tasks/run-application/horizontal-pod-autoscale.md#L113-L118)). Then configure probes, resource requests, draining, zone placement, and conservative rollout settings before staged load and failure tests.

   Validate at least these limits: worst-case startup; long-request completion during termination; API/database capacity after zone loss; and actual network-policy enforcement. Kubernetes documents probe actions, shutdown deadlines, placement rules, and enforcement prerequisites—not those application outcomes. Exercise drain, rollout, missing metrics, zone failure, and database recovery. For topology-constrained storage, evaluate supported `WaitForFirstConsumer` provisioning to avoid binding without Pod scheduling knowledge ([storage-class documentation, lines 177–195](docs/concepts/storage/storage-classes.md#L177-L195)).
