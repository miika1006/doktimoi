Decision: revise the design before production approval. Kubernetes provides disruption controls, health signals, and resource policies, but these do not establish end-to-end request completion or database availability. The recommendations below are configuration choices grounded in the supplied v1.32 documentation. Source paths are relative to the supplied `docs/` directory; ranges identify source lines.

1. **PDB protection differs by disruption.** During **node failure**, `minAvailable: 5` cannot prevent lost replicas; involuntary disruptions count against the budget. During an **eviction-based drain**, the budget restricts evictions: with six healthy matching replicas, one can be evicted before further evictions must wait. Direct deletion bypasses protection. During a **Deployment rollout**, unavailable Pods count against the budget, but the Deployment is not constrained by it.

   Proposed `maxUnavailable: 2` therefore permits four available replicas. Recommend `maxUnavailable: 1`, `maxSurge: 1`, with capacity for replacements; `maxUnavailable: 0` is more conservative if surge capacity exists. These settings govern rollout behavior, not concurrent failures. Keep HPA’s minimum at six if six is the operating baseline. Sources: `concepts/workloads/pods/disruptions.md:99–145`; `concepts/workloads/controllers/deployment.md:1183–1211`.

2. **Explicitly configure zone spreading.** Use an API-specific `labelSelector`, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, targeting two replicas per zone. The topology key identifies node labels whose equal values form domains. With `DoNotSchedule`, skew limits the difference between the target domain’s matching-Pod count and the global minimum. `ScheduleAnyway` prefers reduced skew but allows scheduling despite imbalance.

   Choose strictness deliberately. `minDomains: 3` with `DoNotSchedule` can block replacements when fewer than three domains remain eligible: the global minimum becomes zero. Without it, two remaining eligible zones can be rebalanced, subject to capacity. An unavailable zone’s treatment depends on node presence, affinity, and taint inclusion settings. Losing two replicas leaves four immediately; spreading does not guarantee five. Nor does spreading guarantee balance after removals. Source: `concepts/scheduling-eviction/topology-spread-constraints.md:82–130,167–185,196–211,605–619`.

3. **Separate startup, readiness, and recovery.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Until it succeeds, readiness and liveness probes are disabled; their configured delays begin afterward. Repeated startup failure kills the container, subject to its restart policy.

   Use readiness to report whether the API can serve requests, including required database functionality. Failure removes the Pod from matching Service endpoints without itself restarting the container. Use liveness for conditions restart can repair, such as deadlock; avoid making a transient database outage automatically trigger restarts. Probe semantics are documented; suitable health checks and thresholds require application testing. Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–400`; `concepts/workloads/pods/pod-lifecycle.md:479–494`.

4. **Thirty seconds is a deadline, not a request-completion guarantee.** The grace-period countdown begins **before** `preStop`. The hook runs before the runtime is asked to send TERM to the container’s main process; hook time consumes the same budget. A still-running hook can receive a one-off two-second extension. Remaining processes receive SIGKILL when grace expires. Some runtimes honor an image’s alternative `STOPSIGNAL`.

   Endpoint updates happen concurrently with shutdown. Terminating EndpointSlice entries are not immediately removed, but have `ready: false`; draining integrations can examine `serving`. Implement request draining and signal handling, then size grace for measured hook and request duration. The documents do not guarantee that every long request finishes. Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:1000–1008`; `concepts/workloads/pods/pod-lifecycle.md:565–639`.

5. **Set resources explicitly and measure their effects.** CPU requests inform scheduling and provide the denominator for CPU-utilization HPA. Containers can exceed requests when resources permit. CPU limits impose throttling; memory limits can cause reactive OOM termination, rather than CPU-style throttling or an immediate allocation ceiling.

   Set CPU requests for every relevant container. If some containers lack them, Pod CPU utilization is undefined and HPA takes no action for that metric. Account for admission defaults: when only a limit is supplied, Kubernetes can copy it into the request. Choose requests and limits using startup and sustained-load measurements. Sources: `concepts/configuration/manage-resources-containers.md:18–23,27–66`; `tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **Expect conservative HPA decisions.** The basic calculation is the ceiling of current replicas multiplied by current/desired metric value. Missing metrics are set aside, then assumed at 100% of target for downscaling and 0% for upscaling, dampening changes. Not-yet-ready CPU Pods are also set aside and, when considering scale-up, conservatively treated as consuming 0%.

   Default readiness-delay and CPU-initialization windows are 30 seconds and five minutes. Recalculation can cancel scaling if it reverses direction or falls within tolerance, default 10%. Downscale stabilization defaults to five minutes and selects the highest recommendation in that window. Thus reported utilization and actual scaling can differ. Metrics availability is a prerequisite; Metrics Server is generally a separate add-on. Source: `tasks/run-application/horizontal-pod-autoscale.md:113–118,129–218`.

7. **Adopt least-privilege networking.** Establish namespace-wide ingress and egress isolation, then allow approved callers to the API port, API egress to the database port, and corresponding database ingress. Explicitly allow necessary DNS egress to the cluster’s actual resolver destinations and ports; validate these rather than assuming a portable resolver layout.

   Ingress and egress isolation are independent. Policies are additive unions, so an existing allow-all policy defeats tighter restrictions. A Pod-to-Pod connection requires both source egress and destination ingress permission; reply traffic is implicitly allowed. Enforcement requires a network plugin supporting NetworkPolicy: creating objects alone has no effect. Sources: `concepts/services-networking/network-policies.md:45–81,115–122,208–262`.

8. **Reject base64 Secrets in Git as protection.** Base64 obscures data but does not keep it secret; repository readers can recover credentials. Keep usable credentials out of Git, enable Secret encryption at rest, restrict Secret access through least-privilege RBAC, and expose each Secret only to containers requiring it.

   Kubernetes stores Secrets unencrypted in etcd by default. Encryption at rest addresses that storage exposure, not repository disclosure or authorized API access. Review workload-creation permissions too: someone authorized to create Pods—or indirectly Deployments—in a namespace can use that ability to read its Secrets. Sources: `concepts/configuration/secret.md:35–48,282–307,453–457`.

9. **Manage existing PVs separately.** Dynamically provisioned PVs inherit their StorageClass reclaim policy, defaulting to `Delete`. Changing the class does not retroactively change existing PV policies; inspect and edit or patch those PVs separately.

   PVC deletion releases the claim. With `Retain`, the PV and data remain for manual reclamation. With a supporting plugin, `Delete` removes both the PV and underlying storage asset. StatefulSet deletion or scale-down is a separate lifecycle decision: PVC retention defaults to `Retain`; optional `whenDeleted` and `whenScaled` policies can delete affected claims. Confirm the documented feature-gate prerequisites. Recommend explicit retention for database claims and PVs pending recovery validation. Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:178–210`; `concepts/workloads/controllers/statefulset.md:387–423`.

10. **Prioritize rollout and evidence.** First remove repository credential exposure, verify encryption/RBAC, and inspect existing PV reclaim policies. Second deploy and test network isolation, including DNS and database access. Third measure startup, resource consumption, and shutdown; configure probes, requests, HPA, grace, zone spreading, and surge capacity. Finally exercise a staged rollout, eviction-based drain, zone failure, missing metrics, and database recovery before approval.

   Acceptance must validate at least these unresolved limits: maximum request-draining duration; whether CPU tracks API demand adequately; replacement capacity during zone loss; actual CNI enforcement; and database durability, backup restoration, and cross-zone storage accessibility. Dynamic provisioning alone establishes none of these. Topology-constrained storage may require supported `WaitForFirstConsumer` provisioning to avoid unschedulable Pods. Sources: `concepts/workloads/pods/disruptions.md:225–232`; `tasks/run-application/horizontal-pod-autoscale.md:129–218`; `concepts/services-networking/network-policies.md:45–49`; `concepts/storage/storage-classes.md:171–199`.
