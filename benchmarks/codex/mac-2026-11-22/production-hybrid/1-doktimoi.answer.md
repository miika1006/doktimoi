**Decision memo — revise before production approval**

The proposed design does not establish five-replica availability, safe request draining, credential confidentiality, or database durability. Approve a staged rollout only after the configuration changes and validation below. All citations refer to local files relative to `/private/var/folders/3t/t35161bs2slggt46tnrk0b4c0000gn/T/doktimoi-bench-1-doktimoi-JPse57/docs`; recommendations are configuration choices, not additional Kubernetes guarantees.

1. **PDB protection depends on the disruption.** During **node failure**, `minAvailable: 5` cannot prevent unavailability; involuntary disruptions count against the budget but cannot be blocked. During **node drain**, tools using the Eviction API respect the budget: with six healthy selected Pods, one eviction can proceed, while further evictions may wait for recovery. Direct deletion bypasses that protection. During a **Deployment rolling update**, unavailable Pods count against the budget, but the Deployment controller is not constrained by it. Thus `maxUnavailable: 2` permits rollout availability to fall to four. Recommend `maxUnavailable: 1`, `maxSurge: 1`, matching selectors, and capacity for the surge; this targets five available during rollout, without guaranteeing protection against concurrent failures. Keep HPA’s minimum at six if that operating assumption matters. Sources: `concepts/workloads/pods/disruptions.md:104-145`; `tasks/run-application/configure-pdb.md:148-155`; `concepts/workloads/controllers/deployment.md:1183-1211`.

2. **Configure explicit zone spreading.** Use an API label selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`; six replicas can then achieve 2/2/2 when scheduling conditions permit. `topologyKey` groups equally labelled nodes into domains. With `DoNotSchedule`, skew limits the difference between the target domain’s matching-Pod count and the global minimum; violating placements remain unscheduled. `ScheduleAnyway` prefers reduced skew but permits imbalance, subject to other scheduling requirements. Recommend hard spreading initially, with a deliberate outage policy. An unavailable zone does not have one universal scheduling outcome: eligibility depends on affinity and taint handling, and domains without nodes are unknown to the scheduler. With `minDomains: 3`, fewer eligible domains make the minimum zero and can block replacements. Omitting it behaves as one. Neither choice preserves five replicas immediately after losing two Pods in one zone. Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:76-136`, `167-194`, `605-623`.

3. **Separate startup, readiness, and liveness.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case startup. Until it succeeds, both other probes are disabled. Exhausting startup failures kills the container, followed by its restart policy. After startup, readiness should indicate whether the API can serve requests, including required database availability; failed readiness removes its address from matching Service endpoints without itself restarting the container. Liveness should detect an unhealthy application, such as deadlock, rather than merely database unavailability; failure kills the container and invokes its restart policy. These checks require application-defined health semantics. Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311-347`; `concepts/workloads/pods/pod-lifecycle.md:476-497`, `512-529`.

4. **Thirty seconds is a deadline, not a request-completion guarantee.** The grace-period countdown starts **before** `preStop`; hook execution consumes that budget. Kubelet runs the hook before requesting TERM delivery to container process 1. A hook still running at expiry receives a small, one-off two-second extension request; remaining processes are forcibly killed with SIGKILL. Endpoint updates proceed concurrently with shutdown: terminating EndpointSlice entries are not immediately removed, but have `ready: false` for regular traffic; `serving` supports draining decisions. Implement application shutdown that finishes open requests, then choose grace time from measured hook and request durations. The documents do not establish instantaneous traffic convergence or successful completion of every connection. Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:1000-1008`; `concepts/workloads/pods/pod-lifecycle.md:584-645`.

5. **Size resources before tuning CPU autoscaling.** CPU requests are scheduling inputs: the scheduler checks summed requests against node capacity. Containers may exceed requests when resources permit. CPU limits enforce throttling; memory limits instead permit reactive OOM termination, rather than CPU-style throttling or necessarily immediate killing upon over-allocation. Set explicit, measured CPU requests for every relevant container. CPU-utilization HPA divides usage by requests; if some containers lack the relevant request, Pod utilization is undefined and HPA takes no action for that metric. Inspect admitted specifications: where no admission default intervenes, a specified limit can become the request automatically. Sources: `concepts/configuration/manage-resources-containers.md:27-67`, `230-241`; `tasks/run-application/horizontal-pod-autoscale.md:89-102`.

6. **Expect conservative HPA decisions.** The basic calculation is the ceiling of current replicas multiplied by current-to-target metric ratio, with default tolerance 0.1. Deleting and failed Pods are excluded; missing metrics and certain not-yet-ready CPU samples are set aside. Missing samples are then assumed at 100% of target for downscaling and 0% for upscaling. Not-yet-ready Pods also dampen an otherwise indicated upscale using a zero-consumption assumption. If recalculation reverses direction or enters tolerance, scaling stops. Default readiness-delay and CPU-initialization settings are 30 seconds and five minutes. Downscaling selects the highest recommendation within the default five-minute stabilization window. Therefore reported utilization and the raw ratio need not predict the actual replica change. A working resource-metrics API, usually separately deployed Metrics Server, is a prerequisite. Sources: `tasks/run-application/horizontal-pod-autoscale.md:113-218`.

7. **Replace default allow with explicit connection permissions.** Establish default-deny ingress and egress, then allow approved callers to the API port, API egress to the database port, and database ingress from API Pods. Allow DNS queries to the cluster’s actual resolver, plus only other demonstrated dependencies. Isolation is independent in each direction; policies combine additively as a union, so an existing broad allow defeats narrower restrictions. A connection requires both source egress and destination ingress permission; reply traffic is implicitly allowed. Validate namespace and Pod selectors, ports, and resolver placement. NetworkPolicy requires an enforcing network plugin/CNI: creating objects alone has no effect, and node traffic has documented exceptions. Sources: `concepts/services-networking/network-policies.md:13-81`; `concepts/security/multi-tenancy.md:209-223`.

8. **Reject base64 Secrets in Git as a protection mechanism.** The documentation demonstrates decoding base64 back into credentials and explicitly calls encoded authentication data “obscured but not secret.” Enable Secret encryption at rest: Kubernetes otherwise stores Secrets unencrypted in etcd. Apply least-privilege RBAC and expose each Secret only to containers that need it. Restrict Pod creation and indirect workload creation too: someone authorized to create Pods in a namespace can use that ability to read its Secrets, including through a Deployment. Choose a protected credential-delivery workflow; cluster encryption does not establish confidentiality for credentials already committed to Git. Sources: `concepts/configuration/secret.md:282-307`, `35-48`.

9. **Treat PVC retention and PV reclamation separately.** Dynamically created PVs inherit the StorageClass reclaim policy, defaulting to `Delete`. Changing the class is not a retroactive repair: inspect and edit or patch existing PVs individually. After PVC deletion releases a volume, `Retain` preserves the PV and data for manual reclamation; `Delete`, for supporting plugins, removes both PV and backing storage. StatefulSet deletion or scaling normally retains template-created PVCs. Its separate `whenDeleted` and `whenScaled` policies can instead delete affected PVCs after Pods terminate; the supplied documentation requires `StatefulSetAutoDeletePVC` enabled on the API server and controller manager. If the database uses a StatefulSet, inspect those settings explicitly. Sources: `concepts/storage/storage-classes.md:126-135`; `concepts/storage/persistent-volumes.md:179-210`; `concepts/workloads/controllers/statefulset.md:390-423`.

10. **Prioritize validation as release gates.** First, remove the credential exposure and verify encryption, RBAC, and workload-creation permissions. Second, confirm database recovery procedures, existing PV policies, and PVC retention. Third, verify NetworkPolicy enforcement with allowed and denied connection tests, including DNS. Fourth, deploy measured requests, probes, shutdown handling, zone spreading, compatible rollout settings, and functioning HPA metrics. Finally, exercise a drain, rolling update, zone outage, database interruption, and scaling under representative long-request load. Validate at least these unresolved limits: application request-draining correctness and duration; capacity and placement after zone loss; database recovery and storage durability; probe accuracy; and whether CPU utilization predicts service demand. The documents establish mechanisms, not those application or cluster outcomes. Sources: `concepts/workloads/pods/disruptions.md:104-145`; `concepts/workloads/pods/pod-lifecycle.md:612-645`; `concepts/scheduling-eviction/topology-spread-constraints.md:605-623`; `concepts/storage/persistent-volumes.md:179-210`.
