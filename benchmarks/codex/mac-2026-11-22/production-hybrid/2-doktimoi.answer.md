Decision: revise before production approval. The proposed controls do not establish five-replica availability, safe request draining, or database durability. The following separates documented behavior from recommended configuration and remaining validation.

1. **PDB and rollout availability.** `minAvailable: 5` cannot prevent involuntary node failure; unavailable Pods nevertheless consume the budget. During a normal, eviction-based node drain, it constrains voluntary evictions: starting with six healthy replicas, one eviction can proceed, and further evictions may wait for recovery. Direct deletion bypasses this protection. Deployment rolling updates are **not constrained by PDBs**, although their unavailable Pods count against the budget. Thus `maxUnavailable: 2` permits four available replicas at desired scale six. Set it to at most `1`; preferably choose `maxUnavailable: 0, maxSurge: 1`, with surge capacity provisioned. These are rollout controls, not protection against simultaneous failures. 2. **Zone placement.** Configure an API-specific selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`; verify node labels and capacity. With three eligible zones, strict placement supports a balanced six-Pod distribution. Under `DoNotSchedule`, skew limits the target domain’s matching-Pod count relative to the global minimum; violating placements remain unscheduled. `ScheduleAnyway` instead prefers reduced skew while permitting imbalance—choose this explicitly if recovery capacity outweighs strict distribution. Zone unavailability does not imply automatic recovery: eligibility matters. With `minDomains: 3`, fewer than three eligible domains makes the global minimum zero, potentially blocking replacement Pods. Without it, the default is one. Domains absent from existing nodes are unknown, and Pod removal need not preserve balance. 3. **Probes.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Until it succeeds, readiness and liveness probes are disabled. Configure readiness to establish that the API can serve requests, including required database availability; its failure removes the Pod from matching Service endpoints without itself restarting the container. Use liveness for application failure such as deadlock, avoiding database-dependent restart cascades. Startup or liveness failure kills the container, with restart governed by `restartPolicy`. Startup success enables the other probes; readiness success admits Service traffic. These mechanisms depend on meaningful application checks and suitable thresholds. 4. **Termination and long requests.** The grace-period countdown starts **before** `preStop`; the hook consumes that budget. Kubelet runs the hook, then requests TERM delivery to the container process. A still-running hook can receive a one-off two-second extension; remaining processes receive SIGKILL after grace expires. Concurrently, terminating EndpointSlice entries remain visible temporarily but have `ready: false`, excluding regular load-balanced traffic; `serving` supports draining decisions. Thirty seconds is therefore no request-completion guarantee. Implement signal handling and connection draining, and size grace for the hook plus measured request completion. 5. **Resource sizing.** CPU requests drive scheduling feasibility; containers can use spare resources above their requests. CPU limits impose throttling, potentially affecting latency. Memory limits behave differently: enforcement is reactive through OOM kills, rather than CPU-style throttling or guaranteed immediate rejection. Set measured requests and limits for every relevant container. Utilization-based HPA divides usage by requests; missing relevant requests in some containers leaves Pod CPU utilization undefined, preventing action for that metric. An omitted request is not necessarily absent in the admitted Pod: defaults may apply, and otherwise a specified limit is copied into its request. 6. **HPA’s conservative calculations.** The raw calculation is the ceiling of current replicas multiplied by current/target metric. HPA sets aside missing metrics and initializing CPU samples. Missing metrics are assumed at 100% of target for downscaling and 0% for upscaling; not-yet-ready Pods additionally dampen scale-up with a zero-consumption assumption. A recalculation that reverses direction or enters tolerance produces no scaling. Default readiness-delay and CPU-initialization windows are 30 seconds and five minutes. Downscale stabilization defaults to five minutes, selecting the highest recommendation within that window. Consequently, reported utilization and the raw ratio need not predict the actual replica change. Verify actual resolver destinations and ports. Isolation applies independently per direction. Policies are additive unions: another broad allow can defeat the intended restriction. For Pod-to-Pod connections, source egress and destination ingress must both permit traffic; replies are implicitly allowed. Ingress isolation also retains documented node-originated access. A NetworkPolicy-capable networking implementation is a prerequisite—creating policy objects alone can have no effect. 8. **Secrets.** Reject base64-only Secrets in Git: encoding obscures data but does not make it secret. Enable encryption at rest for Kubernetes Secrets, which otherwise default to unencrypted etcd storage; this does not protect repository copies. Apply least-privilege RBAC and expose credentials only to containers needing them. Restrict workload creation too: authorization to create Pods, including indirectly through Deployments, permits access to any Secret in that namespace. Restricting direct Secret reads alone is insufficient. 9. **Storage lifecycle.** Dynamically provisioned PVs inherit their StorageClass reclaim policy when created; changing the class is not a retroactive update to existing PVs.
