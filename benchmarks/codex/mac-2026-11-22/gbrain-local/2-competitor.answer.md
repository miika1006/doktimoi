**Decision memo — revise before production approval.** The proposed fields do not establish an end-to-end availability, security, or durability guarantee. Approve only after the configuration changes and validation below. Citations refer exclusively to the supplied Kubernetes v1.32 corpus; recommendations are configuration choices derived from those documented behaviors.

1. **PDB protection depends on the disruption.** Node failure is involuntary: a PDB cannot prevent it, although unavailable Pods count against the budget. During a node drain using the Eviction API, a correctly selected `minAvailable: 5` PDB restricts voluntary eviction; with six healthy replicas, it permits one disruption, and further evictions can block. Direct deletion bypasses this protection. Deployment rolling updates are explicitly unconstrained by PDBs, so `maxUnavailable: 2` permits rollout availability to fall to four. Choose `maxUnavailable: 1`, `maxSurge: 1`, or more conservatively zero unavailable with one surge, and provide scheduling capacity. These control rollout actions, not simultaneous failures. See [disruptions, lines 107–140](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/workloads/pods/disruptions.md:107) and [Deployment, lines 1183–1211](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/workloads/controllers/deployment.md:1183).

2. **Spread explicitly across zones.** Use an application label selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`. The topology key groups equally labelled nodes into domains. With `DoNotSchedule`, skew bounds matching Pods in the target domain relative to the global minimum; unsatisfiable placements remain pending. `ScheduleAnyway` instead prefers reduced skew while allowing imbalance. Recommend hard spreading normally, with an explicit outage policy. When a zone becomes unavailable, placement depends on eligible domains, taints, and capacity: `minDomains: 3` makes the global minimum zero when fewer than three domains remain eligible, potentially blocking replacements. Soft spreading favors placement but sacrifices strict balance. Six balanced replicas imply two per zone, so losing one can leave four. Scheduling constraints do not preserve balance after removals. See [spread definitions, lines 82–130](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/scheduling-eviction/topology-spread-constraints.md:82), [eligibility and labels, lines 167–211](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/scheduling-eviction/topology-spread-constraints.md:167), and [limitations, lines 605–619](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/scheduling-eviction/topology-spread-constraints.md:605).

3. **Separate startup, readiness, and liveness.** Configure a startup probe with sufficient failure threshold and period for measured startup duration. Other probes remain disabled until startup succeeds. Startup failure kills the container, with restart governed by its restart policy; liveness failure similarly triggers killing and restart. Readiness should indicate whether requests can actually succeed, including required database availability where appropriate. Readiness failure removes the Pod from matching Service endpoints without itself restarting the container. Liveness should assess application health independently of a temporary database outage. HTTP health endpoints are suitable if the application implements those meanings; their correctness is an application prerequisite. See [probe behavior, lines 479–497](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/workloads/pods/pod-lifecycle.md:479) and [probe selection, lines 512–557](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/workloads/pods/pod-lifecycle.md:512).

4. **Thirty seconds is a shutdown budget, not a request-completion guarantee.** Deletion records the grace period before local shutdown begins. The kubelet runs `preStop` first when configured and grace is nonzero, then requests TERM delivery to container process 1. Hook execution consumes the grace period; it does not precede a fresh thirty-second allowance. An overlong hook receives a small, one-off two-second extension. Remaining processes receive SIGKILL when grace expires. Concurrently, terminating endpoints remain temporarily in EndpointSlices with `ready: false`; `serving` supports draining-aware consumers. Size grace for hook work and measured request draining, and implement signal handling. The docs do not establish completion of arbitrary long requests or instantaneous traffic convergence. See [termination, lines 565–639](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/workloads/pods/pod-lifecycle.md:565).

5. **Set resource requests deliberately.** CPU requests inform scheduling and provide the denominator for utilization-based HPA; they are not CPU ceilings. Containers can exceed requests when resources permit. CPU limits enforce throttling, potentially affecting latency. Memory limits use reactive OOM killing rather than analogous throttling; excess allocation need not cause immediate termination. Configure measured CPU and memory requests and tested limits. If relevant containers lack effective CPU requests, Pod CPU utilization is undefined and HPA takes no action for that metric. Check admitted values: a limit can become the request when no request or admission default exists. See [resources, lines 18–66](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/configuration/manage-resources-containers.md:18) and [HPA utilization, lines 89–102](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/tasks/run-application/horizontal-pod-autoscale.md:89).

6. **Expect conservative HPA decisions.** The basic calculation rounds up current replicas multiplied by current-to-target utilization. Missing metrics are initially set aside, then assumed at 100% of target for downscaling and 0% for upscaling. Not-yet-ready CPU Pods are also set aside; during potential upscaling they are conservatively treated as consuming zero. Readiness interpretation uses configurable timing windows, defaulting to thirty seconds and five minutes. Recalculation can cancel scaling if direction reverses or enters tolerance, default 10%. Downscale stabilization selects the highest recommendation within a default five-minute window. Consequently, displayed utilization and the raw ratio need not predict the action. Verify the separately supplied resource metrics API. See [HPA, lines 113–118 and 129–218](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/tasks/run-application/horizontal-pod-autoscale.md:113).

7. **Replace default allow with explicit communication permissions.** Select API and database Pods with default-deny ingress and egress policies, then allow approved callers to the API port, API egress to the database port, and corresponding database ingress. Add required DNS access and explicitly inventory other dependencies. Ingress and egress isolation are independent. Policies are additive unions: a broad allow elsewhere defeats a narrow policy’s intended restriction. Both source egress and destination ingress must permit a connection; permitted replies are implicitly allowed. A CNI/networking implementation supporting NetworkPolicy is mandatory—creating objects alone has no effect. Validate allowed and denied flows. See [NetworkPolicy, lines 45–81 and 105–122](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/services-networking/network-policies.md:45) and [DNS allowance guidance, lines 215–233](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/security/multi-tenancy.md:215).

8. **Reject base64 Secrets in Git as protection.** Base64 obscures values but does not keep them secret; repository readers can recover credentials. Remove that storage pattern. Kubernetes Secrets are also unencrypted in etcd by default. Enable encryption at rest, apply least-privilege RBAC, and expose each Secret only to containers that need it. Encryption at rest does not protect a readable Git manifest. Restrict Pod creation and indirect workload creation too: someone authorized to create Pods in a namespace can use that capability to read its Secrets, even without direct Secret-reading permission. See [Secret encoding, lines 282–307](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/configuration/secret.md:282) and [Secret security prerequisites, lines 35–48](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/configuration/secret.md:35).

9. **Audit existing PVs individually.** Dynamically provisioned PVs inherit the StorageClass reclaim policy at creation, defaulting to `Delete`. A later class-policy change does not retroactively change existing PV policies; edit or patch those PVs explicitly. After PVC deletion, `Retain` preserves the released PV and data for manual reclamation. Supported `Delete` behavior removes both PV and backing storage. StatefulSet deletion or scale-down is a separate trigger: PVC retention defaults to `Retain`, but configured `whenDeleted` or `whenScaled: Delete` can delete template-created PVCs, subsequently invoking PV reclamation. Verify the documented feature prerequisite before relying on that setting. See [StorageClass, lines 126–135](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/storage/storage-classes.md:126), [PV reclamation, lines 178–210](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/storage/persistent-volumes.md:178), and [StatefulSet retention, lines 391–423](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/workloads/controllers/statefulset.md:391).

10. **Prioritize validation before rollout.** First remove exposed credentials, verify encryption/RBAC, and prove network-policy enforcement. Second audit PV policies and database recovery; for topology-constrained storage, evaluate supported `WaitForFirstConsumer` provisioning. Third establish probe semantics, resource sizing, HPA metrics, minimum replica policy, and surge capacity. Finally stage a rollout, eviction-based drain, node/zone failure, missing-metrics event, and long-request termination while observing readiness and completed requests. Required validation limits include actual startup duration, shutdown/request completion, surviving-zone capacity, CNI enforcement, and database failover/durability. These documents describe mechanisms; they do not establish those application or cluster outcomes. This checklist follows the cited disruption, probe, networking, and HPA constraints; storage scheduling prerequisites appear in [StorageClass, lines 171–199](/private/tmp/doktimoi-bench-2-competitor-jeIJrI/docs/concepts/storage/storage-classes.md:171).
