**Decision: revise the design before production rollout.** The proposed settings do not establish five-replica availability, completion of long requests, credential confidentiality, or database recovery. The following distinguishes documented behavior from recommended configuration and validation requirements. Citations refer only to the supplied documentation.

1. **PDB and rollout availability.** `minAvailable: 5` cannot prevent involuntary node failures; those losses still count against the budget. During an eviction-based node drain, the PDB constrains admitted evictions: with six healthy replicas, one disruption fits the budget, and further evictions may block until recovery. Direct Pod deletion bypasses that protection. Deployment rolling updates are also not constrained by PDBs, although their unavailable Pods count against the budget ([disruptions.md, lines 107–140](docs/concepts/workloads/pods/disruptions.md#L107-L140)).

   Consequently, `maxUnavailable: 2` permits rollout availability to fall to four at six desired replicas. Recommend `maxUnavailable: 0`, `maxSurge: 1`, with capacity for the extra Pod; `maxUnavailable: 1` is the less conservative configuration compatible with a five-of-six rollout floor. These control rollout behavior, not simultaneous infrastructure failures ([deployment.md, lines 1183–1211](docs/concepts/workloads/controllers/deployment.md#L1183-L1211)).

2. **Zone spreading.** Configure an application-matching `labelSelector`, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`; aim for two replicas per zone. `topologyKey` groups nodes by label value. Under `DoNotSchedule`, skew limits the difference between the target domain’s matching-Pod count and the global minimum. `ScheduleAnyway` prefers reduced skew but allows placement that violates the preferred balance ([topology-spread-constraints.md, lines 82–130](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L82-L130), [lines 196–210](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L196-L210)).

   Choose strict placement only with an explicit outage tradeoff. With `minDomains: 3`, fewer eligible zones makes the global minimum zero, potentially blocking replacements in surviving zones. Without it, the default is one; behavior still depends on eligible nodes and taints. A disappeared zone may cease being counted altogether. Constraints do not rebalance existing Pods after removal. Losing one zone from a two/two/two distribution leaves four replicas, regardless of the PDB ([same document, lines 95–115, 167–185](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L95-L185), [607–619](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L607-L619)).

3. **Probes for slow startup.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case startup. The documentation’s 300-second example illustrates configuration, not an appropriate application-specific deadline ([configure-liveness-readiness-startup-probes.md, lines 315–347](docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md#L315-L347)).

   Startup success enables the other probes. Readiness should represent ability to serve requests, including a required database dependency; readiness failure removes the Pod from matching Service endpoints without itself restarting the container. Liveness should detect an unhealthy application process rather than merely database unavailability. Startup or liveness failure kills the container subject to restart policy ([pod-lifecycle.md, lines 479–497](docs/concepts/workloads/pods/pod-lifecycle.md#L479-L497), [509–528](docs/concepts/workloads/pods/pod-lifecycle.md#L509-L528)). Thus, database disruption should not automatically trigger a fleet-wide liveness restart.

4. **Termination and long requests.** Deletion records the grace deadline; the kubelet begins shutdown and executes `preStop`, when configured and grace is nonzero, before requesting TERM to container process 1. The hook consumes the existing grace period; it does not receive an additional 30 seconds. An unfinished hook can receive a small, one-off two-second extension. Remaining processes receive SIGKILL when grace expires ([pod-lifecycle.md, lines 581–610](docs/concepts/workloads/pods/pod-lifecycle.md#L581-L610), [636–645](docs/concepts/workloads/pods/pod-lifecycle.md#L636-L645)).

   Endpoint changes occur concurrently. Terminating EndpointSlice entries are not immediately removed, but have `ready: false`; `serving` can support draining decisions. **Thirty seconds does not guarantee request completion.** Implement shutdown handling and size grace for hook execution plus request draining, then validate routing convergence and actual long-request behavior ([same document, lines 612–632](docs/concepts/workloads/pods/pod-lifecycle.md#L612-L632)).

5. **Resources and utilization-based HPA.** CPU requests influence scheduling and reserve resources; they are not CPU ceilings. Containers may exceed requests when resources are available. CPU limits enforce throttling, whereas memory limits are enforced reactively through possible OOM kills rather than CPU-style throttling ([manage-resources-containers.md, lines 18–53](docs/concepts/configuration/manage-resources-containers.md#L18-L53)).

   Set explicit, measured CPU requests for every relevant container. HPA CPU utilization is usage relative to requests; missing relevant requests makes Pod utilization undefined, so HPA takes no action for that metric. Inspect effective admitted configuration: absent another default, specifying a limit without a request causes Kubernetes to copy the limit into the request ([horizontal-pod-autoscale.md, lines 89–102](docs/tasks/run-application/horizontal-pod-autoscale.md#L89-L102); [manage-resources-containers.md, lines 63–67](docs/concepts/configuration/manage-resources-containers.md#L63-L67)). Limit values still require performance and memory testing.

6. **HPA’s conservative adjustments.** The basic calculation rounds up current replicas multiplied by current/desired metric value, but default tolerance is 0.1. HPA discards failed Pods, ignores terminating Pods, and sets aside missing metrics and qualifying not-yet-ready CPU samples. Missing samples are assumed at 100% of target for downscale and 0% for upscale; not-yet-ready Pods can further dampen upscale. Reversal of direction or entry into tolerance cancels scaling. Reported utilization excludes these conservative adjustments ([horizontal-pod-autoscale.md, lines 129–202](docs/tasks/run-application/horizontal-pod-autoscale.md#L129-L202)).

   Default downscale stabilization selects the highest recommendation within five minutes. Therefore, displayed utilization and the raw ratio need not predict the actual replica change. Confirm configured controller windows and a functioning metrics API; Metrics Server is a separately deployed prerequisite ([same document, lines 113–118](docs/tasks/run-application/horizontal-pod-autoscale.md#L113-L118), [213–218](docs/tasks/run-application/horizontal-pod-autoscale.md#L213-L218)).

7. **Least-privilege networking.** Apply default-deny ingress and egress to selected application/database Pods, then allow only intended callers to the API port, API egress to database destinations/ports, and database ingress from API Pods. Add required operational dependencies explicitly. Ingress and egress isolation are independent; policies combine additively, so a broad existing allowance remains effective. Both source egress and destination ingress must permit a connection; return traffic for allowed connections is implicitly permitted ([network-policies.md, lines 51–81](docs/concepts/services-networking/network-policies.md#L51-L81)).

   Permit DNS to the actual resolver, normally TCP/UDP 53, and test Service-name resolution ([dns-debugging-resolution.md, lines 158–173](docs/tasks/administer-cluster/dns-debugging-resolution.md#L158-L173)). Enforcement requires a supporting network plugin: merely creating NetworkPolicy objects has no effect without one ([network-policies.md, lines 45–49](docs/concepts/services-networking/network-policies.md#L45-L49)).

8. **Secrets protection.** Reject base64-encoded credentials in Git as a confidentiality mechanism. The docs explicitly describe base64 as obscuring data without making it secret ([secret.md, lines 305–307](docs/concepts/configuration/secret.md#L305-L307)). Enable encryption at rest for Secrets, least-privilege RBAC, and container-specific access. Restrict workload creation as well as direct Secret reads: permission to create Pods—or indirectly Deployments—in a namespace permits access to its Secrets ([same document, lines 35–48](docs/concepts/configuration/secret.md#L35-L48)).

   Verify effective API-server encryption configuration rather than assuming encryption is enabled. This protects API data in etcd; it does not establish protection for Git copies or mounted database files ([encrypt-data.md, lines 21–31](docs/tasks/administer-cluster/encrypt-data.md#L21-L31), [53–65](docs/tasks/administer-cluster/encrypt-data.md#L53-L65)).

9. **Storage lifecycle.** Changing a StorageClass’s reclaim policy does not retroactively change existing PV policies; inspect and patch those PVs separately. Dynamically provisioned volumes inherit the class policy, defaulting to `Delete`. `Retain` leaves released storage and data for manual reclamation; supported `Delete` removes both the PV and backing storage asset ([persistent-volumes.md, lines 178–210](docs/concepts/storage/persistent-volumes.md#L178-L210)).

   PVC deletion triggers reclamation, with deletion postponed while a Pod actively uses the claim ([same document, lines 123–136](docs/concepts/storage/persistent-volumes.md#L123-L136)). StatefulSet deletion/scaling is a separate layer: PVC retention defaults to `Retain`; configurable `whenDeleted` and `whenScaled` can delete template-generated claims. Verify the documented feature prerequisite before relying on those settings ([statefulset.md, lines 391–423](docs/concepts/workloads/controllers/statefulset.md#L391-L423)).

10. **Prioritized rollout and validation checklist.** First, remove credential exposure, verify encryption/RBAC, and inspect existing PV policies. Second, establish resource requests, metrics collection, and enforced network policies. Third, validate probes and graceful shutdown before applying conservative rollout settings and zone spreading. Finally, exercise drain, failed startup, zone loss, HPA growth/downscale, and storage recovery under representative load.

   Release gates must validate at least these unestablished limits: worst-case startup time; long-request completion within grace; surviving-zone and surge capacity; and database recovery/data integrity. Probe timing and termination provide mechanisms, not application timing guarantees; topology-aware provisioning itself depends on storage-driver support ([probe configuration, lines 315–347](docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md#L315-L347); [termination, lines 619–639](docs/concepts/workloads/pods/pod-lifecycle.md#L619-L639); [storage-classes.md, lines 177–199](docs/concepts/storage/storage-classes.md#L177-L199)).
