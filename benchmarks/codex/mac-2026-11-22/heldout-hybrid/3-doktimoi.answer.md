Resolve the conflict between exclusive batch nodes and interactive workloads reclaiming their capacity before rollout.

1. **CronJob execution is approximate.** A schedule can create two Jobs or none; reporting must therefore be idempotent. `concurrencyPolicy: Allow` permits overlap; `Forbid` skips a scheduled run while its predecessor remains active; `Replace` replaces the active run. These policies apply only within one CronJob. Choose `Forbid` if overlapping reports are unsafe, while accepting missed runs. (`concepts/workloads/controllers/cron-jobs.md:107–143,211–226`)

   `startingDeadlineSeconds` limits lateness in starting a Job, rather than its runtime; expired occurrences are skipped. Values below ten seconds may fail because the controller checks every ten seconds. More than 100 missed schedules prevents starting; a configured deadline bounds the missed-schedule counting window. Runs blocked by `Forbid` count as missed. Set `.spec.timeZone`, preferably explicitly to `Etc/UTC`; otherwise the controller manager’s local zone applies. (`concepts/workloads/controllers/cron-jobs.md:107–126,176–188,228–251`)

2. **Separate retries, runtime, and cleanup.** Job Pods allow only `restartPolicy: Never` or `OnFailure`. With `Never`, failed Pods are replaced; with `OnFailure`, containers can restart within their Pod. `backoffLimit` defaults to six, with exponential replacement delays capped at six minutes. Failed-Pod counts and, for `OnFailure`, container retry counts can exhaust it. (`concepts/workloads/controllers/job.md:210–221,358–380`)

   Set Job-level `activeDeadlineSeconds` to bound the entire Job across replacement Pods. It takes precedence over remaining retries: reaching it terminates running Pods and fails the Job with `DeadlineExceeded`. Exhausting backoff can fail the Job earlier; neither mechanism automatically restarts a failed Job. `ttlSecondsAfterFinished` only makes completed or failed Jobs eligible for cascading cleanup after the specified interval. It does not constrain runtime, and eligibility does not promise instantaneous deletion. (`concepts/workloads/controllers/job.md:615–663,738–775`)

3. **Combine exclusion with required placement.** Taint batch nodes, for example `dedicated=batch:NoSchedule`, give batch Pods the matching toleration, and require node affinity to nodes labeled `dedicated=batch`. A toleration merely permits placement; alone, it also permits batch Pods on ordinary nodes. Required affinity confines them, while the taint excludes Pods lacking the toleration. Control who can supply those tolerations; the fields alone do not establish team isolation. (`concepts/scheduling-eviction/taint-and-toleration.md:12–24,176–191`)

   `NoSchedule` blocks new placements without removing existing Pods. `NoExecute` also evicts existing non-tolerating Pods; matching tolerations can delay eviction with `tolerationSeconds`. Prefer `NoSchedule` for initial dedication unless eviction is deliberately intended. (`concepts/scheduling-eviction/taint-and-toleration.md:109–130,157–172`)

4. **Priority requires feasible placement.** Create cluster-scoped PriorityClasses with lower numeric priority for batch and higher priority for interactive services; reference them through Pod-template `priorityClassName`. Choose batch `preemptionPolicy: Never` to prevent batch from displacing others. This does not protect batch from higher-priority preemptors. Interactive classes need `PreemptLowerPriority`, the default, to reclaim capacity through preemption. (`concepts/scheduling-eviction/pod-priority-preemption.md:35–73,103–127`)

   Preemption only helps where removing lower-priority Pods makes the incoming Pod schedulable. If interactive services cannot tolerate batch-node taints, they cannot reclaim that capacity. Decide whether exclusivity or shared emergency capacity takes precedence. Victims receive graceful termination, delaying reclamation. PodDisruptionBudgets are considered best effort and may be violated. (`concepts/scheduling-eviction/pod-priority-preemption.md:185–194,214–238`)

5. **Quota controls admission, not guaranteed capacity.** Verify that ResourceQuota admission is enabled and create quotas in each team namespace. New Pods must specify CPU/memory requests or limits as required by the quota; explicitly supplying both avoids ambiguity and makes resource planning clearer. LimitRange can supply defaults. Distinguish `requests.cpu`/`requests.memory` from `limits.cpu`/`limits.memory`: each caps its respective aggregate across non-terminal Pods. (`concepts/policy/resource-quotas.md:20–58,79–105`)

   Creation or updates exceeding quota fail with HTTP `403 FORBIDDEN`; they are not simply admitted to wait for capacity. Quota changes do not affect already-created resources. Aggregate namespace quotas can exceed cluster capacity, so quota allowance does not reserve runnable capacity. (`concepts/policy/resource-quotas.md:35–40,65–75`)

6. **ConfigMap propagation depends on consumption.** Ordinary mounted ConfigMap volumes eventually receive projected updates. Delay can reach the kubelet sync period plus cache propagation delay; watch propagation, TTL caching, or direct retrieval changes that delay. A `subPath` mount receives no updates. Environment variables remain unchanged until Pod restart. File projection does not establish that the reporting process rereads files or safely changes configuration mid-run. (`concepts/configuration/configmap.md:191–209`)

   Choose either deliberately reloadable settings or versioned settings fixed for each report. An immutable ConfigMap cannot become mutable again, nor can its `data` or `binaryData` change. Replacement requires deletion/recreation or a different object; existing Pods retain their old mount point, so recreate consumers when replacing the object. (`concepts/configuration/configmap.md:299–328`; `tutorials/configuration/updating-configuration-via-a-configmap.md:723–734`)

7. **Memory-pressure eviction is not simply lowest priority first.** After attempted resource reclamation, kubelet ranks Pods first by whether usage exceeds requests, then priority, then usage relative to requests. BestEffort and Burstable Pods exceeding requests go first; Guaranteed and below-request Burstable Pods go last. QoS itself is not the sorting input. Even the latter group can be evicted when system consumption threatens node stability. (`concepts/scheduling-eviction/node-pressure-eviction.md:319–354`)

   Node-pressure eviction ignores PodDisruptionBudgets and the Pod’s `terminationGracePeriodSeconds`. Hard thresholds cause immediate termination; soft thresholds use kubelet eviction grace configuration. Batch must tolerate abrupt interruption regardless of its normal shutdown settings. (`concepts/scheduling-eviction/node-pressure-eviction.md:25–41,185–206`)

8. **Restricted admission validates; it does not repair manifests.** With PodSecurity admission active, set namespace `pod-security.kubernetes.io/enforce=restricted` and pin `enforce-version=v1.32`. Restricted includes all Baseline controls and restricts volume types; ConfigMap volumes are allowed. Require non-root execution and prohibit explicit UID zero. For Linux, disable privilege escalation, explicitly select `RuntimeDefault` or `Localhost` seccomp, drop `ALL` capabilities, and add back only `NET_BIND_SERVICE` if needed. Apply relevant requirements to application, init, and ephemeral containers; Windows exceptions exist. (`reference/access-authn-authz/admission-controllers.md:715–725`; `reference/labels-annotations-taints/_index.md:2369–2399`; `concepts/security/pod-security-standards.md:299–455,500–504`)

   `enforce` rejects violations; `audit` records them without rejection; `warn` returns user-visible warnings without rejection, including for workload templates. Audit/warn first, but finish with enforcement. Admission does not inject missing security settings. Restrict namespace-label permissions and cover newly created namespaces. (`tasks/configure-pod-container/migrate-from-psp.md:49–89,247–272,313–320`; `reference/labels-annotations-taints/_index.md:2435–2451`)

9. **Disable unnecessary credential injection explicitly.** Kubernetes assigns the namespace’s default ServiceAccount when none is specified and normally supplies credentials. In current versions these are short-lived, rotating projected tokens; rotation does not remove the credential’s availability to the workload. Set Pod-template `spec.automountServiceAccountToken: false`, and also disable automounting on team ServiceAccounts as a default. The Pod setting takes precedence over the ServiceAccount setting. This controls automatic mounting; it does not establish that images or explicit mounts contain no other credentials. (`concepts/security/service-accounts.md:141–157`; `tasks/configure-pod-container/configure-service-account.md:32–57,66–100`)

10. **Roll out in risk order.** First resolve node-sharing policy, protect namespace policy permissions, and validate admission prerequisites. Next standardize restricted-compliant Job templates, token opt-out, resource declarations, required affinity, tolerations, and priority. Then select concurrency, lateness, retry, runtime, configuration-version, and cleanup policies. Finally canary one team before expanding; use security dry-run, audit, and warning results to fix violations before enforcement. These steps combine the controls above with the documented security rollout tools. (`tasks/configure-pod-container/migrate-from-psp.md:247–272`)

   Validation must include duplicate/retried report safety; acceptable recovery after abrupt termination; interactive scheduling latency under preemption and node constraints; application configuration reload behavior; and actual requests, memory peaks, and eviction thresholds. The cited scheduling, ConfigMap, and eviction documents establish mechanisms, not these application or cluster outcomes. Test quota rejection, overdue schedules, deadline termination, missing token mounts, and forbidden security settings before general rollout.
