**Decision memo — revise before production rollout.** The proposed fields do not jointly guarantee availability, request completion, or database durability. Adopt the following configuration choices, then validate their behavior under load and failure. Citations refer to source lines in the supplied local `docs/` corpus.

1. **The PDB does not guarantee five available replicas in all three cases.** During node failure, involuntary disruption can take availability below five; it counts against the budget but cannot be prevented. During a normal node drain using the Eviction API, the PDB restricts voluntary evictions: with six healthy replicas, only one can be disrupted before replacements recover. Drain can block or time out; direct deletion bypasses this protection. During Deployment rolling updates, unavailable Pods count against the budget, but the Deployment is not constrained by it. Thus, `maxUnavailable: 2` permits four available replicas. Recommend `maxUnavailable: 0, maxSurge: 1`, with capacity for the extra Pod; `maxUnavailable: 1` also aligns with a five-replica rollout floor at six desired replicas. Neither protects against concurrent failures. Sources: `docs/concepts/workloads/pods/disruptions.md:99–145`; `docs/concepts/workloads/controllers/deployment.md:1183–1211`.

2. **Configure explicit zone spreading.** Use an API label selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, targeting two replicas per zone. The topology key groups identically labelled nodes into domains. With `DoNotSchedule`, skew limits the difference between matching Pods in the candidate domain and the global minimum; unsatisfiable placements remain pending. `ScheduleAnyway` instead prefers placements reducing skew without enforcing the bound. Choose deliberately between strict distribution and replacement capacity during zone loss. With `minDomains: 3`, fewer than three eligible domains makes the global minimum zero, potentially blocking replacements in surviving zones. Eligibility depends on affinity and taint handling; an unavailable zone does not automatically imply a particular scheduling outcome. Spreading also does not rebalance existing Pods after removal. Losing a zone containing two replicas initially leaves four, regardless of the PDB. Sources: `docs/concepts/scheduling-eviction/topology-spread-constraints.md:78–130,167–185,605–619,525–529`.

3. **Use startup protection, service readiness, and narrowly defined liveness.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Readiness and liveness probes begin only after startup succeeds. Exhausting startup failures kills the container, subject to its restart policy. Readiness should report whether the API can accept useful work, including relevant dependency availability; becoming unready removes the Pod from Service load balancing without requiring a restart. Liveness should detect failures a restart can repair, such as deadlock. Avoid making a temporary database outage trigger repeated API restarts. Probe thresholds and health semantics are application configuration choices, not documented guarantees of correct detection. Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:13–46,311–347,349–354`.

4. **Budget shutdown time for both hooks and request draining.** Deletion records the grace period; the kubelet begins shutdown and runs `preStop`, when configured and grace is nonzero, before requesting TERM delivery. The hook consumes the grace period—it does not receive a separate shutdown budget. A still-running hook can receive a one-off two-second extension. Remaining processes eventually receive SIGKILL. Ordinary containers have no guaranteed inter-container shutdown order; image stop signals can also affect signal delivery. Endpoint processing happens concurrently: terminating endpoints remain temporarily in EndpointSlices but have `ready: false`, excluding regular traffic; `serving` can support draining. **Thirty seconds does not guarantee long-request completion.** Measure hook duration, connection draining, and application shutdown, then set adequate grace. Source: `docs/concepts/workloads/pods/pod-lifecycle.md:565–639`.

5. **Set measured resource requests and limits.** CPU requests inform placement and provide the denominator for utilization-based HPA; they are not CPU consumption ceilings. Containers may exceed requests when resources permit. CPU limits enforce throttling, which can increase request latency. Memory limits are enforced reactively through OOM kills, rather than CPU-style throttling; exceeding one can terminate the container. Set explicit CPU requests for every relevant container: if some containers lack them, Pod CPU utilization is undefined and HPA takes no action for that metric. Inspect admission defaults too: a limit can become the request when no request/default exists. Sources: `docs/concepts/configuration/manage-resources-containers.md:20–66,230–240`; `docs/tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **Expect conservative HPA decisions, not the raw ratio alone.** The basic calculation is the ceiling of current replicas multiplied by current/desired metric value. Missing metrics are set aside initially, then assumed at 100% of target for downscaling and 0% for upscaling, damping changes. CPU metrics from not-yet-ready Pods are also set aside; during potential scale-up, those Pods are conservatively assumed to consume 0% of target. Readiness heuristics default to a 30-second initial readiness delay and five-minute CPU initialization period. A revised ratio reversing direction or falling within tolerance produces no scaling. Downscale stabilization defaults to five minutes and selects the highest recommendation in that window. Verify the metrics API, usually supplied by separately deployed Metrics Server. Source: `docs/tasks/run-application/horizontal-pod-autoscale.md:113–118,129–218`.

7. **Replace default allow with explicit connection permissions.** Establish default-deny ingress and egress for the relevant namespaces, then allow approved callers to API ports, API egress to database ports, matching database ingress, and DNS queries to the cluster’s actual DNS endpoints. Add other dependencies individually. Ingress and egress isolation are independent; a Pod-to-Pod connection requires permission at both source egress and destination ingress. Policies combine additively: a permissive existing policy can reopen access despite a default-deny policy. Reply traffic for allowed connections is implicitly allowed. A supporting network plugin/CNI is a prerequisite; creating accepted NetworkPolicy objects alone has no effect without enforcement. Sources: `docs/concepts/services-networking/network-policies.md:45–81,105–113`; `docs/concepts/security/multi-tenancy.md:208–234`.

8. **Reject base64 Secrets in Git as sufficient protection.** Base64 is a data representation, not a confidentiality boundary: the documentation demonstrates direct conversion of credentials into those strings. Remove this storage pattern and use a controlled secret-delivery process. Enable API-data encryption at rest and least-privilege RBAC; Secrets otherwise default to unencrypted storage in etcd. Restrict which containers receive each Secret. Pod-creation permission matters because someone able to create Pods—or indirectly Deployments—in a namespace can use that capability to read its Secrets. Restrict workload creation as well as direct Secret access. API-data encryption does not establish encryption of database volumes. Sources: `docs/tasks/inject-data-application/distribute-credentials-secure.md:17–28`; `docs/concepts/configuration/secret.md:35–48,453–457`; `docs/tasks/administer-cluster/encrypt-data.md:20–31,53–64`.

9. **Treat PV reclamation and PVC retention as separate decisions.** Dynamically provisioned PVs inherit their StorageClass reclaim policy, defaulting to `Delete`. Changing the class does not retroactively change existing PV policies; edit or patch those PVs explicitly. With `Retain`, deleting a PVC leaves a released PV and its data requiring manual reclamation. With supported `Delete` plugins, reclamation removes both the PV and underlying storage asset. StatefulSet deletion/scaling normally retains template PVCs; configurable `whenDeleted` and `whenScaled` policies can instead delete them, after which PV reclamation applies. Confirm the documented feature prerequisites. The API Deployment itself does not establish the database’s controller or retention settings. Sources: `docs/concepts/storage/storage-classes.md:126–135`; `docs/concepts/storage/persistent-volumes.md:178–210`; `docs/concepts/workloads/controllers/statefulset.md:387–423`.

10. **Roll out in priority order and require evidence before promotion.** First secure credentials and verify database PVC/PV retention and recovery procedures. Next establish enforced network permissions, explicit resource requests, working metrics, zone constraints, and surge capacity. Then deploy the probes and draining behavior, followed by the compatible rollout strategy. Exercise slow startup, database interruption, rolling update, drain, zone loss, missing metrics, and long requests during termination. Validate at least these unresolved limits: application health-check accuracy; maximum request/shutdown duration; surviving-zone and surge capacity; actual CNI enforcement; and database recovery and storage behavior. These documents describe mechanisms, not successful outcomes for this application. Sources: `docs/concepts/workloads/pods/pod-lifecycle.md:591–639`; `docs/concepts/scheduling-eviction/topology-spread-constraints.md:605–619`; `docs/concepts/services-networking/network-policies.md:45–49`; `docs/concepts/storage/persistent-volumes.md:178–210`.
