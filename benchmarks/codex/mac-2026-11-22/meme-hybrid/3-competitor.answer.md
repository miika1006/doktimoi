Decision: revise the design before production approval. Six replicas provide redundancy, but the proposed settings do not establish five continuously available replicas, completed long requests, or database durability. The recommendations below distinguish Kubernetes behavior from configuration choices and validation requirements. All citations are local paths relative to the supplied corpus directory, `docs/`; ranges are source lines.

1. **PDB protection differs by disruption.** Node failure is involuntary: a PDB cannot prevent it, although unavailable Pods count against the budget. During node drain through the Eviction API, `minAvailable: 5` permits eviction only when at least five selected Pods remain healthy; drain can wait or time out. Direct deletion bypasses this protection. Deployment rolling updates count against the budget but are **not constrained by it**. Thus, `maxUnavailable: 2` permits rollout availability to fall to four at six desired replicas. Recommend `maxUnavailable: 0`, `maxSurge: 1`, with capacity for the extra Pod; `maxUnavailable: 1` is also compatible with a five-replica rollout floor absent other failures. Neither prevents concurrent failures. Sources: `concepts/workloads/pods/disruptions.md:99–145`; `tasks/run-application/configure-pdb.md:131–154`; `concepts/workloads/controllers/deployment.md:1183–1211`.

2. **Configure explicit zone spreading.** Use an API label selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, aiming for two replicas per zone when capacity permits. The topology key identifies node-label domains. With `DoNotSchedule`, skew limits the difference between a candidate domain’s matching-Pod count and the global minimum; violating placements remain pending. `ScheduleAnyway` instead prefers placements that reduce skew but permits imbalance. Zone loss removes two replicas from a balanced six-Pod deployment, immediately leaving four. Replacement placement depends on eligible domains, labels, taints, and capacity. With `minDomains: 3`, fewer than three eligible domains makes the global minimum zero, potentially blocking replacements. Soft spreading trades placement strictness for scheduling flexibility. Spreading also does not guarantee continued balance after removals. Source: `concepts/scheduling-eviction/topology-spread-constraints.md:82–130,167–185,558–560,605–619`.

3. **Separate startup, serving readiness, and process health.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Until it succeeds, readiness and liveness probes are disabled. Thereafter, readiness should reflect whether the API can serve requests, including necessary database access; readiness failure removes its Service endpoints without restarting the container. Liveness should detect a condition for which restarting helps, such as deadlock, rather than treating every database interruption as a process failure. Startup or liveness failure reaching the configured threshold kills the container, with restart governed by restart policy. Probe timing and useful health criteria require application testing. Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–368`; `concepts/workloads/pods/pod-lifecycle.md:479–497`.

4. **Thirty seconds is a shutdown budget, not a request-completion guarantee.** The grace-period countdown starts before `preStop`. The kubelet runs the hook before requesting TERM delivery to the container’s main process; the hook consumes that same budget. An overrun can receive a small two-second extension. Remaining processes receive SIGKILL after grace expires. Endpoint processing happens concurrently: terminating EndpointSlice entries are not immediately removed, but have `ready: false`; `serving` can support draining implementations. Configure the application to stop accepting work and finish existing requests, then size grace for measured hook and request durations. The documents do not guarantee instantaneous propagation or successful completion within 30 seconds. Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:1006–1008`; `concepts/workloads/pods/pod-lifecycle.md:572–639`.

5. **Set resource requests deliberately.** CPU requests influence scheduling capacity checks and CPU allocation under contention; they are not usage ceilings. Containers can use more than their requests when resources permit. CPU limits impose throttling, whereas memory limits are enforced reactively through possible OOM killing, rather than CPU-style throttling. Set requests and limits from measurements, including startup and long-request workloads. CPU-utilization HPA calculates usage relative to CPU requests: if relevant requests are missing from some containers, Pod utilization is undefined and that metric cannot drive scaling. Inspect effective admitted resources because a specified limit can become the request when no request or admission default exists. Sources: `concepts/configuration/manage-resources-containers.md:27–66,230–265`; `tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **Expect HPA to depart from the raw ratio.** The basic recommendation is the ceiling of current replicas multiplied by current/desired metric value. Missing metrics are initially set aside, then conservatively assumed at 100% of target for downscaling and 0% for upscaling. Not-yet-ready CPU Pods are also set aside and can dampen scale-up through a 0% assumption. If adjustment reverses direction or enters tolerance, scaling stops. Defaults include 30-second initial-readiness delay, five-minute CPU initialization period, and five-minute downscale stabilization, which selects the highest recent recommendation. Reported utilization excludes these adjustments. Verify metrics availability—usually requiring separately deployed Metrics Server—and actual controller settings. Source: `tasks/run-application/horizontal-pod-autoscale.md:113–118,129–218`.

7. **Replace default allow with explicit least privilege.** Select the API and database Pods for ingress and egress isolation, then allow only approved callers to the API port and API Pods to the database port. Add required DNS egress to the actual cluster resolver, commonly UDP/TCP 53. Ingress and egress isolation are independent; a Pod-to-Pod connection must satisfy source egress and destination ingress. Policies combine additively, so another broad allowance defeats an intended restriction; audit all applicable policies. Return traffic for allowed connections is implicitly permitted. A NetworkPolicy-capable networking implementation is a prerequisite: creating policy objects alone has no effect. DNS destinations and enforcement must be tested locally. Sources: `concepts/services-networking/network-policies.md:45–81,105–122`; `tasks/administer-cluster/dns-debugging-resolution.md:158–174`.

8. **Base64 is insufficient protection.** It obscures credentials without making them secret; repository readers can recover them. Remove this credential-storage approach and use a protected delivery process. Enable encryption at rest for Secrets, apply least-privilege RBAC, and expose each Secret only to containers needing it. Kubernetes otherwise stores Secrets unencrypted in etcd by default. Restrict workload creation as well as direct Secret reads: someone authorized to create Pods—or indirectly create them through a Deployment—in a namespace can use that access to read its Secrets. Encryption in etcd does not protect the Git copy. Sources: `concepts/configuration/secret.md:35–48,305–307,658–669`.

9. **Reclaim policy and PVC retention govern different events.** Dynamically provisioned PVs inherit their StorageClass reclaim policy, defaulting to `Delete`. Changing the class does not retrofit existing PV policies; inspect and edit or patch those PVs separately. After PVC deletion releases a volume, `Retain` leaves the PV and data requiring administrator reclamation. Supported `Delete` behavior removes both the PV and backing storage. StatefulSet deletion or scaling ordinarily retains template-created PVCs. Its optional retention policy can instead delete them through separate `whenDeleted` and `whenScaled` settings, subject to the documented feature prerequisite; subsequent storage reclamation follows the PV policy. Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:180–210`; `concepts/workloads/controllers/statefulset.md:387–423`.

10. **Prioritize validation before rollout.** First secure credentials, restrict workload permissions, and inspect database PVC/PV retention and recovery arrangements. Next confirm network-policy enforcement and metrics prerequisites. Then configure resources, probes, zone spreading, conservative rollout settings, and measured termination grace. Finally exercise a rollout, Eviction-API drain, zone outage, missing metrics, database interruption, and long requests during shutdown. Acceptance must establish application startup bounds, request-draining behavior, remaining-zone capacity, and database recovery/data integrity; these documents do not establish those limits for this system. Keep an HPA minimum consistent with the six-replica operating baseline.
