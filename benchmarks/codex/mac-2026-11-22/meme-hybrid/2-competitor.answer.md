**Decision: revise before production approval.** The proposal combines useful controls, but they do not establish an end-to-end availability or data-safety guarantee. The recommendations below distinguish documented behavior from configuration choices and prerequisites.

All source paths below are local, relative to the supplied `docs/` directory; line ranges refer to source lines.

1. **PDB protection depends on the disruption.** During **node failure**, `minAvailable: 5` cannot prevent lost replicas; involuntary disruptions count against the budget afterward. During an **eviction-based node drain**, it constrains admitted evictions: with six healthy replicas, one can be evicted before further eviction must wait. Direct deletion bypasses it. During a **Deployment rolling update**, unavailable Pods count against the budget, but the Deployment is not constrained by the PDB. Consequently, `maxUnavailable: 2` permits availability to fall to four. Recommend `maxUnavailable: 0, maxSurge: 1`, with capacity for the extra Pod; `maxUnavailable: 1` also matches a five-replica rollout floor at six desired replicas. Neither protects against concurrent failures.  
   Sources: `concepts/workloads/pods/disruptions.md`, lines 99–145; `concepts/workloads/controllers/deployment.md`, lines 1183–1211.

2. **Configure explicit zone spreading.** Put a constraint in the Deployment Pod template using its application selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`. The key groups nodes with identical label values into domains. With `DoNotSchedule`, skew bounds the target domain’s matching-Pod count relative to the global minimum; unsatisfiable Pods remain Pending. `ScheduleAnyway` prefers reduced skew but permits imbalance. Six replicas can normally settle as two per zone, assuming suitable nodes and capacity. An unavailable zone complicates eligibility: affinity and taint policies affect which domains count. If it remains counted but cannot accept Pods, hard spreading can block replacements. If it disappears from eligible domains, remaining zones can accept replacements; specifying `minDomains: 3` instead makes the global minimum zero when fewer qualify, potentially blocking recovery. Choose that tradeoff explicitly; spreading does not restore failed replicas immediately.  
   Sources: `concepts/scheduling-eviction/topology-spread-constraints.md`, lines 78–130, 167–185, 206–211, 605–619.

3. **Separate startup, service readiness, and recoverable failure.** Use a startup probe with a measured startup allowance, expressed through `failureThreshold × periodSeconds`. Until it succeeds, readiness and liveness probes are disabled; their configured delays begin afterward. Use readiness to indicate whether the API can serve requests, including required database availability where appropriate. Readiness failure removes the Pod from matching Service endpoints without restarting the container. Use liveness for application failures that restarting can resolve, such as deadlock; avoid making database unavailability alone a restart trigger. Startup or liveness failure reaching its threshold triggers container termination/restart under the restart policy. These endpoint semantics do not establish instantaneous interruption of existing connections.  
   Sources: `concepts/workloads/pods/pod-lifecycle.md`, lines 479–497, 524–528; `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md`, lines 342–367, 398–422.

4. **Thirty seconds is a shutdown budget, not a completion promise.** The grace-period countdown begins **before** `preStop`; hook execution consumes that budget. The kubelet runs the hook before requesting the container’s TERM signal. The runtime normally sends SIGTERM, although an image’s configured stop signal may apply. Remaining processes receive SIGKILL after grace expires; an overrunning hook can receive a small, one-off two-second extension. Concurrently, terminating Service endpoints are marked terminating and `ready: false`, rather than immediately disappearing from EndpointSlices. The `serving` condition supports draining-aware consumers. Configure application shutdown to stop accepting work and finish open requests, then size grace from observed request and cleanup durations. The docs provide no guarantee that thirty seconds completes these long requests.  
   Sources: `reference/kubernetes-api/workload-resources/pod-v1.md`, lines 1000–1008; `concepts/workloads/pods/pod-lifecycle.md`, lines 572–639.

5. **Set resource requests deliberately.** CPU requests affect scheduling capacity checks and typically relative CPU allocation during contention; they are not a maximum. Containers may use resources above their requests when available. CPU limits restrict CPU time through throttling, potentially affecting latency. Memory limits operate through reactive OOM killing, rather than equivalent CPU-style throttling; over-allocation need not cause an immediate kill. Set measured CPU requests on every relevant container: utilization-based HPA computes usage against requests. If relevant requests are missing, Pod CPU utilization is undefined and HPA takes no action for that metric. Inspect admitted configuration because a specified limit can become the request when none was supplied.  
   Sources: `concepts/configuration/manage-resources-containers.md`, lines 27–66, 230–265; `tasks/run-application/horizontal-pod-autoscale.md`, lines 89–102.

6. **Expect conservative HPA decisions.** The basic recommendation is the ceiling of current replicas multiplied by current-to-target metrics, but missing metrics and readiness modify it. Missing-metric Pods are assumed at 100% of target for downscaling and 0% for upscaling, damping changes. Not-yet-ready CPU Pods are set aside and, when considering scale-up, conservatively assumed at 0%. Readiness classification uses configurable defaults of thirty seconds for initial readiness delay and five minutes for CPU initialization. A recalculated ratio that reverses direction or falls within tolerance produces no scaling. Default downscale stabilization chooses the highest recommendation in the preceding five minutes. Reported utilization excludes these conservative adjustments, so it can appear inconsistent with scaling. Metrics Server or another appropriate metrics API provider is a prerequisite.  
   Source: `tasks/run-application/horizontal-pod-autoscale.md`, lines 113–118, 129–218.

7. **Replace unrestricted connectivity with explicit allowances.** Select application and database Pods with default-deny ingress and egress policies, then allow approved callers to the API port, API-to-database traffic, and required DNS resolution. Ingress and egress isolation are independent. Policies combine additively: a broad allowance elsewhere can reopen traffic, and policy order cannot override it. A Pod-to-Pod connection needs both source egress and destination ingress permission; replies to allowed connections are implicitly allowed. Permit DNS to the cluster’s actual resolver using its required protocols and ports—the documented DNS Service exposes UDP/TCP 53. Validate selectors and any local resolver arrangement. Crucially, a CNI/network controller implementing NetworkPolicy is required; merely creating policies has no effect otherwise.  
   Sources: `concepts/services-networking/network-policies.md`, lines 45–81, 105–122; `tasks/administer-cluster/dns-debugging-resolution.md`, lines 158–174.

8. **Reject base64 credentials in Git as a protection mechanism.** Base64 obscures data; it does not make it secret. Move usable credentials out of ordinary repository manifests into a controlled delivery mechanism. Kubernetes Secrets are unencrypted in etcd by default: enable encryption at rest, restrict Secret access through least-privilege RBAC, and expose credentials only to necessary containers. Encryption of cluster storage does not protect repository copies. Restrict workload creation too: permission to create Pods, including indirectly through Deployments, can provide access to any Secret in that namespace. Secret-read restrictions alone therefore do not establish confidentiality.  
   Source: `concepts/configuration/secret.md`, lines 35–48, 305–307, 453–457.

9. **Treat PV reclamation and PVC retention as separate decisions.** Dynamically provisioned PVs inherit their StorageClass reclaim policy at creation; changing the class does not retrofit existing PVs. Inspect and edit existing PV policies individually. `Retain` leaves released storage and its data for manual reclamation after PVC deletion. Supported `Delete` behavior removes both the PV and backing storage; it is the StorageClass default. StatefulSet deletion or downscaling retains template PVCs by default, unlike explicit PVC deletion. Optional `whenDeleted` and `whenScaled` retention settings can delete affected PVCs, then the PV reclaim policy governs storage disposal. Verify the documented controller/API-server feature-gate prerequisite before depending on that behavior.  
   Sources: `concepts/storage/storage-classes.md`, lines 126–135; `concepts/storage/persistent-volumes.md`, lines 178–210; `concepts/workloads/controllers/statefulset.md`, lines 391–423.

10. **Validate in priority order.** First remove credential exposure and inspect existing PV reclamation settings. Second verify encryption, RBAC, CNI enforcement, permitted database access, and DNS. Third deploy measured requests, probes, shutdown handling, zone constraints, and the revised rollout; retain at least six desired replicas through HPA configuration if that is the operating baseline. Finally exercise rollout, eviction-based drain, abrupt node/zone loss, missing metrics, and disposable PVC deletion. Validate at least these unresolved limits: request completion and endpoint propagation during shutdown; surviving-zone capacity and scheduling; CPU-based scaling’s relationship to application latency; and database failover, storage accessibility, and recoverability. The documents describe control behavior, not successful outcomes for this application or cluster.  
   Sources: `concepts/workloads/pods/disruptions.md`, lines 130–145; `concepts/workloads/pods/pod-lifecycle.md`, lines 619–639; `concepts/scheduling-eviction/topology-spread-constraints.md`, lines 605–619; `tasks/run-application/horizontal-pod-autoscale.md`, lines 153–218.
