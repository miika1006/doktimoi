Approve the design conditionally: Kubernetes provides admission, scheduling and lifecycle controls, but these do not guarantee exactly-once reporting, immediate yielding or application recovery. Resolve the conflict between exclusive batch nodes and interactive access before rollout.

All source paths below are relative to the supplied local `docs/` directory; citations include source line ranges.

1. **CronJob execution.** A CronJob does **not** guarantee exactly one Job per schedule: creation is approximate, and either duplicate Jobs or no Job may occur. Make reporting idempotent. `concurrencyPolicy: Allow` permits overlap; `Forbid` skips a scheduled execution while the previous run remains unfinished; `Replace` replaces the unfinished run. These policies apply only within one CronJob. Choose `Forbid` if overlapping reports are unacceptable, understanding that it can miss runs. `startingDeadlineSeconds` bounds lateness of Job creation, not runtime; expired occurrences are skipped. More than 100 missed schedules prevents starting; a configured deadline narrows the counting window. Values below ten seconds risk missing controller checks. Set `.spec.timeZone`, such as `Etc/UTC`; otherwise the controller manager’s local zone applies. Sources: `concepts/workloads/controllers/cron-jobs.md:107–143,176–188,211–244`.

2. **Retries, runtime and cleanup.** Choose `restartPolicy: Never` for replacement Pods after failures, or `OnFailure` for container restarts within Pods. `backoffLimit` defaults to six; failed Pods and, with `OnFailure`, container restarts contribute to its two failure calculations. Either reaching the limit fails the Job; replacement uses exponential backoff. Set Job-level `activeDeadlineSeconds` to cap total Job duration across retries. It takes precedence over remaining retries: reaching it terminates running Pods and causes `DeadlineExceeded`. A failed Job does not automatically restart. `ttlSecondsAfterFinished` only makes a finished Job eligible for cascading cleanup; it cannot stop an overlong run. Under the documented default behavior in v1.32, terminal conditions wait for all Pods to terminate, so the deadline is not an instantaneous shutdown guarantee. Sources: `concepts/workloads/controllers/job.md:358–382,615–727,737–776`.

3. **Dedicated placement.** Taint batch nodes, for example `dedicated=batch:NoSchedule`, and give batch Pods matching tolerations. A toleration permits placement but does not require it. Also label those nodes and require matching node affinity; use `requiredDuringSchedulingIgnoredDuringExecution`, because preferred affinity permits fallback. Required affinity does not relocate a Pod if labels change afterward. Keep unrelated Pods off by withholding matching tolerations and controlling who can submit them. `NoSchedule` blocks new intolerant Pods but leaves existing ones running. `NoExecute` additionally evicts existing intolerant Pods; matching tolerations can permit indefinite residence or limit it through `tolerationSeconds`. Introducing a taint alone therefore does not establish exclusive occupancy. Sources: `concepts/scheduling-eviction/taint-and-toleration.md:101–150,176–191`; `concepts/scheduling-eviction/assign-pod-node.md:104–123`.

4. **Yielding through priority.** Define cluster-scoped PriorityClasses with batch below interactive services, and reference them through `priorityClassName`. Higher integer values mean higher priority. Interactive classes need `preemptionPolicy: PreemptLowerPriority` to reclaim occupied capacity; `Never` only improves queue position and does not prevent the Pod itself being preempted. Batch can use `Never` to avoid displacing other workloads. Victims receive their graceful termination period, delaying replacement scheduling. PDB protection is best effort and may be violated. Crucially, interactive Pods must tolerate batch taints and satisfy node constraints to reclaim batch capacity. If “other Pods off” means absolute exclusion, priority cannot resolve that contradiction. Sources: `concepts/scheduling-eviction/pod-priority-preemption.md:51–76,103–126,149–190,214–262`.

5. **Namespace quotas.** Specify CPU and memory requirements explicitly in every container. The precise obligation follows the quota keys: `requests.cpu`/`requests.memory` require requests, while `limits.cpu`/`limits.memory` require limits. Plain `cpu` and `memory` quota keys mean request totals. Configure both categories if both need bounding; use LimitRange defaults where appropriate. A creation or update exceeding quota fails with HTTP `403 FORBIDDEN`; it is not accepted merely to wait for quota. Adding or changing quota does not affect already-created resources, including running Pods. Quota constrains namespace allocation but does not reserve sufficient physical capacity: aggregate quotas can exceed cluster capacity. Sources: `concepts/policy/resource-quotas.md:20–77,94–106,462–469`.

6. **ConfigMap changes.** Ordinary mounted ConfigMap volumes update eventually. Delay can reach the kubelet sync period plus cache propagation delay; watch, TTL caching and direct API reads have different propagation behavior. This establishes file projection, not that the report process reloads settings. A `subPath` mount receives no ConfigMap updates. Environment-variable consumers require a Pod restart. An immutable ConfigMap cannot have its data changed or immutability reversed; operators must delete/recreate it, and the docs recommend recreating consuming Pods because existing mounts persist. For reproducible reports, choose a new immutable ConfigMap per configuration revision and reference it from subsequent Jobs; validate that workflow in the application. Sources: `concepts/configuration/configmap.md:191–209,299–328`.

7. **Memory-pressure eviction.** After resource reclamation fails, the kubelet ranks Pods first by whether usage exceeds requests, then priority, then usage relative to requests. Consequently, BestEffort and Burstable Pods exceeding requests generally go first; Guaranteed and Burstable Pods below requests go last. QoS is an approximation of this ordering, not the ranking input itself. Low batch priority therefore does not universally override memory-request behavior. System-resource exhaustion can still force eviction of otherwise protected Pods. Node-pressure eviction honors neither PDBs nor Pod `terminationGracePeriodSeconds`. Soft thresholds use the configured `eviction-max-pod-grace-period`; hard thresholds use zero seconds. Batch recovery must tolerate abrupt termination. Sources: `concepts/scheduling-eviction/node-pressure-eviction.md:20–36,318–353`.

8. **Restricted security.** Enforce restricted through namespace Pod Security labels, with PodSecurity admission operating. It validates submitted Pods; it does not supply missing security settings. Restricted includes all Baseline controls, permits only listed volume types, requires non-root execution and prohibits explicit UID zero. For Linux, require `allowPrivilegeEscalation: false`, an allowed seccomp profile (`RuntimeDefault` or `Localhost`), and dropping `ALL` capabilities, adding back only `NET_BIND_SERVICE` if needed. Applicable checks include init and ephemeral containers. Enforce rejects violating Pods; audit records violations without blocking; warn returns warnings without blocking. Test workloads before enforcement and protect namespace-label permissions. “Everywhere” also requires reviewing exemptions and system workloads. Sources: `concepts/security/pod-security-standards.md:299–455`; `reference/access-authn-authz/admission-controllers.md:715–725`; `tasks/configure-pod-container/migrate-from-psp.md:49–87,247–281`; `tutorials/security/cluster-level-pss.md:173–206`.

9. **Unneeded API credentials.** Pods receive the namespace’s default ServiceAccount when none is specified, and automatically mounted credentials enable API access under that account’s authorization. Set `automountServiceAccountToken: false` in every batch Job’s Pod template, or on its ServiceAccount as a default. The Pod setting takes precedence when both specify a value. Use a dedicated account with narrowly authorized access for workloads that actually call the API. Disabling automount addresses automatic credential injection; review manifests for credentials explicitly supplied through other means. It is not a blanket guarantee that the application possesses no credentials. Sources: `tasks/configure-pod-container/configure-service-account.md:34–59,67–100`.

10. **Prioritized rollout and validation.** First, resolve interactive eligibility on batch nodes; provision and verify labels, taints, required affinity and priority relationships. Second, establish namespace quotas, explicit container resources and token opt-outs. Third, dry-run restricted policy, soak audit/warn, repair workloads and enforce; review exemptions before claiming universal coverage. Fourth, deploy idempotent reports with explicit time zone, overlap policy, lateness deadline, retry budget, runtime deadline, configuration revision and cleanup retention. Finally, exercise quota rejection, retry exhaustion, deadline termination, preemption, memory pressure and ConfigMap changes. These checks follow the documented controls and policy rollout guidance cited above, particularly `tasks/configure-pod-container/migrate-from-psp.md:247–281`.

    Application or cluster validation must establish at least four remaining limits: duplicate execution cannot corrupt reports; checkpoint/recovery survives abrupt termination; interactive scheduling latency meets its target despite placement constraints and victim grace periods; and configuration reload behavior preserves report consistency. Neither namespace quotas nor the existence of these API fields establishes those outcomes. Relevant documented boundaries: `concepts/workloads/controllers/cron-jobs.md:211–244`; `concepts/scheduling-eviction/pod-priority-preemption.md:214–262`; `concepts/scheduling-eviction/node-pressure-eviction.md:20–36`; `concepts/configuration/configmap.md:191–209`.
