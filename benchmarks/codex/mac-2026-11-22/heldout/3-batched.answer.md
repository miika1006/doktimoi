Decision memo: adopt the design with explicit scheduling, failure, configuration, and admission policies. Kubernetes supplies useful controls, but these documents do not guarantee exactly-once reporting, immediate resource reclamation, or application correctness after interruption.

1. **CronJob scheduling is approximate.** Kubernetes can create two Jobs or no Job for a scheduled occurrence; reports therefore need idempotent processing. `concurrencyPolicy: Allow` permits overlap; `Forbid` skips a run while the previous run remains unfinished; `Replace` replaces the previous run. These policies apply only within one CronJob. Choose `Forbid` if overlapping reports are undesirable, but accept skipped or delayed occurrences. `startingDeadlineSeconds` bounds lateness of Job creation, not execution duration. Without it, occurrences have no starting deadline. More than 100 missed schedules prevents creation; setting the deadline restricts the missed-schedule counting window. A `Forbid` skip counts as missed. Values below ten seconds can prevent scheduling. Set `.spec.timeZone`, preferably an agreed explicit zone such as `Etc/UTC`; otherwise the controller manager’s local zone applies.  
   Sources: [docs/concepts/workloads/controllers/cron-jobs.md](docs/concepts/workloads/controllers/cron-jobs.md), lines 109–143, 180–188, 213–240.

2. **Bound retries and total runtime separately.** Job Pod templates permit only `Never` or `OnFailure`. With `OnFailure`, failed containers restart within their Pod; with `Never`, container failure can fail the Pod, which the Job controller replaces. `backoffLimit` defaults to six, with exponential retry delays capped at six minutes. Its accounting includes failed Pods and, for `OnFailure`, container retries in Pending or Running Pods. Reaching the limit fails the Job and terminates remaining Pods. Set the **Job-level** `activeDeadlineSeconds` for the hours-long execution budget: it takes precedence over remaining retries and produces `DeadlineExceeded`. An earlier exhausted backoff limit can still fail the Job first. Neither mechanism automatically restarts a failed Job. `ttlSecondsAfterFinished` controls subsequent cleanup of completed or failed Jobs and dependent Pods; it is not a runtime limit or an exact deletion-time guarantee.  
   Sources: [docs/concepts/workloads/controllers/job.md](docs/concepts/workloads/controllers/job.md), lines 217–221, 318–334, 360–378, 623–663, 737–775.

3. **Combine node exclusion with placement requirements.** Label batch nodes, taint them `dedicated=batch:NoSchedule`, and give batch Pods a matching toleration plus `requiredDuringSchedulingIgnoredDuringExecution` node affinity for that label. A toleration permits placement; it neither attracts Pods nor confines them to those nodes. Required affinity confines initial scheduling; preferred affinity does not. Label changes after scheduling do not evict Pods. `NoSchedule` blocks new, untolerating Pods but leaves existing residents; `NoExecute` also evicts existing untolerating Pods, with tolerating Pods optionally bounded by `tolerationSeconds`. Enforcing exclusivity requires controlling who can submit matching tolerations and maintaining node labels; merely adding these fields is insufficient.  
   Sources: [docs/concepts/scheduling-eviction/taint-and-toleration.md](docs/concepts/scheduling-eviction/taint-and-toleration.md), lines 18–25, 97–115, 181–191; [docs/concepts/scheduling-eviction/assign-pod-node.md](docs/concepts/scheduling-eviction/assign-pod-node.md), lines 105–118.

4. **Use lower batch priority, but resolve the exclusivity conflict.** Create cluster-scoped PriorityClasses with batch below interactive services, and reference them in Pod templates. Higher integer values mean higher priority. Interactive Pods need `PreemptLowerPriority`—the default—to preempt batch victims. Setting batch’s `preemptionPolicy: Never` prevents batch from preempting others; it does not protect batch from being preempted. Victims receive their graceful termination period, delaying interactive scheduling. PDB protection is best effort and can be violated. Crucially, preemption helps only when removing victims makes a node eligible: interactive Pods excluded from batch nodes cannot reclaim their capacity. Strict exclusivity and sharing that capacity with interactive services require a policy decision, such as permitting selected interactive workloads onto batch nodes.  
   Sources: [docs/concepts/scheduling-eviction/pod-priority-preemption.md](docs/concepts/scheduling-eviction/pod-priority-preemption.md), lines 34–41, 51–57, 107–127, 185–194, 218–238.

5. **Quota is admission control, not reserved capacity.** Specify explicit CPU and memory requests and limits in every container template. Precisely, `requests.cpu`/`requests.memory` quota requires corresponding requests; `limits.cpu`/`limits.memory` requires corresponding limits. Defaults can be supplied through LimitRange. Creation or update that exceeds quota fails with HTTP `403 Forbidden`; the rejected Pod does not run. Quota enforcement requires the ResourceQuota admission plugin and a quota object in the namespace. New or changed quotas do not affect already-created resources, including running Pods. Aggregate namespace quotas can exceed cluster capacity, so passing admission does not establish schedulability.  
   Sources: [docs/concepts/policy/resource-quotas.md](docs/concepts/policy/resource-quotas.md), lines 21–41, 59–60, 74–87, 464–469.

6. **Choose a deliberate configuration-consistency model.** Ordinary ConfigMap volumes eventually receive edits. Projection delay can reach the kubelet sync period plus cache propagation delay, depending on watch, TTL-cache, or direct-fetch configuration. This establishes file projection, not that the report application reloads those files correctly. `subPath` mounts do not receive updates. Environment variables do not update automatically and require Pod restart. Immutable ConfigMaps prohibit changing `data`/`binaryData` and cannot be made mutable again; deletion and recreation are required, with Pod recreation recommended. For reproducible reports, choose versioned immutable configuration per run; for live edits, validate application reload behavior and accept propagation delay.  
   Source: [docs/concepts/configuration/configmap.md](docs/concepts/configuration/configmap.md), lines 191–208, 299–328.

7. **Memory-pressure eviction has different rules from preemption.** After node-level reclamation proves insufficient, kubelet ranks Pods first by whether usage exceeds requests, then priority, then usage relative to requests. Thus BestEffort/Burstable Pods exceeding requests are generally evicted before Guaranteed/Burstable Pods below requests. Within the first group, priority precedes degree of excess. QoS names are an approximation, not the actual ordering input; low batch priority alone does not ensure batch always goes first. Node-pressure eviction ignores PDBs and Pod `terminationGracePeriodSeconds`. Soft thresholds use the eviction-specific grace configuration; hard thresholds terminate immediately with zero grace.  
   Source: [docs/concepts/scheduling-eviction/node-pressure-eviction.md](docs/concepts/scheduling-eviction/node-pressure-eviction.md), lines 20–36, 318–353.

8. **Restricted requires compatible Pod specifications and active admission enforcement.** Enable/verify PodSecurity admission and label namespaces `pod-security.kubernetes.io/enforce=restricted`; pin `enforce-version=v1.32` for predictable policy selection. Restricted includes all Baseline controls plus allowed volume types, non-root execution, prohibition of UID zero, and Linux-specific requirements: disable privilege escalation, explicitly select permitted seccomp profiles, and drop `ALL` capabilities, adding back only `NET_BIND_SERVICE`. Check application, init, and ephemeral containers; one violation fails Pod validation. `enforce` rejects violating Pod creation; `audit` records violations without blocking; `warn` returns warnings without blocking, including for Job templates. These are validation controls, not automatic remediation of incompatible images.  
   Sources: [docs/reference/access-authn-authz/admission-controllers.md](docs/reference/access-authn-authz/admission-controllers.md), lines 714–723; [docs/concepts/security/pod-security-standards.md](docs/concepts/security/pod-security-standards.md), lines 299–451; [docs/reference/labels-annotations-taints/_index.md](docs/reference/labels-annotations-taints/_index.md), lines 2369–2448.

9. **Disable unnecessary credential automounting explicitly.** Pods without an explicit ServiceAccount use their namespace’s `default` account. API credentials are automatically mounted by default. Set `automountServiceAccountToken: false` on the workload ServiceAccount and/or in the Job’s Pod template. The Pod setting overrides the ServiceAccount setting, so the latter alone is not an unoverrideable restriction. Validate the resulting Pod mounts and separately review explicit credential sources; disabling automount documents control of automatic mounting, not proof that no credentials exist anywhere in the container.  
   Source: [docs/tasks/configure-pod-container/configure-service-account.md](docs/tasks/configure-pod-container/configure-service-account.md), lines 34–41, 67–100.

10. **Roll out in this priority order.**
   - First resolve exclusive-node versus interactive-reclamation policy; validate eligible-node placement and preemption under saturation.
   - Verify admission prerequisites, configure quotas and resource declarations, remove unnecessary token mounts, and remediate Restricted warnings before enforcing it everywhere.
   - Set schedule zone, overlap policy, lateness budget, retry limit, runtime deadline, and cleanup retention; test duplicate runs, controller delays, failure, and timeout.
   - Select configuration semantics, then test edits during long runs and memory-pressure shutdown.

   At least four limits still require validation: report idempotency after duplicate execution; interactive recovery latency after victim termination; application configuration reload correctness; and survival or recovery after abrupt memory-pressure termination. The documents explicitly establish duplicate execution risk, preemption delay, eventual projection, and immediate hard eviction—not application correctness or a service-level deadline.
