Decision memo: adopt the design only after resolving the tension between exclusive batch nodes and yielding capacity to interactive services. The documents support the following controls, but do not establish application correctness, sufficient capacity, or recovery latency. Citations below identify supplied local files and inclusive source line ranges.

1. **CronJob execution is approximate.** A CronJob can create two Jobs or none for a schedule; reports must therefore be idempotent. `concurrencyPolicy: Allow` permits overlap; `Forbid` skips an occurrence while its predecessor runs, although a delayed start may remain possible within its deadline; `Replace` replaces the running Job. These policies apply only within one CronJob. Choose `Forbid` if overlapping reports are undesirable, without treating it as an exactly-once guarantee. Set `startingDeadlineSeconds` to the acceptable lateness: expired occurrences are skipped. Values below ten seconds may miss the controller’s checks. More than 100 missed schedules prevents creation; with a deadline, counting covers that deadline window. A `Forbid` skip counts as missed. Explicitly set `.spec.timeZone`, such as `Etc/UTC`; otherwise the controller manager’s local zone applies.  
   Sources: `docs/concepts/workloads/controllers/cron-jobs.md:107–143,175–190,210–240`.

2. **Bound retries and elapsed runtime separately.** With `restartPolicy: OnFailure`, failed containers restart inside their Pod; with `Never`, container failure can fail the Pod and trigger a replacement. Applications must handle either restart path. `backoffLimit` defaults to six, with exponential replacement delays; it counts failed Pods and, for `OnFailure`, container restarts in pending/running Pods. Either count reaching the limit fails the Job. Set Job-level `activeDeadlineSeconds` to bound the whole run across replacement Pods: it takes precedence over remaining retries, terminates running Pods, and produces `DeadlineExceeded`. Earlier retry exhaustion can still end the Job first. Failed Jobs do not automatically restart. `ttlSecondsAfterFinished` controls subsequent cleanup, including dependent Pods, rather than runtime; expiry makes deletion eligible, not instantaneous.  
   Sources: `docs/concepts/workloads/controllers/job.md:315–343,360–375,623–636,658–663,737–775`.

3. **Combine exclusion and placement controls.** Taint batch nodes with a dedicated `NoSchedule` taint, give batch Pods its matching toleration, and require affinity to batch-node labels. A toleration permits placement; it does not force it. Use `requiredDuringSchedulingIgnoredDuringExecution`, because preferred affinity permits fallback. Required affinity also does not evict Pods if labels later change. `NoSchedule` leaves existing Pods running; `NoExecute` additionally evicts intolerant residents, immediately or after their `tolerationSeconds`. Enforce who may add tolerations and placement overrides; a user-editable toleration is insufficient isolation. For protected node labels, the documented prerequisites are the Node authorizer and NodeRestriction admission plugin.  
   Sources: `docs/concepts/scheduling-eviction/taint-and-toleration.md:97–110,181–191`; `docs/concepts/scheduling-eviction/assign-pod-node.md:56–68,105–118`.

4. **Make batch lower priority, but resolve node eligibility.** Create cluster-scoped PriorityClasses, reference them through `priorityClassName`, and assign interactive Pods higher integer priority. Choose `preemptionPolicy: Never` for batch to prevent it preempting others; this does not protect batch from preemption. Interactive classes need `PreemptLowerPriority` to reclaim occupied capacity. Preemption finds a node where removing lower-priority Pods makes the incoming Pod schedulable. Therefore, interactive Pods excluded from batch nodes cannot reclaim those nodes: either explicitly allow selected interactive workloads there or accept separate capacity pools. Victims receive graceful termination, delaying replacement scheduling. PDB protection is best effort and can be violated. Priority consequently provides neither immediate service recovery nor guaranteed placement.  
   Sources: `docs/concepts/scheduling-eviction/pod-priority-preemption.md:51–56,103–127,149–154,185–194,216–238`.

5. **Quota is admission control, not reserved capacity.** Configure explicit CPU and memory requests and limits for every container. More precisely, request quotas require incoming containers’ requests; limit quotas require their limits. `cpu` and `memory` quota keys mean request totals, while `limits.cpu` and `limits.memory` constrain limits across non-terminal Pods. Resource creation or updates violating quota receive HTTP 403; a Job does not bypass this Pod admission check. LimitRange defaults can supply omitted values. New or changed quota does not affect already-created resources, including running Pods. Aggregate namespace quotas can exceed cluster capacity, so admission within quota does not guarantee scheduling.  
   Sources: `docs/concepts/policy/resource-quotas.md:27–60,74–77,99–105,462–469`.

6. **Select ConfigMap consumption deliberately.** Ordinary mounted ConfigMap volumes eventually receive changed keys. Propagation can take the kubelet sync period plus cache delay; watch is the default propagation strategy. This establishes file projection, not that the report reloads settings correctly. A `subPath` mount receives no updates. Environment-variable consumers require Pod restart. For consistent settings throughout a long report, consider a versioned immutable ConfigMap per release. `immutable: true` cannot be reversed, and its data cannot be edited; replacement requires deletion/recreation, with Pod recreation recommended because existing Pods retain mount points. This conflicts with editing that same object throughout the day.  
   Sources: `docs/concepts/configuration/configmap.md:191–208,299–329`.

7. **Memory-pressure eviction is not priority alone.** After node-level reclamation fails, kubelet ranks Pods first by whether usage exceeds requests, then priority, then usage relative to requests. BestEffort and Burstable Pods exceeding requests are generally first; Guaranteed and Burstable Pods below requests are last, ordered by priority. QoS is an explanatory approximation, not the ranking input itself. Thus low batch priority alone does not ensure batch is evicted before every interactive Pod. Node-pressure eviction ignores PDBs and Pod `terminationGracePeriodSeconds`. Soft thresholds use kubelet eviction grace settings; hard thresholds terminate immediately with zero grace.  
   Sources: `docs/concepts/scheduling-eviction/node-pressure-eviction.md:26–36,188–197,319–353`.

8. **Restricted enforcement requires compliant workloads.** Enable PodSecurity admission and label namespaces `pod-security.kubernetes.io/enforce=restricted`; pin `enforce-version=v1.32` for predictable policy evaluation. Restricted includes Baseline controls and limits volume types, permitting ConfigMap volumes. It requires non-root execution, forbids explicit UID zero, and, for Linux, requires `allowPrivilegeEscalation: false`, an allowed explicit seccomp profile, and dropping `ALL` capabilities, with only `NET_BIND_SERVICE` optionally restored. Init and ephemeral containers also matter. Admission validates rather than repairing manifests. Enforce rejects violating Pod creation; audit records violations without blocking; warn returns warnings without blocking. “Everywhere” also requires checking cluster defaults and exemptions rather than copying the tutorial’s `kube-system` exemption.  
   Sources: `docs/reference/access-authn-authz/admission-controllers.md:714–723`; `docs/reference/labels-annotations-taints/_index.md:2369–2396`; `docs/concepts/security/pod-security-standards.md:299–450`; `docs/tasks/configure-pod-container/migrate-from-psp.md:56–60,262–265`; `docs/tutorials/security/cluster-level-pss.md:193–207`.

9. **Disable unnecessary credential automounting explicitly.** ServiceAccount API credentials are mounted by default. Set `automountServiceAccountToken: false` in each batch Pod template, and preferably on its ServiceAccount as the default for consumers. A Pod setting takes precedence over its ServiceAccount setting, so verify generated Pods and constrain unwanted overrides. This controls automatic mounting; it does not establish that a workload contains no separately supplied credentials.  
   Source: `docs/tasks/configure-pod-container/configure-service-account.md:67–100`.

10. **Roll out in this priority order.**

   - Resolve whether interactive workloads may use batch nodes; test taints, required affinity, admission restrictions, and actual preemption.
   - Dry-run Restricted against existing Pods, then soak audit/warn across nightly runs; repair templates, disable token automounting, and enable enforcement.
   - Set requests, limits, quotas, and priority classes; test missing-resource and over-quota rejection.
   - Configure schedule zone, lateness, concurrency, retry/runtime limits, and evidence retention before TTL cleanup.
   - Exercise duplicate starts, interruption, memory pressure, and ConfigMap changes before broad rollout.

   These checks follow the documented dry-run/soak workflow and the limitations above. At least four limits remain application or cluster validation responsibilities: duplicate-safe report output, completion within its deadline, configuration reload consistency, and interactive recovery time under real eligibility, capacity, and termination settings. None is guaranteed by configuring the corresponding fields.  
   Sources: `docs/tasks/configure-pod-container/migrate-from-psp.md:247–272`; `docs/concepts/workloads/controllers/cron-jobs.md:213–240`; `docs/concepts/configuration/configmap.md:193–208`; `docs/concepts/scheduling-eviction/pod-priority-preemption.md:185–238`.
