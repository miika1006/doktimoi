Decision: adopt the design conditionally. First resolve whether batch nodes are exclusive or available to interactive services during contention. Then validate admission controls, retry behavior, configuration handling, and interruption recovery before rollout. The documented mechanisms do not establish end-to-end report correctness or service availability.

1. **CronJob execution is approximate.** Kubernetes explicitly permits two Jobs or no Job for a scheduled occurrence; reports must be idempotent. `concurrencyPolicy: Allow` permits overlap, `Forbid` skips an occurrence while its predecessor remains unfinished, and `Replace` replaces the unfinished run. These policies apply only within one CronJob. Choose `Forbid` if overlapping reports are undesirable, while accepting missed runs. `startingDeadlineSeconds` limits how late an occurrence may start; it does not limit runtime. More than 100 missed schedules prevents a start; setting the deadline bounds the counting window. `Forbid` skips count as missed schedules. Avoid deadlines below ten seconds because the controller checks every ten seconds. Set `.spec.timeZone`, preferably explicitly; otherwise the controller manager’s local timezone applies. Sources: `docs/concepts/workloads/controllers/cron-jobs.md:109–143,180–186,213–240`.

2. **Bound retries and total runtime separately.** Jobs allow `restartPolicy: Never` or `OnFailure`. With `Never`, failed Pods are replaced; with `OnFailure`, containers can restart within a Pod. `backoffLimit`, default six, counts failed Pods and, for `OnFailure`, container restarts in Pending or Running Pods; either calculation reaching the limit fails the Job. Replacement Pods use exponential backoff. Set Job-level `activeDeadlineSeconds` to bound the entire Job across Pods. It takes precedence over retry allowance: reaching it terminates running Pods and fails the Job even with retries remaining. Exhausting backoff can fail it earlier. Failed Jobs do not automatically restart. `ttlSecondsAfterFinished` only makes completed or failed Jobs eligible for cascading cleanup; retain enough time for diagnosis. Sources: `docs/concepts/workloads/controllers/job.md:219–221,320–332,358–380,623–663,737–775`.

3. **Use both repulsion and a hard placement requirement.** Taint batch nodes, for example `dedicated=batch:NoSchedule`, and give batch Pods the matching toleration. Also label those nodes and require matching `requiredDuringSchedulingIgnoredDuringExecution` node affinity. Tolerations permit placement but neither require nor guarantee it; required affinity confines scheduling. Keep ordinary Pods from acquiring that toleration through platform controls—this is a configuration prerequisite, not an automatic exclusivity guarantee. `NoSchedule` blocks new non-tolerating Pods but leaves existing ones. `NoExecute` also evicts existing non-tolerating Pods; matching tolerations can permit indefinite or time-limited residence. Required affinity does not evict Pods after node labels change. Sources: `docs/concepts/scheduling-eviction/taint-and-toleration.md:13–21,99–110,181–191`; `docs/concepts/scheduling-eviction/assign-pod-node.md:109–118`.

4. **Priority needs compatible placement rules.** Create cluster-scoped PriorityClasses with batch below interactive services and reference them through `priorityClassName`. Batch can use `preemptionPolicy: Never`: it cannot preempt others but remains preemptible. Interactive Pods need `PreemptLowerPriority`, the default, to initiate preemption. Victims receive graceful termination, delaying reclaimed capacity. PDB protection is best effort and can be violated. Crucially, preemption only helps where removing lower-priority Pods makes the pending Pod schedulable. If interactive services cannot tolerate batch-node taints, evicting batch there does not help them. Decide between strict exclusivity and permitting selected interactive services onto batch nodes; cluster fullness alone guarantees no useful preemption. Sources: `docs/concepts/scheduling-eviction/pod-priority-preemption.md:53–56,107–127,151–157,187–194,218–238`.

5. **Quota is admission control, not reserved capacity.** CPU and memory quota requires corresponding resource declarations. Specifically, `requests.cpu`/`requests.memory` quota requires each incoming container’s requests; `limits.cpu`/`limits.memory` requires limits. Configure both explicitly or establish suitable defaults. A creation or update violating quota fails with HTTP 403; an over-quota Pod is rejected rather than admitted to wait for capacity. Quota changes do not affect already-created resources, including running Pods. ResourceQuota admission must be enabled and a quota must exist in each namespace. Aggregate namespace quotas may exceed cluster capacity, so quota compliance does not establish schedulability. Sources: `docs/concepts/policy/resource-quotas.md:26–41,74–87,462–469`.

6. **Choose configuration semantics deliberately.** Ordinary ConfigMap volume projections update eventually. Delay can reach the kubelet sync period plus cache propagation delay, depending on watch, TTL-cache, or direct-fetch configuration. This establishes file projection behavior, not application reload behavior. A `subPath` mount receives no updates. Environment-variable consumers require a Pod restart. With `immutable: true`, neither immutability nor `data`/`binaryData` can be changed; deletion and recreation are required, and recreating consuming Pods is recommended. For reproducible reports, choose a distinct immutable configuration version per run rather than editing its settings mid-run. That versioning strategy is a platform choice; the docs do not establish consistent application-level configuration snapshots. Sources: `docs/concepts/configuration/configmap.md:191–208,299–328`.

7. **Memory-pressure eviction is not simply “lowest priority first.”** After resource reclamation fails, kubelet first considers whether usage exceeds requests, then priority, then usage relative to requests. BestEffort and Burstable Pods exceeding requests are the first group; Guaranteed and Burstable Pods below requests are last, ordered by priority. QoS itself is not the eviction ranking input. Thus low batch priority alone does not establish eviction before every interactive Pod; requests and observed usage matter. Node-pressure eviction ignores PDBs and Pod `terminationGracePeriodSeconds`. Soft thresholds use kubelet’s configured eviction grace mechanism; hard thresholds terminate immediately with zero grace. Sources: `docs/concepts/scheduling-eviction/node-pressure-eviction.md:26–36,318–353`.

8. **Restricted requires compliant Pods and effective admission.** Set namespace `pod-security.kubernetes.io/enforce=restricted` and pin `enforce-version=v1.32`. Restricted includes Baseline controls and limits volume types; ConfigMap volumes remain allowed. For Linux workloads, require non-root execution, prohibit explicit UID zero, set `allowPrivilegeEscalation: false`, specify `RuntimeDefault` or `Localhost` seccomp, and drop `ALL` capabilities, adding back only `NET_BIND_SERVICE` if needed. Include init and ephemeral containers. Enforce rejects noncompliant Pod creation; audit records violations without blocking; warn returns warnings without blocking, including for Job templates. Verify the PodSecurity controller and exemptions: namespace labels alone do not establish universal coverage. Sources: `docs/concepts/security/pod-security-standards.md:299–451`; `docs/reference/labels-annotations-taints/_index.md:2369–2465`; `docs/reference/access-authn-authz/admission-controllers.md:714–726`; `docs/tutorials/security/cluster-level-pss.md:191–207`.

9. **Disable unnecessary credential automounting.** ServiceAccount admission normally supplies a default account and adds an API-token volume and container mounts. Set `automountServiceAccountToken: false` in each Job’s Pod template, or on its ServiceAccount for the account-wide default. When both specify the field, the Pod setting takes precedence; an account-level setting is therefore not an unoverrideable prohibition. Verify admitted Pods and avoid explicitly supplying unnecessary credentials. Automount opt-out controls automatic mounting; it does not establish that every possible credential source is absent. API access, when required, also depends on authorization policy. Sources: `docs/reference/access-authn-authz/service-accounts-admin.md:402–419`; `docs/tasks/configure-pod-container/configure-service-account.md:53–59,67–100`.

10. **Roll out in this priority order.** First, resolve the exclusive-node/preemption conflict and verify eligible interactive Pods can actually reclaim batch capacity; the feasibility condition is explicit in `docs/concepts/scheduling-eviction/pod-priority-preemption.md:187–194`. Second, inventory workloads with restricted audit/warn, repair templates, verify exemptions, then enforce pinned v1.32 policy; see `docs/reference/labels-annotations-taints/_index.md:2369–2465`. Third, validate quota rejection, placement restrictions, and absent automatic tokens using the controls above. Fourth, canary CronJobs with explicit timezone, overlap policy, retry/runtime bounds, and diagnostic retention. Exercise failed Pods, long runs, missed schedules, preemption, memory pressure, and ConfigMap edits; their distinct behaviors are documented in `docs/concepts/workloads/controllers/job.md:623–663`, `docs/concepts/workloads/controllers/cron-jobs.md:213–240`, and `docs/concepts/scheduling-eviction/node-pressure-eviction.md:26–36`. Release gates requiring application or cluster evidence include duplicate-safe report writes, recovery after abrupt termination, acceptable interactive recovery latency, realistic resource requests, and correct configuration reload or snapshot behavior. These documents supply mechanisms, not guarantees of those outcomes.
