Decision: adopt the design only after resolving the conflict between exclusive batch nodes and reclaiming their capacity for interactive services. The controls below provide scheduling, admission and lifecycle behavior; they do not establish report correctness, recovery time or application compatibility. Citations identify local corpus paths and inclusive source lines.

1. **CronJob execution is approximate, not exactly once.** Two Jobs, or no Job, may be created for a schedule; reports must therefore be idempotent. `concurrencyPolicy: Allow` permits overlap, `Forbid` skips a run while its predecessor remains unfinished, and `Replace` replaces the unfinished run. These policies cover only Jobs from the same CronJob. Choose `Forbid` if overlapping reports are unacceptable, while accepting missed runs. `startingDeadlineSeconds` bounds how late a Job may start, not its runtime. Values below ten seconds may miss the controller’s checks. More than 100 missed schedules prevent starting; a configured deadline restricts the counting window. Set `.spec.timeZone`, such as `Etc/UTC`; otherwise the controller manager’s local zone applies.  
   Sources: `docs/concepts/workloads/controllers/cron-jobs.md:109–143,180–186,213–240`.

2. **Bound retries and total runtime separately.** With `restartPolicy: OnFailure`, failed containers restart inside the same Pod; with `Never`, container failure can fail the Pod and the Job controller creates replacements. `backoffLimit` defaults to six; counting includes failed Pods and, for `OnFailure`, container retries in Pending or Running Pods. Replacements use exponential backoff. Set Job-level `activeDeadlineSeconds` to cap duration across all its Pods: it takes precedence over remaining retries, terminates running Pods and produces `DeadlineExceeded`. Either mechanism permanently fails that Job; Pod restart policy does not restart failed Jobs. `ttlSecondsAfterFinished` only makes completed or failed Jobs eligible for cascading cleanup after the specified interval; it cannot stop an overlong run.  
   Sources: `docs/concepts/workloads/controllers/job.md:318–342,358–374,623–663,737–775`.

3. **Combine repulsion with a hard placement requirement.** Label batch nodes, taint them `dedicated=batch:NoSchedule`, give batch Pods the matching toleration, and require that label through `requiredDuringSchedulingIgnoredDuringExecution` node affinity. Tolerations permit placement but neither force nor guarantee it; affinity provides the restriction. Preferred affinity is insufficient. Keep ordinary Pods from obtaining matching tolerations through platform admission controls. `NoSchedule` leaves existing Pods running; `NoExecute` also evicts non-tolerating residents, with `tolerationSeconds` optionally delaying eviction. These are not absolute isolation guarantees: explicit `nodeName` bypasses scheduler taint checks, and affinity does not remove Pods after labels change.  
   Sources: `docs/concepts/scheduling-eviction/taint-and-toleration.md:13–25,65–71,99–110,181–191`; `docs/concepts/scheduling-eviction/assign-pod-node.md:103–118`.

4. **Use lower batch priority, but resolve node eligibility first.** Create cluster-scoped PriorityClasses and reference them through `priorityClassName`, with interactive priority higher than batch. Choose batch `preemptionPolicy: Never` to prevent batch from preempting others; batch remains preemptible. Interactive classes need `PreemptLowerPriority`, the default, to reclaim capacity. Preemption helps only where removing lower-priority Pods makes a node feasible. Consequently, excluding every interactive Pod from batch nodes prevents interactive workloads reclaiming that capacity; authorize an explicit interactive exception or revise the yielding requirement. Victims receive graceful termination, delaying replacement scheduling. PodDisruptionBudgets receive best-effort consideration and may be violated.  
   Sources: `docs/concepts/scheduling-eviction/pod-priority-preemption.md:53–73,107–127,151–154,187–194,216–238`.

5. **Quota is admission control, not reserved cluster capacity.** Verify that ResourceQuota admission is enabled. For `requests.cpu` and `requests.memory`, every incoming container must specify corresponding requests; `limits.cpu` and `limits.memory` require corresponding limits. Supply both explicitly in templates, or deliberately configure defaults. Quota sums cover non-terminal Pods. Creation or updates exceeding quota fail with HTTP `403 Forbidden`; a Job object existing does not imply its Pods can be admitted. Quota changes do not affect already-created resources, including running Pods. Namespace quotas can collectively exceed cluster capacity, so they do not establish schedulability.  
   Sources: `docs/concepts/policy/resource-quotas.md:36–60,74–87,99–105,464–469`.

6. **Choose a configuration consistency model.** Ordinary ConfigMap volume projections update eventually: delay can reach the kubelet sync period plus cache propagation delay, dependent on its configured detection strategy. This establishes file projection behavior, not whether the report process rereads files or safely handles mid-run changes. A `subPath` mount never receives these updates. Environment variables do not update automatically and require Pod restart. An immutable ConfigMap cannot have its data changed or immutability reversed; deletion and recreation are required, and recreating consuming Pods is recommended. For reproducible reports, choose a distinct immutable configuration per release/run and update future templates accordingly.  
   Source: `docs/concepts/configuration/configmap.md:191–208,299–328`.

7. **Memory-pressure eviction is not simply “lowest priority first.”** After node-level reclamation fails, kubelet ranks Pods by whether usage exceeds requests, then priority, then usage relative to requests. BestEffort and Burstable Pods exceeding requests are generally evicted before Guaranteed or Burstable Pods below requests. QoS labels themselves are not the ranking input. Thus low batch priority alone does not establish that batch always dies before interactive workloads. Node-pressure eviction disregards PDBs and does not promise the Pod’s configured termination grace period. Hard thresholds cause immediate termination; soft thresholds use kubelet eviction grace settings, with the detailed rules limiting allowed termination time.  
   Sources: `docs/concepts/scheduling-eviction/node-pressure-eviction.md:26–36,187–206,318–353`.

8. **Restricted requires compliant Pod specifications and functioning admission.** Enable/check PodSecurity admission and set namespace label `pod-security.kubernetes.io/enforce=restricted`. Every applicable container, including init and ephemeral containers, must comply; one violation fails validation. Restricted includes Baseline plus an allowed volume list, non-root execution, no explicit UID zero, and—for Linux—disabled privilege escalation, explicit `RuntimeDefault` or `Localhost` seccomp, and dropping `ALL` capabilities with only `NET_BIND_SERVICE` permitted back. ConfigMap volumes are allowed. `enforce` rejects violating new Pods; `audit` records violations without forbidding them; `warn` returns immediate warnings. Do not interpret labels as proof that existing workloads were repaired. Audit exemptions and cluster defaults before claiming coverage “everywhere.”  
   Sources: `docs/concepts/security/pod-security-standards.md:299–451`; `docs/reference/access-authn-authz/admission-controllers.md:714–723`; `docs/tasks/configure-pod-container/migrate-from-psp.md:253–280`; `docs/tutorials/security/cluster-level-pss.md:190–207`.

9. **Disable unnecessary credential automounting explicitly.** Pods otherwise receive the namespace’s default ServiceAccount when none is specified, and applications can use automatically mounted credentials. Set `automountServiceAccountToken: false` in the Job’s Pod template; also set it on team ServiceAccounts as the default posture. The Pod setting overrides the ServiceAccount setting, so the latter alone is insufficient enforcement. Check templates for overrides and other explicit credential sources: disabling automatic mounting does not establish the absence of every possible credential. Reading projected ConfigMap files does not itself justify granting the application API credentials.  
   Source: `docs/tasks/configure-pod-container/configure-service-account.md:34–58,67–100`.

10. **Roll out in this priority order.** First, resolve the exclusive-node/preemption conflict and validate permitted node eligibility under full load. Second, make report output idempotent and test interruption, retry exhaustion and deadline expiry. Third, apply requests, limits, quotas and token opt-outs to templates. Fourth, dry-run Restricted enforcement, soak audit/warn through actual nightly executions, repair violations, then enforce across namespaces and review exemptions. Existing-Pod checks can miss CronJobs. Finally, select configuration versioning and cleanup retention, and test update visibility and failure observability.

    At least four limits still require validation: duplicate-safe report output, interactive scheduling latency after victim termination, application configuration reload behavior, and realistic memory requests/eviction behavior. The documents guarantee none of those application or cluster outcomes. CronJob template changes affect future Jobs only, so explicitly validate newly created Jobs and their Pods.
