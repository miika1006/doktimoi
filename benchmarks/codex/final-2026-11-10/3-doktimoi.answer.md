**Decision: revise before production approval.** The proposed settings do not establish five-replica availability, safe request draining, or database durability. The recommendations below distinguish documented behavior from configuration choices and operational prerequisites. Citations are local paths relative to the supplied `docs/` directory.

1. **The PDB is not a universal availability guarantee.** Node failure is involuntary: a PDB cannot prevent it, although unavailable Pods count against the budget. During node drain, an eviction-respecting tool such as `kubectl drain` submits eviction requests that can be rejected and retried; `minAvailable: 5` constrains those evictions, rather than guaranteeing recovery or preventing concurrent failures. Deployment rolling updates are not constrained by PDBs, though their unavailable Pods count against the budget.  
   **Recommendation:** replace `maxUnavailable: 2`, which permits four available replicas at desired count six, with `maxUnavailable: 0, maxSurge: 1`; provision surge capacity. `maxUnavailable: 1` is also compatible with a five-replica rollout floor, but leaves less margin. Neither protects against simultaneous failures.  
   Sources: `concepts/workloads/pods/disruptions.md:92–136`; `concepts/workloads/controllers/deployment.md:1183–1211`.

2. **Configure explicit zone spreading and choose the failure tradeoff.** Use an API label selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, targeting two replicas per zone when all three zones are eligible and capacity permits. The topology key groups nodes by label value. With `DoNotSchedule`, skew limits the difference between the target domain’s matching-Pod count and the global minimum; violating placements remain unscheduled. `ScheduleAnyway` prefers reduced skew but permits imbalance.

   A zone outage does not guarantee replacement capacity: scheduling depends on eligible domains, labels, affinity, taints, and resources. With `minDomains: 3`, fewer than three eligible domains makes the global minimum zero, potentially blocking replacements in surviving zones. Omitting it defaults to one, allowing balancing across remaining eligible domains. Choose strict spreading or degraded-zone placement deliberately. Losing two replicas from a 2/2/2 distribution leaves four, not five.  
   Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:81–134,209`; `concepts/workloads/pods/disruptions.md:130–136`.

3. **Use startup protection, traffic readiness, and narrowly defined liveness.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Readiness and liveness probes begin only after startup succeeds. Exhausting startup failures kills the container, with restart governed by its restart policy.

   Readiness should report whether the API can serve useful requests, including necessary database dependency checks. Failed readiness removes it from Service traffic without requiring a restart. Liveness should detect a condition a restart can remedy, such as a deadlock; avoid treating every database outage as container failure. Liveness failure triggers restart behavior. These probe meanings are application design choices; Kubernetes does not establish their correctness.  
   Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–367`; `reference/kubernetes-api/workload-resources/pod-v1.md:1018–1028`.

4. **Thirty seconds is a deadline, not a request-completion guarantee.** The grace-period countdown starts **before** `preStop`. The hook runs before the runtime sends TERM to the container’s main process, consuming the same shutdown budget. An unfinished hook can receive a small, one-off two-second extension. At expiration, remaining processes receive `SIGKILL`.

   Endpoint processing happens concurrently with shutdown. Terminating endpoints are not immediately removed from EndpointSlices, but have `ready: false` and are excluded from regular traffic; the `serving` condition supports draining-aware consumers. Existing requests still require application handling. Measure hook duration, longest supported requests, and shutdown work; then configure sufficient grace and implement TERM handling and connection draining. The docs do not promise instantaneous traffic propagation or successful completion within 30 seconds.  
   Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:1700–1702`; `concepts/workloads/pods/pod-lifecycle.md:584–645`.

5. **Size resource requests and limits deliberately.** CPU requests inform scheduling and provide the denominator for utilization-based HPA. They are not a consumption ceiling: a container can use additional available resources. CPU limits enforce throttling, potentially extending request duration. Memory limits instead use reactive OOM killing; exceeding one does not necessarily cause immediate termination.

   Set realistic CPU requests for all relevant containers. If some lack requests, Pod CPU utilization is undefined and HPA cannot act on that metric. Account for defaulting: absent another admission-time default, specifying a limit without a request copies the limit into the request. Validate resource settings under startup and sustained load.  
   Sources: `concepts/configuration/manage-resources-containers.md:15–67`; `tasks/run-application/horizontal-pod-autoscale.md:89–101`.

6. **HPA intentionally differs from the raw utilization ratio.** The basic calculation is the ceiling of current replicas multiplied by current/desired metric value, with default tolerance 0.1. Failed Pods are discarded and terminating Pods ignored. Missing metrics are set aside; CPU samples from not-yet-ready Pods or before readiness are also set aside.

   Missing samples are conservatively assumed at 100% of target during downscale and 0% during upscale. Not-yet-ready Pods are additionally assumed at 0% when assessing upscale. These adjustments dampen scaling; reversal of direction or entry into tolerance cancels action. Default readiness-delay and CPU-initialization windows are 30 seconds and five minutes. Downscale stabilization defaults to five minutes and selects the highest recommendation in that window. Metrics availability, usually through separately installed Metrics Server, is a prerequisite.  
   Sources: `tasks/run-application/horizontal-pod-autoscale.md:112–202,214–219`.

7. **Replace default allow with tested, additive least privilege.** Apply default-deny ingress and egress, then allow approved callers to the API port, API egress to the database port, corresponding database ingress, and DNS queries to the cluster resolver. Add other dependencies only when justified.

   Ingress and egress isolation are independent. Applicable policies combine by union: another broad allow defeats the intended restriction, and policy ordering cannot override it. A Pod-to-Pod connection requires both source egress and destination ingress permission; allowed reply traffic is implicit. Ingress isolation also permits traffic from the Pod’s node, so this is not absolute isolation. A supporting CNI implementation is mandatory; otherwise NetworkPolicy resources are ignored. Validate permitted and denied connections, including DNS.  
   Sources: `concepts/services-networking/network-policies.md:51–81`; `concepts/security/multi-tenancy.md:208–234`.

8. **Base64 is not sufficient protection; reject plaintext-equivalent credentials in Git.** The documentation demonstrates recovering Secret contents by decoding base64 and explicitly describes encoded credentials as “obscured but not secret.” Encoding does not provide confidentiality.

   Enable and verify encryption at rest: Secrets otherwise reside unencrypted in etcd. Configure least-privilege RBAC and expose each Secret only to containers requiring it. Restrict workload-creation permissions too: anyone authorized to create Pods in a namespace—including indirectly through Deployments—can read that namespace’s Secrets. Denying direct Secret reads alone therefore does not close access. Encryption of etcd does not protect a separately committed Git copy.  
   Sources: `concepts/configuration/secret.md:35–49,306`; `tasks/administer-cluster/encrypt-data.md:573–588`.

9. **Treat reclaim policy and StatefulSet retention as separate controls.** Dynamically provisioned PVs inherit their StorageClass reclaim policy, defaulting to `Delete`. Changing the class is not a retroactive update to existing PVs; inspect and explicitly patch those PVs. With `Retain`, PVC deletion leaves the PV released and its data requiring manual reclamation. With supported `Delete` implementations, reclamation removes both the PV and external storage asset.

   StatefulSet deletion or scale-down does not, by default, delete its template-created PVCs. `persistentVolumeClaimRetentionPolicy` can independently select `Delete` for either event, subject to feature availability; resulting PVC deletion then invokes PV reclamation behavior. For the database, choose retention explicitly rather than inferring durability from dynamic provisioning.  
   Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:185–210`; `concepts/workloads/controllers/statefulset.md:387–422`.

10. **Prioritize validation before expanding production exposure.** First, remove exposed credentials, verify encryption/RBAC and CNI enforcement, and audit existing PV policies. Second, implement probes, measured shutdown grace, resource requests, zone constraints, and the revised rollout strategy. Third, verify metrics delivery and align HPA minimum replicas with the availability objective. Finally, exercise rollout, eviction-based drain, zone loss, database interruption, and PVC lifecycle behavior in a representative environment.

   Acceptance requires application or cluster evidence for at least these limits: worst-case startup time; long-request completion during termination; surviving-zone and surge capacity; effective network enforcement; and database recovery/data durability. The cited mechanisms do not establish those outcomes merely by accepting configuration.  
   Sources: `concepts/workloads/pods/disruptions.md:108–136`; `concepts/workloads/pods/pod-lifecycle.md:612–640`; `tasks/run-application/horizontal-pod-autoscale.md:112–117`; `concepts/storage/persistent-volumes.md:185–210`.
