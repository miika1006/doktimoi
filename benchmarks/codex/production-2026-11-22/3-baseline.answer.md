**Decision memo:** Revise the design before production approval. Kubernetes provides useful controls, but the proposed settings do not establish five-replica availability, safe request draining, credential confidentiality, or database recoverability. The recommendations below are configuration choices; their operational sufficiency requires validation.

1. **PDB and rollout availability.** `minAvailable: 5` cannot prevent involuntary node failures; those losses nevertheless consume the disruption budget. With six healthy replicas, a drain using the Eviction API can voluntarily disrupt one before further evictions are blocked. Direct deletion bypasses that protection. Deployment rolling updates are not constrained by PDBs, although their unavailable Pods count against the budget. Thus `maxUnavailable: 2` permits rollout availability to fall to four. Recommend `maxUnavailable: 1, maxSurge: 1`, or conservatively `0/1` when capacity permits. These govern rollout behavior, not simultaneous infrastructure failures. Sources: `docs/concepts/workloads/pods/disruptions.md:99–136`; `docs/concepts/workloads/controllers/deployment.md:1183–1211`.

2. **Zone spreading.** Configure a selector matching the API replicas, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`; with suitable capacity, six replicas can occupy three zones as 2/2/2. Identical values of the topology label define a domain. Under `DoNotSchedule`, skew bounds the target domain’s count relative to the global minimum; `ScheduleAnyway` merely prefers placements reducing skew. Choose hard spreading only after deciding the outage tradeoff: an unavailable zone still counted as eligible can block replacement placement. If it disappears from eligible domains, default `minDomains: 1` permits balancing across survivors; explicitly requiring three domains makes the minimum zero when fewer remain, potentially blocking replacements. Scheduling does not guarantee rebalancing after removals. Sources: `docs/concepts/scheduling-eviction/topology-spread-constraints.md:82–130,607–619`.

3. **Probes for slow startup.** Use a startup probe with `failureThreshold × periodSeconds` covering measured worst-case initialization. Until it succeeds, readiness and liveness probes are disabled; their initial-delay clocks also wait. Readiness should indicate ability to serve requests, including required database availability. Its failure withdraws the Pod from matching Service endpoints without restarting the container. Liveness should detect an application failure that restart can remedy; avoid making database outages alone trigger restart cascades. Startup or liveness failure at the configured consecutive-failure threshold triggers container restart behavior. Probe endpoints and timing remain application choices. Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–318,398–422`; `docs/concepts/workloads/pods/pod-lifecycle.md:479–497,514–528`.

4. **Termination and long requests.** The grace-period countdown begins **before** `preStop`; the hook consumes that budget. Normally, kubelet runs the hook before requesting TERM delivery to the container’s main process. A still-running hook can receive a one-off two-second extension. At grace expiry, remaining processes receive SIGKILL. Concurrently, terminating Service endpoints are marked terminating and `ready: false`, preventing regular load-balancer traffic; they are not immediately removed from EndpointSlices. The `serving` condition supports draining-aware consumers. Thirty seconds does not guarantee request completion: measure hook duration, signal handling, longest supported requests, and traffic-withdrawal behavior, then size the budget accordingly. Sources: `docs/reference/kubernetes-api/workload-resources/pod-v1.md:1006–1008`; `docs/concepts/workloads/pods/pod-lifecycle.md:591–639`.

5. **Resource sizing and CPU autoscaling.** Set realistic CPU requests for every relevant container. Requests drive scheduling capacity checks and typically CPU weighting under contention; they are not usage ceilings. CPU limits enforce throttling, which can affect latency. Memory limits are enforced reactively through OOM handling, potentially terminating processes rather than slowing execution. Utilization-based HPA measures CPU relative to requests: if relevant requests are missing from some containers, Pod utilization is undefined and HPA takes no action for that metric. Inspect effective admitted specifications: absent requests can default from limits. Sources: `docs/concepts/configuration/manage-resources-containers.md:29–53,63–66,230–264`; `docs/tasks/run-application/horizontal-pod-autoscale.md:89–101`.

6. **HPA’s conservative adjustments.** The raw calculation is the ceiling of current replicas multiplied by observed/target utilization, with default tolerance 0.1. HPA sets aside missing metrics and, for CPU, not-yet-ready Pods or samples preceding readiness. Missing samples are assumed at 100% of target during downscale and 0% during upscale; not-yet-ready Pods also dampen prospective upscale using 0%. If recalculation reverses direction or enters tolerance, scaling stops. Default readiness-delay and CPU-initialization windows are 30 seconds and five minutes. Downscale stabilization defaults to five minutes, selecting the highest recommendation in that window. Consequently, status utilization and actual scaling can differ. A functioning resource-metrics API is prerequisite. Source: `docs/tasks/run-application/horizontal-pod-autoscale.md:89–90,130–218`.

7. **Least-privilege networking.** Apply default-deny ingress and egress, then allow approved client-to-API traffic, API-to-database traffic on the database port, and required supporting flows. Isolation is directional: selecting a Pod for ingress does not isolate egress. Policies combine additively, so an existing broad allow can defeat a narrow policy’s intended restriction. Both source egress and destination ingress must permit a Pod-to-Pod connection; reply traffic is implicitly allowed. Explicitly permit DNS to the actual resolver configuration; the documented kube-dns example exposes UDP and TCP 53. Enforcement requires a supporting network plugin—creating policy objects alone does nothing. Sources: `docs/concepts/services-networking/network-policies.md:47–81,234–262`; `docs/tasks/administer-cluster/dns-debugging-resolution.md:158–168`.

8. **Secrets protection.** Reject base64-encoded credentials in Git as sufficient protection: the documentation demonstrates decoding and calls the encoded authentication value “obscured but not secret.” Remove exposed credentials and rotate them as an operational recommendation. Enable Secret encryption at rest and least-privilege RBAC, and expose Secrets only to required containers. Encryption at rest protects stored cluster data, not repository copies. Pod-creation privileges matter because someone permitted to create Pods—or indirectly Deployments—in a namespace can read its Secrets through workloads. Existing Secrets must also be rewritten to apply newly configured encryption. Sources: `docs/concepts/configuration/secret.md:284–306,35–48`; `docs/tasks/administer-cluster/encrypt-data.md:603–607`.

9. **Storage lifecycle.** Changing a StorageClass reclaim policy does not retroactively change existing PV policies; inspect and patch those PVs individually. Dynamically provisioned PVs inherit the class policy, defaulting to `Delete`. After PVC deletion releases the claim, `Retain` preserves the PV and data for manual reclamation; supported `Delete` implementations remove both PV and backing storage. StatefulSet deletion or downscaling ordinarily retains claims. Its separate PVC-retention settings can request deletion for either event, subject to the documented feature-gate prerequisite; resulting PVC deletion then invokes PV reclamation. Prefer explicit retention for database data pending recovery requirements. Sources: `docs/concepts/storage/storage-classes.md:126–135`; `docs/concepts/storage/persistent-volumes.md:178–210`; `docs/concepts/workloads/controllers/statefulset.md:391–423`.

10. **Prioritized rollout and validation checklist.**

   - First protect credentials and data: verify RBAC, encryption, existing PV policies, PVC retention, and a tested database recovery procedure. Kubernetes retention semantics do not establish database backup or recovery correctness. Sources: `docs/concepts/configuration/secret.md:35–48`; `docs/concepts/storage/persistent-volumes.md:185–210`.
   - Establish CPU requests, working metrics, probe thresholds, and graceful shutdown; load-test startup and long requests before rolling out. Application latency, probe accuracy, and request completion remain unproven. Sources: `docs/tasks/run-application/horizontal-pod-autoscale.md:89–101`; `docs/concepts/workloads/pods/pod-lifecycle.md:619–639`.
   - Verify CNI enforcement and allowed/denied connectivity, including DNS; policy propagation has no exact completion time exposed by the API. Source: `docs/concepts/services-networking/network-policies.md:362–381`.
   - Finally validate zone labels, surge capacity, rollout availability, drain blocking, and zone-loss recovery. Check storage topology and driver support: `WaitForFirstConsumer` can align provisioning with scheduling, but dynamic provisioning alone does not establish cross-zone database availability. Sources: `docs/concepts/storage/storage-classes.md:171–195`; `docs/concepts/workloads/pods/disruptions.md:107–136`.
