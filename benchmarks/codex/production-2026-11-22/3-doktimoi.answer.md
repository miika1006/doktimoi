**Decision memo: revise before production approval.** Six replicas across three zones provide useful redundancy, but the proposed settings do not establish five-replica availability, completed long requests, or database durability. Recommendations below are configuration choices; documented behavior and remaining validation requirements are identified separately.

All citations are local paths relative to the supplied `docs/` directory.

1. **PDB and rollout availability.** `minAvailable: 5` cannot prevent involuntary node failures, although unavailable Pods consume the budget. During an eviction-based node drain, the PDB constrains admitted evictions; direct Pod deletion bypasses it. With six healthy replicas, it permits one healthy replica’s eviction before replacements recover. Deployment rolling updates count against the budget but are **not constrained by it**. Thus `maxUnavailable: 2` permits rollout availability to fall to four. Recommend `maxUnavailable: 0, maxSurge: 1`, with sufficient surge capacity; `maxUnavailable: 1` is also compatible with a five-replica rollout floor at desired replicas six. Neither setting guarantees availability during concurrent failures.  
   Sources: `concepts/workloads/pods/disruptions.md:92-145`; `concepts/workloads/controllers/deployment.md:1184-1211`.

2. **Zone placement.** Configure an application-matching `labelSelector`, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`. The topology key groups equally labelled nodes into domains. With `DoNotSchedule`, skew limits the target domain’s matching-Pod count relative to the global minimum; balanced placement can yield 2/2/2. `ScheduleAnyway` prefers reducing skew but allows imbalance. Choose explicitly between strict spreading and replacement flexibility. If a zone becomes unavailable, scheduling depends on eligible domains, labels, taints, and capacity. With `minDomains: 3`, fewer than three eligible domains makes the global minimum zero, potentially blocking replacements. Without it, the default is one; a vanished domain may cease counting. Existing placement is not continuously guaranteed after removals. Losing two replicas leaves four regardless of the PDB.  
   Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:76-126`, `:166-189`, `:605-623`.

3. **Probes for slow startup.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Until startup succeeds, readiness and liveness probes do not begin. Startup failure eventually kills the container, subject to its restart policy. After startup, readiness should represent ability to accept requests; an unready Pod is removed from Service load-balancing backends without requiring a restart. Liveness should detect a condition that restarting can repair, such as deadlock, rather than ordinary load or a temporary database outage. That endpoint choice requires application validation: the docs warn that incorrect liveness checks can cause cascading restarts.  
   Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:14-48`, `:311-347`.

4. **Termination and long requests.** The grace-period countdown begins **before** `preStop`; hook execution consumes the same budget. On normal graceful termination, the kubelet runs the hook, then asks the runtime to send TERM to container process 1. A still-running hook can receive a one-off two-second extension. At grace expiry, remaining processes receive SIGKILL. Endpoint processing happens concurrently: terminating endpoints remain represented temporarily but have `ready: false`, excluding regular traffic; `serving` supports consumers implementing draining. Thirty seconds is a default, not a request-completion guarantee. Implement signal handling and draining, then size grace time for measured hook duration and outstanding requests.  
   Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:992-1012`; `concepts/workloads/pods/pod-lifecycle.md:584-610`, `:612-644`.

5. **Resource sizing and utilization HPA.** CPU requests inform scheduling and supply the denominator for utilization-based HPA; they are not CPU ceilings. Containers may exceed requests when resources are available. CPU limits enforce throttling, whereas memory limits are enforced reactively through OOM kills; exceeding memory does not necessarily cause an immediate kill. Set realistic CPU requests for every relevant container and load-test limits, since throttling can affect latency. If some containers lack the relevant request, Pod CPU utilization is undefined and HPA takes no action for that metric. Check effective admitted settings: absent requests can inherit specified limits.  
   Sources: `concepts/configuration/manage-resources-containers.md:21-67`; `tasks/run-application/horizontal-pod-autoscale.md:85-102`.

6. **HPA’s conservative adjustments.** The raw recommendation is the rounded-up product of current replicas and current/desired metric ratio. HPA ignores deleting Pods, discards failed Pods, and initially sets aside missing metrics and certain not-yet-ready CPU samples. It then assumes missing metrics equal 100% of target for downscaling and 0% for upscaling; not-yet-ready Pods also dampen prospective upscaling using 0%. A reversed direction or ratio within tolerance causes no action. Default readiness-delay and CPU-initialization windows are 30 seconds and five minutes. Downscale stabilization defaults to five minutes, selecting the highest recommendation in that window. Consequently, reported utilization and the raw ratio need not predict the actual change.  
   Sources: `tasks/run-application/horizontal-pod-autoscale.md:129-202`, `:212-218`.

7. **Least-privilege networking.** Establish ingress and egress default-deny isolation, then allow intended callers to the API port, API connections to the database port, and DNS queries to the actual cluster resolver. Use precise Pod/namespace selectors or appropriate destination ranges. Isolation is independent by direction. Policies are additive unions, so a broad allow policy can defeat the intended restriction; evaluation order cannot override it. A Pod-to-Pod connection requires both source egress and destination ingress permission, with reply traffic implicitly allowed. Enforcement requires a network plugin supporting NetworkPolicy: creating objects alone has no effect. Validate permitted and forbidden traffic against the deployed CNI and DNS arrangement.  
   Sources: `concepts/services-networking/network-policies.md:44-81`; `concepts/security/multi-tenancy.md:210-235`.

8. **Secrets and Git.** Reject base64-encoded credentials in Git as a protection mechanism: the docs demonstrate decoding and explicitly describe base64 data as obscured, not secret. Secrets are unencrypted in etcd by default. Enable and verify encryption at rest, configure least-privilege RBAC, and restrict which containers receive credentials. Encryption at rest does not protect a readable repository copy. Pod creation permissions also matter: someone allowed to create Pods in a namespace can obtain its Secrets, including indirectly through Deployment creation. Therefore review workload-creation privileges alongside direct Secret access.  
   Sources: `concepts/configuration/secret.md:35-48`, `:280-307`; `tasks/administer-cluster/encrypt-data.md:574-588`.

9. **Storage lifecycle.** Dynamically provisioned PVs inherit their StorageClass reclaim policy; its default is `Delete`. Changing the class’s policy does not retrofit existing PVs: inspect and explicitly patch those PVs. `Retain` leaves a deleted claim’s PV released, with data requiring manual reclamation. For supporting plugins, `Delete` removes both the PV and backing storage. Distinguish this from StatefulSet deletion or scaling: PVC retention defaults to `Retain`. Optional `whenDeleted`/`whenScaled: Delete` policies delete affected template-created PVCs, after which PV reclamation matters. The conceptual docs require `StatefulSetAutoDeletePVC` enabled on the API server and controller manager. These StatefulSet rules apply only if the database uses that controller.  
   Sources: `concepts/storage/storage-classes.md:126-135`; `concepts/storage/persistent-volumes.md:185-210`; `concepts/workloads/controllers/statefulset.md:387-425`.

10. **Prioritized rollout and validation checklist.** First remove exposed credential material, verify encryption/RBAC, and inspect database PVC/PV retention before destructive lifecycle tests. Second deploy supported network policies and test DNS, caller access, database access, and denied paths. Third measure startup, CPU/memory demand, and longest requests; configure probes, resources, draining, and grace time accordingly. Fourth verify zone labels, eligible capacity and surge headroom, then exercise rollout, eviction-based drain, node loss, and zone loss separately. Finally test HPA under load, readiness transitions, and missing metrics, with a working resource metrics API—usually supplied by separately installed Metrics Server.

    Release gates must include application request completion, database recovery/data integrity, CNI enforcement, and surviving-zone capacity. These documents do not establish those outcomes for this installation. They also do not guarantee preserved spreading after scale-down or bounded recovery time. Record measured acceptance criteria before approval.  
    Sources: `tasks/run-application/horizontal-pod-autoscale.md:113-118`; `concepts/workloads/pods/pod-lifecycle.md:612-644`; `concepts/services-networking/network-policies.md:44-49`; `concepts/storage/persistent-volumes.md:185-210`; `concepts/scheduling-eviction/topology-spread-constraints.md:605-623`.
