Decision: revise the design before production approval. Kubernetes provides controls for disruption, scheduling, health, and resource use, but the proposed settings do not establish five available replicas or safe completion of long requests. The recommendations below distinguish documented behavior from configuration choices and validation prerequisites. Citations refer only to the supplied local documentation.

1. **The PDB does not guarantee five replicas in all three cases.** Node failures are involuntary disruptions: PDBs cannot prevent them, although unavailable Pods count against the budget. During a drain using the Eviction API, a matching `minAvailable: 5` PDB restricts voluntary eviction; from six healthy replicas, it permits one disruption, and further evictions may block. Direct deletion bypasses this protection. Deployment rolling updates are not constrained by PDBs, so `maxUnavailable: 2` permits an availability floor of four. Recommend `maxUnavailable: 1`, `maxSurge: 1`, with capacity for the surge. This aligns rollout behavior with five available replicas under normal update conditions; concurrent failures remain possible.  
   Sources: `docs/concepts/workloads/pods/disruptions.md:99–145`; `docs/concepts/workloads/controllers/deployment.md:1183–1211`.

2. **Configure explicit zone spreading and choose the outage tradeoff.** Use a selector matching this API, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`; with three eligible zones and six successfully scheduled Pods, the intended distribution is two per zone. `topologyKey` identifies node-label domains. With `DoNotSchedule`, skew limits placement relative to the global minimum; violating Pods remain pending. `ScheduleAnyway` makes balance a preference, allowing placement despite skew. A zone outage therefore has no universal recovery outcome: eligibility, remaining capacity, and constraints matter. Explicit `minDomains: 3` makes the global minimum zero when fewer than three domains are eligible, potentially blocking replacements. Prefer soft spreading if restoring replicas outweighs strict balance. Losing two replicas still leaves only four initially. Constraints do not guarantee continued balance after removals.  
   Sources: `docs/concepts/scheduling-eviction/topology-spread-constraints.md:82–128,607–623`.

3. **Separate startup protection, traffic readiness, and restart detection.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Until it succeeds, readiness and liveness probes are disabled. Startup failure beyond its threshold kills the container, subject to restart policy. Thereafter, readiness should test whether the API can serve requests, including required database availability; failure removes the Pod from matching Service endpoints without itself restarting the container. Liveness should detect an unhealthy application requiring restart, rather than treating every database outage as application failure. Liveness failure kills the container, again subject to restart policy. Endpoint removal documents routing behavior, not a guarantee that every in-flight request stops immediately.  
   Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–318`; `docs/concepts/workloads/pods/pod-lifecycle.md:479–497,520–528`.

4. **Thirty seconds is a shutdown budget, not a completion guarantee.** The grace-period countdown begins before `preStop`, so the hook consumes the same budget as application cleanup. The kubelet runs the hook before requesting TERM delivery to the container’s main process; ordinary containers have no guaranteed mutual shutdown order. A still-running hook can receive a one-off two-second extension. At expiration, remaining processes receive SIGKILL. Concurrently, terminating Service endpoints remain represented in EndpointSlices with `terminating` status and `ready: false`, excluding them from regular traffic; `serving` supports draining decisions. Measure request duration and shutdown behavior, implement draining, and select a grace period covering both the hook and completion work.  
   Sources: `docs/reference/kubernetes-api/workload-resources/pod-v1.md:1006–1008`; `docs/concepts/workloads/pods/pod-lifecycle.md:591–639`.

5. **Size requests and limits from measurements.** CPU requests influence scheduling and CPU allocation under contention; they are not usage ceilings. CPU limits restrict execution through throttling, potentially extending request duration. Memory limits use reactive OOM enforcement: excess allocation can lead to termination rather than CPU-style throttling. Set explicit CPU requests for every relevant container because utilization-based HPA calculates usage relative to requests. If a container lacks the relevant request, Pod CPU utilization is undefined and HPA takes no action for that metric. Inspect effective configuration: absent other defaulting, specifying a limit without a request causes Kubernetes to copy the limit into the request.  
   Sources: `docs/concepts/configuration/manage-resources-containers.md:18–66,252–265`; `docs/tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **Expect HPA decisions to differ from the displayed ratio.** The basic calculation rounds up current replicas multiplied by current-to-target utilization, but missing metrics and CPU startup readiness modify it. Missing-metric Pods are conservatively assumed to consume 100% of target during downscale and 0% during upscale. Not-yet-ready Pods are also assumed to consume 0% when damping upscale. A recalculated ratio that reverses direction or falls within tolerance produces no scaling. Defaults include 10% tolerance, a 30-second initial readiness delay, and a five-minute CPU initialization period. Default downscale stabilization chooses the highest recommendation within five minutes. Reported average utilization excludes these conservative adjustments, explaining apparent discrepancies.  
   Source: `docs/tasks/run-application/horizontal-pod-autoscale.md:131–216`.

7. **Replace default allow with explicit, tested connection permissions.** First verify that the installed CNI/network plugin enforces NetworkPolicy; creating objects alone can have no effect. Apply namespace default-deny ingress and egress, then allow approved callers to the API port, API access to the database port, and required DNS access to the actual cluster resolver. DNS destinations and ports are cluster-specific configuration to verify, not established by this design. Ingress and egress isolation are independent. Policies combine additively, so a broad allow elsewhere can reopen access. For Pod-to-Pod connections, source egress and destination ingress must both permit the connection; replies are implicitly allowed. NetworkPolicy also retains documented node-traffic exceptions.  
   Sources: `docs/concepts/services-networking/network-policies.md:45–81,210–259,450–462`.

8. **Base64 is serialization, not adequate Secret protection.** Anyone who obtains the Git manifest can recover the encoded value; remove readable credentials from that workflow. Kubernetes documents base64 as the serialized representation of Secret data and warns that Secrets are unencrypted in etcd by default. Enable encryption at rest, apply least-privilege RBAC, and expose each Secret only to containers needing it. Restrict workload creation as well as direct Secret reads: permission to create Pods in a namespace—including indirectly through Deployments—can provide access to any Secret there. Encryption at rest does not remedy a readable Git copy or excessive workload-creation permissions.  
   Sources: `docs/reference/kubernetes-api/config-and-storage-resources/secret-v1.md:45–47`; `docs/concepts/configuration/secret.md:35–48`.

9. **Audit existing PVs individually; class policy is inherited at provisioning.** A different StorageClass reclaim policy does not retroactively rewrite existing PV policies; existing PVs require editing or patching. Dynamic provisioning defaults to `Delete` unless configured otherwise. After PVC deletion, `Retain` leaves the PV and data for manual reclamation; supported `Delete` implementations remove both the PV and backing storage. StatefulSet deletion or scale-down is a separate PVC-retention decision: default `Retain` preserves template-created PVCs, while configurable `whenDeleted` and `whenScaled` deletion policies can remove them. The documented feature-gate prerequisites must hold. For database storage, prefer deliberate retention pending a tested recovery procedure.  
   Sources: `docs/concepts/storage/storage-classes.md:128–135`; `docs/concepts/storage/persistent-volumes.md:180–210`; `docs/concepts/workloads/controllers/statefulset.md:391–423`.

10. **Roll out in dependency order.** First correct Secret handling and verify network enforcement and storage retention. Next measure resource demand, startup, request duration, and database capacity; configure probes, requests, and shutdown accordingly. Then establish zone placement, surge capacity, compatible rollout settings, and an HPA minimum consistent with the chosen six-replica baseline. Finally exercise rolling updates, drains, zone loss, missing metrics, denied connections, and storage recovery before promotion. Acceptance needs application or cluster validation of at least: successful long-request draining, capacity after zone loss, CNI enforcement, CPU’s usefulness as a demand signal, and database recovery. These documents establish mechanisms, not those outcomes. Topology-constrained storage also needs scheduling validation; consider `WaitForFirstConsumer`.  
   Sources: `docs/concepts/workloads/pods/disruptions.md:107–145`; `docs/tasks/run-application/horizontal-pod-autoscale.md:153–216`; `docs/concepts/storage/storage-classes.md:173–191`; `docs/concepts/services-networking/network-policies.md:45–49`.
