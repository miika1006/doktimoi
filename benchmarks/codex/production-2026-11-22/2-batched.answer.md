**Decision memo: revise the design before production rollout.** Kubernetes provides controls for disruption, scheduling, health, security, and storage lifecycle. Their presence does not establish application availability or database safety. The recommendations below distinguish documented behavior from choices requiring validation. All citations refer to the supplied local documentation.

1. **The PDB does not guarantee five available replicas in all three cases.** Involuntary node failures cannot be prevented by PDBs, although unavailable Pods count against the budget. During an ordinary node drain using the Eviction API, `minAvailable: 5` limits permitted evictions; requests can be rejected and retried. Direct deletion bypasses that protection. Deployment rolling updates also bypass PDB enforcement, so `maxUnavailable: 2` permits availability to fall to four. Recommend `maxUnavailable: 1`, `maxSurge: 1`, with capacity for surge Pods. This makes rollout policy compatible with five available replicas at desired scale six, without guaranteeing protection against concurrent failures. Sources: [disruptions.md, lines 99–145](docs/concepts/workloads/pods/disruptions.md#L99-L145); [deployment.md, lines 1185–1211](docs/concepts/workloads/controllers/deployment.md#L1185-L1211).

2. **Configure explicit zone spreading and choose the outage tradeoff.** Use the API’s shared labels as `labelSelector`, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, targeting two replicas per zone. `topologyKey` groups nodes by label value. With `DoNotSchedule`, skew limits the target domain’s matching-Pod count relative to the global minimum; violating placements remain unscheduled. `ScheduleAnyway` instead prefers placements reducing skew, allowing imbalance. Recommend the latter if restoring capacity during zone loss takes priority over strict balance. Hard constraints can block replacements when an unavailable domain remains counted. If it disappears from eligibility, calculations change; `minDomains: 3` explicitly makes the global minimum zero when fewer than three domains qualify. Neither mode guarantees continuous balance after Pod removal. Sources: [topology-spread-constraints.md, lines 82–130](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L82-L130), [167–185](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L167-L185), [605–619](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L605-L619).

3. **Separate startup completion, traffic eligibility, and restart detection.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case startup. Until it succeeds, other probes are disabled; their initial delays begin afterward. Use readiness to establish whether the API can serve useful requests, including required database availability where appropriate. Readiness failure removes the Pod from matching Service endpoints but leaves its container running. Use liveness for an application failure that restarting can resolve, rather than making database unavailability automatically restart every API replica. Startup or liveness failure at its configured threshold triggers container shutdown/restart according to restart policy. Sources: [configure-liveness-readiness-startup-probes.md, lines 311–347](docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md#L311-L347), [398–422](docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md#L398-L422); [pod-lifecycle.md, lines 479–497](docs/concepts/workloads/pods/pod-lifecycle.md#L479-L497), [524–528](docs/concepts/workloads/pods/pod-lifecycle.md#L524-L528).

4. **Thirty seconds is a shutdown budget, not a request-completion guarantee.** The grace-period countdown begins before `preStop`; the hook consumes that budget. The kubelet runs the hook, then requests TERM delivery to the container’s main process. A still-running hook can receive a one-off two-second extension. Remaining processes receive SIGKILL when grace expires. Endpoint handling proceeds concurrently: terminating EndpointSlice entries are not immediately removed, but have `ready: false`; `serving` can support draining-aware consumers. Implement signal handling and connection draining, then size grace for hook time and outstanding work. The documentation does not establish that this application’s long requests finish within thirty seconds. Sources: [pod-v1.md, lines 1006–1008](docs/reference/kubernetes-api/workload-resources/pod-v1.md#L1006-L1008); [pod-lifecycle.md, lines 581–639](docs/concepts/workloads/pods/pod-lifecycle.md#L581-L639).

5. **Set resource requests and limits deliberately.** CPU requests inform scheduling and establish the denominator for CPU-utilization HPA; they are not CPU ceilings. Containers may exceed requests when resources permit. CPU limits cause throttling. Memory limits are enforced reactively through OOM kills, rather than CPU-style throttling, and exceeding a memory limit need not cause immediate termination. For Pod CPU-utilization scaling, missing relevant requests on some containers makes utilization undefined and prevents action for that metric. Specify requests for every relevant container and verify admitted values: when a limit exists without a request or admission default, Kubernetes copies the limit into the request. Sources: [manage-resources-containers.md, lines 18–66](docs/concepts/configuration/manage-resources-containers.md#L18-L66); [horizontal-pod-autoscale.md, lines 89–102](docs/tasks/run-application/horizontal-pod-autoscale.md#L89-L102).

6. **Expect HPA decisions to differ from the raw CPU ratio.** The basic calculation rounds up current replicas multiplied by current/desired metrics, with default tolerance 0.1. Missing metrics are conservatively assumed at 100% of target for downscaling and 0% for upscaling. Not-yet-ready Pods are set aside; when evaluating an otherwise indicated upscale, they are assumed at 0%, dampening it. Recalculation can cancel scaling if direction reverses or falls within tolerance. CPU readiness classification uses configurable defaults of thirty seconds for initial readiness delay and five minutes for initialization. Downscaling uses the highest recommendation within the default five-minute stabilization window. These mechanisms and startup delay mean CPU HPA is not immediate capacity insurance. Sources: [horizontal-pod-autoscale.md, lines 129–218](docs/tasks/run-application/horizontal-pod-autoscale.md#L129-L218).

7. **Replace default allow with explicit ingress and egress allowances.** Select all relevant Pods with default-deny policies for both directions. Then permit authorized callers to the API port, API egress to database destinations/ports, and database ingress from API Pods. Permit DNS egress to the actual cluster resolver, including its required UDP/TCP ports; the documented kube-dns example exposes both on port 53. Ingress and egress isolation are independent, and both connection ends must allow establishment. Policies are additive unions: an existing broad allow cannot be overridden by adding deny policies. A NetworkPolicy-capable CNI implementation is a prerequisite; creating objects without enforcement has no effect. Sources: [network-policies.md, lines 45–81](docs/concepts/services-networking/network-policies.md#L45-L81), [210–259](docs/concepts/services-networking/network-policies.md#L210-L259); [dns-debugging-resolution.md, lines 158–173](docs/tasks/administer-cluster/dns-debugging-resolution.md#L158-L173).

8. **Base64 is insufficient protection for credentials in Git.** The documentation explicitly describes a base64-encoded credential as “obscured but not secret.” Remove readable credentials from committed manifests and adopt a controlled delivery mechanism. Enable Secret encryption at rest: Secrets are stored unencrypted in etcd by default. Apply least-privilege RBAC and restrict which containers receive credentials. Review workload-creation permissions as carefully as direct Secret reads: permission to create Pods in a namespace, including indirectly through Deployments, permits access to that namespace’s Secrets. Encryption at rest does not establish confidentiality for copies committed to Git. Sources: [secret.md, lines 35–48](docs/concepts/configuration/secret.md#L35-L48), [305–307](docs/concepts/configuration/secret.md#L305-L307), [453–457](docs/concepts/configuration/secret.md#L453-L457).

9. **Existing PVs retain their own reclaim policy.** Changing the StorageClass policy is not a retroactive update; inspect and patch existing PVs separately. Dynamically provisioned PVs inherit the class policy, whose default is `Delete`. After PVC deletion, `Retain` leaves the released PV and data for manual reclamation. With supporting plugins, `Delete` removes both PV and backing storage. StatefulSet deletion or scale-down is a separate trigger: PVC retention defaults to `Retain`. Optional `whenDeleted` and `whenScaled: Delete` settings delete affected template PVCs, after which PV reclaim policy matters; the documented feature gate must be enabled. Sources: [storage-classes.md, lines 126–135](docs/concepts/storage/storage-classes.md#L126-L135); [persistent-volumes.md, lines 178–210](docs/concepts/storage/persistent-volumes.md#L178-L210); [statefulset.md, lines 387–423](docs/concepts/workloads/controllers/statefulset.md#L387-L423).

10. **Prioritize validation before increasing exposure.** First, secure credentials and verify existing PV policies and recovery procedures. Second, establish CNI enforcement, DNS/database allowances, and negative connectivity tests. Third, measure startup and shutdown, configure probes/resources, and verify the metrics API prerequisite. Fourth, keep HPA’s minimum at six if six is the operational baseline, configure spreading and compatible rollout limits, then test rollout, drain, node loss, zone loss, and autoscaling under load.

    Release criteria must include limits these documents do not guarantee: useful throughput with five or four survivors; completion of long requests during termination; database failover and recoverability; and actual spare capacity and policy enforcement.
