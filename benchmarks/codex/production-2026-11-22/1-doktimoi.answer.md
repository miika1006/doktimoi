1. **PDB and rollout availability.** A PDB cannot prevent involuntary node failure; resulting unavailable Pods nevertheless count against its budget. During an eviction-based drain, a correctly selected `minAvailable: 5` budget constrains further voluntary evictions: with six healthy replicas, one can be evicted, and subsequent requests may wait. Direct deletion bypasses this protection. Deployment rolling updates also bypass PDB enforcement, although their unavailable Pods count against the budget. Consequently, `maxUnavailable: 2` permits four available replicas. Choose `maxUnavailable: 1, maxSurge: 1` to align rollout-induced unavailability with five; consider zero unavailable if capacity permits. Neither prevents concurrent failures. Sources: `concepts/workloads/pods/disruptions.md:92–137`, `concepts/workloads/pods/disruptions.md:59–65`; `concepts/workloads/controllers/deployment.md:1182–1215`.

2. **Zone placement.** Configure a matching application selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, targeting two replicas per zone when all three domains are eligible and have capacity. The key groups nodes by label value. With `DoNotSchedule`, skew limits the target domain’s matching-Pod count relative to the global minimum; with `ScheduleAnyway`, reducing skew is a scheduling preference. Choose hard spreading only with an explicit outage policy: if an unavailable zone still affects the minimum, replacements elsewhere can remain Pending. If it disappears from eligible domains, calculations change; setting `minDomains: 3` forces a zero minimum with fewer eligible domains and can block recovery elsewhere. Soft spreading favors placement during degradation. Neither repairs existing imbalance automatically. Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:76–126`, `:178–190`, `:203–211`, `:605–622`.

3. **Probes for slow startup.** Use a startup probe with `failureThreshold × periodSeconds` covering measured worst-case initialization. Until it succeeds, readiness and liveness probes do not start; exhausting its budget kills the container, subject to restart policy. Use readiness to indicate whether this instance can accept requests, including necessary dependency availability. Failed readiness removes the Pod from Service load balancing without itself requesting a restart. Use liveness for recoverable-by-restart failures such as deadlock; making database unavailability a liveness failure risks unnecessary restarts and cascading load. Probe thresholds and endpoints require application testing. Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:13–48`, `:311–347`.

4. **Termination and long requests.** The grace-period countdown begins before `preStop`; the hook consumes that same budget. The kubelet runs the hook before asking the runtime to send TERM to container process 1. A still-running hook can receive a one-off two-second extension. Endpoint handling proceeds concurrently: terminating endpoints remain represented temporarily but have `ready: false`, excluding regular traffic; `serving` exposes readiness for draining-aware consumers. At expiry, remaining processes receive SIGKILL. Thirty seconds therefore does **not** guarantee request completion. Implement application draining and signal handling, then size grace time for hook execution and outstanding work. Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:992–1006`; `concepts/workloads/pods/pod-lifecycle.md:584–645`.

5. **Resource settings.** Specify realistic CPU requests for every relevant container: requests drive placement and provide the denominator for utilization-based HPA. A request is not a consumption ceiling; spare capacity can be used above it. CPU limits enforce throttling, potentially increasing latency. Memory limits are enforced reactively through OOM kills, rather than CPU-style throttling; excess memory is not necessarily killed immediately. Missing relevant container requests leave Pod CPU utilization undefined, so HPA takes no action for that metric. Account for admission defaults and limit-to-request copying before diagnosing “missing” requests. Sources: `concepts/configuration/manage-resources-containers.md:27–67`, `:230–241`; `tasks/run-application/horizontal-pod-autoscale.md:89–103`.

6. **HPA conservatism.** The initial recommendation is the rounded-up product of current replicas and current/desired metric ratio, with default tolerance 0.1. Deleting and failed Pods are excluded; missing metrics and qualifying not-yet-ready CPU Pods are set aside. Missing metrics are conservatively assumed at 100% of target for downscaling and 0% for upscaling. Not-yet-ready Pods also dampen upscaling through a 0% assumption. A recalculation that reverses direction or enters tolerance produces no scaling. Default readiness-delay and CPU-initialization windows are 30 seconds and five minutes. Downscale stabilization defaults to 300 seconds, selecting the highest recent recommendation. Thus reported utilization and raw-ratio arithmetic need not predict the actual replica change. Sources: `tasks/run-application/horizontal-pod-autoscale.md:125–202`, `:213–219`, `:455–486`.

7. **Least-privilege networking.** Establish ingress and egress default-deny policies, then allow approved callers to the API port, API-to-database traffic on the required port, and necessary DNS egress to the actual cluster resolver. Configure database ingress correspondingly when it is policy-controlled. Ingress and egress isolation are independent; a Pod-to-Pod connection must pass both source egress and destination ingress. Policies form an additive union, so an existing allow-all policy defeats restrictive additions and must be removed. Verify namespace/Pod selectors, resolver destinations, and allowed protocols in this cluster. A NetworkPolicy object has no enforcement effect without supporting CNI/network-policy implementation. Sources: `concepts/services-networking/network-policies.md:45–79`, `:224–252`; `concepts/services-networking/service.md:929–947`.

8. **Secrets protection.** Base64 is reversible encoding, not confidentiality; reject base64-only Secrets in Git. Kubernetes documents encoded credentials as “obscured but not secret,” and Secrets are unencrypted in etcd by default. Enable encryption at rest, verify encrypted storage, and apply least-privilege RBAC plus container-specific access. Restrict Pod and Deployment creation too: someone authorized to create a Pod in a namespace can use it to read that namespace’s Secrets without direct Secret-read permission. At-rest encryption does not protect credentials already exposed through repository access. Sources: `concepts/configuration/secret.md:34–49`, `:291–307`; `tasks/administer-cluster/encrypt-data.md:534–588`.

9. **Storage lifecycle.** StorageClass reclaim policy is inherited when dynamic PVs are provisioned; changing the class does not retroactively change existing PV policies. Inspect and patch existing PVs individually. With `Retain`, deleting a PVC leaves a released PV and its data requiring manual reclamation. With supported `Delete`, reclamation removes both PV and backing storage. This differs from StatefulSet deletion or scale-down: PVC retention defaults to `Retain`. Optional `whenDeleted`/`whenScaled: Delete` policies delete affected template-created PVCs, subsequently invoking PV reclamation. Their documented prerequisite is enabling `StatefulSetAutoDeletePVC` on the API server and controller manager; verify effective configuration. Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:185–210`; `concepts/workloads/controllers/statefulset.md:387–425`.

10. **Prioritized rollout and validation checklist.** First, remove repository credential exposure, verify encryption/RBAC, inventory actual PV reclaim policies, and prove database restore procedures. Second, verify network-policy enforcement and stage explicit API, database, and DNS allowances with positive and negative connection tests. Third, configure probes, measured resource requests, shutdown handling, compatible rollout settings, and HPA bounds consistent with the availability objective; verify the resource-metrics API prerequisite. Finally, rehearse rolling updates, eviction-based drains, abrupt node/zone loss, missing metrics, and disposable PVC/StatefulSet deletion scenarios.

   Acceptance still requires application or cluster evidence for **maximum startup duration**, **long-request draining and routing convergence**, **surviving-zone capacity**, and **database recovery/data durability**. These documents establish mechanisms, not those workload-specific outcomes.
