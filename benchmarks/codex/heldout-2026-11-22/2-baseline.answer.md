Decision memo: approve the platform conditionally. The design needs explicit scheduling, admission and application controls. Kubernetes documents approximate scheduling, bounded retries and several forms of eviction; these do not establish exactly-once reporting, uninterrupted execution or guaranteed interactive-service latency.

Citations below identify local files relative to the supplied workspace and their source line ranges.

1. **CronJob scheduling is not exactly once.** A scheduled occurrence can create two Jobs or none; reports therefore need idempotent effects. Choose `concurrencyPolicy: Forbid` if overlapping reports are unacceptable: it skips an occurrence while the previous Job runs, although a later start remains subject to the starting deadline. `Allow`, the default, permits overlap; `Replace` replaces the running Job. These controls apply only within one CronJob. Set `startingDeadlineSeconds` to the useful lateness window; expired occurrences are skipped. More than 100 missed schedules prevents a start; a configured deadline limits the counting window. Values below ten seconds may miss scheduling because the controller checks every ten seconds. Set `.spec.timeZone`, preferably explicitly to `Etc/UTC`; otherwise the controller manager’s local zone applies. Sources: `docs/concepts/workloads/controllers/cron-jobs.md`, lines 109–143, 180–186, 213–240.

2. **Separate retry, runtime and retention limits.** Jobs permit `restartPolicy: Never` or `OnFailure`. With `OnFailure`, failed containers restart within their Pod; with `Never`, container failure can fail the Pod and trigger a replacement. Applications must tolerate both repeated execution and incomplete prior output. `backoffLimit` defaults to six and counts failed Pods plus, for `OnFailure`, container retries in Pending/Running Pods; reaching either count fails the Job. Set Job-level `activeDeadlineSeconds` to bound total runtime across Pods. It takes precedence over remaining retries: deadline expiry terminates running Pods and prevents further retries. Neither failure mechanism automatically restarts the failed Job. `ttlSecondsAfterFinished` only makes completed or failed Jobs eligible for cascading cleanup; it does not limit runtime or promise deletion at an exact instant. Sources: `docs/concepts/workloads/controllers/job.md`, lines 220–221, 318–342, 360–374, 623–663, 741–775.

3. **Use both a taint and required node affinity.** Label batch nodes and require that label through `requiredDuringSchedulingIgnoredDuringExecution`; preferred affinity permits fallback elsewhere. Taint those nodes, for example `dedicated=batch:NoSchedule`, and give batch Pods the matching toleration. A toleration permits placement but neither attracts the Pod nor guarantees scheduling. Other Pods must lack that toleration, requiring control over submitted specifications. `NoSchedule` blocks new placements but leaves existing Pods running. `NoExecute` also evicts existing non-tolerating Pods; matching tolerations can allow indefinite residence or specify `tolerationSeconds`. Required affinity is evaluated when scheduling: subsequent label changes do not move running Pods. Sources: `docs/concepts/scheduling-eviction/taint-and-toleration.md`, lines 13–24, 99–110, 181–191; `docs/concepts/scheduling-eviction/assign-pod-node.md`, lines 105–118.

4. **Make batch priority lower, but resolve the placement contradiction.** Create cluster-scoped PriorityClasses and select them through Pod `priorityClassName`; larger integer values mean higher priority. Give interactive Pods higher priority and `PreemptLowerPriority`; optionally give batch Pods `preemptionPolicy: Never`, preventing them from preempting others while leaving them preemptible. Preemption works only when removing lower-priority Pods makes a node feasible for the pending Pod. Thus strict exclusion of interactive Pods from batch nodes prevents those services reclaiming batch capacity. Choose either exclusive pools or explicitly permitted interactive access. Victims receive graceful termination, delaying capacity recovery. PodDisruptionBudgets receive best-effort consideration and can be violated. Sources: `docs/concepts/scheduling-eviction/pod-priority-preemption.md`, lines 53–57, 107–127, 151–154, 187–194, 218–238.

5. **Quotas constrain admission, not available capacity.** Specify CPU and memory requests and limits explicitly for every container. The exact requirement follows the quota keys: `requests.cpu`/`requests.memory` require requests; `limits.cpu`/`limits.memory` require limits. Plain `cpu` and `memory` quota keys mean requests. These quotas aggregate the corresponding declarations across non-terminal Pods. Creation or update violating quota fails with HTTP 403; an excess Pod is rejected rather than admitted to wait for quota. Installing or changing quota does not affect already-created resources, including running Pods. Namespace quota totals can exceed cluster capacity, so quota availability does not guarantee placement. Sources: `docs/concepts/policy/resource-quotas.md`, lines 33–41, 74–77, 99–105, 464–469.

6. **Choose configuration consistency deliberately.** Ordinary mounted ConfigMap volumes update eventually. Delay can reach the kubelet sync period plus cache propagation delay, depending on its watch/cache configuration. This guarantees eventual projection, not application reload or a consistent configuration snapshot throughout an hours-long report. ConfigMap environment variables do not update automatically and require Pod restart; `subPath` mounts receive no updates. With `immutable: true`, neither data mutation nor reverting immutability is allowed. Delete/recreate is possible, but existing Pods retain their mount point and recreation is recommended. For reproducible reports, choose a distinct immutable configuration version per run and validate the application’s loading behavior. Sources: `docs/concepts/configuration/configmap.md`, lines 191–208, 303–328.

7. **Memory-pressure eviction is not simply “lowest priority first.”** After unsuccessful node-level reclamation, the kubelet ranks Pods by whether usage exceeds requests, then priority, then usage relative to requests. BestEffort/Burstable Pods exceeding requests are generally evicted before Guaranteed/Burstable Pods below requests; within the former group priority and excess usage matter. QoS class itself is not the ranking input. Low batch priority therefore does not guarantee batch will always be evicted before interactive workloads. Node-pressure eviction does not honor PodDisruptionBudgets or guarantee the Pod’s configured termination grace period. Hard thresholds use zero seconds; soft thresholds use the kubelet’s eviction grace configuration. Sources: `docs/concepts/scheduling-eviction/node-pressure-eviction.md`, lines 20–36, 188–211, 318–353.

8. **Restricted enforcement requires compliant templates and functioning admission.** Verify PodSecurity admission, then label namespaces `pod-security.kubernetes.io/enforce=restricted`; pin `enforce-version=v1.32` for reviewed behavior. Restricted includes every Baseline control, restricts volume types, requires non-root execution and disallows UID 0. For Linux, require `allowPrivilegeEscalation: false`, an allowed explicit seccomp profile, and dropping `ALL` capabilities; only `NET_BIND_SERVICE` may be added back. Apply relevant controls to regular, init and ephemeral containers. Enforcement rejects violating Pods; audit records violations without blocking; warn returns warnings without blocking, including for workload templates. These are admission checks, not proof that applications remain functional. Sources: `docs/reference/access-authn-authz/admission-controllers.md`, lines 718–723; `docs/reference/labels-annotations-taints/_index.md`, lines 2369–2396, 2434–2448; `docs/concepts/security/pod-security-standards.md`, lines 299–451, 500–504; `docs/tasks/configure-pod-container/migrate-from-psp.md`, lines 262–265.

9. **Disable unnecessary token automounting explicitly.** ServiceAccount API credentials are mounted automatically by default. Put `automountServiceAccountToken: false` in the CronJob’s Pod template, and set it on the batch ServiceAccount as the default for its consumers. The Pod setting overrides the ServiceAccount setting, so a ServiceAccount default alone is insufficient enforcement against overrides. Inspect resulting Pods for explicitly supplied credentials too: disabling automount addresses automatic mounting, not every way credentials could enter a container. Restricted compliance does not replace this separate configuration decision. Source: `docs/tasks/configure-pod-container/configure-service-account.md`, lines 67–100.

10. **Roll out in this priority order.** First, resolve whether interactive services may enter batch nodes; validate allowed and forbidden placements before testing preemption. Second, make templates Restricted-compliant, disable token automounting, declare resources, and test quota rejection. Dry-run namespace enforcement and soak audit/warn across a nightly cycle before enforcing everywhere, including validating system-workload compatibility. Third, configure timezone, overlap policy, start deadline, retry/runtime limits and retention. Fourth, exercise failures, prolonged execution, configuration edits, preemption and memory pressure.

    Acceptance must validate at least these limits: application idempotency and partial-output recovery; interactive placement and recovery latency; measured memory requests and eviction behavior; and application configuration reload or snapshot consistency. The cited documents establish none of those application outcomes.
