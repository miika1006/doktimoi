Decision: proceed only after resolving the conflict between exclusive batch nodes and reclaiming their capacity for interactive services. Kubernetes supplies admission and scheduling mechanisms; these documents do not establish report correctness, completion deadlines, or service availability. Citations link to supplied local documents; labels give source line ranges.

1. **CronJob execution is approximate.** It does not guarantee exactly one Job per schedule: duplicate Jobs or no Job are possible, so reports must be idempotent. `concurrencyPolicy: Allow` permits overlap; `Forbid` skips an occurrence while the previous run remains unfinished; `Replace` replaces the current run. These policies apply only within one CronJob. Choose `Forbid` if overlapping reports are undesirable, while accepting missed occurrences. [CronJob:130–143, 213–217][cron]

   `startingDeadlineSeconds` limits lateness of **Job creation**, not runtime; expired occurrences are skipped. Unset means no starting deadline. Values below ten seconds risk never scheduling because the controller checks every ten seconds. More than 100 missed schedules prevents creation; a configured deadline narrows the counting window. Forbid-induced skips count as missed. Set an explicit `.spec.timeZone`, such as `Etc/UTC`; otherwise the controller manager’s local zone applies. [CronJob:109–126, 180–188, 228–240][cron]

2. **Bound retries, runtime, and retention separately.** Job Pods allow `restartPolicy: Never` or `OnFailure`. With `Never`, failed Pods are replaced; `OnFailure` allows container restarts within a Pod. `backoffLimit` defaults to six, with exponentially delayed replacement attempts. Failed Pods count toward it; with `OnFailure`, container restarts in Pending or Running Pods also count. Either calculation reaching the limit fails the Job. [Job:219–221, 358–380, 623–626][job]

   Set Job-level `activeDeadlineSeconds` for the overall duration across all Pods. It takes precedence over remaining retry allowance: deadline expiry terminates running Pods and fails the Job with `DeadlineExceeded`. Neither limit restarts a failed Job. Termination grace can delay complete shutdown. `ttlSecondsAfterFinished` only makes finished Jobs eligible for cascading cleanup; it does not stop an overlong run. Choose retention sufficient for diagnosis. [Job:628–663, 689–711, 737–775][job]

3. **Use both repulsion and required placement.** Taint batch nodes, for example `dedicated=batch:NoSchedule`, give batch Pods the matching toleration, and require their node affinity to match a batch-node label. Tolerations merely permit placement; they do not confine Pods. Required affinity constrains scheduling; preferred affinity permits fallback. Label changes do not evict already scheduled Pods. [Taints:181–191][taints]; [Affinity:103–118][affinity]

   `NoSchedule` blocks new untolerating Pods but leaves existing ones. `NoExecute` also evicts existing untolerating Pods; `tolerationSeconds` can delay that eviction. Control who may supply tolerations, and account for direct `nodeName` assignment bypassing the scheduler. Strictly excluding interactive Pods from batch nodes prevents them from reclaiming that capacity; either authorize interactive use there or validate a separate capacity arrangement. [Taints:65–71, 97–110][taints]; [Priority:187–194][priority]

4. **Give interactive Pods higher priority, with eligible capacity.** Create cluster-scoped PriorityClasses with lower values for batch and higher values for interactive workloads; reference them through `priorityClassName`. Higher values mean higher priority. Set batch `preemptionPolicy: Never` if batch must not displace other workloads. This does **not** protect batch from preemption. Interactive classes need `PreemptLowerPriority`, the default, to reclaim resources. [Priority:51–57, 103–127, 151–154][priority]

   Preemption works only where removing lower-priority Pods makes the incoming Pod schedulable; it cannot remove taint or affinity restrictions. Victims receive their graceful termination period, delaying replacement capacity. PDB protection is best effort: the scheduler seeks victims that avoid violations but can proceed despite their PDBs. Priority therefore provides neither immediate takeover nor an availability guarantee. [Priority:187–194, 216–238][priority]

5. **Quota is admission accounting, not reserved capacity.** CPU/memory quotas require resource declarations on new Pods; missing declarations can cause rejection. Specify explicit requests and limits consistently, or deliberately configure LimitRange defaults, and ensure declarations satisfy the quota’s chosen request/limit dimensions. `cpu` and `memory` quota keys mean summed requests; `limits.cpu` and `limits.memory` count limits across non-terminal Pods. [Quota:39–60, 97–105][quota]

   A creation or update violating quota receives HTTP `403 Forbidden`; an over-quota Pod is rejected rather than admitted to wait for scheduling. Adding or changing quota does not affect already created resources, including running Pods. Quotas exceeding cluster capacity can still produce contention. ResourceQuota admission must actually be enabled. [Quota:26–41, 74–84][quota]

6. **Choose configuration consistency explicitly.** Ordinary ConfigMap volume projections update eventually. Delay can reach the kubelet sync period plus cache propagation delay; this is not immediate delivery. `subPath` mounts receive no updates. Environment-variable consumers require Pod restart. File projection alone does not establish that the report process rereads settings or handles a change consistently during an hours-long run. [ConfigMap:191–208][config]

   `immutable: true` prevents subsequent data changes and cannot be reversed. Updating requires replacement; deleting and recreating the same ConfigMap leaves existing Pods holding the deleted object’s mount point, so recreation of those Pods is recommended. Prefer versioned immutable configuration per report run if reproducibility is required; that is a platform choice. [ConfigMap:299–328][config]

7. **Memory-pressure eviction is not simply “lowest priority first.”** After resource reclamation fails, kubelet ranks Pods by whether consumption exceeds requests, then priority, then usage relative to requests. BestEffort/Burstable Pods exceeding requests are generally evicted before Guaranteed/Burstable Pods below requests. QoS class itself is not the selection input. Consequently, low batch priority alone does not guarantee batch always leaves first. [Eviction:318–353][eviction]

   Node-pressure eviction ignores PDBs and the Pod’s `terminationGracePeriodSeconds`. Soft thresholds use configured `eviction-max-pod-grace-period`; hard thresholds use zero seconds. Reports must tolerate abrupt termination. [Eviction:26–36][eviction]

8. **Restricted requires compliant Pod specifications and functioning admission.** Require PodSecurity admission and namespace labels `pod-security.kubernetes.io/enforce=restricted` and `enforce-version=v1.32`. Enforce rejects noncompliant Pod creation; audit records violations without blocking; warn returns warnings without blocking, including for workload templates. [Admission:119–130][admission]; [Labels:2369–2396, 2434–2448][labels]; [Migration:262–265][migration]

   Restricted includes all Baseline controls and restricts volume types. For Linux containers, require non-root execution, prohibit explicitly setting UID zero, disable privilege escalation, select `RuntimeDefault` or `Localhost` seccomp, and drop `ALL` capabilities, adding back only `NET_BIND_SERVICE` if needed. Check init and ephemeral containers too; OS-specific rules matter. A failing container invalidates the Pod. “Everywhere” requires testing system components as well: the supplied tutorial demonstrates restricted violations in `kube-system`. [Standards:299–451][standards]; [Cluster tutorial:145–171][cluster]

9. **Disable unnecessary token automounting.** Pods normally receive mounted ServiceAccount API credentials; the namespace default ServiceAccount is assigned if none is selected. Put `automountServiceAccountToken: false` in the Job’s Pod template and/or on its ServiceAccount. The Pod setting takes precedence, so a ServiceAccount default alone is overridable. Validate actual Pod mounts and prevent unnecessary overrides. This switch controls automatic mounting; it does not establish that applications cannot receive credentials through other configured inputs. [ServiceAccount:32–54, 67–100][sa]

10. **Prioritized rollout and validation checklist.** Treat these as release gates:

   - **First:** resolve node exclusivity versus interactive takeover; test affinity, tolerations, direct assignment controls, and preemption on eligible nodes. [Taints:65–71, 181–191][taints]; [Priority:187–194][priority]
   - **Second:** inventory every workload, including dormant CronJobs and system components; dry-run Restricted, observe audit/warn, fix templates, then enforce. Disable unnecessary token mounting and test quota rejection. [Migration:242–265][migration]; [ServiceAccount:67–100][sa]; [Quota:26–41][quota]
   - **Third:** configure schedule zone, overlap policy, lateness, runtime, retries, retention, and configuration versioning; exercise duplicate execution, failures, and termination. [CronJob:109–143, 180–217][cron]; [Job:623–663, 737–775][job]
   - **Finally:** load-test takeover latency and memory pressure before broad rollout. At least four limits remain unguaranteed: application idempotency/checkpoint recovery, completion within the nightly window, configuration reread consistency, and interactive recovery latency under real placement and termination constraints. [CronJob:213–217][cron]; [ConfigMap:191–208][config]; [Priority:216–238][priority]; [Eviction:26–36][eviction]
