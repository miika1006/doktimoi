Decision memo: adopt the design conditionally. Kubernetes supplies useful admission and scheduling controls, but the proposed isolation and yielding requirements conflict unless interactive services may also use batch nodes. The choices below require explicit configuration and validation. Citations identify local corpus paths and inclusive source line ranges.

1. **CronJob execution is not exactly once.** The controller may create two Jobs or none for a scheduled execution; report processing must therefore be idempotent. Choose `concurrencyPolicy: Forbid` if overlapping reports are undesirable: it skips an occurrence while the preceding Job runs, although a later start can remain possible within the starting deadline. `Allow`, the default, permits overlap; `Replace` replaces the running Job. These policies cover only Jobs belonging to the same CronJob. (`docs/concepts/workloads/controllers/cron-jobs.md`, lines 128–143, 211–225.)

   Set `startingDeadlineSeconds` according to how late a report remains useful; it limits delayed creation, not runtime. Values below ten seconds may prevent scheduling. More than 100 missed schedules prevents a start; the deadline, when set, bounds the missed-schedule counting window. `Forbid` skips count as misses. Set `.spec.timeZone`, for example `Etc/UTC`; otherwise the controller manager’s local timezone applies. (`docs/concepts/workloads/controllers/cron-jobs.md`, lines 107–126, 176–188, 227–240.)

2. **Bound retries and runtime separately; TTL only cleans up.** With `restartPolicy: OnFailure`, failed containers restart inside their Pod; with `Never`, container failure can fail the Pod and trigger a replacement. Applications must tolerate both restarts and incomplete previous output. `backoffLimit` defaults to six; retries use exponential delays capped at six minutes. Failed Pods, and container retries under `OnFailure`, contribute to its calculations. (`docs/concepts/workloads/controllers/job.md`, lines 316–342, 358–380.)

   Set Job-level `activeDeadlineSeconds` to bound total Job duration across Pods. It takes precedence over `backoffLimit`: reaching the deadline terminates running Pods and prevents further retries even with retry budget remaining. An earlier exhausted backoff limit can also fail the Job. Failed Jobs do not automatically restart. `ttlSecondsAfterFinished` makes completed or failed Jobs eligible for cascading deletion after the chosen interval; it neither limits runtime nor retries failures. Preserve diagnostics before cleanup. (`docs/concepts/workloads/controllers/job.md`, lines 623–663, 737–775.)

3. **Use a taint plus required node affinity.** Label batch nodes, taint them `dedicated=batch:NoSchedule`, and give batch Pods the matching toleration plus `requiredDuringSchedulingIgnoredDuringExecution` affinity for that label. Tolerations permit placement; they do not attract Pods or guarantee scheduling. Required affinity confines batch placement; preferred affinity cannot enforce this requirement. (`docs/concepts/scheduling-eviction/taint-and-toleration.md`, lines 18–25, 181–191; `docs/concepts/scheduling-eviction/assign-pod-node.md`, lines 103–118.)

   `NoSchedule` leaves existing Pods running. `NoExecute` additionally evicts intolerant existing Pods; matching tolerations can allow indefinite residence or specify `tolerationSeconds`. Admission controls must prevent unauthorized tolerations and placement bypasses: explicitly setting `nodeName` bypasses scheduler enforcement of `NoSchedule`. Label changes also do not evict Pods under the stated affinity type. (`docs/concepts/scheduling-eviction/taint-and-toleration.md`, lines 65–71, 97–110; `docs/concepts/scheduling-eviction/assign-pod-node.md`, lines 116–118.)

4. **Give batch lower priority, but resolve node eligibility first.** Create cluster-scoped PriorityClasses, assign a lower numeric value to batch, and set `priorityClassName` in workload templates. Choose batch `preemptionPolicy: Never` to prevent batch from preempting other workloads; it remains preemptible. Interactive services need higher priority and `PreemptLowerPriority`, the default, to displace batch. (`docs/concepts/scheduling-eviction/pod-priority-preemption.md`, lines 34–57, 103–127.)

   Preemption works only where removing lower-priority Pods makes the pending Pod schedulable. Consequently, excluding *all* interactive Pods from batch nodes prevents them from reclaiming batch capacity. Either authorize selected interactive services on those nodes or accept separate capacity pools. Victims receive their graceful termination period, delaying replacement scheduling. PDB protection is best effort and may be violated. (`docs/concepts/scheduling-eviction/pod-priority-preemption.md`, lines 185–194, 216–238.)

5. **Quota is admission control, not reserved capacity.** For `requests.cpu` and `requests.memory` quotas, every incoming container needs the corresponding request; limit quotas require corresponding limits. Configure explicit requests and limits, or suitable LimitRange defaults. Exceeding quota rejects creation or update with HTTP 403; it does not admit an oversized Pod to wait for resources. (`docs/concepts/policy/resource-quotas.md`, lines 36–60, 462–469.)

   Compute quotas aggregate nonterminal Pods; `cpu` and `memory` mean request quotas. Quota changes do not affect already-created resources. Namespace quotas can collectively exceed cluster capacity, so admission does not guarantee schedulability. Verify that ResourceQuota admission is enabled. (`docs/concepts/policy/resource-quotas.md`, lines 74–105.)

6. **Choose configuration consistency deliberately.** Ordinary ConfigMap volume projections update eventually. Delay can reach the kubelet sync period plus cache propagation delay; watch, TTL-cache and direct-fetch strategies differ. That guarantees eventual file projection, not application reload or a consistent configuration throughout a multi-hour report. Validate application rereading behavior. (`docs/concepts/configuration/configmap.md`, lines 191–208.)

   `subPath` mounts receive no updates. Environment-variable consumers require a Pod restart. Immutable ConfigMaps prohibit changing `data` or `binaryData` and cannot become mutable again; deletion and recreation is possible, with Pod recreation recommended. For reproducible reports, choose versioned immutable ConfigMaps and reference the selected version in each run. (`docs/concepts/configuration/configmap.md`, lines 205–208, 299–328.)

7. **Memory-pressure eviction does not simply select the lowest-priority Pod.** After node-level reclamation fails, kubelet ranks Pods by whether usage exceeds requests, then priority, then usage relative to requests. Above-request BestEffort/Burstable Pods are evicted before the described within-request group; priority operates within that ordering. QoS names help estimate outcomes but are not the actual ordering input. (`docs/concepts/scheduling-eviction/node-pressure-eviction.md`, lines 318–342.)

   Node-pressure eviction honors neither PDBs nor the Pod’s configured `terminationGracePeriodSeconds` as a guarantee. Soft eviction uses kubelet eviction grace configuration; hard thresholds cause immediate termination with zero grace. Batch recovery must tolerate abrupt interruption. (`docs/concepts/scheduling-eviction/node-pressure-eviction.md`, lines 26–36, 185–212.)

8. **Restricted enforcement requires compliant Pods and functioning admission.** Configure namespace `pod-security.kubernetes.io/enforce=restricted`, preferably pinned with `enforce-version=v1.32`, and verify PodSecurity admission. Restricted includes Baseline controls and restricts volumes; ConfigMap volumes are permitted. All applicable regular, init and ephemeral containers must comply. Linux requirements include disabling privilege escalation, requiring nonroot execution, prohibiting UID zero, explicit allowed seccomp, and dropping `ALL` capabilities with only `NET_BIND_SERVICE` optionally restored. Some controls are OS-specific. (`docs/reference/access-authn-authz/admission-controllers.md`, lines 714–723; `docs/reference/labels-annotations-taints/_index.md`, lines 2369–2396; `docs/concepts/security/pod-security-standards.md`, lines 299–451.)

   `enforce` rejects noncompliant creation; `audit` records violations without blocking; `warn` returns user warnings, including for workload templates. Enforcement does not establish that existing Pods have been remediated. Audit exemptions before claiming coverage everywhere. (`docs/tasks/configure-pod-container/migrate-from-psp.md`, lines 253–280; `docs/reference/labels-annotations-taints/_index.md`, lines 2434–2448; `docs/tutorials/security/cluster-level-pss.md`, lines 193–207.)

9. **Disable unnecessary credential automounting explicitly.** Omitting `serviceAccountName` selects the namespace’s default ServiceAccount; it does not avoid credentials. Set Pod-level `spec.automountServiceAccountToken: false`, or set `automountServiceAccountToken: false` on its ServiceAccount. The Pod setting wins when both specify a value. This controls automatic mounting, not every possible manually supplied credential. (`docs/tasks/configure-pod-container/configure-service-account.md`, lines 38–58, 67–100.)

   ConfigMap volumes and environment injection use kubelet processing, so those consumption methods need no application API reader. Direct API consumption is a different design requiring appropriate authentication and authorization. (`docs/concepts/configuration/configmap.md`, lines 97–115.)

10. **Roll out in this order, with explicit acceptance tests.**

   - Resolve exclusive batch capacity versus interactive reclamation; then test taints, affinity, priority and unauthorized placement attempts against questions 3–4.
   - Apply explicit resource settings and quotas; verify missing-resource and quota-exceeding rejection. Disable token automounting and inspect resulting Pods.
   - Dry-run Restricted namespace enforcement, soak audit/warn through nightly runs, repair templates, then enforce. The documented dry-run checks existing Pods; audit catches workloads not currently running. (`docs/tasks/configure-pod-container/migrate-from-psp.md`, lines 247–280.)
   - Test duplicate execution, retry exhaustion, deadline termination, configuration changes and memory-pressure recovery before enabling cleanup.

   Application or cluster validation must establish at least four limits: duplicate-safe report output, actual configuration reload behavior, interactive scheduling latency under eligible-node constraints, and recovery after immediate eviction. The documents establish none of those application outcomes; their relevant boundaries are documented in `cron-jobs.md`, lines 213–240; `configmap.md`, lines 191–208; `pod-priority-preemption.md`, lines 185–238; and `node-pressure-eviction.md`, lines 26–36, under the paths cited above.
