Approve the design conditionally: it needs explicit scheduling, retry, security, and configuration policies. Resolve one architectural conflict first: excluding interactive Pods from batch nodes prevents those services from reclaiming batch capacity through preemption.

All citations below refer to files beneath the supplied local `docs/` directory. Recommendations are configuration choices; the cited behavior is documented Kubernetes v1.32 behavior.

1. **CronJob execution is approximate, not exactly once.** A schedule can produce two Jobs or none, so reports must be idempotent. `concurrencyPolicy: Allow` permits overlap; `Forbid` skips an occurrence while the previous Job runs; `Replace` replaces the running Job. These policies apply only within the same CronJob. `startingDeadlineSeconds` bounds lateness in creating a Job, independently of its runtime. More than 100 missed schedules prevents startup; setting a deadline changes the counting window to that deadline. Forbid-induced skips count as missed schedules, and deadlines below ten seconds may prevent scheduling. Set `.spec.timeZone`, preferably `Etc/UTC`; otherwise the controller manager’s local timezone applies. Sources: `concepts/workloads/controllers/cron-jobs.md:100–143,176–188,211–244`.

2. **Bound retries and total runtime separately.** `backoffLimit` defaults to six; failed Pods are recreated with exponential delays starting at ten seconds and capped at six minutes. With `restartPolicy: Never`, failed Pods count; with `OnFailure`, container restarts in Pending or Running Pods also count. Either calculation reaching the limit fails the Job. Choose `Never` for clearer failure inspection, with retained external logs. Job-level `activeDeadlineSeconds` covers the Job across replacement Pods, terminates running Pods, and takes precedence over remaining retries. Neither limit automatically restarts a failed Job. `ttlSecondsAfterFinished` controls subsequent cleanup of Complete or Failed Jobs and dependent Pods; it does not bound runtime. Sources: `concepts/workloads/controllers/job.md:358–382,615–663,737–793`.

3. **Combine exclusion with required placement.** Taint batch nodes, for example `dedicated=batch:NoSchedule`, and give batch Pods matching tolerations. Add a batch-node label and required node affinity to those Pods. Tolerations permit placement but do not require it; required affinity supplies that constraint. Preferred affinity is insufficient. `NoSchedule` blocks new intolerant Pods without removing existing ones. `NoExecute` also evicts existing intolerant Pods; matching tolerations can permit indefinite residence or specify `tolerationSeconds`. Required affinity ignores later label changes during execution. These mechanisms require controlled configuration: manually setting `nodeName` bypasses scheduler handling of `NoSchedule`, so a taint alone does not establish tenant-proof isolation. Sources: `concepts/scheduling-eviction/taint-and-toleration.md:29–150,176–191`; `concepts/scheduling-eviction/assign-pod-node.md:95–155`.

4. **Give interactive services higher priority, but preserve feasible placement.** Create cluster-scoped PriorityClasses and select them through `priorityClassName`; larger values mean higher priority. Choose low-priority, non-preempting batch Pods with `preemptionPolicy: Never`, and allow interactive Pods to use `PreemptLowerPriority`. `Never` prevents initiating preemption, not becoming a victim. Preemption helps only where removing lower-priority Pods makes the incoming Pod schedulable. Thus, strict exclusion of every non-batch Pod conflicts with reclaiming batch nodes for interactive services: either permit designated interactive services there or accept separate capacity pools. Victims receive their graceful termination period, delaying replacement. PDB compliance is best effort and can be violated. Sources: `concepts/scheduling-eviction/pod-priority-preemption.md:51–76,103–147,165–238`.

5. **Quota governs admission, not guaranteed capacity.** Declare explicit CPU and memory requests and limits in templates, matching the quota keys; alternatively configure and verify LimitRange defaults. `cpu` and `memory` quota keys mean aggregate requests, while `limits.cpu` and `limits.memory` constrain aggregate limits across non-terminal Pods. Missing required declarations can cause rejection. A creation or update exceeding quota fails with HTTP `403 Forbidden`; the proposed Pod is not merely admitted to wait for quota. Quota changes do not affect already-created resources, including running Pods. Quotas also do not eliminate contention when their totals exceed cluster capacity. Verify ResourceQuota admission is enabled. Source: `concepts/policy/resource-quotas.md:15–105`.

6. **Choose configuration consistency deliberately.** Ordinary ConfigMap volumes eventually receive updated projected keys. Delay can reach the kubelet sync period plus cache propagation delay; watch is the default strategy, with TTL caching and direct requests also configurable. The documents establish file projection, not application rereading or atomic adoption of an entire report configuration. A `subPath` mount receives no updates. Environment variables require Pod restart to change. An immutable ConfigMap cannot have its data changed or its immutability reversed; it must be deleted and recreated, and recreating consuming Pods is recommended. For reproducible nightly reports, choose versioned immutable configuration and explicitly select a version per run. Source: `concepts/configuration/configmap.md:191–209,299–328`.

7. **Memory-pressure eviction is not simply “lowest priority first.”** After node-level reclamation fails, kubelet ranks Pods first by whether usage exceeds requests, then priority, then usage relative to requests. BestEffort and Burstable Pods exceeding requests are evicted first; Guaranteed and Burstable Pods below requests are last. QoS is an estimate of ordering, not the ranking input itself. Even these last-resort Pods may be evicted when system daemons exceed reservations. Node-pressure eviction ignores PDBs and Pod `terminationGracePeriodSeconds`: soft thresholds use configured `eviction-max-pod-grace-period`, while hard thresholds use zero seconds. Low batch priority therefore does not guarantee the intended memory-pressure victim order without appropriate requests. Source: `concepts/scheduling-eviction/node-pressure-eviction.md:2–36,318–362`.

8. **Restricted requires compliant Pods and active admission enforcement.** Configure namespace `pod-security.kubernetes.io/enforce=restricted` and pin `enforce-version=v1.32`; verify PodSecurity admission and any exemptions. Restricted includes all Baseline controls, restricts volume types, requires non-root execution, and prohibits explicitly selecting UID zero. For Linux, require `allowPrivilegeEscalation: false`, an explicit `RuntimeDefault` or `Localhost` seccomp profile, and dropping `ALL` capabilities, with only `NET_BIND_SERVICE` optionally restored. Applicable checks cover regular, init, and ephemeral containers. Windows has documented exceptions. Enforce rejects violating Pod creation; audit records violations without blocking; warn returns warnings without blocking. The standard’s existence does not establish image compatibility or effective cluster configuration. Sources: `concepts/security/pod-security-standards.md:299–470,495–504`; `reference/labels-annotations-taints/_index.md:2370–2465`; `reference/access-authn-authz/admission-controllers.md:119–131`; `tasks/configure-pod-container/migrate-from-psp.md:247–272`.

9. **Disable unnecessary token automounting explicitly.** With ServiceAccount admission active, Pods normally receive an API-access token volume; an omitted service account becomes `default`. Set `automountServiceAccountToken: false` on the team ServiceAccount and in batch Pod templates. A Pod-level value takes precedence over the ServiceAccount value, so the account setting alone does not enforce the platform’s intent against overrides. File-based ConfigMap consumers should not receive credentials merely to read their mounted settings. This setting establishes an automount opt-out; it does not establish that no credential was supplied through another mechanism. Sources: `tasks/configure-pod-container/configure-service-account.md:67–100`; `reference/access-authn-authz/service-accounts-admin.md:396–421`.

10. **Roll out in this priority order.** First resolve the capacity-pool conflict, inventory admission configuration and exemptions, and dry-run Restricted against existing workloads. Enable audit/warn, repair templates, then enforce Restricted on existing and newly created namespaces. Second, establish node labels, taints, required affinity, PriorityClasses, requests, limits, quotas, and token opt-outs. Third, configure CronJob concurrency, timezone, lateness, Job deadlines, retry limits, cleanup retention, and configuration versioning. Finally, exercise duplicate execution, controller outages, quota exhaustion, Pod failure, preemption, memory pressure, and ConfigMap changes.

    Acceptance requires application or cluster validation of at least: report idempotency and checkpoint recovery; actual configuration reload behavior; acceptable interactive-service scheduling delay; and realistic memory requests, reservations, and eviction settings. None is guaranteed by the documented API fields.
