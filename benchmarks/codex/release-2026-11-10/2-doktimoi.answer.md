1. **PDB and rollout availability.** A PDB cannot prevent involuntary node failures; those losses merely count against its budget. During a drain using the Eviction API, a correctly selected `minAvailable: 5` budget permits one healthy replica’s eviction from six, then blocks further budget-breaking evictions. This is conditional protection: direct deletion bypasses it, and concurrent failures remain possible. Deployment rolling updates are not constrained by PDBs, although their unavailable Pods count against the budget. Thus, `maxUnavailable: 2` permits rollout availability to fall to four. Recommend `maxUnavailable: 0`, `maxSurge: 1`, with capacity for the surge and terminating Pods; `maxUnavailable: 1` is the less conservative compatible choice. Neither protects against simultaneous failures.  
   Sources: `concepts/workloads/pods/disruptions.md:92–145`; `concepts/workloads/controllers/deployment.md:1189–1212,327–332`.

2. **Zone placement.** Configure a Deployment Pod-template spread constraint selecting this API’s Pods, with `topologyKey: topology.kubernetes.io/zone` and `maxSkew: 1`. The key groups nodes into zones. With `DoNotSchedule`, skew limits the difference between the target domain’s matching-Pod count and the global minimum across eligible domains; violating placements remain pending. `ScheduleAnyway` instead prefers reduced skew without enforcing that limit. Six Pods can achieve 2/2/2 when capacity and eligibility permit.

   An unavailable zone does not imply automatic safe redistribution. Outcomes depend on remaining eligible domains, labels, taints, and capacity. With `minDomains: 3`, fewer eligible domains make the global minimum zero, potentially blocking replacement placement. Without it, the default is one. Choose strict spreading versus scheduling flexibility explicitly. Losing a two-replica zone initially leaves four, and constraints do not guarantee continued balance after removals.  
   Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:76–126,550–560,605–623`.

3. **Slow-starting probes.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Readiness and liveness probes—and their configured delays—begin only after startup succeeds. Readiness should report ability to accept API work; a failed readiness check removes the Pod from Service load balancing while its container continues running. Liveness should detect an unrecoverable condition such as deadlock, rather than indiscriminately restart containers during a database outage. Startup or liveness failure at the configured threshold triggers container termination/restart, subject to restart policy. These mechanisms do not establish that the chosen health endpoint accurately represents application health.  
   Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:16–41,311–347,398–421`.

4. **Termination and long requests.** The grace-period countdown begins **before** `preStop`; the hook consumes that budget. The kubelet runs the hook before asking the runtime to send TERM to container process 1. A still-running hook can receive a one-off two-second extension. At grace expiry, remaining processes receive SIGKILL. Endpoint updates proceed concurrently: terminating endpoints remain represented temporarily, with `ready: false` for regular traffic; `serving` supports consumers implementing draining.

   Thirty seconds is a default, not a request-completion guarantee. Configure a measured budget covering hook execution and application shutdown, implement signal handling and connection draining, and test actual traffic-path behavior.  
   Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:992–1012`; `concepts/workloads/pods/pod-lifecycle.md:584–640`.

5. **Resources and utilization-based HPA.** CPU requests inform scheduling and provide the denominator for CPU utilization. Requests are not usage ceilings: containers may consume additional available resources. CPU limits enforce throttling; memory limits are enforced reactively through OOM kills, rather than analogous throttling or guaranteed immediate termination at the limit. Choose requests and limits from measurements, including startup and database-wait workloads.

   If relevant CPU requests are absent from some containers, Pod CPU utilization is undefined and HPA takes no action for that metric. Explicitly configure requests for all relevant containers; note that a limit can become the request when no request or admission default exists.  
   Sources: `concepts/configuration/manage-resources-containers.md:15–67`; `tasks/run-application/horizontal-pod-autoscale.md:87–102`.

6. **HPA’s conservative adjustments.** The basic calculation is the ceiling of current replicas multiplied by current/desired metric value. HPA sets aside missing metrics and qualifying not-yet-ready CPU observations. Missing metrics are conservatively treated as 100% of target during downscale and 0% during upscale; not-yet-ready Pods further dampen prospective upscale through a 0% assumption. If recalculation reverses direction or falls within tolerance, scaling stops. Default tolerance is 10%; readiness-delay and CPU-initialization windows default to 30 seconds and five minutes.

   Downscale stabilization defaults to five minutes and selects the highest recommendation within that window. Consequently, actual scaling can differ from the raw ratio and displayed utilization. A functioning resource metrics API, commonly supplied by separately installed Metrics Server, is prerequisite.  
   Sources: `tasks/run-application/horizontal-pod-autoscale.md:113–118,129–218`.

7. **Least-privilege networking.** Start with default-deny ingress and egress, then allow approved callers to the API port, API egress to the database port, corresponding database ingress, and necessary DNS queries to the cluster’s resolver. Determine actual selectors, destinations, and DNS ports from the cluster.

   Ingress and egress isolation are independent. Policies combine additively: a broad allow policy cannot be overridden by adding a deny policy. A Pod-to-Pod connection requires both source egress and destination ingress permission; reply traffic is implicitly allowed. Node-traffic exceptions mean isolation is not absolute. A NetworkPolicy-capable CNI/controller is essential—creating policy objects without enforcement has no effect.  
   Sources: `concepts/services-networking/network-policies.md:20–81`; `concepts/security/multi-tenancy.md:208–234`.

8. **Secret protection.** Base64 is reversible encoding, not sufficient confidentiality; reject base64-only credentials in Git. The documentation demonstrates decoding and describes encoded credentials as obscured rather than secret. Kubernetes Secrets are stored unencrypted in etcd by default. Enable encryption at rest, protect its keys, verify stored ciphertext, and apply least-privilege RBAC and container access.

   Restrict Pod and Deployment creation permissions too: someone authorized to create Pods in a namespace can use them to read that namespace’s Secrets. Encryption at rest does not repair repository exposure or prevent authorized API retrieval.  
   Sources: `concepts/configuration/secret.md:35–48,286–306`; `tasks/administer-cluster/encrypt-data.md:347–364,534–588`.

9. **Storage lifecycle.** Changing a StorageClass reclaim setting does not retroactively change existing PVs’ policies; inspect and patch those PVs individually. Dynamically provisioned PVs inherit their class’s policy, defaulting to `Delete`. With supporting plugins, `Delete` removes the PV and backing storage. `Retain` leaves storage and a released PV after PVC deletion, requiring manual reclamation.

   PVC deletion is distinct from StatefulSet deletion or scale-down. StatefulSet template PVCs are retained by default; `persistentVolumeClaimRetentionPolicy.whenDeleted` and `whenScaled` can independently request deletion, requiring the documented feature gate. These settings govern PVC lifecycle; the PV reclaim policy then governs storage reclamation. Recommend explicit retention choices for database storage.  
   Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:185–210`; `concepts/workloads/controllers/statefulset.md:387–425`.

Second, configure probes, measured resource requests, graceful shutdown, compatible rollout settings, and deliberate zone constraints. Third, validate metrics availability and HPA behavior under startup spikes and missing metrics. Finally, stage a rollout, drain, node/zone outage, longest-request termination, denied-network test, and storage recovery exercise before promotion.

Also verify CNI enforcement and whether CPU utilization predicts this API’s capacity needs. These are validation obligations derived from the documented mechanisms, not promised outcomes.
