**Decision memo: revise before production approval.** The proposed settings do not establish five-replica availability, safe request draining, or database durability. The following recommendations distinguish Kubernetes behavior from configuration choices and validation requirements. Citations reference paths relative to the supplied corpus directory.

1. **PDB and rollout availability.** `minAvailable: 5` cannot prevent node failures; involuntary disruptions count against the budget but are not blocked. During an Eviction-API-based node drain, the PDB limits voluntary evictions: with six healthy replicas, one can be evicted before further evictions must wait. Direct deletion bypasses that protection. Deployment rolling updates are not constrained by PDBs, although their unavailable Pods count against the budget. Consequently, `maxUnavailable: 2` permits four available replicas. Recommend `maxUnavailable: 1`, `maxSurge: 1`, with capacity for the surge; alternatively, zero unavailable provides a stricter rollout policy. Neither configuration prevents concurrent failures. Keep the HPA minimum at six if preserving this operating baseline is required.  
   Sources: `docs/concepts/workloads/pods/disruptions.md:99–136`; `docs/concepts/workloads/controllers/deployment.md:1189–1211`.

2. **Zone placement.** Configure an API label selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, targeting two replicas per zone. The key groups nodes with identical label values into domains. With `DoNotSchedule`, skew limits the difference between the target domain’s matching-Pod count and the global minimum; violating placements remain pending. `ScheduleAnyway` instead prefers placements reducing skew, allowing imbalance. Choose strict placement if distribution outweighs immediate replacement capacity, or soft placement if outage recovery takes priority. With strict `minDomains: 3`, fewer than three eligible domains makes the global minimum zero, potentially blocking replacements in surviving zones. Actual outage behavior depends on eligible nodes, taints, labels, and capacity. Constraints do not guarantee continued balance after removals.  
   Sources: `docs/concepts/scheduling-eviction/topology-spread-constraints.md:82–128,527–529,605–619`.

3. **Slow-start probes.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. An HTTP health endpoint is suitable if it meaningfully detects application startup. Startup success enables readiness and liveness probes; until then, both are disabled. Readiness should indicate ability to serve requests, including required dependencies where appropriate. Its failure removes the Pod from matching Service endpoints without itself restarting the container. Liveness should detect conditions requiring restart, such as deadlock; avoid making a temporary database outage automatically imply that restarting helps. Startup or liveness failure reaching the configured threshold causes termination and restart according to restart policy. Endpoint removal does not establish instantaneous cessation of all traffic or completion of existing requests.  
   Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–347`; `docs/concepts/workloads/pods/pod-lifecycle.md:479–497,512–526`.

4. **Termination and long requests.** The grace-period countdown begins **before** `preStop`; the hook consumes the same budget as application shutdown. The kubelet runs the hook before requesting TERM delivery to the container’s main process. An overlong hook can receive a one-off two-second extension; remaining processes receive SIGKILL when graceful termination expires. Endpoint updates occur alongside local shutdown, rather than forming a guaranteed serial handoff. Terminating EndpointSlice entries are not immediately removed, but have `ready: false`; consumers needing drain status can inspect `serving`. Thirty seconds is therefore a deadline, not a guarantee that requests finish. Configure signal handling and draining, then size grace time for hook execution and measured request completion.  
   Sources: `docs/reference/kubernetes-api/workload-resources/pod-v1.md:1008`; `docs/concepts/workloads/pods/pod-lifecycle.md:591–639`.

5. **Resource sizing and HPA prerequisites.** CPU requests inform scheduling and provide the denominator for utilization-based HPA; they are not CPU ceilings. Containers can exceed requests when resources are available. CPU limits impose throttling, potentially slowing initialization and requests. Memory limits behave differently: enforcement is reactive through OOM killing, and exceeding the limit need not produce immediate termination. Set measured requests for every relevant container, including sidecars, and choose limits through load testing. If relevant CPU requests are absent, Pod CPU utilization is undefined and HPA does not act on that metric. Inspect effective admitted configuration: absent explicit requests may be defaulted, including copying a supplied limit.  
   Sources: `docs/concepts/configuration/manage-resources-containers.md:18–53,64–66`; `docs/tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **HPA’s conservative decisions.** The basic calculation is the ceiling of current replicas multiplied by current-to-target metric ratio, with default tolerance 0.1. HPA sets aside missing metrics and qualifying not-yet-ready CPU samples. Missing metrics are assumed to equal 100% of target during downscale and 0% during upscale, damping either change. Not-yet-ready Pods additionally count as 0% during a potential upscale. If recalculation reverses direction or enters tolerance, scaling stops. Readiness handling uses configurable defaults of 30 seconds for initial readiness delay and five minutes for CPU initialization. Downscale stabilization defaults to five minutes and selects the highest recommendation in that window. Reported utilization excludes these conservative adjustments, explaining apparent disagreement between status and scaling.  
   Source: `docs/tasks/run-application/horizontal-pod-autoscale.md:131–202,213–218`.

7. **Least-privilege networking.** Apply default-deny ingress and egress, then allow identified clients to the API port, API egress to the database port, and matching database ingress from API Pods. Add necessary DNS egress to the actual cluster resolver; the documented DNS Service exposes UDP and TCP port 53. Explicitly identify any additional dependencies. Isolation is independent by direction and begins when a selecting policy includes that direction. Policies combine additively: a broad allow policy undermines narrower rules, regardless of ordering. Both source egress and destination ingress must permit a connection; response traffic is implicitly allowed. NetworkPolicy requires a supporting network plugin—creating objects alone provides no enforcement. Validate actual resolver paths and allowed/denied connections.  
   Sources: `docs/concepts/services-networking/network-policies.md:45–81,210–259`; `docs/tasks/administer-cluster/dns-debugging-resolution.md:158–173`.

8. **Secret protection.** Reject base64-only Secrets in Git: the documentation explicitly describes base64 values as obscured, not secret. Enable Secret encryption at rest; the documented default is unencrypted storage in etcd. Apply least-privilege RBAC and expose Secrets only to containers needing them. Review workload-creation permissions as carefully as direct Secret-read permissions: someone authorized to create Pods in a namespace can read its Secrets through those Pods, including indirectly through Deployment creation. Encryption at rest addresses stored cluster data; it does not make a Git copy confidential or remove authorized workload access. Repository credential handling therefore needs a separate controlled process.  
   Source: `docs/concepts/configuration/secret.md:35–48,286–306`.

9. **Storage lifecycle.** Changing a StorageClass reclaim policy does not retrofit existing PVs: inspect and edit their own reclaim policies. Dynamically provisioned PVs inherit the class policy, defaulting to `Delete`. `Retain` leaves a released PV and its data for manual reclamation after PVC deletion. With supporting plugins, `Delete` removes both the PV and backing storage. In-use protection delays PVC deletion; it does not establish indefinite retention. StatefulSet deletion or scale-down normally retains claims. Its separate PVC retention policy can select `Delete` for `whenDeleted` or `whenScaled`, after Pod deletion; the documented prerequisite is enabling the corresponding feature gate. Claim deletion then exposes storage to the PV’s reclaim policy.  
   Sources: `docs/concepts/storage/storage-classes.md:126–135`; `docs/concepts/storage/persistent-volumes.md:123–136,178–210`; `docs/concepts/workloads/controllers/statefulset.md:391–423`.

10. **Prioritized rollout and validation checklist.** First, remove base64-only credential handling, establish encryption/RBAC, and explicitly select database PV retention. Second, verify network-policy enforcement and test DNS, API, and database allow rules plus negative cases. Third, deploy measured resource requests, startup/readiness/liveness probes, and graceful shutdown; align rollout availability and HPA bounds. Finally, exercise rolling updates, node drains, zone loss, metric outages, and long requests under load before promotion.

    Acceptance must validate at least these undocumented application-specific limits: worst-case startup duration, request-drain completion time, and CPU saturation’s relationship to latency. Also validate surviving-zone capacity, database recovery and storage accessibility, and actual network enforcement. The documents describe mechanisms, not this application’s latency, recovery time, or durability guarantees.
