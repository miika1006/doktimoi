Revise the design before production approval. Kubernetes v1.32 documents useful controls, but they do not establish that this application will preserve five serving replicas, finish long requests, or recover its database safely. Recommendations below are configuration choices; application and cluster behavior still require validation. Source paths are relative to the supplied `docs/` directory.

1. **PDB and rollout availability.** `minAvailable: 5` cannot prevent involuntary node failures; those losses nevertheless consume the disruption budget. During an Eviction API based node drain, the PDB constrains permitted evictions: with six healthy replicas, one can be disrupted before further evictions must wait. This depends on correct selectors and maintenance tools respecting eviction; direct Pod deletion bypasses PDBs. Deployment rolling updates also bypass PDB enforcement, although their unavailable Pods count against the budget. Thus `maxUnavailable: 2` permits the update to reduce availability to four. Recommend `RollingUpdate`, `maxUnavailable: 1`, and `maxSurge: 1`, with spare scheduling capacity. This aligns update behavior with a five-replica floor at desired scale six; it does not protect against simultaneous failures.  
   Sources: `concepts/workloads/pods/disruptions.md:99–145`; `concepts/workloads/controllers/deployment.md:1183–1211`.

2. **Zone placement.** Configure topology spread using the API’s labels, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`. The topology key groups equally labeled nodes into domains. With `DoNotSchedule`, skew limits the difference between matching Pods in the target domain and the global minimum; `ScheduleAnyway` instead prefers placements reducing skew without enforcing that bound. Six replicas can consequently achieve two per zone when capacity and eligibility permit. Recommend strict spreading initially, with an explicit outage policy. If a failed zone remains counted, strict constraints can block replacements. If it ceases to be eligible, remaining domains can accept replacements under the default `minDomains: 1`; specifying `minDomains: 3` instead makes the global minimum zero when fewer than three domains qualify, potentially blocking recovery. Neither option guarantees five survivors: losing two replicas leaves four. Removal also does not guarantee continued balance.  
   Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:82–130,167–185,605–619`.

3. **Slow-start probes.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case startup. Use readiness to test whether the API can serve useful requests, including necessary database availability; use liveness for conditions a restart can resolve, such as deadlock. Those endpoint semantics are application choices. Startup suppresses both other probes until success; their configured initial delays then begin. Repeated startup or liveness failure triggers container restart according to restart policy. Readiness failure keeps the container running but marks it unready and removes it from matching Service endpoints. Probe periods and thresholds mean failure detection is not instantaneous.  
   Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:315–367,398–422`; `concepts/workloads/pods/pod-lifecycle.md:479–497`.

4. **Termination and long requests.** Graceful deletion establishes the termination deadline before the kubelet runs `preStop`; the hook consumes the grace period rather than receiving a separate allowance. The kubelet runs `preStop` before requesting TERM, normally SIGTERM, for the container’s main process. Remaining processes receive SIGKILL after grace expires; an unfinished hook can receive a small, one-off two-second extension. Endpoint processing occurs concurrently with local shutdown. Terminating EndpointSlice endpoints are not immediately removed, but have `ready: false`; `serving` supports draining decisions. Thirty seconds is therefore a shutdown budget, **not a request-completion guarantee**. Implement signal handling and connection draining, then size grace for measured hook time and outstanding-request completion.  
   Source: `concepts/workloads/pods/pod-lifecycle.md:572–639`.

5. **Resource settings and CPU HPA.** Set measured CPU requests for every relevant container. Requests guide scheduling and CPU allocation under contention; they are not a maximum. Containers may use spare resources above requests. CPU limits impose throttling, whereas memory limits can cause reactive OOM termination rather than throttling or an immediate kill at every overshoot. CPU utilization HPA measures usage relative to requests. If relevant requests are missing from some containers, Pod CPU utilization is undefined and HPA cannot act on that metric. Inspect admitted Pods: when a limit exists without a request or admission default, Kubernetes copies the limit into the request.  
   Sources: `concepts/configuration/manage-resources-containers.md:18–23,29–66,252–265`; `tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **HPA’s conservative decisions.** The raw formula is the ceiling of current replicas multiplied by current/desired metric value. HPA excludes terminating and failed Pods, sets aside missing metrics, and handles not-yet-ready CPU samples specially. Missing samples are conservatively assumed to consume 100% of target during downscale and 0% during upscale; not-yet-ready Pods also dampen a prospective upscale using 0%. If recomputation reverses direction or falls within tolerance, scaling is skipped. Default tolerance is 10%; readiness classification uses configurable windows defaulting to 30 seconds and five minutes. Downscale stabilization defaults to five minutes and selects the highest recommendation in that window. Consequently, displayed average utilization and the raw ratio may not explain the final replica count.  
   Source: `tasks/run-application/horizontal-pod-autoscale.md:129–218`.

7. **Least-privilege networking.** Replace default allow with policies selecting all relevant Pods and explicitly isolating both ingress and egress. Add narrowly scoped allowances for approved callers to API ports, API egress to database destinations and ports, database ingress from API Pods, and DNS queries to the actual cluster resolver. Ingress and egress isolation are independent. Policies combine additively: an existing broad allow defeats a narrower restriction. For a Pod-to-Pod connection, source egress and destination ingress must both permit it; replies to permitted connections are implicitly allowed. Prerequisite: the installed networking implementation must enforce NetworkPolicy—creating the objects alone has no effect. Validate actual selectors, resolver placement, and packet paths.  
   Sources: `concepts/services-networking/network-policies.md:45–81,254–262`; `concepts/security/multi-tenancy.md:215–233`.

8. **Secrets and Git.** Base64 is encoding, not sufficient confidentiality protection. Reject base64 credentials committed to Git and use a controlled secret-delivery workflow. Kubernetes requires base64 strings in Secret `data`, but explicitly describes encoded credentials as obscured rather than secret. Secrets are unencrypted in etcd by default: enable encryption at rest, configure least-privilege RBAC, and expose credentials only to containers needing them. Restrict workload creation as well as direct Secret reads: someone allowed to create a Pod—or indirectly a Deployment—in a namespace can use that ability to read its Secrets. At-rest encryption does not protect a separate Git copy.  
   Source: `concepts/configuration/secret.md:35–48,305–307,453–457`.

9. **Storage lifecycle.** StorageClass reclaim policy is inherited when dynamic PVs are created; changing the class does not retrofit existing PV policies. Inspect and edit or patch existing PVs separately. After PVC deletion, `Retain` leaves the PV released with data requiring manual reclamation. For supporting plugins, `Delete` removes both PV and backing storage; it is the StorageClass default. StatefulSet deletion or scale-down is a separate decision: claim retention defaults to `Retain`. Configured `whenDeleted` and `whenScaled` policies can delete template-created PVCs, after which PV reclaim behavior applies. Verify the documented feature-gate prerequisites. Dynamic provisioning alone establishes neither database replication nor recoverability.  
   Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:178–210`; `concepts/workloads/controllers/statefulset.md:391–423`.

10. **Prioritized rollout and validation checklist.** First, remove repository credential exposure, verify encryption/RBAC, and inventory existing PV reclaim and StatefulSet retention policies before destructive maintenance. Second, validate NetworkPolicy enforcement and required DNS/database connectivity. Third, establish requests, working metrics collection, probes, termination handling, spread constraints, and the revised rollout settings; keep HPA’s minimum at six if this availability design assumes six. Finally, rehearse an update, eviction-based drain, zone outage, metric loss, and database recovery under representative load. Approval requires measured startup bounds, long-request drain completion, surviving-zone capacity, CPU/load correlation, and database restore/failover behavior. These are application or cluster validation limits, not guarantees supplied by these documents.  
   Sources: `concepts/configuration/secret.md:35–48`; `concepts/services-networking/network-policies.md:45–81`; `tasks/run-application/horizontal-pod-autoscale.md:113–118,153–218`; `concepts/workloads/pods/disruptions.md:195–232`; `concepts/workloads/pods/pod-lifecycle.md:619–639`; `concepts/storage/persistent-volumes.md:178–210`.
