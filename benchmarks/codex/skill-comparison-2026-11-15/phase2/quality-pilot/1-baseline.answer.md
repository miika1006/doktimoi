Decision: revise before production approval. The proposed settings do not establish five available replicas through failures or safe completion of long requests. The recommendations below are configuration choices; the cited guarantees apply only within their documented scope. All paths are relative to the supplied documentation corpus.

1. **PDB, failures, drains, and updates.** `minAvailable: 5` cannot prevent a node failure from taking availability below five: involuntary disruptions count against the budget but cannot be prevented. During an eviction-based node drain, the PDB constrains voluntary disruptions; with six healthy matching Pods, one eviction can proceed, while subsequent evictions may wait for recovery. This requires tools that respect the Eviction API. Deployment rolling updates are not constrained by PDBs, although their unavailable Pods count against the budget ([disruptions.md](docs/concepts/workloads/pods/disruptions.md), lines 99–136).

   `maxUnavailable: 2` permits rollout availability to fall to four. Recommend `maxUnavailable: 1`, `maxSurge: 1`, with capacity for the surge; this aligns the rollout’s configured floor with five, without guaranteeing survival of concurrent failures ([deployment.md](docs/concepts/workloads/controllers/deployment.md), lines 1185–1211).

2. **Zone placement.** Configure a workload-matching topology spread selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`; aim for two replicas per zone. `topologyKey` groups nodes by label value. With `DoNotSchedule`, skew limits the difference between the target domain’s matching Pod count and the global minimum. `ScheduleAnyway` instead prefers placements reducing skew while allowing imbalance ([topology-spread-constraints.md](docs/concepts/scheduling-eviction/topology-spread-constraints.md), lines 82–128).

   Choose `ScheduleAnyway` if replacement capacity in surviving zones takes priority over strict balance. Strict placement can leave replacements pending. In particular, `minDomains: 3` with fewer than three eligible domains makes the global minimum zero. Failure behavior depends on domain eligibility and remaining capacity; scheduling cannot restore a failed zone. Domains are discovered from existing nodes, and Pod removal does not guarantee preserved balance (same document, lines 107–126, 605–619). Losing two evenly spread replicas leaves four, regardless of the PDB.

3. **Probes for slow startup.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. After startup succeeds, use readiness to report ability to serve, including required dependency availability, and liveness to detect an application condition requiring restart. Avoid treating a temporary database outage as automatic evidence that restarting helps.

   Startup suppresses both other probes until success. Startup or liveness failure triggers container killing and the restart policy; readiness failure removes the Pod from matching Service endpoints without that restart action ([pod-lifecycle.md](docs/concepts/workloads/pods/pod-lifecycle.md), lines 479–497). The startup budget and temporary dependency/readiness distinction are documented in [configure-liveness-readiness-startup-probes.md](docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md), lines 311–358. Endpoint changes do not establish instantaneous interruption of every existing connection.

4. **Termination and long requests.** The grace-period countdown begins **before** `preStop`, so the hook consumes the shutdown budget ([pod-v1.md](docs/reference/kubernetes-api/workload-resources/pod-v1.md), lines 1006–1008). The kubelet runs the hook, then triggers TERM to container process 1; an overlong hook gets a small one-off two-second extension. Remaining processes receive SIGKILL when grace expires ([pod-lifecycle.md](docs/concepts/workloads/pods/pod-lifecycle.md), lines 581–609, 634–639).

   Endpoint processing happens concurrently with shutdown. Terminating endpoints remain temporarily in EndpointSlices with `ready: false`; `serving` supports draining-aware consumers (same document, lines 612–632). Thirty seconds is a default budget, not a request-completion guarantee. Implement signal handling and draining, then size grace for hook execution, propagation, and measured request completion.

5. **Resource sizing and CPU HPA.** CPU requests inform scheduling and typically determine relative CPU allocation under contention; they are not usage ceilings. CPU limits impose throttling. Memory limits use reactive OOM enforcement, potentially killing a process rather than slowing it like CPU throttling ([manage-resources-containers.md](docs/concepts/configuration/manage-resources-containers.md), lines 18–53, 252–265).

   Set measured CPU requests for every relevant container. Utilization-based HPA computes usage relative to requests; missing relevant requests make Pod CPU utilization undefined and prevent action for that metric ([horizontal-pod-autoscale.md](docs/tasks/run-application/horizontal-pod-autoscale.md), lines 89–102). Check effective admitted configuration: a limit can become the request when no request or admission default exists ([manage-resources-containers.md](docs/concepts/configuration/manage-resources-containers.md), lines 63–66). Select limits through latency and memory testing.

6. **HPA’s conservative adjustments.** The basic calculation is the ceiling of current replicas multiplied by current/desired metric. HPA ignores terminating Pods, discards failed Pods, and initially sets aside missing metrics and certain not-yet-ready CPU samples. Missing samples are assumed at 100% of target for downscaling and 0% for upscaling; not-yet-ready Pods dampen upscaling using 0%. A revised ratio that reverses direction or falls within tolerance produces no scaling action ([horizontal-pod-autoscale.md](docs/tasks/run-application/horizontal-pod-autoscale.md), lines 135–197).

   Readiness handling uses configurable defaults of 30 seconds and five minutes. Downscale stabilization defaults to five minutes, selecting the highest recommendation within that window. Thus the raw ratio—and even reported average utilization—need not predict the actual replica change (same document, lines 167–218).

7. **Least-privilege networking.** Apply default-deny ingress and egress, then allow approved callers to the API port, API egress to the database port, corresponding database ingress, and necessary DNS traffic. Narrow peers using namespace and Pod selectors together where appropriate ([network-policies.md](docs/concepts/services-networking/network-policies.md), lines 144–155, 254–262).

   Ingress and egress isolation are independent. Policies combine additively: a broad allow remains effective despite another restrictive policy. Both source egress and destination ingress must permit a connection; replies to allowed connections are implicitly allowed (same document, lines 53–81). Explicitly allow the actual cluster resolver; the documented DNS example exposes UDP and TCP 53 ([dns-debugging-resolution.md](docs/tasks/administer-cluster/dns-debugging-resolution.md), lines 158–173). Enforcement requires a supporting network plugin/CNI; creating the resource alone has no effect ([network-policies.md](docs/concepts/services-networking/network-policies.md), lines 45–49).

8. **Secrets.** Reject base64-encoded credentials in Git as sufficient protection. Base64 is the serialized representation of Secret data, not an established confidentiality boundary ([secret-v1.md](docs/reference/kubernetes-api/config-and-storage-resources/secret-v1.md), lines 45–47). Recommend removing credential values from ordinary manifests and rotating exposed credentials.

   Kubernetes documents unencrypted etcd storage by default and recommends encryption at rest, least-privilege RBAC, and restricting access to specific containers. Pod creation permission also matters: someone authorized to create Pods, including indirectly through Deployments, can read Secrets in that namespace ([secret.md](docs/concepts/configuration/secret.md), lines 35–48). Encryption at rest does not protect a readable Git copy.

9. **Storage lifecycle.** Changing a StorageClass reclaim policy does not retroactively change existing PV policies. Dynamically provisioned PVs inherit the class policy; existing PVs requiring another policy must themselves be edited or patched. The class default is `Delete` ([storage-classes.md](docs/concepts/storage/storage-classes.md), lines 126–135; [persistent-volumes.md](docs/concepts/storage/persistent-volumes.md), lines 203–210).

   After PVC deletion, `Retain` leaves the released PV and data requiring manual reclamation. Supported `Delete` implementations remove both PV and backing storage ([persistent-volumes.md](docs/concepts/storage/persistent-volumes.md), lines 180–210). StatefulSet deletion/scaling retains PVCs by default; optional `whenDeleted` and `whenScaled` policies can delete generated claims, subsequently exposing their PV reclaim behavior ([statefulset.md](docs/concepts/workloads/controllers/statefulset.md), lines 391–423). Dynamic provisioning alone establishes neither database replication nor cross-zone recovery.

10. **Prioritized rollout and validation checklist.** First secure credentials and verify encryption/RBAC; establish enforcing network policies and test permitted and denied connections. Second inspect existing PV reclaim policies, explicitly retain database claims, and test recovery. For topology-constrained storage, evaluate supported `WaitForFirstConsumer` provisioning ([storage-classes.md](docs/concepts/storage/storage-classes.md), lines 171–195).

    Third configure probes, measured resource requests, draining, zone placement, and the compatible rollout. Keep HPA’s minimum at six if six is the operating baseline; verify the resource metrics API prerequisite ([horizontal-pod-autoscaler-v2.md](docs/reference/kubernetes-api/workload-resources/horizontal-pod-autoscaler-v2.md), lines 86–88; [horizontal-pod-autoscale.md](docs/tasks/run-application/horizontal-pod-autoscale.md), lines 350–361).

    Finally rehearse slow startup, long-request termination, drain, rollout, missing metrics, and zone loss. Application startup bounds, request-draining correctness, surviving-zone capacity, CNI enforcement, and database recovery time remain validation requirements—not guarantees supplied by these fields or documents.
