**Decision memo — revise before production approval**

The proposed settings do not establish five-replica availability, completed long requests, effective isolation, or database durability. Approve deployment only after the configuration changes and validation below. Citations refer to paths relative to the supplied `docs/` directory; ranges are original source lines.

1. **PDB protection depends on the disruption.** Node failure is involuntary: a PDB cannot prevent it, although unavailable Pods count against the budget. During an eviction-based node drain, `minAvailable: 5` permits one disruption when all six Pods are healthy; subsequent evictions can be rejected until availability recovers. This depends on maintenance tools respecting the Eviction API. Deployment rolling updates bypass PDB enforcement, although their unavailable Pods count against the budget. Thus, `maxUnavailable: 2` permits rollout availability to fall to four. Recommend `maxUnavailable: 0`, `maxSurge: 1`, with capacity for the additional Pod; `maxUnavailable: 1` is compatible with a five-replica rollout floor but leaves less margin. Neither configuration prevents independent failures. Sources: `concepts/workloads/pods/disruptions.md:92–145`; `concepts/workloads/controllers/deployment.md:1184–1212`.

2. **Spread across zones explicitly.** Use a matching application `labelSelector`, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, with verified node labels. Under `DoNotSchedule`, skew bounds the target domain’s matching-Pod count relative to the global minimum; unsatisfiable placements remain pending. `ScheduleAnyway` instead prefers placements reducing skew and allows violations. Choose hard spreading for normal operation, while explicitly deciding outage behavior. If a failed zone remains eligible, its low count can block replacements elsewhere. If it disappears from eligible domains, default `minDomains: 1` permits balancing across remaining domains. Setting `minDomains: 3` makes the global minimum zero when fewer than three eligible domains remain, potentially blocking recovery. Six evenly spread replicas also initially lose two when a zone fails. Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:76–134,167–190,606–624`.

3. **Separate startup, readiness, and liveness.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case startup. Until startup succeeds, readiness and liveness probes do not begin; their initial-delay clocks also wait. Use readiness to represent whether the API can accept requests, including necessary database functionality. Failed readiness makes the Pod unready and removes it from Service load balancers without restarting the container. Use liveness for unrecoverable process failure, such as deadlock, rather than treating every dependency outage as a restart condition. Startup or liveness failure reaching its threshold triggers container restart handling. Probe endpoints, thresholds, and dependency behavior require application testing. Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:15–48,311–347,398–429`.

4. **Thirty seconds is a deadline, not a request-completion guarantee.** The termination grace-period countdown starts before `preStop`; the hook consumes that budget. The kubelet runs the hook before asking the runtime to send TERM to container process 1. An unfinished hook can receive a one-off two-second extension. At grace expiry, remaining processes receive SIGKILL. Concurrently, Service endpoint handling marks terminating EndpointSlice endpoints `ready: false`; they are not immediately removed, and `serving` supports draining-aware consumers. Implement application shutdown that stops accepting work and completes open requests, then size the grace period for hook execution plus draining. The documents do not guarantee that 30 seconds finishes arbitrary long requests. Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:1002–1006`; `concepts/workloads/pods/pod-lifecycle.md:584–645`.

5. **Requests and limits serve different purposes.** Set explicit CPU requests for every relevant container: scheduling checks requested resources against node capacity, and utilization-based HPA measures CPU usage relative to requests. Requests are not usage ceilings; spare resources may be used. CPU limits impose throttling, which can affect request latency. Memory limits use reactive OOM enforcement: excess allocation may lead to termination when memory pressure is detected, rather than CPU-style throttling. If relevant CPU requests remain missing, Pod utilization is undefined and HPA takes no action for that metric. Note that a limit can become the request when neither an explicit request nor admission default exists. Sources: `concepts/configuration/manage-resources-containers.md:27–66,230–241`; `tasks/run-application/horizontal-pod-autoscale.md:89–103`.

6. **HPA deliberately modifies the raw ratio.** The basic recommendation is the ceiling of current replicas multiplied by current/target metric value, subject to tolerance. Missing metrics are conservatively treated as target utilization during downscale and zero during upscale. Not-yet-ready Pods are set aside for CPU calculations and can further dampen upscale through assumed zero consumption. A recalculated ratio reversing direction or falling within tolerance produces no scaling. Default readiness-related windows are 30 seconds and five minutes; these are configurable controller settings. Downscale stabilization defaults to five minutes and chooses the highest recommendation in that window. Verify the resource metrics API—usually supplied by separately installed Metrics Server—rather than assuming HPA’s existence ensures functioning metrics. Sources: `tasks/run-application/horizontal-pod-autoscale.md:112–118,128–218`.

7. **Adopt explicit least-privilege networking.** Establish default-deny ingress and egress, then allow approved callers to the API port, API egress to the database port, and required DNS access. For a Pod-hosted database, allow corresponding database ingress from API Pods. Isolation is independent by direction; both source egress and destination ingress must permit a Pod-to-Pod connection. Policies combine additively, so an existing allow-all policy defeats narrower restrictions and must be removed. Reply traffic for allowed connections is implicitly permitted. Permit DNS to the actual resolver endpoints and required protocols; the documented cluster DNS example exposes UDP and TCP port 53. A CNI/network plugin implementing NetworkPolicy is a prerequisite: creating policy objects alone has no effect. Sources: `concepts/services-networking/network-policies.md:41–85,224–252`; `tasks/administer-cluster/dns-debugging-resolution.md:158–194`.

8. **Reject base64 Secrets in Git as protection.** Base64 is reversible encoding: the documentation shows retrieving and decoding Secret data. It does not establish repository confidentiality. Keep usable credentials out of Git, enable Secret encryption at rest, configure least-privilege RBAC, and restrict which containers receive each Secret. Secrets are stored unencrypted in etcd by default; encryption must be configured and verified. Restrict Pod and Deployment creation permissions too: someone authorized to create Pods in a namespace can indirectly read its Secrets by mounting them, even without direct Secret-read permission. At-rest encryption does not make an authorized API retrieval confidential from that caller. Sources: `concepts/configuration/secret.md:34–48`; `tasks/administer-cluster/encrypt-data.md:534–588`.

9. **Storage retention is decided at multiple layers.** Dynamically provisioned PVs inherit the StorageClass reclaim policy, defaulting to `Delete`. Changing the class is not a retroactive migration of existing PV policies; inspect and explicitly patch existing PVs. After PVC deletion, `Retain` leaves the PV released with data requiring manual reclamation. For supporting plugins, `Delete` removes both the PV and backing storage asset. StatefulSet deletion or scale-down normally retains template-created PVCs, so it does not automatically trigger PV reclamation. Optional `whenDeleted` and `whenScaled` policies can delete those PVCs; verify the documented `StatefulSetAutoDeletePVC` feature-gate prerequisite. These settings do not establish database replication or recoverability. Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:185–210`; `concepts/workloads/controllers/statefulset.md:387–422`.

10. **Prioritize validation before rollout.** First remove repository credentials, verify encryption/RBAC, and test allow/deny networking including DNS. Second establish measured startup probes, resource requests, functioning metrics, and bounded shutdown behavior. Third apply the compatible rollout strategy, verify surge capacity and zone placement, then exercise node drains, rolling updates, zone loss, and HPA transitions under load. Finally inspect actual PV policies and test database recovery and PVC lifecycle behavior in a disposable environment. Explicit unresolved limits include maximum request-draining time, database availability and recoverability, CNI enforcement, and surviving-zone capacity. The documents specify mechanisms; they do not guarantee these application or cluster properties. Sources: `concepts/workloads/pods/disruptions.md:107–145`; `concepts/workloads/controllers/deployment.md:327–332`; `concepts/scheduling-eviction/topology-spread-constraints.md:606–624`; `concepts/storage/persistent-volumes.md:185–210`.
