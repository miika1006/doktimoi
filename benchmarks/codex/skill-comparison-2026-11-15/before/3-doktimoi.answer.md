**Decision memo — revise before production approval**

The proposed configuration does not establish five-replica availability or safe completion of long requests. Approve deployment only after correcting rollout controls, securing networking and credentials, and validating failure recovery. All citations below refer to source paths relative to the supplied `docs/` directory; recommendations are configuration choices, not additional Kubernetes guarantees.

1. **PDB protection depends on the disruption.** Node failure is involuntary: a PDB cannot prevent it, although unavailable Pods count against the budget. A node drain using the Eviction API respects the PDB; with six healthy replicas, `minAvailable: 5` normally permits one eviction, and subsequent evictions can wait. Direct deletion bypasses that protection. Deployment rolling updates are not constrained by PDBs, so `maxUnavailable: 2` permits availability to fall to four. Recommend `maxUnavailable: 0`, `maxSurge: 1`, with capacity for the surge; `maxUnavailable: 1` is also compatible with a five-replica rollout floor at desired replicas six. Neither protects against simultaneous failures.  
   Sources: `concepts/workloads/pods/disruptions.md:92–140`; `concepts/workloads/controllers/deployment.md:1184–1209`.

2. **Spread deliberately, with an explicit failure tradeoff.** Use an application label selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, targeting two replicas per zone. The topology key groups nodes by their label values. With `DoNotSchedule`, skew limits the target domain’s matching-Pod count relative to the global minimum; violating placements remain unscheduled. `ScheduleAnyway` instead favors placements that reduce skew without enforcing that limit. A zone outage can therefore leave replacements Pending under hard constraints. Eligibility matters: with `minDomains: 3`, fewer eligible domains makes the global minimum zero; without it, the default is one. Choose strict spreading versus recovery placement consciously. Existing distribution is not guaranteed after removals, and domains are discovered from existing nodes.  
   Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:76–132,605–623`.

3. **Give startup its own budget.** Configure a startup probe with `failureThreshold × periodSeconds` covering measured worst-case initialization. Readiness should indicate ability to serve requests; liveness should detect a condition for which restarting is useful, such as a deadlock. These endpoint semantics require application validation. While startup probing is active, readiness and liveness probes do not run; they begin after startup succeeds. Readiness failure removes the Pod from matching Service endpoints without itself restarting the container. Startup or liveness failure reaching its failure threshold causes termination and restart according to the restart policy. Thus startup tolerance need not weaken steady-state failure detection.  
   Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–347`; `concepts/workloads/pods/pod-lifecycle.md:475–499`.

4. **Thirty seconds is a shutdown budget, not a request-completion guarantee.** The grace-period countdown begins before `preStop`; the hook consumes that budget. During ordinary graceful termination, kubelet runs the hook, then asks the runtime to send TERM to container process 1. An unfinished hook can receive a one-off two-second extension. Remaining processes receive SIGKILL when grace expires. Concurrently, terminating Service endpoints are marked terminating and `ready: false`, excluding them from regular traffic; they are not immediately removed, and `serving` supports draining-aware consumers. Configure graceful application shutdown and a grace period covering measured draining and request completion. These documents do not establish a bound for this API’s requests.  
   Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:1008`; `concepts/workloads/pods/pod-lifecycle.md:584–645`.

5. **Set requests from measurements and limits deliberately.** CPU requests participate in scheduling capacity checks and provide the denominator for utilization-based HPA; they are not usage ceilings. Containers can exceed requests when resources are available. CPU limits enforce a ceiling through throttling, which can affect latency. Memory limits work differently: enforcement is reactive through OOM kills, rather than CPU-style throttling, and exceeding a limit does not necessarily cause an immediate kill. If relevant CPU requests are missing from some containers, Pod CPU utilization is undefined and HPA takes no action for that metric. Inspect effective admitted settings: absent requests can be copied from limits.  
   Sources: `concepts/configuration/manage-resources-containers.md:27–67,230–241`; `tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **Expect conservative HPA decisions.** The basic calculation is the ceiling of current replicas multiplied by current-to-target metric ratio, but missing metrics and readiness modify it. Missing-metric Pods are assumed to consume 100% of target during downscale and 0% during upscale. Not-yet-ready Pods can also be treated as consuming zero during upscale, damping expansion. A recalculated ratio that reverses direction or falls within tolerance causes no scaling. CPU readiness handling has configurable defaults of 30 seconds for initial readiness delay and five minutes for initialization. Default downscale stabilization is 300 seconds, selecting the highest recommendation within the window. Consequently, reported utilization and immediate replica changes can differ.  
   Sources: `tasks/run-application/horizontal-pod-autoscale.md:124–202,433–487`.

7. **Replace default allow with explicit connection permissions.** Select API and database Pods with default-deny ingress and egress policies, then allow approved callers to the API port, API-to-database traffic on the required port, and necessary DNS queries. Ingress and egress isolation are independent. Policies combine additively: an existing broad allow cannot be overridden by adding a deny policy. A Pod-to-Pod connection needs permission from both source egress and destination ingress; reply traffic is implicitly allowed. Preserve DNS explicitly when restricting egress. A prerequisite is a network plugin implementing NetworkPolicy—creating policy objects alone can have no effect. Validate actual selectors, paths, and enforcement.  
   Sources: `concepts/services-networking/network-policies.md:45–81,224–252`; `concepts/security/multi-tenancy.md:211–223`.

8. **Reject base64 Secrets in Git as sufficient protection.** Base64 obscures credentials but does not make them secret. Kubernetes Secrets are stored unencrypted in etcd by default. Enable encryption at rest, verify stored encryption, apply least-privilege RBAC, and expose each Secret only to required containers. Encryption at rest does not secure a separate Git copy; remove readable credentials from that workflow. Pod-creation permission also requires scrutiny: someone authorized to create Pods in a namespace can read its Secrets through those Pods, including indirectly through Deployment creation. Restricting direct Secret reads alone therefore leaves a documented access route.  
   Sources: `concepts/configuration/secret.md:34–48,306`; `tasks/administer-cluster/encrypt-data.md:534–588`.

9. **StorageClass changes do not retrofit existing PVs.** Dynamically provisioned PVs inherit the class’s reclaim policy when provisioned; inspect and patch existing PVs individually when changing retention expectations. `Delete`, the default, removes the PV and backing storage for supporting plugins. `Retain` leaves a released PV and its data after PVC deletion, requiring manual reclamation. PVC deletion is separate from deleting or scaling a StatefulSet: its default PVC-retention behavior is `Retain`. Optional `whenDeleted` and `whenScaled` policies can delete template-created PVCs, subject to the documented feature-gate prerequisite; the PV’s reclaim policy then determines storage disposition. Dynamic provisioning alone establishes neither database durability nor recovery readiness.  
   Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:185–210`; `concepts/workloads/controllers/statefulset.md:387–423`.

10. **Prioritize validation before exposure.** First secure credential delivery, verify encryption/RBAC, inspect existing PV policies, and rehearse database recovery. Second establish network isolation and test approved traffic, denied traffic, and DNS. Third measure startup, resource demand, and request draining; configure probes, requests, limits, and termination time accordingly. Fourth apply spreading and the revised rollout strategy, retaining six as the HPA minimum if six is the operating baseline. Finally exercise a rollout, Eviction-API drain, node/zone failure, and HPA behavior with missing metrics and slow-starting Pods. Observe availability and Pending replacements. Application-specific request completion, surviving-zone capacity, actual network enforcement, and database recovery remain validation requirements—not guarantees supplied by these documents.  
    Sources: `concepts/workloads/controllers/deployment.md:327–332`; `concepts/scheduling-eviction/topology-spread-constraints.md:95–124`; `concepts/workloads/pods/pod-lifecycle.md:612–645`; `tasks/run-application/horizontal-pod-autoscale.md:167–202`; `concepts/services-networking/network-policies.md:45–49`.
