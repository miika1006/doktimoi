**Decision memo: revise before production approval.** The proposed settings do not establish five available replicas, uninterrupted long requests, secure credentials, or durable database recovery. The recommendations below are configuration choices grounded in the supplied Kubernetes v1.32 documentation; their operational effectiveness still requires validation. All cited paths are relative to the supplied `docs/` directory.

1. **PDB protection differs across the three disruption cases.** During node failure, `minAvailable: 5` cannot prevent replica loss: involuntary disruptions count against the budget but are not constrained by it. During an ordinary `kubectl drain`, eviction requests respect the PDB and may be rejected and retried; with six healthy replicas, the budget ordinarily permits one unavailable replica. This depends on using the Eviction API rather than direct deletion. Deployment rolling updates are explicitly not constrained by PDBs. Consequently, `maxUnavailable: 2` permits rollout availability to fall to four. Recommend `maxUnavailable: 1`, `maxSurge: 1`, with capacity for the surge; choose zero unavailable if rollout capacity permits. These regulate rollout behavior, not simultaneous failures. Sources: `concepts/workloads/pods/disruptions.md:99–136`; `concepts/workloads/controllers/deployment.md:1189–1211`.

2. **Configure explicit zone spreading and choose the outage tradeoff.** Use an API label selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`; six successfully placed replicas across three eligible zones should produce two per zone. The topology key groups nodes by equal label values. With `DoNotSchedule`, skew limits the difference between the target domain’s count and the global minimum; violating placements remain unscheduled. `ScheduleAnyway` instead prefers placements that reduce skew. During zone unavailability, replacement placement depends on eligible domains, existing counts, taints, capacity, and `minDomains`. Setting `minDomains: 3` makes the global minimum zero when fewer than three domains qualify, potentially blocking replacements in surviving zones. Leaving it unset behaves as one. Zone loss can immediately remove two replicas; spreading cannot guarantee five survivors or automatic rebalancing after removals. Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:83–130,606–619`.

3. **Separate startup, traffic eligibility, and restart decisions.** Configure a startup probe with sufficient `failureThreshold` and `periodSeconds` for measured startup time. While it has not succeeded, readiness and liveness probes are disabled. Startup failure kills the container, followed by the restart policy. Readiness should indicate ability to serve requests, including required database availability; failure removes the Pod from matching Service endpoints without itself restarting the container. Liveness should detect an application condition that warrants restart, such as a deadlock, rather than treating every database outage as application death. Liveness failure also kills the container under its restart policy. These are documented mechanisms; useful health endpoints and thresholds are application responsibilities. Sources: `concepts/workloads/pods/pod-lifecycle.md:474–528,544–557`.

4. **Thirty seconds is a shutdown budget, not a request-completion guarantee.** The grace-period clock begins before `preStop`, so the hook consumes that budget. The kubelet runs the hook before asking the runtime to send TERM to container process 1; an overrun can receive a one-off two-second extension. Endpoint updates occur alongside shutdown, not as a guaranteed completed prerequisite: terminating EndpointSlice entries may remain, but have `ready: false`; `serving` supports draining decisions. At grace expiry, remaining processes receive SIGKILL. Configure application draining and a grace period covering measured hook and request-completion time. The documents do not establish that every long request finishes within 30 seconds. Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:1000–1008`; `concepts/workloads/pods/pod-lifecycle.md:584–639`.

5. **Resource settings must support both scheduling and autoscaling.** CPU requests participate in scheduler capacity checks and typically influence CPU allocation under contention; they are not CPU ceilings. A container can exceed its request when resources permit. On Linux, CPU limits enforce ceilings through throttling. Memory limits instead use reactive OOM enforcement: exceeding a limit may result in termination when memory pressure is detected, rather than immediate throttling. Utilization-based CPU HPA divides usage by CPU requests. If relevant requests are absent from some containers, Pod CPU utilization is undefined and HPA takes no action for that metric. Set deliberate requests for every relevant container and load-test limits. Sources: `concepts/configuration/manage-resources-containers.md:27–67,231–258`; `tasks/run-application/horizontal-pod-autoscale.md:89–101`.

6. **HPA deliberately departs from the raw utilization ratio.** Its baseline is the ceiling of current replicas multiplied by current/desired metric value, with a default 10% tolerance. Missing metrics and not-yet-ready CPU Pods are set aside initially. Missing metrics are then assumed at 100% of the target for downscaling and zero for upscaling; not-yet-ready Pods are assumed at zero when damping an upscale. If recalculation reverses direction or falls within tolerance, scaling is skipped. Default readiness-delay and CPU-initialization windows are 30 seconds and five minutes. Downscale stabilization defaults to five minutes, selecting the highest recommendation within that window. Reported utilization can therefore differ from the value driving scaling. Sources: `tasks/run-application/horizontal-pod-autoscale.md:129–202,213–218`.

7. **Replace default allow with tested, directional least privilege.** Start with policies selecting the relevant Pods and denying both ingress and egress. Add narrowly scoped ingress from intended callers, API egress to the database port, corresponding database ingress, and required DNS access. Ingress and egress isolation are independent; policies combine additively as a union, so a broad allow policy defeats narrower restrictions. A Pod-to-Pod connection must satisfy both source egress and destination ingress restrictions; replies to allowed connections are implicitly allowed. NetworkPolicy enforcement requires a supporting network plugin/CNI: creating policy objects alone does not establish isolation. Validate DNS and permitted and forbidden connections using the actual cluster networking. Sources: `concepts/services-networking/network-policies.md:51–81`; `concepts/security/multi-tenancy.md:208–234`.

8. **Reject base64 Secrets in Git as credential protection.** Base64 is a reversible representation; the supplied encryption example explicitly shows how API-returned base64 content can be decoded. Encryption at rest protects stored cluster data, not a committed manifest. Remove credentials from that workflow and rotate exposed values as an operational recommendation. Enable Secret encryption at rest, apply least-privilege RBAC, and expose Secrets only to containers that require them. Restrict workload creation too: authorization to create Pods—including indirectly through Deployments—can permit reading any Secret in that namespace. Merely denying direct Secret reads is insufficient. Sources: `tasks/administer-cluster/encrypt-data.md:579–588`; `concepts/configuration/secret.md:35–48`.

9. **Treat PV reclamation and StatefulSet PVC retention as separate lifecycles.** Dynamically provisioned PVs inherit their StorageClass reclaim policy, defaulting to `Delete`. Changing the class is not a retroactive update to existing PVs; inspect and patch those PVs individually. After PVC deletion, `Retain` leaves a released PV and data requiring manual reclamation. With a supporting plugin, `Delete` removes both the PV and external storage asset. StatefulSet deletion or scaling normally retains template-created PVCs; optional `whenDeleted` and `whenScaled` policies can delete them instead. The supplied guide identifies feature-gate prerequisites for that configuration. These PVC policies are distinct from PV reclaim policy. Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:178–210`; `concepts/workloads/controllers/statefulset.md:387–422`.

10. **Roll out through prioritized validation gates.** First, protect credentials and database data: rotate exposed credentials, verify encryption/RBAC, inspect existing PV policies, and prove backup restoration. Second, establish resource requests, probe behavior, termination draining, and compatible rollout settings. Third, verify zone labels and capacity, enforce network policies, then exercise HPA under load. Finally, rehearse rollout, drain, node failure, and zone loss separately. These checks follow the distinct mechanisms documented above: `concepts/workloads/pods/disruptions.md:99–136`; `concepts/workloads/pods/pod-lifecycle.md:474–557,584–639`; `concepts/storage/persistent-volumes.md:185–210`. Approval requires application or cluster evidence for at least four unresolved limits: request completion during shutdown, startup and probe timing, surviving-zone capacity and placement, and database recovery/data integrity. API fields alone establish none of those outcomes.
