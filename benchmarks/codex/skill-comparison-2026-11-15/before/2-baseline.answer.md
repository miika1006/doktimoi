Decision: revise the design before production rollout. The supplied v1.32 documentation describes useful controls, but does not establish that this application can maintain five serving replicas through failures, finish long requests within 30 seconds, or recover its database safely. The recommendations below are configuration choices unless identified as documented behavior. Citations name local files relative to the supplied corpus root.

1. **PDB and rollout availability.** `minAvailable: 5` cannot prevent an involuntary node failure; lost replicas count against the budget. During an eviction-based node drain, a correctly selected PDB constrains voluntary evictions: with six healthy replicas, one can be disrupted before further evictions must wait. Direct deletion bypasses that protection. Deployment rolling updates are not constrained by PDBs, although their unavailable Pods count against the budget. Therefore `maxUnavailable: 2` permits rollout availability to fall to four. Recommend `maxUnavailable: 1, maxSurge: 1`, with capacity for the surge; `maxUnavailable: 0` is a stricter alternative. Neither guarantees five through concurrent failures. [Sources: `docs/concepts/workloads/pods/disruptions.md:99–136`; `docs/concepts/workloads/controllers/deployment.md:1189–1211`.]

2. **Zone distribution.** Configure a topology spread constraint selecting the API’s Pods, using `topologyKey: topology.kubernetes.io/zone` and `maxSkew: 1`. With three eligible zones and sufficient capacity, target two replicas per zone. `topologyKey` groups nodes by label value; under `DoNotSchedule`, skew is the difference between the target domain’s matching-Pod count and the global minimum. Violating placements remain unscheduled. `ScheduleAnyway` instead favors smaller skew while permitting placement elsewhere. Choose explicitly between strict balance and recovery flexibility. If a zone disappears from eligible domains, `minDomains: 3` makes the global minimum zero and can block replacements in surviving zones; omitting it allows recalculation over remaining domains. Actual behavior depends on eligibility and remaining nodes. Removal does not guarantee continued balance. Losing a two-replica zone initially leaves four. [Sources: `docs/concepts/scheduling-eviction/topology-spread-constraints.md:82–130,607–619`.]

3. **Probes for slow startup.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Until it succeeds, readiness and liveness probes do not begin. Use readiness to indicate ability to accept requests, including necessary database availability; use liveness for conditions where restarting helps, such as deadlock. These endpoint semantics require application implementation. After the configured consecutive failures, startup or liveness failure triggers a container restart; readiness failure keeps the container running, marks the Pod unready, and removes it from Service load balancing. Readiness withdrawal does not establish completion of existing requests. [Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:14–35,311–318,412–422`.]

4. **Termination and long requests.** The termination deadline and grace period are recorded before local shutdown begins. The kubelet runs `preStop`, then asks the runtime to send TERM to process 1; the hook consumes the existing grace period rather than receiving an additional full period. A still-running hook can receive a one-off two-second extension. At expiry, remaining processes receive SIGKILL. Concurrently, terminating Service endpoints are marked terminating and `ready: false`, rather than immediately disappearing; `serving` supports draining decisions. Thirty seconds is a shutdown allowance, not a request-completion guarantee. Implement draining and signal handling, then size the grace period for hook execution plus measured request completion. [Sources: `docs/concepts/workloads/pods/pod-lifecycle.md:581–639`.]

5. **Resources and CPU utilization.** Set explicit CPU requests for every relevant container. Requests drive scheduling and provide the denominator for utilization-based HPA; they are not usage ceilings. CPU limits enforce throttling, which can affect request latency. Memory limits behave differently: enforcement uses reactive OOM kills, potentially terminating a container rather than slowing it down. Choose requests and limits from startup and sustained-load measurements. If relevant container CPU requests are missing, Pod CPU utilization is undefined and HPA takes no action for that metric. Inspect admitted configuration: absent requests can be copied from limits when no admission default supplies them. [Sources: `docs/concepts/configuration/manage-resources-containers.md:18–53,64–66`; `docs/tasks/run-application/horizontal-pod-autoscale.md:89–102`.]

6. **HPA’s conservative adjustments.** The raw recommendation is the rounded-up product of current replicas and current/desired metric ratio. HPA sets aside missing metrics and, for CPU, certain not-yet-ready Pods. Missing metrics are conservatively assumed at 100% of target for downscaling and 0% for upscaling; not-yet-ready Pods further dampen scale-up using 0%. A revised ratio that reverses direction or enters tolerance causes no scaling. Default readiness-delay and CPU-initialization settings are 30 seconds and five minutes. Downscale stabilization chooses the highest recommendation within a default five-minute window. Thus observed scaling can differ from the raw ratio and reported utilization. A working resource metrics API, usually separately installed Metrics Server, is a prerequisite. [Sources: `docs/tasks/run-application/horizontal-pod-autoscale.md:114–118,132–218`.]

7. **Least-privilege networking.** Establish default-deny ingress and egress, then allow intended callers to the API port, API egress to the database port, corresponding database ingress, and required DNS traffic. Use scoped Pod/namespace selectors and actual deployment ports. Ingress and egress isolation are independent: selecting a Pod for one direction does not isolate the other. Policies combine additively, so an existing broad allow can defeat the intended restriction. Both source egress and destination ingress must allow a Pod-to-Pod connection; replies to allowed connections are implicitly permitted. Verify the actual DNS destination and UDP/TCP needs—the documented DNS Service exposes port 53 for both. A NetworkPolicy-capable CNI/controller is mandatory; creating policy objects alone has no effect. [Sources: `docs/concepts/services-networking/network-policies.md:45–81,210–259`; `docs/tasks/administer-cluster/dns-debugging-resolution.md:159–173`.]

8. **Secrets.** Reject base64-encoded Secrets in Git as sufficient protection. The documentation explicitly describes base64 authentication data as “obscured but not secret”; encoding is also the required representation of Secret `data`, not an encryption control. Enable encryption at rest for Secrets, apply least-privilege RBAC, and restrict which containers receive credentials. Secrets are stored unencrypted in etcd by default. Audit workload-creation privileges as well as direct Secret permissions: someone authorized to create Pods in a namespace can read its Secrets through those Pods, including indirectly through Deployment creation. Encryption at rest does not establish protection for committed copies in Git. [Sources: `docs/concepts/configuration/secret.md:35–48,306,455–456`.]

9. **Storage reclamation and workload lifecycle.** Changing a StorageClass’s reclaim setting does not retroactively rewrite existing PV policies; inspect and patch existing PVs individually. Dynamically provisioned PVs inherit the class policy, whose default is `Delete`. After PVC deletion, `Retain` preserves the released PV and data for manual reclamation; supported `Delete` implementations remove both PV and backing storage. StatefulSet deletion or scaling is a separate decision: PVC retention defaults to `Retain`, while optional `whenDeleted` and `whenScaled` policies can delete template-generated PVCs after affected Pods terminate. The supplied documentation requires the feature gate on API server and controller manager for that field. Do not infer database protection merely from dynamic provisioning. [Sources: `docs/concepts/storage/storage-classes.md:126–135`; `docs/concepts/storage/persistent-volumes.md:178–210`; `docs/concepts/workloads/controllers/statefulset.md:391–423`.]

10. **Prioritized rollout and validation checklist.** First, remove reliance on encoded Git credentials, verify encryption/RBAC, and inspect existing database PV reclamation plus StatefulSet PVC retention. Second, validate CNI enforcement and required allowed/denied connections, including DNS. Third, implement startup/readiness/liveness endpoints and graceful draining; load-test resource settings and HPA metrics. Fourth, deploy explicit spread rules and the compatible rollout strategy, reserve surge capacity, and rehearse drains, rollouts, node loss, and zone loss. Check available replicas, pending replacements, endpoint conditions, interrupted requests, and database recovery.

    Release gates must include application/cluster validation of at least these limits: worst-case startup duration; long-request completion and signal handling; surviving-zone capacity and replacement scheduling; CPU-based scaling’s ability to protect latency and database capacity; and database recovery/data durability. These documents specify mechanisms, not successful outcomes for this application.
