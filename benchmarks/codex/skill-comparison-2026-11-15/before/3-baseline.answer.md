Decision: revise before production approval. Kubernetes provides useful controls here, but the proposed settings do not establish five continuously available replicas, completed long requests, secure credentials, or database durability. The following separates documented behavior from recommended configuration and validation.

1. **PDB protection depends on the disruption.** Node failure is involuntary: a PDB cannot prevent it, although unavailable Pods count against the budget. During an Eviction API based node drain, `minAvailable: 5` restricts voluntary evictions; drain may wait for replacements or time out. Direct deletion bypasses that protection. Deployment rollouts are not constrained by PDBs, so `maxUnavailable: 2` permits four available replicas at a desired count of six. Recommend `maxUnavailable: 1, maxSurge: 1`, or conservatively `0, 1` with sufficient capacity. These constrain rollout behavior, not simultaneous failures. Sources: [docs/concepts/workloads/pods/disruptions.md:99–141](docs/concepts/workloads/pods/disruptions.md#L99-L141); [docs/concepts/workloads/controllers/deployment.md:1185–1211](docs/concepts/workloads/controllers/deployment.md#L1185-L1211).

2. **Spread by zone, with an explicit failure tradeoff.** Configure a selector matching the API Pods, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`; with six schedulable replicas, target two per zone. The topology key identifies node labels defining domains. Under `DoNotSchedule`, skew limits the target domain’s matching-Pod count relative to the global minimum; `ScheduleAnyway` prefers reduced skew without enforcing it. Recommend strict spreading normally, but document recovery behavior: with `minDomains: 3`, fewer than three eligible domains makes the global minimum zero, potentially blocking replacements. Without it, remaining eligible domains can permit redistribution. “Unavailable” is not itself an eligibility definition; labels, affinity and taints matter. Constraints also do not guarantee balance after removals. Source: [docs/concepts/scheduling-eviction/topology-spread-constraints.md:82–130,607–619](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L82-L130).

3. **Use startup protection and separate readiness from liveness.** Set a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Other probes remain disabled until startup succeeds; their initial delays then begin. Readiness should test whether the API can serve requests, including required database availability where appropriate. Failed readiness withdraws Service traffic without restarting the container. Liveness should detect a condition restart can repair, such as a deadlock; avoid making temporary database failure a restart trigger. Consecutive startup or liveness failures reaching their threshold trigger termination/restart behavior, subject to restart policy. Sources: [docs/concepts/workloads/pods/pod-lifecycle.md:479–497](docs/concepts/workloads/pods/pod-lifecycle.md#L479-L497); [docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–367,398–421](docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md#L311-L367).

4. **Thirty seconds is a deadline, not a completion guarantee.** Deletion records the grace deadline; kubelet runs `preStop` before asking the runtime to send TERM to container process 1. The hook consumes the same grace period rather than receiving an additional thirty seconds. An overrun can receive a small, one-off two-second extension. Remaining processes receive SIGKILL when grace expires. Concurrently, terminating Service endpoints remain temporarily in EndpointSlices with `terminating` status and `ready: false`, excluding regular traffic; `serving` supports draining decisions. Choose grace time from measured hook, draining and request durations, and implement TERM handling. The docs establish no guarantee that long requests finish. Source: [docs/concepts/workloads/pods/pod-lifecycle.md:581–639](docs/concepts/workloads/pods/pod-lifecycle.md#L581-L639).

5. **Resource settings must support both scheduling and autoscaling.** CPU requests inform scheduling and typically determine relative CPU weighting under contention; they are not usage ceilings. CPU limits impose throttling. Memory limits instead use reactive OOM enforcement, potentially killing the container; exceeding a request alone is different from exceeding a limit. Set measured requests for every relevant container. CPU utilization HPA calculates usage relative to requests: missing relevant requests make Pod utilization undefined and prevent action for that metric. Inspect effective settings because, absent another default, specifying only a limit copies it into the request. Sources: [docs/concepts/configuration/manage-resources-containers.md:18–66,252–263](docs/concepts/configuration/manage-resources-containers.md#L18-L66); [docs/tasks/run-application/horizontal-pod-autoscale.md:89–102](docs/tasks/run-application/horizontal-pod-autoscale.md#L89-L102).

6. **HPA deliberately moderates the raw ratio.** Its basic calculation rounds up `currentReplicas × currentMetric / desiredMetric`, with default tolerance of 0.1. Missing metrics are initially set aside, then conservatively assumed at 100% of target for downscale and 0% for upscale. CPU metrics from not-yet-ready Pods are also set aside; those Pods are assumed at 0% when moderating upscale. Defaults include a thirty-second initial readiness delay and five-minute CPU initialization period. Recalculation can cancel scaling if direction reverses or falls within tolerance. Downscale stabilization selects the highest recommendation within the default five-minute window. Consequently, displayed utilization and actual scaling can differ. Source: [docs/tasks/run-application/horizontal-pod-autoscale.md:130–218](docs/tasks/run-application/horizontal-pod-autoscale.md#L130-L218).

7. **Replace unrestricted networking with explicit connection allowances.** Establish default-deny ingress and egress, then allow intended callers to the API port and API Pods to the database port. Permit DNS access to the cluster’s actual resolver; determine its destinations and protocols from cluster configuration. DNS is required when using Service names, but these documents do not establish this cluster’s resolver deployment. Ingress and egress isolation are independent. Policies combine additively, so broad existing allowances remain effective. Pod-to-Pod connections require both source egress and destination ingress permission; reply traffic is implicitly allowed. Enforcement requires a supporting CNI/network controller—creating policy objects alone achieves nothing. Sources: [docs/concepts/services-networking/network-policies.md:45–81,254–259](docs/concepts/services-networking/network-policies.md#L45-L81); [docs/concepts/services-networking/dns-pod-service.md:15–25](docs/concepts/services-networking/dns-pod-service.md#L15-L25).

8. **Base64 is insufficient protection.** Reject readable, base64-encoded credentials in Git: encoding is reversible, and the documentation explicitly calls encoded authentication data “obscured but not secret.” Secrets are unencrypted in etcd by default. Enable and verify encryption at rest, including existing objects; configuration presence alone does not prove migration succeeded. Apply least-privilege RBAC and expose credentials only to necessary containers. Restrict workload creation too: permission to create Pods—or indirectly Deployments—in a namespace can expose any Secret there, even without direct Secret-reading permission. Sources: [docs/concepts/configuration/secret.md:35–48,286–306](docs/concepts/configuration/secret.md#L35-L48); [docs/tasks/administer-cluster/encrypt-data.md:58–73](docs/tasks/administer-cluster/encrypt-data.md#L58-L73).

9. **Reclaim policy and PVC retention are separate decisions.** A dynamically provisioned PV inherits its StorageClass reclaim policy, defaulting to `Delete`. Changing the class does not retroactively rewrite existing PV policies; inspect and patch those PVs explicitly. After PVC deletion, `Retain` preserves the released PV and data for manual reclamation; supported `Delete` implementations remove both PV and backing storage. StatefulSet deletion or scaling normally retains template-created PVCs. Its separate `whenDeleted` and `whenScaled` policies can request PVC deletion, after which PV reclaim behavior applies; the supplied page specifies feature-gate prerequisites. Sources: [docs/concepts/storage/persistent-volumes.md:178–210](docs/concepts/storage/persistent-volumes.md#L178-L210); [docs/concepts/storage/storage-classes.md:128–135](docs/concepts/storage/storage-classes.md#L128-L135); [docs/concepts/workloads/controllers/statefulset.md:391–423](docs/concepts/workloads/controllers/statefulset.md#L391-L423).

10. **Prioritize validation before broad rollout.** First secure credentials, confirm encryption and RBAC, audit existing PV reclaim settings, and test database recovery. Second establish requests, startup/readiness/liveness probes, zone placement and the revised rollout limits. Third deploy restrictive network policies with positive API/database/DNS tests and negative unauthorized-connection tests. Finally exercise node drain, node/zone loss, slow startup, missing metrics and long-request termination under load. Acceptance requires application or cluster evidence for at least four unresolved limits: probe accuracy, request-draining duration, surviving-zone/surge capacity, and database durability/recovery. Dynamic provisioning also requires topology validation: `Immediate` binding can produce unschedulable Pods; consider `WaitForFirstConsumer` where supported. These checks follow the documented constraints above; fields alone do not establish successful outcomes. Sources: [docs/concepts/storage/storage-classes.md:171–190](docs/concepts/storage/storage-classes.md#L171-L190); [docs/concepts/configuration/manage-resources-containers.md:230–241](docs/concepts/configuration/manage-resources-containers.md#L230-L241); [docs/concepts/workloads/pods/pod-lifecycle.md:619–639](docs/concepts/workloads/pods/pod-lifecycle.md#L619-L639).
