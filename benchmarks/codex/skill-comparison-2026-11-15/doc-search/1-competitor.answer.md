**Decision memo — revise before production approval.** Six replicas and Kubernetes configuration fields do not establish end-to-end availability. Approve only after the following configuration changes and validation gates. Citations refer to the supplied documentation corpus; recommendations are configuration choices, not additional Kubernetes guarantees.

1. **PDB protection depends on the disruption.** During **node failure**, `minAvailable: 5` cannot prevent replicas becoming unavailable; those losses count against the budget. During **node drain**, eviction-based tooling respects the PDB, allowing one healthy replica’s eviction when six are healthy, then potentially blocking pending recovery. This requires operators to use the Eviction API. During **Deployment updates**, the controller is not constrained by the PDB, although unavailable updating Pods count against it ([disruptions.md, lines 107–136][disruptions]).

   Proposed `maxUnavailable: 2` permits rollout availability to fall to four. Choose `maxUnavailable: 1, maxSurge: 1`, or conservatively `0/1`, with sufficient surge capacity. These control rollout behavior; they cannot prevent concurrent failures ([deployment.md, lines 1183–1211][deployment]).

2. **Configure explicit zone spreading.** Select the API’s Pods using `labelSelector`, set `topologyKey: topology.kubernetes.io/zone`, and choose `maxSkew: 1`. Under `DoNotSchedule`, skew limits the target domain’s matching-Pod count relative to the global minimum. With three eligible zones and successful placement, six replicas can form 2/2/2. `ScheduleAnyway` merely prefers placements reducing skew; it permits imbalance ([topology-spread-constraints.md, lines 82–130][spread]).

   Recommend hard spreading during normal operation, with an explicit outage recovery decision. An unavailable zone may leave replacements Pending if hard constraints cannot be satisfied. If a domain disappears from eligibility, calculations change: default `minDomains` is one, whereas `minDomains: 3` makes the global minimum zero when fewer than three eligible domains remain, potentially blocking replacements. Eligibility depends on node affinity and taint policies. Domains without nodes are not discovered automatically ([lines 95–122][spread]; [lines 167–190][spread-policy]; [lines 607–619][spread-limits]). Losing a two-replica zone initially leaves four, regardless of the PDB.

3. **Use all three probes with distinct application meanings.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. It suppresses other probes until success; their initial-delay clocks also wait. Use readiness to indicate whether this instance can serve requests, including essential database dependencies, and liveness for conditions recoverable by restarting, such as deadlock ([configure-liveness-readiness-startup-probes.md, lines 311–358][startup]; [lines 398–422][probe-config]).

   Failed readiness makes the Pod unready and removes it from matching Service endpoints; it does not restart the container. Startup or liveness failure after the configured consecutive-failure threshold triggers container restart behavior. Probe endpoint semantics and thresholds require application testing ([pod-lifecycle.md, lines 479–497][probe-lifecycle]; [probe configuration, lines 412–422][probe-config]).

4. **Budget termination for hooks and requests together.** The grace period starts before `preStop`; the hook consumes that budget. The documented flow runs the hook, then sends TERM to the container’s main process. Remaining processes receive SIGKILL when grace expires; an overrunning hook can receive a small, one-off two-second extension ([pod-lifecycle.md, lines 584–610, 636–645][termination]).

   Concurrently, Service endpoint state changes: terminating endpoints are not immediately removed from EndpointSlices, but have `ready: false`; `serving` supports draining decisions. This is not an instantaneous synchronization guarantee between shutdown and every traffic component ([lines 612–632][termination]). **Thirty seconds does not guarantee request completion.** Implement signal handling and connection draining, then size grace for measured hook duration, remaining request duration, and propagation behavior.

5. **Set measured resource requests and limits.** CPU requests inform scheduling and establish the denominator for utilization-based HPA; they are not CPU ceilings. Containers can exceed requests when resources permit. CPU limits enforce throttling, while memory limits are enforced reactively through OOM kills, potentially terminating the container rather than slowing it ([manage-resources-containers.md, lines 18–53][resources]).

   Set explicit CPU requests for all relevant containers. If a container lacks the relevant request, Pod CPU utilization is undefined and HPA takes no action for that metric. However, an omitted manifest request may be defaulted: Kubernetes copies a specified limit when no other request default applies. Inspect admitted Pods, not just Git manifests ([horizontal-pod-autoscale.md, lines 89–102][hpa]; [resource documentation, lines 63–66][resources]).

6. **Expect conservative HPA decisions.** The basic calculation rounds up `currentReplicas × currentMetric / desiredMetric`; default tolerance is 0.1. HPA sets missing metrics aside and excludes certain initializing or not-yet-ready CPU samples. Readiness classification uses configurable defaults of 30 seconds and five minutes ([horizontal-pod-autoscale.md, lines 129–178][hpa-algorithm]).

   Missing samples are assumed at 100% of target for downscaling and 0% for upscaling. Not-yet-ready Pods can further dampen upscaling using 0%. A recalculation that reverses direction or enters tolerance produces no scaling. Reported utilization excludes these adjustments. Downscale stabilization defaults to five minutes and selects the highest recommendation within the window. These rules explain divergence from the raw ratio ([lines 180–218][hpa-adjustments]). A working resource metrics API—usually separately installed Metrics Server—is a prerequisite ([lines 113–118][hpa]).

7. **Replace default allow with explicit isolation and allowances.** Apply default-deny ingress and egress to the application namespace, then allow approved callers to the API port, API egress to the database port, and corresponding database ingress from API Pods. Scope peers with Pod and namespace selectors.

   Ingress and egress isolation are independent. Allowed traffic is the union of applicable policies: a broad allow policy defeats narrower intentions. Both source egress and destination ingress must permit a Pod-to-Pod connection; allowed reply traffic is implicit. Enforcement requires a supporting network plugin; creating policy objects alone has no effect ([network-policies.md, lines 48–81][network]).

   Explicitly allow DNS to the cluster’s actual resolver endpoints, commonly UDP and TCP 53, and test resolution under isolation ([dns-debugging-resolution.md, lines 158–174][dns]). Resolver placement and policy enforcement remain cluster prerequisites.

8. **Reject base64 Secrets in Git as protection.** Base64 provides obscurity, not secrecy; readers can recover the value ([secret.md, lines 305–307][secret-encoding]). Keep recoverable credentials out of Git. Enable Secrets encryption at rest, least-privilege RBAC, and container-specific access. Restrict permission to create Pods or Deployments: that permission can expose any Secret in the namespace through a workload, even without direct Secret-reading permission ([secret.md, lines 35–48][secrets]).

   Encryption is not enabled merely because Secrets exist. Check API-server encryption configuration and verify existing data migrated; configuration presence alone does not establish successful migration ([encrypt-data.md, lines 55–73][encryption]). At-rest encryption also does not protect repository copies.

9. **Treat PVC retention and PV reclamation separately.** A StorageClass policy supplies the policy for dynamically created PVs; changing the class does not retrofit existing PVs. Inspect and edit or patch existing PV policies separately ([storage-classes.md, lines 126–135][storage-class]; [persistent-volumes.md, lines 203–210][pv]).

   After PVC deletion, `Retain` preserves the released PV and data for manual reclamation. Supported `Delete` implementations remove both the PV object and backing storage; dynamically provisioned storage defaults to Delete ([persistent-volumes.md, lines 180–210][pv]). StatefulSet deletion or scale-down retains template PVCs by default. Configured `whenDeleted`/`whenScaled: Delete` can delete affected PVCs after Pod deletion, subsequently invoking PV reclamation. Verify the documented feature prerequisite before relying on that behavior ([statefulset.md, lines 387–443][statefulset]). Prefer explicit retention for database data, with a tested recovery procedure.

10. **Prioritize validation before rollout.** First, remove repository credentials, verify encryption/RBAC, inspect actual PV policies, and establish recovery ownership. Second, verify NetworkPolicy enforcement and allowed DNS/database paths. Third, deploy measured resources, probes, shutdown handling, spread constraints, and the compatible rollout strategy. Finally, exercise rollout, drain, node loss, zone loss, HPA scale-up/down, and controlled storage lifecycle scenarios.

    Release gates must include at least these unguaranteed limits: worst-case startup duration; completion of long requests during shutdown; remaining-zone and surge capacity; database availability, connection capacity, and recovery. Kubernetes documents mechanisms, not this application’s bounds. In particular, spreading can become imbalanced after removal, shutdown can end in SIGKILL, and storage retention requires explicit lifecycle handling ([spread limitations, lines 607–619][spread-limits]; [termination, lines 636–645][termination]; [PV reclamation, lines 180–210][pv]).
