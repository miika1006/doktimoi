**Decision memo — revise before production rollout.** The proposed fields provide useful controls, but they do not establish five-replica availability, request completion, or database durability. Recommendations below are configuration choices grounded only in the supplied Kubernetes v1.32 corpus. All cited paths are relative to the supplied `docs/` directory; line ranges identify the supporting source.

1. **PDB protection depends on the disruption.** During **node failure**, `minAvailable: 5` cannot prevent involuntary disruption; lost Pods nevertheless count against the budget. During **node drain**, tools using the Eviction API respect the PDB: with six healthy replicas, one eviction is initially permissible; subsequent evictions can block pending recovery. Direct deletion bypasses this protection. During **Deployment updates**, unavailable Pods count against the budget, but the Deployment’s rollout is not constrained by it. Therefore, `maxUnavailable: 2` permits the rollout to reduce availability to four.

   Recommend `maxUnavailable: 1`, `maxSurge: 1`, with spare scheduling capacity. This aligns rollout-controlled unavailability with the five-replica objective; concurrent failures can still reduce availability further. Sources: `concepts/workloads/pods/disruptions.md`, lines 62–65, 99–145; `concepts/workloads/controllers/deployment.md`, lines 1183–1211.

2. **Explicitly spread matching API Pods across zones.** Configure the Deployment template with `topologyKey: topology.kubernetes.io/zone`, an API-specific `labelSelector`, and `maxSkew: 1`. With three eligible, adequately provisioned zones, this supports a balanced six-Pod placement of two per zone. `topologyKey` groups nodes by their label values. Under `DoNotSchedule`, skew limits the difference between the target domain’s matching-Pod count and the global minimum; violating Pods remain pending. `ScheduleAnyway` instead prefers placements that reduce skew.

   Choose hard spreading only after accepting its recovery tradeoff. An unavailable zone can block replacement placement if it remains relevant to skew calculations. With `minDomains: 3`, fewer than three eligible domains makes the global minimum zero; omitting it behaves as one and can permit redistribution across surviving eligible domains. Eligibility depends on affinity and taint policies. Neither choice guarantees five survivors: losing a two-Pod zone leaves four. Sources: `concepts/scheduling-eviction/topology-spread-constraints.md`, lines 78–130, 167–185, 206–211, 607–619.

3. **Give slow startup its own probe budget.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Until it succeeds, readiness and liveness probes are disabled. Exhausting its failure allowance kills the container, followed by the restart policy.

   Readiness should test whether the API can serve useful requests, including required database availability where appropriate. Failed readiness removes the Pod from matching Service endpoints without itself restarting the container. Liveness should detect an application condition that warrants restart, such as deadlock; avoid making a database outage alone trigger restart. Liveness failure kills the container and invokes its restart policy. Probe endpoints and thresholds require application validation. Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md`, lines 311–367; `concepts/workloads/pods/pod-lifecycle.md`, lines 479–497, 524–528.

4. **Thirty seconds is a shutdown allowance, not a completion guarantee.** The grace-period countdown begins **before** `preStop`, so hook execution consumes the same budget as application shutdown. The kubelet runs the hook, then asks the runtime to send TERM, ordinarily SIGTERM, to the container’s main process. Image stop-signal configuration can alter that signal. Remaining processes receive SIGKILL when grace expires; an unfinished hook can receive a small, one-off two-second extension.

   Endpoint updates occur concurrently with local shutdown. Terminating EndpointSlice entries are not immediately removed, but have `ready: false`; their `serving` condition supports draining implementations. Configure application shutdown and a grace period covering measured hook, draining, and request durations. The documents establish no guarantee that long requests finish within 30 seconds. Sources: `reference/kubernetes-api/workload-resources/pod-v1.md`, lines 1006–1008; `concepts/workloads/pods/pod-lifecycle.md`, lines 567–639.

5. **Size requests and limits deliberately.** CPU requests contribute to scheduling capacity checks and typically determine relative CPU allocation under contention. They are not usage ceilings: containers can exceed requests when resources permit. On Linux, CPU limits restrict CPU time through throttling; excessive CPU use does not itself cause container termination. Memory limits instead involve reactive OOM enforcement and can result in process termination.

   Set realistic CPU requests on every relevant container. CPU-utilization HPA measures consumption relative to requests; if relevant requests are missing, Pod utilization is undefined and HPA does not act for that metric. Inspect effective configuration: absent requests can inherit specified limits when no admission default applies. Sources: `concepts/configuration/manage-resources-containers.md`, lines 27–66, 230–265, 275–276; `tasks/run-application/horizontal-pod-autoscale.md`, lines 89–102.

6. **Expect HPA decisions to differ from the raw ratio.** HPA initially sets aside missing metrics and, for CPU, certain not-yet-ready Pods or samples preceding readiness. It recomputes conservatively: missing metrics assume 100% of target during downscale and 0% during upscale; not-yet-ready Pods can further dampen upscale using a zero assumption. A recalculated ratio that reverses direction or falls within tolerance produces no scaling action.

   Default readiness-delay and CPU-initialization settings are 30 seconds and five minutes. Default downscale stabilization selects the highest recommendation within five minutes. Rounding, default 10% tolerance, conservative adjustments, and stabilization therefore separate actual scaling from the basic ratio. Metrics availability is a prerequisite, commonly supplied by separately installed Metrics Server. Source: `tasks/run-application/horizontal-pod-autoscale.md`, lines 113–118, 129–218.

7. **Replace default allow with explicit communication allowances.** Establish ingress and egress isolation for the API and database, then allow approved callers to the API port and API Pods to the database port. Use namespace and Pod selectors matching the intended trust boundaries. Add DNS access to the actual cluster resolver and only other necessary dependencies.

   Ingress and egress isolation are independent. Policies combine additively: a broad existing allowance remains effective despite adding a restrictive policy. A connection requires both source egress and destination ingress permission when those directions are isolated; permitted reply traffic is implicit. Verify the installed network plugin implements NetworkPolicy—creating objects without enforcement has no effect. Sources: `concepts/services-networking/network-policies.md`, lines 45–81, 147–155; `concepts/security/multi-tenancy.md`, lines 215–220.

8. **Reject base64 Secrets in Git as protection.** Base64 is a representation of the credential, not confidentiality protection. Keep usable credentials out of repository manifests and adopt controlled secret delivery. Enable encryption at rest explicitly: Kubernetes documents unencrypted etcd storage as the default.

   Apply least-privilege RBAC and restrict which containers receive secrets. Review workload-creation privileges alongside direct Secret access: permission to create Pods in a namespace, including indirectly through Deployments, permits reading that namespace’s Secrets. Encryption at rest does not remove this authorized-access route. Sources: `tasks/inject-data-application/distribute-credentials-secure.md`, lines 17–28; `concepts/configuration/secret.md`, lines 35–48, 453–457.

9. **Treat PVC retention and PV reclamation separately.** Dynamically provisioned PVs inherit their StorageClass reclaim policy, defaulting to `Delete`. Changing the class policy does not retroactively change existing PVs; inspect and edit or patch those PVs individually.

   After PVC deletion, `Retain` leaves the PV and data for manual reclamation. With supporting plugins, `Delete` removes both the PV object and backing storage. StatefulSet deletion or scale-down normally retains its template-created PVCs. Optional `whenDeleted` and `whenScaled` retention settings can instead delete affected PVCs, after which PV reclamation applies. Verify the documented feature-gate prerequisites. Sources: `concepts/storage/storage-classes.md`, lines 126–135; `concepts/storage/persistent-volumes.md`, lines 178–210; `concepts/workloads/controllers/statefulset.md`, lines 387–423.

10. **Prioritize rollout and validation as follows.**

   - **First:** secure credential delivery and RBAC; inspect actual PV reclaim policies and StatefulSet PVC retention before destructive operations.
   - **Second:** configure probes, measured shutdown grace, CPU requests, compatible rollout limits, zone spreading, and enforced network allowances.
   - **Third:** validate under load: roll an update, drain a node through eviction, simulate node and zone loss, exercise cold starts and missing metrics, test denied connections and DNS, and rehearse database recovery.

   Keep at least these limits explicit: application request-draining time, usable readiness semantics, surviving-zone capacity, CPU scaling’s relationship to demand, and database recovery/durability are **not guaranteed by these documents**. Capacity can block replacement Pods, and scale-down can leave topology imbalanced. Sources: `concepts/workloads/pods/disruptions.md`, lines 195–232; `concepts/scheduling-eviction/topology-spread-constraints.md`, lines 605–619; shutdown, HPA, networking, and storage sources cited above.
