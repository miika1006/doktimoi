**Decision memo:** Revise the design before production approval. Kubernetes provides useful controls, but these settings do not establish an end-to-end availability or data-safety guarantee. Citations below are local paths relative to the supplied corpus root; `L` identifies source lines.

1. **PDB protection and rolling updates.** `minAvailable: 5` does not guarantee five available replicas during node failure: involuntary disruptions cannot be prevented, although they count against the budget. During a node drain using the Eviction API, the PDB constrains voluntary evictions; from six healthy replicas, it ordinarily permits one unavailable replica and blocks further evictions until recovery. Direct deletion bypasses this protection. Deployment rolling updates count against the budget but are not constrained by it. Thus, `maxUnavailable: 2` permits an update to leave only four available replicas. Recommend `maxUnavailable: 0, maxSurge: 1`, with spare scheduling capacity; `maxUnavailable: 1` is also compatible with a five-replica update floor. Neither protects against simultaneous failures. Sources: `docs/concepts/workloads/pods/disruptions.md`, L99–145; `docs/concepts/workloads/controllers/deployment.md`, L1183–1211.

2. **Zone placement.** Configure topology spread using the API’s Pod selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`. With sufficient eligible capacity, six replicas can spread 2/2/2. The key identifies domains through node labels. Under `DoNotSchedule`, skew limits the difference between the target domain’s matching Pod count and the global minimum; violating placements remain pending. `ScheduleAnyway` merely prefers placements reducing skew. Explicitly decide outage behavior: `minDomains: 3` with hard spreading makes the global minimum zero when fewer than three domains are eligible, potentially blocking replacements in surviving zones. Omitting it permits balancing across remaining eligible domains. Eligibility depends on affinity and taint policies; an unavailable zone is not automatically absent from calculations. Losing two replicas still leaves four initially. Sources: `docs/concepts/scheduling-eviction/topology-spread-constraints.md`, L82–130, L167–185, L206–214, L605–619.

3. **Probes for slow startup.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Until it succeeds, readiness and liveness probes are disabled. Exhausting startup failures kills the container, followed by its restart policy. Use readiness to indicate actual request-serving capability, including required database availability where appropriate; failure removes the Pod from matching Service endpoints without requiring a restart. Use liveness for application failure such as deadlock, keeping it independent of transient database outages. Liveness failure kills the container and invokes its restart policy. These mechanisms require meaningful application health checks and tuned thresholds. Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md`, L311–347; `docs/concepts/workloads/pods/pod-lifecycle.md`, L479–497, L512–528.

4. **Termination and long requests.** The grace-period countdown starts before `preStop`; the hook consumes the shutdown budget. After the hook, the runtime normally sends SIGTERM to the container’s main process, although image stop-signal configuration can affect this. Remaining processes receive SIGKILL when grace expires; an overrunning hook receives a small, one-off two-second extension. Endpoint processing happens concurrently: terminating endpoints remain represented temporarily with `ready: false`; `serving` supports draining-aware consumers. Thirty seconds is a default timeout, not a guarantee that requests finish. Configure a measured budget covering hook execution, draining, request completion, and cleanup, and implement signal handling. Sources: `docs/reference/kubernetes-api/workload-resources/pod-v1.md`, L1006–1008; `docs/concepts/workloads/pods/pod-lifecycle.md`, L572–577, L591–639.

5. **Resource sizing and utilization HPA.** CPU requests inform scheduling and resource allocation; they also supply the denominator for utilization-based CPU autoscaling. Containers may consume above requests when resources are available. CPU limits impose throttling, potentially increasing request latency; memory limits instead cause reactive OOM enforcement and may kill containers rather than immediately preventing allocation. Set measured requests and limits for every relevant container. If relevant CPU requests remain missing, Pod CPU utilization is undefined and HPA takes no action for that metric. Account for admission defaults: when only a limit is specified, Kubernetes can copy it into the request. Sources: `docs/concepts/configuration/manage-resources-containers.md`, L18–23, L27–66; `docs/tasks/run-application/horizontal-pod-autoscale.md`, L89–102.

6. **HPA’s conservative calculation.** The raw calculation is the ceiling of current replicas multiplied by current/desired metric value, subject to default 10% tolerance. Deleted and failed Pods are excluded; missing metrics and not-yet-ready CPU samples are set aside. Missing metrics are conservatively assumed at 100% of target during downscaling and 0% during upscaling. Not-yet-ready Pods are also assumed at 0% when considering scale-up, damping expansion. If recalculation reverses direction or enters tolerance, scaling stops. Readiness interpretation uses configurable defaults of 30 seconds and a five-minute CPU initialization period. Downscaling selects the highest recommendation within the default five-minute stabilization window. Therefore displayed utilization and actual scaling can differ. Sources: `docs/tasks/run-application/horizontal-pod-autoscale.md`, L129–218.

7. **Least-privilege networking.** Select API and database Pods with default-deny ingress and egress policies, then explicitly allow approved callers to the API port, API egress to the database port, matching database ingress, and necessary DNS access. Add other dependencies only after inventory. Ingress and egress isolation are independent. Policies are additive unions: another broad allow policy can reopen access, so audit all applicable policies. A Pod-to-Pod connection requires permission at both source egress and destination ingress; replies to allowed connections are implicitly allowed. Prerequisite: the installed CNI/network solution must implement NetworkPolicy; creating objects alone has no effect. Sources: `docs/concepts/services-networking/network-policies.md`, L45–81, L105–122; `docs/concepts/security/multi-tenancy.md`, L208–220.

8. **Secret protection.** Reject base64-encoded credentials in Git as a security control: encoding obscures values without making them secret. Remove readable credentials from version-controlled manifests and use a controlled delivery mechanism. Enable encryption at rest for Secrets, which are otherwise unencrypted in etcd by default; enforce least-privilege RBAC and restrict container access. Also restrict permission to create Pods and controllers: someone able to create a Pod in a namespace can use it to read that namespace’s Secrets, even without direct Secret-read permission. Storage encryption does not protect a readable repository copy. Sources: `docs/concepts/configuration/secret.md`, L35–48, L102–129, L305–307.

9. **Storage reclamation and workload lifecycle.** A StorageClass reclaim-policy change does not retroactively update existing PVs: dynamically provisioned PVs inherit the class policy at creation; inspect and patch existing PVs separately. `Delete`, the class default, removes the PV and backing storage where supported. `Retain` leaves storage and data after PVC deletion, requiring manual reclamation. PVC deletion is distinct from StatefulSet deletion or scale-down: template PVCs default to retention. Optional `whenDeleted` and `whenScaled` policies can delete the affected PVCs, after which PV reclamation applies. Verify the documented feature prerequisites before relying on automatic PVC deletion. Sources: `docs/concepts/storage/storage-classes.md`, L126–135; `docs/concepts/storage/persistent-volumes.md`, L178–210; `docs/concepts/workloads/controllers/statefulset.md`, L391–423.

10. **Prioritized rollout and validation checklist.** First, remove exposed credentials, verify encryption/RBAC, inspect existing PV policies, and test database backup restoration. Second, establish CNI enforcement and test allowed API/database/DNS paths plus denied paths. Third, deploy measured resources, probes, shutdown handling, zone constraints, and the revised update strategy; verify surge capacity. Fourth, load-test slow startup, long-request termination, rolling updates, drains, node failure, and zone loss while observing endpoints and HPA. Set an explicit HPA minimum consistent with the intended baseline and verify metrics availability. Release only after confirming application request completion, surviving-zone capacity, database failover/data recovery, and actual policy enforcement—none follows from field existence. Sources: documents cited above; additionally `docs/tasks/run-application/horizontal-pod-autoscale.md`, L113–118; `docs/concepts/storage/storage-classes.md`, L171–184; `docs/concepts/scheduling-eviction/topology-spread-constraints.md`, L605–619.
