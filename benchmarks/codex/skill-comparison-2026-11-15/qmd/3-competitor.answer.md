The design needs changes before production approval. Kubernetes documents mechanisms for controlling disruption, scheduling, and resource use; those mechanisms do not establish end-to-end availability, request completion, or database durability. The recommendations below are configuration choices grounded in the supplied v1.32 corpus, with remaining validation requirements identified explicitly.

1. **PDB and rollout.** `minAvailable: 5` does not guarantee five available replicas during node failure: PDBs cannot prevent involuntary disruptions, although those disruptions consume the budget. During a drain that uses the Eviction API, it constrains permitted evictions; draining can block while replacements become healthy. Direct deletion bypasses that protection. During a Deployment update, unavailable Pods count against the budget, but the Deployment is not constrained by it. Consequently, `maxUnavailable: 2` permits rollout availability to fall to four of six. Recommend `maxUnavailable: 0`, `maxSurge: 1`, with capacity for the surge; `maxUnavailable: 1` is also compatible with a five-replica rollout floor. Neither setting protects against simultaneous failures. Sources: [disruptions.md, lines 99–145](docs/concepts/workloads/pods/disruptions.md#L99-L145); [deployment.md, lines 1183–1211](docs/concepts/workloads/controllers/deployment.md#L1183-L1211).

2. **Zone placement.** Configure a topology spread constraint selecting the API Pods, using `topologyKey: topology.kubernetes.io/zone` and `maxSkew: 1`. Verify node zone labels. With three usable zones and six replicas, aim for two per zone. `topologyKey` identifies domains through equal node-label values. Under `DoNotSchedule`, skew is the difference between matching Pods in the target domain and the global minimum; violating placements remain unscheduled. `ScheduleAnyway` instead prefers placements that reduce skew. Zone failure therefore requires an explicit tradeoff: hard spreading can block replacements; soft spreading permits concentration elsewhere, subject to other scheduling constraints. With `minDomains: 3`, fewer eligible domains make the global minimum zero, potentially blocking further placement. Eligibility and surviving nodes matter; automatic redistribution is not guaranteed, and Pod removal can leave imbalance. Sources: [topology-spread-constraints.md, lines 78–130](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L78-L130), [lines 605–623](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L605-L623).

3. **Probes for slow startup.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. After startup succeeds, use readiness to indicate ability to serve requests, including necessary dependencies, and liveness to detect unrecoverable local failure such as deadlock. Avoid making a transient database outage itself a reason to restart every API container. Startup disables both other probes until success; their configured delays then begin. Repeated startup or liveness failures trigger container restart behavior. Readiness failure leaves the container running but marks the Pod unready and removes it from matching Service endpoints. These signals require application-specific implementations and thresholds. Sources: [probe configuration, lines 311–367](docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md#L311-L367), [lines 398–422](docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md#L398-L422); [pod-lifecycle.md, lines 479–497](docs/concepts/workloads/pods/pod-lifecycle.md#L479-L497).

4. **Termination and long requests.** The grace-period countdown begins **before** `preStop`; the hook consumes that budget. During ordinary graceful termination, kubelet executes the hook before requesting TERM delivery. Remaining processes receive SIGKILL when grace expires; an unfinished hook gets a small, one-off two-second extension. Endpoint processing happens concurrently: terminating endpoints are not immediately removed from EndpointSlices, but have `ready: false`, excluding regular traffic; `serving` supports draining-aware consumers. Thirty seconds is a timeout, not a request-completion guarantee. Implement shutdown that stops accepting work and drains existing requests, then size grace for measured hook and request duration. Sources: [pod API, line 1008](docs/reference/kubernetes-api/workload-resources/pod-v1.md#L1008); [pod-lifecycle.md, lines 572–639](docs/concepts/workloads/pods/pod-lifecycle.md#L572-L639).

5. **Requests, limits, and CPU HPA.** Set explicit CPU requests for every relevant container, based on measurement. Requests drive scheduling capacity checks and typically CPU weighting under contention; they are not usage ceilings. CPU limits constrain execution through throttling. Memory limits instead use reactive OOM enforcement: exceeding a limit can cause termination rather than throttling, and enforcement is not necessarily immediate. CPU utilization HPA divides usage by requests; if relevant container requests are missing, Pod utilization is undefined and HPA cannot act on that metric. Inspect admitted configuration: absent requests can be defaulted from limits. Sources: [resource management, lines 29–66](docs/concepts/configuration/manage-resources-containers.md#L29-L66), [lines 230–265](docs/concepts/configuration/manage-resources-containers.md#L230-L265); [HPA, lines 89–102](docs/tasks/run-application/horizontal-pod-autoscale.md#L89-L102).

6. **HPA adjustments.** HPA starts with the rounded-up replica count from current replicas multiplied by the current-to-target metric ratio. It sets aside missing metrics and qualifying not-yet-ready CPU samples. For missing metrics, recalculation assumes target utilization for downscaling and zero utilization for upscaling; not-yet-ready Pods also dampen an otherwise indicated upscale using zero. A reversed direction or ratio within tolerance suppresses scaling. Default readiness-delay and CPU-initialization windows are 30 seconds and five minutes. Downscale stabilization defaults to five minutes and chooses the highest recommendation in that window. Thus scaling can differ materially from the raw ratio and reported average. A functioning metrics API, commonly supplied by separately deployed Metrics Server, is a prerequisite. Sources: [HPA, lines 113–118](docs/tasks/run-application/horizontal-pod-autoscale.md#L113-L118), [lines 129–218](docs/tasks/run-application/horizontal-pod-autoscale.md#L129-L218).

7. **Least-privilege networking.** Establish default-deny ingress and egress, then allow approved callers to the API port, API access to the database port, and required DNS resolution to the actual cluster resolver. Treat resolver destinations and ports as cluster-specific configuration to validate. Ingress and egress isolation are independent. Policies combine additively: an existing allow-all policy defeats restrictions in that direction. A Pod-to-Pod connection requires permission from both source egress and destination ingress; replies are implicitly permitted. NetworkPolicy enforcement requires a supporting network plugin/controller—creating the resource alone has no effect. This is port/protocol filtering, not an absolute communications boundary. Sources: [network-policies.md, lines 45–81](docs/concepts/services-networking/network-policies.md#L45-L81), [lines 235–276](docs/concepts/services-networking/network-policies.md#L235-L276); [DNS configuration, lines 42–55](docs/concepts/services-networking/dns-pod-service.md#L42-L55).

8. **Secrets.** Reject base64-encoded credentials in Git as sufficient protection: base64 obscures values without making them secret. Remove exposed credentials from that workflow and replace them with controlled secret delivery. Enable and verify API-data encryption at rest; Secrets are unencrypted in etcd by default. Apply least-privilege RBAC and expose credentials only to containers needing them. Restrict Pod and Deployment creation as well: permission to create Pods in a namespace enables reading any Secret there by mounting it. Encryption at rest does not prevent authorized API retrieval or protect repository copies. Sources: [secret.md, lines 305–307](docs/concepts/configuration/secret.md#L305-L307), [lines 35–48](docs/concepts/configuration/secret.md#L35-L48); [encrypt-data.md, lines 53–66](docs/tasks/administer-cluster/encrypt-data.md#L53-L66).

9. **Storage lifecycle.** A StorageClass reclaim-policy change does not retroactively change existing PV policies; inspect and patch those PVs individually. Dynamically provisioned PVs inherit the class policy at creation, defaulting to `Delete`. On PVC deletion, `Retain` leaves the released PV and data for manual reclamation; supported `Delete` implementations remove both PV and backing storage. StatefulSet deletion or downscaling is a separate trigger: its PVC retention defaults to `Retain`. Optional `whenDeleted` and `whenScaled` policies can delete template-created PVCs; the supplied documentation requires the corresponding feature gate on API server and controller manager. Do not assume the database uses a StatefulSet merely because it is stateful. Sources: [storage-classes.md, lines 128–135](docs/concepts/storage/storage-classes.md#L128-L135); [persistent-volumes.md, lines 178–210](docs/concepts/storage/persistent-volumes.md#L178-L210); [statefulset.md, lines 387–423](docs/concepts/workloads/controllers/statefulset.md#L387-L423).

10. **Prioritized rollout and validation checklist.** First secure credential delivery and verify existing database PV policies. Second verify CNI enforcement, DNS access, zone labels, surge capacity, and metrics availability. Third deploy measured requests, startup/readiness/liveness probes, graceful shutdown, and the revised rollout strategy. Finally rehearse an update, eviction-based drain, zone outage, database interruption, and storage recovery under representative load.

    Acceptance must validate at least these unresolved limits: worst-case startup time; completion of long requests during draining; remaining-zone capacity; CPU utilization’s relationship to demand; and database recovery/durability. The documents establish neither those application properties nor this cluster’s implementations. Ground these tests in the documented capacity-dependent drain behavior, termination deadline, metrics prerequisite, and storage-plugin-dependent deletion semantics.
