**Decision memo: revise before production approval.** The proposed fields do not establish five-replica availability, request completion, network isolation, or database durability. Adopt the configuration choices below, then validate the application and cluster prerequisites. All citations refer to local files relative to the supplied `docs/` directory; ranges are source lines.

1. **PDB and rollout availability.** `minAvailable: 5` cannot prevent involuntary node-failure losses; those losses nevertheless consume the disruption budget. During an ordinary `kubectl drain`, eviction requests respect the PDB and retry when rejected, potentially blocking the drain. This constrains permitted evictions; it cannot guarantee five healthy replicas through concurrent failures. Deployment rolling updates are explicitly outside PDB enforcement, although their unavailable Pods count against the budget. Thus `maxUnavailable: 2` permits four available replicas from six. Recommend `maxUnavailable: 0`, `maxSurge: 1`, with spare scheduling capacity; `maxUnavailable: 1` is compatible with a five-replica rollout floor but leaves less margin. Neither protects against independent failures. Sources: `concepts/workloads/pods/disruptions.md:92–145`; `concepts/workloads/controllers/deployment.md:1183–1212`.

2. **Zone spreading and zone loss.** Configure a matching application selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, targeting 2/2/2 placement. The topology key groups nodes sharing its label value. With `DoNotSchedule`, skew limits the target domain’s matching-Pod count relative to the global minimum; violating placements remain pending. `ScheduleAnyway` instead prefers reduced skew while allowing imbalance. Recommend the former when strict spreading outweighs immediate replacement capacity; choose the latter deliberately if surviving-zone capacity takes priority. Zone-loss behavior depends on eligible domains, labels, affinity and taints. With `minDomains: 3`, fewer eligible domains make the global minimum zero, potentially blocking replacements. Omitted `minDomains` behaves as one. Constraints do not guarantee rebalancing after removal. Losing two replicas also immediately leaves four. Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:76–126,205–209,605–623`.

3. **Probes for slow startup.** Use a startup probe with `failureThreshold × periodSeconds` covering measured worst-case initialization. Until it succeeds, readiness and liveness probes do not run. Exhausting startup failures kills the container, subject to its restart policy. After startup, readiness should test whether the API can accept requests; failure removes its IP from matching Service endpoints without itself requiring a restart. Liveness should detect unrecoverable failure, such as deadlock, rather than routine overload or temporary database unavailability; its failure kills the container, followed by restart-policy handling. Probe endpoints and thresholds are application choices requiring load testing: the docs warn that incorrect liveness checks can cause cascading failures. Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:13–48,311–347`; `concepts/workloads/pods/pod-lifecycle.md:474–497`.

4. **Termination and long requests.** The grace-period countdown begins **before** `preStop`; the hook consumes that budget. During ordinary graceful termination, kubelet runs the hook before asking the runtime to send TERM to process 1. A still-running hook can receive a small, one-off two-second extension. Remaining processes receive SIGKILL when graceful shutdown expires. Concurrently, terminating EndpointSlice entries remain present but have `ready: false`, excluding regular traffic; `serving` supports consumers implementing draining. These concurrent actions do not establish instantaneous traffic withdrawal or completion of existing requests. Thirty seconds is a default, not a completion guarantee. Implement signal handling and draining, then size grace time for hooks and measured request duration. Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:992–1008`; `concepts/workloads/pods/pod-lifecycle.md:584–642`.

5. **Resources and CPU utilization.** Set explicit CPU requests for every relevant container: scheduling uses requests against node capacity, and HPA CPU utilization is measured relative to requests. Requests are not consumption ceilings; containers can exceed them when resources permit. CPU limits impose throttling, potentially increasing latency. Memory limits instead use reactive OOM enforcement: exceeding a limit may lead to termination rather than immediate throttling. If a limit exists without a request or admission default, Kubernetes copies that limit into the request. Missing relevant CPU requests make Pod utilization undefined, and HPA does not act on that metric. Choose values from measurements rather than assuming limits ensure performance. Sources: `concepts/configuration/manage-resources-containers.md:27–67,230–241`; `tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **HPA’s conservative adjustments.** The raw recommendation is the ceiling of current replicas multiplied by current/desired metric value, with default tolerance 0.1. Failed Pods are discarded, terminating Pods ignored, and missing metrics set aside. CPU measurements from not-yet-ready Pods are also set aside. Missing metrics are conservatively treated as 100% of target during downscale and 0% during upscale; not-yet-ready Pods are treated as 0% when damping upscale. Reversal of direction or entry into tolerance cancels scaling. Default readiness-delay and CPU-initialization periods are 30 seconds and five minutes. Downscale stabilization defaults to 300 seconds, choosing the highest recommendation within the window. Metrics API availability, usually through separately deployed Metrics Server, is a prerequisite. Sources: `tasks/run-application/horizontal-pod-autoscale.md:113–219`.

7. **Least-privilege networking.** Select the API and database Pods with default-deny ingress and egress policies, then allow only approved callers to the API port, API-to-database traffic on the database port, DNS resolution, and demonstrated operational dependencies. Ingress and egress isolation are independent: selecting a Pod for one direction does not isolate the other. Policies combine additively, so an existing broad allow remains effective despite a new restrictive policy. Pod-to-Pod connections require both source egress and destination ingress permission; replies to allowed connections are implicitly permitted. Confirm namespace selectors and actual DNS destinations. Enforcement requires a NetworkPolicy-capable networking implementation; merely creating policy objects can have no effect. Sources: `concepts/services-networking/network-policies.md:45–81`; `concepts/security/multi-tenancy.md:208–234`.

8. **Secrets and repository exposure.** Reject base64-encoded Secrets in Git as sufficient protection. The docs describe base64 credentials as obscured but not secret, and show API-returned base64 values can be decoded. Secrets are stored unencrypted in etcd by default. Enable encryption at rest, verify stored ciphertext, and configure least-privilege RBAC and container access. Crucially, restricting direct Secret reads is insufficient: authorization to create Pods in a namespace—including indirectly through Deployments—can expose any Secret there. Review workload-creation permissions alongside Secret permissions. Cluster encryption does not protect credential copies already committed to a repository; remove those copies and replace exposed credentials. Sources: `concepts/configuration/secret.md:35–48,280–306`; `tasks/administer-cluster/encrypt-data.md:534–588`.

9. **Storage lifecycle and existing volumes.** A StorageClass reclaim-policy change does not retroactively rewrite existing PV policies: the class supplies provisioning-time policy; existing PVs require individual edits or patches. Dynamically provisioned volumes default to `Delete` when unspecified. For supporting plugins, `Delete` removes both the PV and backing storage. `Retain` leaves a released PV and its data after PVC deletion, requiring manual reclamation. Separately, StatefulSet-generated PVCs default to retention when the StatefulSet is deleted or scaled down; `persistentVolumeClaimRetentionPolicy` can change either behavior to deletion. PVC deletion then invokes the PV’s reclaim policy. Recommend explicit retention decisions for the database, including inspection of existing PVs. Sources: `concepts/storage/storage-classes.md:32–38,126–135`; `concepts/storage/persistent-volumes.md:185–210`; `reference/kubernetes-api/workload-resources/stateful-set-v1.md:130–146`.

10. **Prioritized rollout and validation checklist.** First, protect credentials and inspect existing database PV policies before destructive lifecycle operations. Second, confirm policy enforcement, DNS access, metrics availability, zone labels and spare capacity. Third, deploy measured resource requests, startup/readiness/liveness checks, graceful shutdown, and the compatible rollout strategy. Finally, exercise rolling updates, eviction-based drains, node and zone loss, missing metrics, and long-request termination while recording availability and errors. These are validation activities, not documented success guarantees. Specifically unresolved are application signal/drain correctness, worst-case startup and request duration, surviving-zone scheduling capacity, CNI enforcement, and database storage failover, recovery and durability. Dynamic provisioning alone establishes none of those database properties. Sources: `concepts/workloads/pods/pod-lifecycle.md:584–642`; `concepts/services-networking/network-policies.md:45–49`; `tasks/run-application/horizontal-pod-autoscale.md:113–119`; `concepts/storage/persistent-volumes.md:185–210`.
