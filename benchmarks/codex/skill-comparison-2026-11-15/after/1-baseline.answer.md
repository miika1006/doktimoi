Decision: revise the design before production approval. Kubernetes provides useful controls, but the proposed settings do not establish five-replica availability, completed requests during shutdown, protected credentials, or database durability. The following recommendations distinguish documented behavior from configuration choices and prerequisites. Citations refer only to the supplied local documentation.

1. **PDB and rollout availability.** `minAvailable: 5` cannot prevent involuntary disruption: node failure can immediately reduce availability below five, although those unavailable Pods count against the budget. During a node drain using the Eviction API, the PDB constrains permitted evictions; requests can be rejected and retried. This protection depends on using eviction rather than direct deletion. Deployment rolling updates are explicitly **not constrained by PDBs**. Consequently, `maxUnavailable: 2` permits four available replicas from six. Choose `maxUnavailable: 1`, preferably `0` with `maxSurge: 1` if capacity permits, and retain the PDB for eviction protection. These controls do not guarantee availability during concurrent failures.  
   Sources: `docs/concepts/workloads/pods/disruptions.md:99–145`; `docs/concepts/workloads/controllers/deployment.md:1183–1211`.

2. **Zone placement.** Configure a matching Pod selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`. With six scheduled replicas and three eligible, adequately provisioned zones, the intended distribution is two per zone. The topology key groups nodes by label value. Under `DoNotSchedule`, skew limits the difference between the target domain’s count and the global minimum; violating placements remain unscheduled. `ScheduleAnyway` merely favors reduced skew. Explicitly choose outage behavior: `minDomains: 3` makes the global minimum zero when fewer than three domains remain eligible, potentially blocking replacements. Omitting it allows balancing across remaining eligible domains. Actual behavior depends on eligibility and surviving node labels; the scheduler discovers domains from existing nodes. Constraints do not guarantee continued balance after Pod removal.  
   Sources: `docs/concepts/scheduling-eviction/topology-spread-constraints.md:82–130,527–529,605–619`.

3. **Probes for slow startup.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case startup. Until startup succeeds, readiness and liveness probes are disabled; their initial delays begin afterward. Use readiness to indicate the API can accept requests, including required database functionality where appropriate. Failed readiness removes the Pod from matching Service endpoints without restarting its container. Use liveness for conditions where restarting helps, such as an application deadlock; avoid making a database outage automatically trigger restarts. Startup or liveness failure at the configured threshold triggers container restart behavior. Probe endpoints and thresholds are application choices, not proof of health.  
   Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–318,398–422`; `docs/concepts/workloads/pods/pod-lifecycle.md:479–497`.

4. **Termination and long requests.** The grace-period countdown begins **before** `preStop`, so the hook consumes the shutdown budget. The kubelet runs the hook, then requests TERM delivery to container process 1; runtime/image stop-signal behavior can affect the signal. A still-running hook can receive a one-off two-second extension. Concurrently, terminating endpoints remain represented in EndpointSlices with `ready: false`, excluding regular traffic; `serving` supports draining decisions. Remaining processes receive SIGKILL when grace expires. Thirty seconds therefore does not guarantee request completion. Implement signal handling and draining, then size grace for the hook, longest supported requests, and cleanup based on tests.  
   Sources: `docs/reference/kubernetes-api/workload-resources/pod-v1.md:1006–1008`; `docs/concepts/workloads/pods/pod-lifecycle.md:567–577,591–639`.

5. **Resource configuration.** Set explicit, measured CPU requests for every relevant container. Requests inform scheduling and CPU weighting under contention; they are not CPU ceilings. CPU limits impose throttling, potentially extending request latency. Memory limits are enforced reactively through OOM killing, rather than CPU-style throttling; exceeding a limit need not cause an immediate kill. Choose memory requests and limits from observed working sets and peaks. CPU-utilization HPA measures usage relative to requests. If relevant container requests are missing, Pod CPU utilization is undefined and HPA takes no action for that metric. Check effective configuration: a limit can become the request when no request or admission default exists.  
   Sources: `docs/concepts/configuration/manage-resources-containers.md:18–66,230–265`; `docs/tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **HPA’s conservative adjustments.** The initial calculation rounds up current replicas multiplied by the current-to-target metric ratio, but this is not necessarily the final scaling decision. Missing metrics are conservatively treated as 100% of target during downscale and 0% during upscale. Not-yet-ready CPU Pods are set aside and, for an otherwise indicated upscale, assumed to consume 0%, dampening growth. Readiness classification uses configurable windows, defaulting to 30 seconds and five minutes. A recalculated ratio that reverses direction or falls within tolerance produces no scaling. Downscale stabilization defaults to five minutes, selecting the highest recommendation within that window. Slow startup can therefore delay useful capacity despite a high reported utilization.  
   Source: `docs/tasks/run-application/horizontal-pod-autoscale.md:132–218`.

7. **Least-privilege networking.** Establish default-deny ingress and egress, then allow the actual client/ingress path to the API port, API egress to the database port, and database ingress from the API. Allow DNS queries to the cluster’s actual DNS destination, plus other demonstrated dependencies. Ingress and egress isolation are independent. Policies are additive unions: another broad allow policy defeats intended restrictions; policy ordering cannot override it. A Pod-to-Pod connection requires permission from both source egress and destination ingress, while replies to permitted connections are implicitly allowed. NetworkPolicy requires an enforcing network plugin/CNI; merely creating policy objects has no effect without support.  
   Sources: `docs/concepts/services-networking/network-policies.md:45–81,115–122,254–259`; `docs/concepts/security/multi-tenancy.md:215–220`.

8. **Secrets.** Reject base64-encoded credentials in Git as adequate protection. The documentation demonstrates decoding base64 and describes encoded authentication data as “obscured but not secret.” Enable encryption at rest for Secrets, which otherwise default to unencrypted etcd storage. Apply least-privilege RBAC and restrict which containers receive credentials. Review workload-creation permissions alongside Secret-read permissions: permission to create a Pod—or indirectly a Deployment—in a namespace can expose any Secret there by mounting it into a workload. Encryption at rest does not solve repository disclosure or authorized API access. Credential delivery and repository protection require separate decisions.  
   Source: `docs/concepts/configuration/secret.md:35–48,280–306`.

9. **Persistent-storage lifecycle.** Changing a StorageClass reclaim policy does not retroactively update existing PVs: dynamically provisioned PVs inherit their policy, and existing PVs must be edited or patched separately. Prefer explicit `Retain` for database storage where accidental deletion must preserve data. After PVC deletion, `Retain` leaves the PV released with data requiring manual reclamation; supported `Delete` removes both PV and backing storage. StatefulSet deletion/scaling normally retains PVCs, unlike explicitly deleting a PVC. Its optional retention policy can independently delete claims on deletion or scale-down, subject to the documented feature-gate prerequisite; the PV’s reclaim policy then governs storage disposal. Dynamic provisioning alone establishes no database recovery guarantee.  
   Sources: `docs/concepts/storage/storage-classes.md:126–135`; `docs/concepts/storage/persistent-volumes.md:178–210`; `docs/concepts/workloads/controllers/statefulset.md:391–421`.

10. **Prioritized rollout and validation checklist.** First remove exposed credential handling, verify encryption/RBAC, inventory existing PV policies, and establish a tested database recovery procedure. Second configure startup/readiness/liveness, graceful draining, resources, compatible rollout settings, and explicit HPA bounds. Third verify zone labels/capacity and the chosen outage tradeoff, then stage network isolation with positive and negative connectivity tests. Finally exercise rollout, eviction-based drain, abrupt node/zone loss, missing metrics, slow startup, and long-request shutdown under load. Required validation limits include application shutdown correctness, sufficient surviving-zone and surge capacity, CNI enforcement, CPU’s usefulness as a demand signal, and database recovery: these documents establish none for this deployment.  
   Sources: `docs/concepts/workloads/pods/disruptions.md:107–136`; `docs/concepts/scheduling-eviction/topology-spread-constraints.md:605–619`; `docs/concepts/services-networking/network-policies.md:45–49`; `docs/tasks/run-application/horizontal-pod-autoscale.md:153–218`; `docs/concepts/storage/persistent-volumes.md:178–210`.
