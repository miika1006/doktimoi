**Decision memo: revise the design before production approval.** The proposed fields do not collectively guarantee five serving replicas, completed requests, or database durability. The following recommendations use only the supplied Kubernetes v1.32 documentation. All source paths below are relative to `/var/folders/3t/t35161bs2slggt46tnrk0b4c0000gn/T/doktimoi-bench-1-doktimoi-gCiX7q/docs`; citations include source line ranges.

1. **PDB protection has three different outcomes.** During **node failure**, `minAvailable: 5` cannot prevent involuntary disruption; unavailable Pods nevertheless consume the budget. During **node drain**, tools using the Eviction API respect the budget: with six healthy matching Pods, one eviction is permitted before replacements restore health. Drain may block or time out; direct deletion bypasses this protection. During a **Deployment rollout**, unavailable Pods count against the budget, but the Deployment controller is not constrained by it. (`concepts/workloads/pods/disruptions.md:61–64,92–136`)

   Proposed `maxUnavailable: 2` therefore permits a rollout availability floor of four. Recommend `maxUnavailable: 0, maxSurge: 1`, with capacity for replacement Pods and overlapping termination. Setting `maxUnavailable: 1` would also align the rollout floor with five at six desired replicas, but leaves less margin. These settings cannot prevent concurrent failures. (`concepts/workloads/controllers/deployment.md:327–332,1183–1206`)

2. **Spread across zones, while choosing the failure tradeoff explicitly.** Select the API’s Pods and use `topologyKey: topology.kubernetes.io/zone`, with consistent node labels and `maxSkew: 1`. The topology key groups nodes into domains. Under `DoNotSchedule`, skew limits the difference between matching Pods in the target domain and the global minimum; under `ScheduleAnyway`, it expresses a preference for reducing skew. Six Pods across three usable zones can thus be balanced two per zone. (`concepts/scheduling-eviction/topology-spread-constraints.md:76–135,197–211`)

   For this API, prefer `ScheduleAnyway` if replacement capacity during an outage matters more than strict balance. Hard constraints can leave replacements Pending when a zone is unavailable. Results depend on eligible domains and taint handling: `minDomains: 3` makes the global minimum zero when fewer than three domains qualify, potentially blocking further placement. Without it, the default is one. Neither mode guarantees five survivors: losing a zone holding two replicas leaves four. Scheduling also does not guarantee rebalancing after removals. (`concepts/scheduling-eviction/topology-spread-constraints.md:95–125,178–191,605–623`)

3. **Use startup protection, readiness for admission, and liveness for recovery.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Only after startup succeeds do readiness and liveness probes begin, including their configured delays. Readiness should indicate ability to serve; failure makes the Pod unready and removes it from Service load balancers without restarting the container. (`tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:21–34,311–347,398–423`)

   Liveness should detect an unrecoverable condition such as deadlock. Repeated startup or liveness failures trigger container restart; repeated readiness failures do not. As a configuration choice, avoid treating a temporary database outage as proof that restarting every API container helps: the docs explicitly warn that poorly designed liveness checks can cause cascading failures. (`tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:13–19,36–48,411–423`)

4. **Thirty seconds is a shutdown budget, not a request-completion guarantee.** The grace-period countdown begins **before** `preStop`. The hook runs before the runtime sends TERM, ordinarily SIGTERM to process 1; image `STOPSIGNAL` settings can affect the signal. Hook execution consumes the available shutdown time. An overrun can receive a one-off two-second extension, but remaining processes ultimately receive SIGKILL. (`reference/kubernetes-api/workload-resources/pod-v1.md:992–1008`; `concepts/workloads/pods/pod-lifecycle.md:565–610,636–646`)

   Endpoint processing happens concurrently with local shutdown. Terminating endpoints remain represented temporarily, with `ready: false` so load balancers avoid regular traffic; `serving` supports consumers implementing draining. This does not establish that existing long requests finish. Measure request duration, application signal handling, and routing convergence; configure enough grace for hooks plus draining and cleanup. (`concepts/workloads/pods/pod-lifecycle.md:612–638`)

5. **Size resource requests and limits from measurements.** CPU and memory requests drive scheduling capacity checks; requests are not usage ceilings. Containers may exceed requests when resources are available. CPU limits enforce throttling, whereas memory limits are enforced reactively through possible OOM kills when memory pressure is detected. A memory limit does not promise immediate termination at the boundary. (`concepts/configuration/manage-resources-containers.md:27–54,230–241`)

   Specify appropriate CPU requests for every container relevant to utilization-based HPA. Utilization is measured relative to requests; if relevant requests are missing, Pod utilization is undefined and HPA cannot act on that metric. A specified limit can become the request when neither an explicit request nor an admission default exists, so inspect effective values. (`concepts/configuration/manage-resources-containers.md:62–67`; `tasks/run-application/horizontal-pod-autoscale.md:89–101`)

6. **HPA deliberately adjusts the raw ratio.** The basic calculation rounds up `currentReplicas × currentMetricValue / desiredMetricValue`, with default tolerance of 0.1. Terminating and failed Pods are excluded; missing metrics and qualifying not-yet-ready CPU samples are set aside. (`tasks/run-application/horizontal-pod-autoscale.md:127–165`)

   Missing samples are conservatively treated as 100% of target for downscale and 0% for upscale. Not-yet-ready Pods further dampen upscale using 0%. If recalculation reverses direction or enters tolerance, scaling stops. Default readiness-delay and CPU-initialization windows are 30 seconds and five minutes. Downscale stabilization selects the highest recommendation within the default five-minute window. Consequently, displayed average utilization and the raw ratio need not predict the actual scaling action. (`tasks/run-application/horizontal-pod-autoscale.md:167–218`)

7. **Replace default allow with explicit connection permissions.** Establish default-deny ingress and egress, then allow approved callers to the API port, API connections to the database port, and required DNS queries to the actual cluster DNS service. Use specific Pod and namespace selectors and narrowly scoped destinations. DNS access must be deliberately preserved. (`concepts/security/multi-tenancy.md:208–234`)

   Ingress and egress isolation are independent. Policies combine additively: an existing broad allow remains effective despite adding a restrictive policy. A connection requires permission at both source egress and destination ingress; permitted replies are implicitly allowed. A supporting network plugin/controller is a prerequisite—creating NetworkPolicy objects alone has no effect. Validate allowed and denied flows on the installed CNI. (`concepts/services-networking/network-policies.md:45–81`)

8. **Base64 Secrets in Git are insufficient protection.** Base64 obscures data but does not make it secret; anyone who reads it can decode it. Remove readable credential values from Git as a configuration decision. Kubernetes Secrets are also unencrypted in etcd by default. Enable encryption at rest, least-privilege RBAC, and access only from containers that need the credentials. (`concepts/configuration/secret.md:34–49,282–307`)

   Restrict Pod and workload creation as well as direct Secret reads: permission to create Pods in a namespace permits indirect access to its Secrets, including through Deployment creation. Verify encrypted storage and successful API decryption; an enabled setting alone is inadequate evidence. (`concepts/configuration/secret.md:34–49`; `tasks/administer-cluster/encrypt-data.md:534–588`)

9. **Reclaim policy belongs to each existing PV.** Dynamically provisioned PVs inherit their StorageClass policy at creation; the default is `Delete`. Changing the class is not a retroactive change to existing PVs—inspect and patch those separately. (`concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:201–210`)

   Following PVC deletion, `Retain` leaves the PV and data for manual reclamation; it is not immediately reusable. With a supporting plugin, `Delete` removes both the PV and external storage asset. StatefulSet deletion or scale-down is a separate lifecycle decision: its PVC retention defaults to `Retain`, while `whenDeleted` and `whenScaled` can request PVC deletion. Choose database retention deliberately; provisioning alone establishes no backup or recovery guarantee. (`concepts/storage/persistent-volumes.md:185–210`; `reference/kubernetes-api/workload-resources/stateful-set-v1.md:130–146`)

10. **Prioritize rollout and validation as follows.**

   - **First, protect credentials and data:** remove encoded credentials from Git, verify encryption/RBAC, inspect existing PV policies, and exercise database restoration. Sources: Secret and storage passages in answers 8–9.
   - **Next, establish serving behavior:** measure startup and shutdown, validate probes and draining, reserve surge capacity, configure zone spread, and use the compatible rollout settings above. Sources: rollout, topology, and lifecycle passages in answers 1–4.
   - **Then, validate control loops and isolation:** verify the resource-metrics API prerequisite, effective requests, HPA behavior, and permitted/denied network flows. Consider HPA `minReplicas: 6` to preserve the planned baseline. (`tasks/run-application/horizontal-pod-autoscale.md:89–115,150–218`; `concepts/services-networking/network-policies.md:45–81`)

   Finally, rehearse drain, rollout, node loss, and zone loss under representative load. The documents do not establish this application’s request-completion time, five-replica throughput, replacement scheduling capacity during zone failure, or database durability and recovery time. These remain application and cluster validation requirements, beyond the documented mechanisms cited above.
