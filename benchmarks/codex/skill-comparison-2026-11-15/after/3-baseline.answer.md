**Decision memo: revise before production approval.** The proposed fields do not collectively guarantee five serving replicas, completed requests, network isolation, or database durability. Adopt the following configuration choices and validate the identified application and cluster dependencies. Citations refer only to the supplied local documentation; line ranges are inclusive.

1. **PDB protection depends on the disruption.** Node failure is involuntary: a PDB cannot prevent it, although unavailable Pods count against its budget. During an Eviction API–based node drain, `minAvailable: 5` constrains permitted evictions; requests can be rejected and retried. This is not protection against concurrent failures or direct deletion. During a Deployment rolling update, unavailable Pods count against the budget, but the Deployment is not constrained by it. Consequently, `maxUnavailable: 2` permits rollout availability to fall to four. Recommend `maxUnavailable: 0`, `maxSurge: 1`, with scheduling capacity for the extra Pod; `maxUnavailable: 1` is compatible with a five-replica rollout floor at six desired replicas, but leaves less margin. Neither setting guarantees availability during failures. Sources: [disruptions.md, lines 99–145](docs/concepts/workloads/pods/disruptions.md#L99-L145); [deployment.md, lines 1186–1211](docs/concepts/workloads/controllers/deployment.md#L1186-L1211).

2. **Spread by zone, with an explicit failure tradeoff.** Recommend a selector matching all API replicas, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`. The key groups nodes by equal label values. With `DoNotSchedule`, skew limits the difference between the target domain’s matching-Pod count and the global minimum; violating placements remain pending. `ScheduleAnyway` makes balanced placement a preference and permits skew. Six evenly placed replicas mean two per zone, so losing one zone initially leaves only four—an arithmetic consequence the PDB cannot prevent. Recovery depends on eligible domains and capacity: `minDomains: 3` makes the minimum zero when fewer than three domains remain eligible, potentially blocking replacements. Omitting it defaults to one, permitting balancing across remaining eligible domains. Choose this tradeoff deliberately; domain discovery depends on existing nodes, and removals need not preserve balance. Sources: [topology-spread-constraints.md, lines 82–130](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L82-L130), [lines 605–619](docs/concepts/scheduling-eviction/topology-spread-constraints.md#L605-L619).

3. **Use all three probes for distinct decisions.** Configure a startup probe with a failure budget covering measured worst-case initialization. Until it succeeds, readiness and liveness probes are disabled; their initial-delay clocks also wait. Use readiness to indicate whether this instance can serve requests, including required database readiness where appropriate. Readiness failure removes its address from matching Service endpoints without restarting the container. Use liveness for conditions requiring restart, such as an application deadlock. Startup or liveness failure at the configured threshold triggers termination/restart behavior; avoid making transient database unavailability automatically restart every API instance. Endpoint criteria and thresholds remain application choices. Sources: [pod-lifecycle.md, lines 479–497](docs/concepts/workloads/pods/pod-lifecycle.md#L479-L497), [lines 544–557](docs/concepts/workloads/pods/pod-lifecycle.md#L544-L557); [configure-liveness-readiness-startup-probes.md, lines 398–422](docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md#L398-L422).

4. **Thirty seconds is a deadline, not a request-completion guarantee.** The grace-period countdown starts **before** `preStop`; the hook consumes that budget. Normally, the hook runs before the runtime sends TERM to the container process. An overlong hook can receive a one-off two-second extension; surviving processes are ultimately killed with SIGKILL. Concurrently, terminating endpoints remain temporarily in EndpointSlices with `terminating` exposed and `ready: false`, excluding regular traffic; `serving` supports draining decisions. These actions are concurrent, not an atomic traffic-cutoff sequence. Set grace time from measured hook duration, longest supported requests, and cleanup, and implement signal handling and connection draining. Sources: [pod-v1.md, lines 1006–1008](docs/reference/kubernetes-api/workload-resources/pod-v1.md#L1006-L1008); [pod-lifecycle.md, lines 591–639](docs/concepts/workloads/pods/pod-lifecycle.md#L591-L639).

5. **Size requests and limits independently.** CPU requests inform scheduling and typically determine relative CPU weighting under contention; they are not a usage ceiling. CPU limits impose throttling. Memory limits are enforced reactively through OOM kills, rather than CPU-style throttling, and exceeding them need not cause immediate termination. Set explicit CPU requests for every relevant container: utilization-based HPA measures usage relative to requests, and missing relevant requests can leave Pod utilization undefined and prevent action for that metric. Check admitted values, because a specified limit can become the request when no request or admission default exists. Sources: [manage-resources-containers.md, lines 18–66](docs/concepts/configuration/manage-resources-containers.md#L18-L66), [lines 230–265](docs/concepts/configuration/manage-resources-containers.md#L230-L265); [horizontal-pod-autoscale.md, lines 89–102](docs/tasks/run-application/horizontal-pod-autoscale.md#L89-L102).

6. **HPA deliberately moderates the raw ratio.** The base calculation is rounded-up current replicas multiplied by current/target metric value, with default tolerance 0.1. Missing metrics are initially set aside, then conservatively assumed at 100% of target for downscaling and zero for upscaling. For CPU, not-yet-ready Pods and samples preceding readiness are also set aside; not-yet-ready Pods count as zero when moderating scale-up. Default readiness and CPU-initialization windows are 30 seconds and five minutes. A recalculated ratio that reverses direction or enters tolerance produces no action. Downscale stabilization defaults to five minutes and selects the highest recommendation in that window. Reported utilization excludes these conservative adjustments, explaining differences between displayed ratios and scaling. Sources: [horizontal-pod-autoscale.md, lines 130–218](docs/tasks/run-application/horizontal-pod-autoscale.md#L130-L218).

7. **Replace default allow with explicit connection permissions.** Apply default-deny ingress and egress, then allow approved clients to API ports and API Pods to the database’s required port. Independently allow the corresponding database ingress. Preserve DNS access to the cluster’s actual resolver endpoints and required ports; Service-name discovery depends on DNS, so validate resolution after isolation. Isolation is directional, and allowed connections are the union of applicable policies: a broad allow policy defeats intended restrictions. Both source egress and destination ingress must permit a Pod-to-Pod connection; reply traffic is implicitly allowed. Enforcement requires a supporting CNI/network controller—creating policy objects alone has no effect. Sources: [network-policies.md, lines 45–81](docs/concepts/services-networking/network-policies.md#L45-L81), [lines 254–262](docs/concepts/services-networking/network-policies.md#L254-L262); [dns-pod-service.md, lines 15–26](docs/concepts/services-networking/dns-pod-service.md#L15-L26).

8. **Base64 does not protect Git credentials.** Reject plaintext-equivalent, base64-encoded Secrets in Git: the documentation explicitly describes base64 credentials as obscured but not secret. Enable Secret encryption at rest and least-privilege RBAC, and restrict exposure to containers needing credentials. Encryption at rest does not protect a readable Git copy. Restrict workload creation too: permission to create Pods, including indirectly through Deployments, can expose any Secret in that namespace. Verify existing data was migrated to encrypted storage; an encryption-provider configuration alone does not establish successful migration. Sources: [secret.md, lines 35–48](docs/concepts/configuration/secret.md#L35-L48), [lines 305–307](docs/concepts/configuration/secret.md#L305-L307); [encrypt-data.md, lines 69–73](docs/tasks/administer-cluster/encrypt-data.md#L69-L73).

9. **Inspect existing PV policies separately.** Dynamically provisioned PVs inherit their StorageClass reclaim policy, defaulting to `Delete`; changing class configuration does not retrofit existing PVs—edit or patch those PVs individually. After PVC deletion, `Retain` leaves the PV released with its data for manual reclamation. Supported `Delete` implementations remove both PV and backing storage. StatefulSet deletion or scaling is a separate PVC-lifecycle decision: retention defaults to `Retain`; configured `whenDeleted`/`whenScaled: Delete` removes applicable template-created PVCs, after which PV reclamation applies. Confirm the documented feature prerequisite before relying on automatic PVC deletion. Sources: [storage-classes.md, lines 126–135](docs/concepts/storage/storage-classes.md#L126-L135); [persistent-volumes.md, lines 178–210](docs/concepts/storage/persistent-volumes.md#L178-L210); [statefulset.md, lines 391–423](docs/concepts/workloads/controllers/statefulset.md#L391-L423).

10. **Roll out in priority order.** First remove Git credential exposure, verify encryption/RBAC, and inspect database PVC/PV retention. Second measure startup, resource demand, and request duration; configure probes, requests, shutdown, and conservative rollout settings. Third establish zone placement, surge capacity, metrics availability, and tested network allow rules. Finally exercise a rollout, drain, zone outage, missing metrics, and database recovery under load. Acceptance must validate at least request completion during termination, CNI enforcement/DNS reachability, spare scheduling capacity, and database recovery/durability; these documents do not guarantee those application outcomes. Metrics APIs are prerequisites, and topology-constrained storage may need driver-supported `WaitForFirstConsumer` to avoid unschedulable Pods. Sources: [horizontal-pod-autoscale.md, lines 350–361](docs/tasks/run-application/horizontal-pod-autoscale.md#L350-L361); [storage-classes.md, lines 171–195](docs/concepts/storage/storage-classes.md#L171-L195); shutdown and networking evidence in answers 4 and 7.
