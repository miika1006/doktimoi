Decision: revise the design before production approval. Kubernetes provides useful controls, but the proposed settings do not establish five-replica availability, completed long requests, protected credentials, or database durability. The recommendations below distinguish documented behavior from configuration choices and validation requirements. Citations refer to local files in the supplied corpus.

1. **The PDB does not guarantee five available replicas in all three cases.** During node failure, involuntary disruption cannot be prevented by a PDB, although unavailable Pods count against its budget. During a normal `kubectl drain`, eviction requests respect the budget and can be rejected and retried; with six healthy replicas, `minAvailable: 5` permits one such disruption. This depends on using the Eviction API rather than direct deletion. Deployment rolling updates are explicitly not limited by PDBs. Consequently, `maxUnavailable: 2` permits rollout availability to fall to four.

   Recommend `maxUnavailable: 1`, `maxSurge: 1`, with capacity for the surge and meaningful readiness checks. Consider a measured `minReadySeconds` before counting replacements as available. These constrain rollout behavior; concurrent failures can still reduce availability. Sources: `docs/concepts/workloads/pods/disruptions.md:99–136`; `docs/concepts/workloads/controllers/deployment.md:1191–1206,1325–1328`.

2. **Spread across zones, but choose the failure tradeoff explicitly.** Use an API Pod selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, aiming for two replicas per zone. The topology key identifies node-label domains. With `DoNotSchedule`, skew limits the difference between the target domain’s matching-Pod count and the global minimum; violating placements remain pending. `ScheduleAnyway` instead prefers placements that reduce skew without enforcing that bound.

   Recommend `ScheduleAnyway` where restoring capacity during zone loss takes priority over strict balance. With hard constraints, the outcome depends on eligible domains: `minDomains: 3` makes the global minimum zero when fewer than three remain, potentially blocking replacements. Without it, the default is one. A failed zone may still affect calculations depending on node eligibility; recovery elsewhere is not guaranteed. Losing two of six evenly spread replicas leaves four immediately. Constraints also need not remain satisfied after removals. Sources: `docs/concepts/scheduling-eviction/topology-spread-constraints.md:82–130,527–529,607–619`.

3. **Use startup protection, readiness for serviceability, and liveness for recoverable hangs.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Until startup succeeds, other probes are disabled, and their initial delays do not begin. Afterward, readiness should establish whether the API can accept requests, including required database dependencies where appropriate. Readiness failure removes its address from matching Service endpoints without restarting the container. Liveness should detect conditions that justify restarting, rather than treating every temporary database outage as a dead process. Startup or liveness failure at the configured threshold triggers container termination and restart handling.

   Probe endpoints, thresholds, and dependency behavior remain application choices. Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–318,398–422`; `docs/concepts/workloads/pods/pod-lifecycle.md:479–497,525–526`.

4. **Thirty seconds is a shutdown deadline, not a request-completion guarantee.** Deletion records the grace period before local shutdown. The kubelet runs a configured `preStop` hook before asking the runtime to send TERM to container process 1; hook execution consumes the same grace period. A still-running hook can receive a small, one-off two-second extension. Remaining processes receive SIGKILL when grace expires. Runtime/image stop-signal configuration can affect the signal used.

   Endpoint processing happens concurrently with shutdown. Terminating endpoints are not immediately removed from EndpointSlices, but have `ready: false`; `serving` supports draining decisions. Configure an application drain procedure and a grace period covering hook work and measured request completion. These passages establish neither instantaneous traffic propagation nor completion of arbitrary long requests. Sources: `docs/concepts/workloads/pods/pod-lifecycle.md:567–597,603–639`.

5. **Size requests and limits from measurements.** CPU requests participate in scheduling capacity checks and typically determine CPU weighting under contention; they are not a CPU ceiling. CPU limits enforce throttling. Memory limits instead use reactive OOM handling: exceeding the limit may cause termination when memory pressure is detected, rather than predictable throttling.

   Set explicit CPU requests for every relevant container and select CPU and memory limits after load testing. Utilization-based HPA measures CPU usage relative to requests. If relevant requests are missing from some containers, Pod CPU utilization is undefined and the autoscaler cannot act for that metric. Field presence alone does not establish adequate throughput or latency. Sources: `docs/concepts/configuration/manage-resources-containers.md:29–53,230–257`; `docs/tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **HPA deliberately adjusts the raw ratio.** Its starting calculation is current replicas multiplied by current/desired metric value, rounded upward, with a default 0.1 tolerance. Missing metrics are set aside, then conservatively treated as 100% of target for downscaling and 0% for upscaling. CPU metrics from not-yet-ready Pods, or preceding readiness, can also be set aside; not-yet-ready Pods are assumed at 0% when damping an otherwise indicated upscale. Recalculation can cancel scaling if it reverses direction or enters tolerance.

   The readiness-delay and CPU-initialization defaults are 30 seconds and five minutes. Default downscale stabilization chooses the highest recommendation within five minutes. Thus displayed average utilization and actual scaling can differ. Sources: `docs/tasks/run-application/horizontal-pod-autoscale.md:132–202,213–218`.

7. **Replace default allow with explicit ingress and egress allowances.** Select the workload Pods with default-deny policies for both directions, then allow approved callers to the API port, API egress to the database port, and corresponding database ingress. If database egress is isolated, allow its necessary outbound dependencies separately.

   Isolation is independent by direction. Applicable policies combine additively, so an existing broad allow policy can defeat the intended restriction. A Pod-to-Pod connection needs both source egress and destination ingress permission; allowed replies are implicit. Permit access to the actual cluster DNS resolver for name-based connections, validating its addresses and protocols locally. DNS naming does not itself grant network access. Prerequisite: an enforcing network plugin; creating policy objects without one has no effect. Sources: `docs/concepts/services-networking/network-policies.md:45–81,116–122`; `docs/concepts/services-networking/dns-pod-service.md:15–26`.

8. **Base64 is insufficient protection for Secrets in Git.** The documentation demonstrates decoding with `base64 -d` and calls encoded credentials “obscured but not secret.” Reject the proposed repository representation as a confidentiality measure. Configure encryption at rest for Kubernetes Secrets, least-privilege RBAC, and access only from containers requiring them. Encryption of cluster storage does not protect a separate Git copy.

   Secrets are stored unencrypted in etcd by default. Restrict workload-creation permissions too: someone authorized to create Pods in a namespace can read its Secrets through those Pods, including indirectly by creating Deployments. Restricting direct Secret reads alone is therefore insufficient. Sources: `docs/concepts/configuration/secret.md:35–48,286–306`.

9. **StorageClass policy changes do not retrofit existing PVs.** Dynamically provisioned PVs inherit their class’s reclaim policy, defaulting to `Delete`; existing PVs needing different behavior must be edited or patched individually. After PVC deletion, `Retain` leaves the released PV and data for manual reclamation. With supporting plugins, `Delete` removes both the PV and backing storage.

   StatefulSet deletion or scale-down ordinarily retains PVCs. Its separate PVC retention settings, `whenDeleted` and `whenScaled`, can request deletion; the documented feature prerequisites must be satisfied. PVC retention and PV reclamation are separate decisions. Recommend explicit retention choices for database storage; dynamic provisioning alone establishes neither backup nor database recoverability. Sources: `docs/concepts/storage/storage-classes.md:128–135`; `docs/concepts/storage/persistent-volumes.md:180–209`; `docs/concepts/workloads/controllers/statefulset.md:391–423`.

10. **Prioritize validation before broad rollout.** First, remove the credential exposure and verify encryption, RBAC, and enforced network allowances. Second, verify existing PV reclaim settings and database recovery procedures before destructive lifecycle tests. Third, establish requests, probes, shutdown behavior, surge capacity, and zone scheduling. Finally, canary the rollout, drain a node, simulate zone loss, and exercise HPA with startup load and missing metrics.

   Explicitly validate four limits the documents do not establish: request completion within grace; adequate surviving-zone capacity; database failover and restore correctness; and useful application throughput under CPU-based scaling. Also verify the resource metrics API—Metrics Server normally requires separate installation. These are acceptance tests, not guarantees inferred from API fields. Sources: `docs/concepts/workloads/pods/disruptions.md:107–136`; `docs/concepts/workloads/pods/pod-lifecycle.md:619–639`; `docs/tasks/run-application/horizontal-pod-autoscale.md:113–118,183–218`; `docs/concepts/storage/persistent-volumes.md:187–209`.
