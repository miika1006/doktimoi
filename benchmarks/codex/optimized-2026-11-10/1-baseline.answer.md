**Decision memo — revise before production approval.** The proposed fields do not establish application availability, safe draining, confidentiality, or database durability. The following recommendations distinguish documented behavior from choices requiring validation. All citations are local paths relative to the supplied corpus root; ranges identify source lines.

1. **PDB and rollout availability.** `minAvailable: 5` cannot guarantee five replicas during node failure: involuntary disruptions are unpreventable and count against the budget. During an eviction-based node drain, the PDB restricts voluntary disruption; rejected evictions wait or time out. This protection requires tools that respect the Eviction API. Deployment rolling updates bypass PDB enforcement, although their unavailable Pods count against its budget. Thus, `maxUnavailable: 2` permits four available replicas from six. Recommend `maxUnavailable: 0`, `maxSurge: 1`, with capacity for the surge; `maxUnavailable: 1` is also compatible with a five-replica rollout floor. Neither setting prevents concurrent failures.  
   Sources: `docs/concepts/workloads/pods/disruptions.md:99–136`; `docs/concepts/workloads/controllers/deployment.md:1191–1211`.

2. **Zone placement.** Configure an API-label selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, targeting two replicas per zone. The key groups nodes by label value. With `DoNotSchedule`, skew limits the difference between the target domain’s matching-Pod count and the global minimum; `ScheduleAnyway` merely prefers placements reducing skew. Recommend strict spreading only with an explicit outage policy. If fewer than three domains remain eligible, `minDomains: 3` makes the global minimum zero and can block replacement scheduling. Omitting it permits balancing across remaining eligible domains, but eligibility depends on affinity and taint policies; an unavailable zone is not automatically excluded. Losing two replicas still leaves only four initially.  
   Sources: `docs/concepts/scheduling-eviction/topology-spread-constraints.md:82–130,167–189,527–529`.

3. **Probes for slow startup.** Use a startup probe with `failureThreshold × periodSeconds` covering measured worst-case startup. Other probes remain disabled until it succeeds; their initial delays then begin. Use readiness to represent ability to serve requests, including necessary database dependencies, and liveness for application failures that warrant restarting. After the configured consecutive failures, startup/liveness failure triggers container restart; readiness failure keeps the container running but marks the Pod unready and removes it from matching Service endpoints. That is traffic eligibility behavior, not a guarantee that existing requests finish.  
   Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–318,398–422`; `docs/concepts/workloads/pods/pod-lifecycle.md:479–497,519–526`.

4. **Termination and long requests.** The grace-period countdown starts **before** `preStop`; the hook consumes the same budget. Normally, the hook runs before the runtime sends SIGTERM to process 1. A still-running hook can receive a one-off two-second extension; surviving processes receive SIGKILL after grace expires. Concurrently, terminating endpoints remain temporarily in EndpointSlices with `ready: false`; `serving` supports draining-aware consumers. Thirty seconds is a default, not a request-completion guarantee. Configure grace from measured hook duration, request duration, and shutdown behavior, and implement signal handling and connection draining.  
   Sources: `docs/reference/kubernetes-api/workload-resources/pod-v1.md:1008–1008`; `docs/concepts/workloads/pods/pod-lifecycle.md:581–639`.

5. **Resources and CPU utilization.** CPU requests guide scheduling and provide the denominator for utilization-based HPA; they are not usage ceilings. Containers can exceed requests when resources permit. CPU limits enforce throttling, whereas memory limits are enforced reactively through OOM kills, potentially terminating a container rather than slowing it. Set measured requests and limits for every relevant container. If some containers lack CPU requests, Pod CPU utilization is undefined and HPA takes no action for that metric. Inspect effective requests: when a limit exists without a request or admission default, Kubernetes copies the limit into the request.  
   Sources: `docs/concepts/configuration/manage-resources-containers.md:18–53,64–66`; `docs/tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **HPA damping and stabilization.** HPA starts with the rounded-up replica-count ratio, but excludes terminating/failed Pods and sets aside missing metrics and certain not-yet-ready CPU samples. Missing metrics are conservatively assumed at 100% of target for downscaling and 0% for upscaling. Not-yet-ready Pods further dampen scale-up through a 0% assumption. If recalculation reverses direction or falls within tolerance, no scaling occurs. Default readiness-delay and CPU-initialization settings are 30 seconds and five minutes. Downscale stabilization defaults to five minutes and selects the highest recommendation in that window. Consequently, observed scaling can differ from the raw ratio and displayed utilization.  
   Source: `docs/tasks/run-application/horizontal-pod-autoscale.md:132–218`.

7. **Least-privilege networking.** Apply default-deny ingress and egress, then explicitly allow the intended caller-to-API and API-to-database paths on required ports. Ingress and egress isolation are independent. Policies are additive unions: a broad allow cannot be overridden by a narrower policy. A Pod-to-Pod connection requires both source egress and destination ingress permission; reply traffic is implicitly permitted. Allow DNS egress to the cluster’s actual resolver, covering its required transports—the documented kube-dns example exposes TCP and UDP 53. Validate resolver topology and selectors locally. A NetworkPolicy-capable CNI/controller is a prerequisite; merely creating policies can have no effect.  
   Sources: `docs/concepts/services-networking/network-policies.md:45–81,210–259`; `docs/tasks/administer-cluster/dns-debugging-resolution.md:159–169`.

8. **Secrets.** Reject base64-encoded credentials in Git as a protection mechanism. The documentation explicitly describes base64 as obscuring, not securing, a credential. Secrets are stored unencrypted in etcd by default. Enable encryption at rest, restrict Secret access through least-privilege RBAC, and expose credentials only to containers needing them. Also restrict Pod and workload creation: someone authorized to create a Pod—or indirectly a Deployment—in a namespace can use that capability to read its Secrets. Encryption at rest does not protect a readable Git copy; repository confidentiality is not established by these Kubernetes controls.  
   Source: `docs/concepts/configuration/secret.md:35–48,305–307`.

9. **Storage and deletion.** Dynamically provisioned PVs inherit their StorageClass reclaim policy, defaulting to `Delete`. Changing the class’s policy is not a retroactive migration of existing PVs; inspect and patch those PVs individually. After PVC deletion, `Retain` leaves the PV released with data requiring manual reclamation. Supported `Delete` implementations remove both the PV and backing storage. StatefulSet deletion/scaling is a separate trigger: PVC retention defaults to `Retain`. Explicit `whenDeleted` or `whenScaled: Delete` can delete template-created PVCs, after which PV reclaim policy applies. Verify the documented feature-gate prerequisites. If the database is external, StatefulSet semantics do not establish its retention behavior.  
   Sources: `docs/concepts/storage/storage-classes.md:126–135`; `docs/concepts/storage/persistent-volumes.md:178–210`; `docs/concepts/workloads/controllers/statefulset.md:391–423`.

10. **Prioritized rollout and validation checklist.** First, remove exposed credential handling, configure encryption/RBAC, and audit existing PV reclaim policies before destructive testing. Second, establish resource requests, probes, termination handling, rollout limits, and an HPA minimum consistent with the intended six-replica baseline. Third, validate zone labels, outage scheduling, surge capacity, and network enforcement. Finally, stage rolling updates, eviction-based drains, zone loss, missing metrics, long-request termination, and storage recovery exercises.

    At least four limits remain application or cluster validation tasks: worst-case startup time, successful draining of long requests, spare capacity during zone loss, and database recovery/durability. Neither probe fields, grace periods, spread constraints, nor reclaim policies guarantee those outcomes. Validate DNS and CNI enforcement too before accepting default-deny rollout.  
    Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–318`; `docs/concepts/workloads/pods/pod-lifecycle.md:619–639`; `docs/concepts/scheduling-eviction/topology-spread-constraints.md:107–126`; `docs/concepts/storage/persistent-volumes.md:185–210`; `docs/concepts/services-networking/network-policies.md:45–49`.
