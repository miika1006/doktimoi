**Decision: revise before production approval.** The proposed fields do not establish five-replica availability, request completion, network enforcement, or database durability. The recommendations below distinguish documented behavior from configuration choices and validation requirements. Citations are relative to the supplied `docs/` directory.

1. **PDB and rollout availability.** A node failure is involuntary: a PDB cannot prevent it, although unavailable Pods count against the budget. During a node drain using the Eviction API, `minAvailable: 5` constrains permitted evictions; with six healthy replicas, one can be voluntarily disrupted. Drain may wait or time out, and direct Pod deletion bypasses this protection. Deployment rolling updates are **not constrained by PDBs**, although their unavailable Pods count against the budget. Thus, `maxUnavailable: 2` permits the rollout to reduce availability to four. Recommend `maxUnavailable: 0`, `maxSurge: 1`, with capacity for the extra Pod; `maxUnavailable: 1` is another choice compatible with a five-of-six rollout floor. Neither protects against concurrent failures. Keep HPA’s minimum consistent with the intended six-replica baseline. Sources: `concepts/workloads/pods/disruptions.md:60-65,92-145`; `concepts/workloads/controllers/deployment.md:1183-1212`.

2. **Zone spreading.** Configure a selector matching this API’s Pods, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, targeting two replicas per zone. The topology key groups nodes with identical label values into domains. With `DoNotSchedule`, skew bounds the difference between the candidate domain’s count and the global minimum; an unsatisfied constraint blocks placement. `ScheduleAnyway` instead prefers placements reducing skew without enforcing that bound. Choose strict spreading only with an explicit outage plan: when a zone disappears, eligibility and `minDomains` matter. With `minDomains: 3` and fewer than three eligible domains, the global minimum becomes zero, potentially blocking replacements in occupied surviving zones. Soft spreading allows that tradeoff but guarantees no balance. Removal or scale-down can also leave an imbalance. Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:76-132,203-211,605-623`.

3. **Probes for slow startup.** Use a startup probe with `failureThreshold × periodSeconds` covering measured worst-case initialization. Until it succeeds, both readiness and liveness probes are disabled. Exhausting startup failures kills the container, subject to its restart policy. After startup, readiness should measure whether this instance can serve requests; readiness failure removes its IP from matching Service endpoints without itself restarting the container. Liveness should detect conditions requiring restart, such as deadlock; failure kills the container, again subject to restart policy. As a design choice, avoid making a shared database outage alone trigger liveness restarts across every API replica. Probe correctness needs application testing: the docs explicitly warn that poor liveness checks can cause cascading failures. Sources: `concepts/workloads/pods/pod-lifecycle.md:474-500`; `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:43-48,311-347`.

4. **Termination and long requests.** The grace-period clock starts **before** `preStop`; the hook consumes that same budget. Normally, kubelet runs the hook first, then asks the runtime to send TERM to process 1. An unfinished hook can receive a one-off two-second extension; after grace expires, remaining processes receive SIGKILL. Endpoint updates occur alongside shutdown: terminating endpoints remain represented temporarily, but have `ready: false` for regular traffic; `serving` supports draining-aware consumers. Thirty seconds is a default, not a request-completion guarantee. Implement TERM handling and draining, then size grace for hook time plus outstanding work and validate actual traffic behavior. Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:992-1008`; `concepts/workloads/pods/pod-lifecycle.md:584-638`.

5. **Resource requests, limits, and HPA.** CPU requests inform scheduling and provide the denominator for utilization-based CPU autoscaling; they are not usage ceilings. Containers can exceed requests when resources are available. CPU limits impose throttling, potentially increasing latency. Memory limits are enforced reactively through OOM kills, rather than CPU-style throttling, and excess allocation need not cause immediate termination. Set realistic requests for every relevant container and benchmark limits. If some containers lack CPU requests, Pod CPU utilization is undefined and HPA takes no action for that metric. Check effective admitted resources: absent another default, specifying a limit without a request causes Kubernetes to copy the limit into the request. Sources: `concepts/configuration/manage-resources-containers.md:23-67`; `tasks/run-application/horizontal-pod-autoscale.md:88-101`.

6. **HPA’s conservative adjustments.** The raw calculation is the ceiling of current replicas multiplied by current/desired metric value, but it is only a starting point. Missing metrics are treated as 100% of target for downscaling and 0% for upscaling, damping changes. CPU metrics from not-yet-ready Pods are set aside; when considering scale-up, those Pods are conservatively treated as consuming 0%. If recomputation reverses direction or falls within tolerance—default 10%—no scaling occurs. Readiness classification uses configurable defaults of 30 seconds initial readiness delay and five minutes CPU initialization period. Downscale stabilization defaults to five minutes and selects the highest recommendation in the window. Reported utilization excludes these conservative adjustments, explaining apparent discrepancies. A working metrics API, usually supplied by separately installed Metrics Server, is a prerequisite. Source: `tasks/run-application/horizontal-pod-autoscale.md:112-118,129-217`.

7. **Least-privilege networking.** Select API and database Pods with default-deny ingress and egress policies, then allow only intended callers into the API, API egress to the database port, and corresponding database ingress. Add narrowly scoped DNS egress to the cluster’s actual resolver; the documented kube-dns Service exposes both UDP and TCP 53. Ingress and egress isolation are independent. Policies combine additively, so an existing broad allow remains effective; policy order cannot override it. Both source egress and destination ingress must permit a connection, while replies to allowed connections are implicitly permitted. This protection requires a network plugin implementing NetworkPolicy: creating objects alone has no effect. Validate selectors, resolver routing, and denied paths in the actual cluster. Sources: `concepts/services-networking/network-policies.md:43-81`; `tasks/administer-cluster/dns-debugging-resolution.md:158-174`.

8. **Secrets protection.** Reject base64-encoded credentials in Git as a confidentiality mechanism: base64 obscures data but does not make it secret. Remove live credential material from that workflow. Kubernetes Secrets are stored unencrypted in etcd by default; enable encryption at rest and verify it. Apply least-privilege RBAC and expose credentials only to containers needing them. Restrict workload-creation permissions as well as direct Secret reads: someone authorized to create Pods in a namespace can read its Secrets through those Pods, including indirectly through Deployment creation. Encryption at rest does not remove this authorized access path or protect repository copies. Sources: `concepts/configuration/secret.md:34-48,304-307`; `tasks/administer-cluster/encrypt-data.md:574-588`.

9. **Storage lifecycle.** A StorageClass supplies the reclaim policy when a dynamic PV is created; changing the class’s policy does not retrofit existing PVs—inspect and patch those PVs separately. The default is `Delete`. With supported plugins, `Delete` removes both the PV and backing storage; `Retain` leaves a released PV and its data after PVC deletion, requiring manual reclamation. StatefulSet deletion or scale-down is a separate lifecycle decision: its PVC retention defaults are `Retain`, while `whenDeleted` and `whenScaled` can request PVC deletion. Only then does the PV reclaim policy determine storage reclamation. For the database, explicitly choose retention and recovery procedures; dynamic provisioning establishes neither backup nor database recovery guarantees. Sources: `concepts/storage/storage-classes.md:126-135`; `concepts/storage/persistent-volumes.md:185-210`; `reference/kubernetes-api/workload-resources/stateful-set-v1.md:130-144`.

10. **Prioritized rollout and validation checklist.** First, protect credentials, verify encryption and RBAC, and inspect existing PV reclaim policies before destructive lifecycle tests. Second, establish enforcing network policies and confirm allowed API/database/DNS paths plus denied alternatives. Third, measure startup and request duration, implement probes and shutdown handling, then configure requests, HPA, zone spreading, and surge capacity. Finally, stage a rollout, drain, node failure, zone outage, missing-metrics event, and database recovery exercise. Release only after checking availability and application outcomes. At least four limits remain unproven by these documents: actual worst-case startup, successful completion of long requests, capacity and scheduling during zone loss, and database restoration correctness. Network enforcement and metrics availability also require cluster verification. Sources: `concepts/workloads/pods/disruptions.md:129-145`; `concepts/workloads/pods/pod-lifecycle.md:612-638`; `concepts/services-networking/network-policies.md:43-49`; `concepts/storage/persistent-volumes.md:185-210`.
