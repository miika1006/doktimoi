Decision: revise before production approval. Kubernetes provides useful controls, but the proposed settings do not establish five-replica availability, completion of long requests, or database durability. The recommendations below distinguish documented behavior from configuration choices and validation prerequisites. Citations refer only to the supplied local corpus.

1. **PDB and rollout availability.** `minAvailable: 5` does **not** guarantee five available replicas during node failure: involuntary disruptions cannot be prevented and count against the budget. During a node drain using the Eviction API, it constrains voluntary evictions; requests can be rejected and retried. Direct deletion bypasses this protection. Deployment rolling updates are not constrained by PDBs, although their unavailable Pods count against the budget. [Source: `docs/concepts/workloads/pods/disruptions.md`, lines 99–136.]

   At six desired replicas, `maxUnavailable: 2` permits a rollout availability floor of four. Choose `maxUnavailable: 1`, `maxSurge: 1`, or conservatively zero unavailable with one surge, providing capacity for the extra Pod. These constrain rollout behavior, not simultaneous failures. [Source: `docs/concepts/workloads/controllers/deployment.md`, lines 1191–1211.]

2. **Zone placement.** Configure a matching application `labelSelector`, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`; aim for two replicas per zone. `topologyKey` groups nodes by label value. With `DoNotSchedule`, skew limits the difference between the target domain’s matching-Pod count and the global minimum. `ScheduleAnyway` instead prefers placements that reduce skew, permitting imbalance. [Source: `docs/concepts/scheduling-eviction/topology-spread-constraints.md`, lines 82–130.]

   Choose hard spreading only if pending replacement Pods are acceptable. If a zone becomes ineligible and `minDomains: 3`, the global minimum becomes zero, potentially blocking replacements in surviving zones. Without that setting, the default minimum-domain count is one. Actual outage behavior depends on domain eligibility; “unavailable” does not itself establish that a domain disappears. A soft constraint favors replacement capacity. Losing a zone containing two replicas still leaves only four immediately. Spreading also does not guarantee balance after deletions. [Same source, lines 95–126, 605–619.]

3. **Slow-start probes.** Use a startup probe with `failureThreshold × periodSeconds` covering measured worst-case initialization. Until it succeeds, readiness and liveness probes are disabled. Exhausting startup failures kills the container, subject to restart policy. After startup, readiness should test ability to serve requests; failure removes the Pod from matching Service endpoints without itself restarting the container. Liveness should detect a condition for which restarting is useful, rather than merely slow initialization or a transient database outage. Liveness failure kills the container, with restart governed by policy. Probe meanings are documented; suitable checks and thresholds are application choices. [Sources: `docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md`, lines 311–346; `docs/concepts/workloads/pods/pod-lifecycle.md`, lines 479–497.]

4. **Termination and long requests.** The grace period is recorded as termination begins; `preStop` runs before the runtime receives TERM/SIGTERM. The hook consumes the grace period—it does not receive an additional full interval. An unfinished hook can receive a small, one-off two-second extension. At grace expiry, remaining processes receive SIGKILL. [Source: `docs/concepts/workloads/pods/pod-lifecycle.md`, lines 581–609, 634–639.]

   Endpoint changes happen concurrently with shutdown. Terminating endpoints are not immediately removed from EndpointSlices but have `ready: false` for regular traffic; `serving` supports draining decisions. Thirty seconds is therefore **not** a request-completion guarantee. Measure hook duration and request drain time, implement graceful signal handling, and configure an adequate budget. [Same source, lines 612–632.]

5. **Resource sizing.** CPU requests inform scheduling and define the denominator for utilization-based HPA; they are not CPU ceilings. Containers may exceed requests when resources permit. CPU limits impose throttling. Memory limits are enforced reactively through OOM kills, so excess memory may cause termination rather than throttling, and enforcement need not be immediate. Set requests and limits from measured workload behavior. [Source: `docs/concepts/configuration/manage-resources-containers.md`, lines 18–53.]

   If relevant CPU requests are missing from some containers, Pod CPU utilization is undefined and HPA takes no action for that metric. Check effective admitted resources: when a limit exists without a request or admission default, Kubernetes copies the limit into the request. [Sources: `docs/tasks/run-application/horizontal-pod-autoscale.md`, lines 89–102; `docs/concepts/configuration/manage-resources-containers.md`, lines 64–66.]

6. **HPA adjustments.** The initial calculation is the rounded-up product of current replicas and current/desired metric values, with default tolerance 0.1. Missing metrics are set aside, then conservatively treated as 100% of target for downscaling and 0% for upscaling. Not-yet-ready Pods also dampen CPU scale-up through an assumed zero contribution. A revised ratio that reverses direction or enters tolerance produces no scaling. Reported utilization can remain the unadjusted value. [Source: `docs/tasks/run-application/horizontal-pod-autoscale.md`, lines 132–202.]

   Readiness classification uses configurable timing heuristics: defaults are 30 seconds for initial readiness delay and five minutes for CPU initialization. Downscale stabilization separately defaults to five minutes and selects the highest recommendation in that window. Consequently, raw-ratio expectations are insufficient. Validate startup behavior against actual controller settings. [Same source, lines 163–178, 213–218.]

7. **Least-privilege networking.** Establish ingress and egress default denial, then explicitly allow approved callers to the API, API-to-database traffic on required ports, DNS, and other demonstrated dependencies. Isolation is directional: selecting a Pod for ingress does not isolate its egress. Policies combine additively, so a broad allow can defeat the intended restriction. Both source egress and destination ingress must permit a connection; reply traffic is implicitly allowed. Node-originated ingress has a documented exception. [Source: `docs/concepts/services-networking/network-policies.md`, lines 53–81, 210–259.]

   Allow DNS only to the actual cluster resolver; the documented example exposes UDP and TCP port 53. Verify the deployed DNS path. A NetworkPolicy-capable CNI/controller is a prerequisite: policy objects alone have no effect. [Sources: `docs/tasks/administer-cluster/dns-debugging-resolution.md`, lines 160–168; `docs/concepts/services-networking/network-policies.md`, lines 47–49.]

8. **Secret protection.** Reject base64-encoded Secrets in Git as a protection mechanism: encoding obscures data but does not make it secret. Enable encryption at rest and least-privilege RBAC, restrict Secret access to necessary containers, and replace repository-held credentials with a controlled delivery process. Encryption of cluster storage does not protect a readable repository copy. [Source: `docs/concepts/configuration/secret.md`, lines 35–48, 306, 455–456.]

   Restrict workload creation as well as direct Secret reads: permission to create Pods in a namespace—including indirectly through Deployments—can expose any Secret there. Default etcd storage is unencrypted. [Same source, lines 35–46.]

9. **Storage lifecycle.** Changing a StorageClass reclaim policy does not retroactively change existing PV policies; inspect and edit existing PVs separately. Dynamically provisioned PVs inherit the class policy, defaulting to `Delete`. `Retain` leaves a released PV and its data for manual reclamation after PVC deletion. Supported `Delete` implementations remove both the PV and backing storage. [Sources: `docs/concepts/storage/storage-classes.md`, lines 126–135; `docs/concepts/storage/persistent-volumes.md`, lines 180–210.]

   StatefulSet deletion/scaling is a separate trigger: PVC retention defaults to `Retain`; `whenDeleted` and `whenScaled` can request PVC deletion, after which PV reclamation applies. Verify the documented feature-gate prerequisite. These StatefulSet settings do not automatically apply to the API Deployment or establish the unspecified database architecture. [Source: `docs/concepts/workloads/controllers/statefulset.md`, lines 391–423.]

10. **Prioritized validation checklist.** First remove exposed credentials, verify RBAC and encryption, test network enforcement, and inspect existing database PV policies. Second implement probes, graceful draining, compatible rollout settings, and zone placement. Third load-test resource sizing and HPA, then rehearse rolling updates, drains, node/zone loss, and disposable PVC deletion.

   Release gates must include measured request completion, startup/probe accuracy, CNI enforcement, replacement capacity during zone loss, and database recovery. These documents establish mechanisms—not application latency bounds, spare cluster capacity, or backup/recovery guarantees. The checklist follows the documented shutdown deadline, policy prerequisite, scheduling restrictions, and destructive reclaim behavior. [Sources: `docs/concepts/workloads/pods/pod-lifecycle.md`, lines 619–639; `docs/concepts/services-networking/network-policies.md`, lines 47–49; `docs/concepts/scheduling-eviction/topology-spread-constraints.md`, lines 107–126; `docs/concepts/storage/persistent-volumes.md`, lines 187–210.]
