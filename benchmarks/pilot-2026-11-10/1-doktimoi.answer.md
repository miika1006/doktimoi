**Decision memo — revise before production approval.** The proposed settings do not establish five-replica availability, safe request draining, or database durability. Adopt the following configuration choices and validate their prerequisites. References below identify paths and source lines within the supplied `docs` corpus.

1. **PDB protection depends on the disruption.** A node failure is involuntary: a PDB cannot prevent it, although unavailable Pods count against the budget. During node drain, tools using the Eviction API respect `minAvailable: 5`; with six healthy replicas, one eviction is permitted, and subsequent requests may wait. Direct deletion bypasses this protection. Deployment rolling updates are not constrained by PDBs, so `maxUnavailable: 2` permits a rollout availability floor of four. Recommend `maxUnavailable: 0`, `maxSurge: 1`, with capacity for the surge; `maxUnavailable: 1` is also compatible with a five-of-six rollout floor. These govern controller actions, not simultaneous failures. Keep the HPA minimum consistent with the six-replica baseline. Sources: `concepts/workloads/pods/disruptions.md:93–141`; `concepts/workloads/controllers/deployment.md:1189–1214`.

2. **Spread explicitly, with a deliberate failure tradeoff.** Select this API’s Pods and use `topologyKey: topology.kubernetes.io/zone`, targeting two replicas per zone. `topologyKey` groups nodes sharing a label value. With `DoNotSchedule`, `maxSkew: 1` limits the difference between the target domain’s matching Pod count and the global minimum; it is a scheduling constraint. `ScheduleAnyway` instead prefers placements reducing skew without enforcing that bound. When a zone becomes unavailable, replacement scheduling depends on eligible domains, taints, capacity, and `minDomains`. In particular, `minDomains: 3` makes the global minimum zero when fewer than three domains qualify, potentially blocking replacements. Recommend strict spreading only with an explicit degraded-zone recovery plan; choose soft spreading if replacement capacity takes priority. Losing two zonal replicas immediately leaves four, regardless of PDB. Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:82–132,165–190,196–212`.

3. **Separate startup, serving readiness, and liveness.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Until startup succeeds, readiness and liveness probes are disabled. Thereafter, readiness should represent whether the API can serve requests; failure removes the Pod from matching Service endpoints without itself restarting the container. Liveness should detect a condition requiring restart, such as a deadlock. Startup or liveness failure triggers killing and restart-policy handling after the configured failure criteria. A database outage should not automatically mean the API needs restarting; dependency-sensitive readiness is an application decision requiring testing. Endpoint removal does not establish instantaneous cessation of every existing connection. Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–347`; `concepts/workloads/pods/pod-lifecycle.md:474–497`.

4. **Thirty seconds is a deadline, not a request-completion guarantee.** The grace-period countdown begins **before** `preStop`; the hook consumes that budget. The kubelet runs the hook, then triggers TERM delivery to the container’s process 1. An overrunning hook can receive a small, one-off two-second extension. At grace expiry, remaining processes receive SIGKILL. In parallel, terminating endpoints remain temporarily represented in EndpointSlices with `ready: false`, excluding them from regular traffic; `serving` supports draining-aware consumers. Configure application shutdown to stop accepting work and finish outstanding requests, and size grace time for the hook plus measured draining time. Long requests may otherwise be killed. Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:992–1008`; `concepts/workloads/pods/pod-lifecycle.md:581–645`.

5. **Requests and limits serve different purposes.** CPU requests inform scheduling and provide the denominator for utilization-based HPA; they are not a CPU ceiling. Containers can exceed requests when resources permit. CPU limits enforce throttling, potentially delaying requests. Memory limits are enforced reactively through OOM killing, rather than CPU-style throttling; exceeding a memory limit does not necessarily cause an immediate kill. Set measured CPU requests for every relevant container. If some containers lack effective CPU requests, Pod CPU utilization is undefined and HPA cannot act on that metric. Inspect admitted specifications: absent requests can be defaulted from limits. Sources: `concepts/configuration/manage-resources-containers.md:18–25,27–53,63–67`; `tasks/run-application/horizontal-pod-autoscale.md:89–101`.

6. **HPA deliberately adjusts the raw ratio.** The basic calculation is the ceiling of current replicas multiplied by current/desired metric value, with default tolerance of 0.1. Missing metrics are conservatively treated as 100% of target for downscaling and 0% for upscaling. Not-yet-ready Pods are set aside for CPU calculations and, when considering scale-up, assumed to consume 0%, damping expansion. Readiness interpretation uses configurable defaults of 30 seconds initial readiness delay and five minutes CPU initialization period. A recalculated ratio that reverses direction or falls within tolerance causes no scaling. Downscale stabilization defaults to five minutes and selects the highest recommendation in that window. Consequently, reported utilization need not reproduce the actual scaling decision. Sources: `tasks/run-application/horizontal-pod-autoscale.md:129–218`.

7. **Replace default allow with tested directional policies.** Establish ingress and egress isolation, then permit only approved callers to the API port, API connections to the database port, DNS resolution to the intended resolver, and other demonstrated dependencies. Ingress and egress isolation are independent. Policies are additive unions: a permissive policy cannot be overridden by adding a restrictive one. For Pod-to-Pod connections, source egress and destination ingress must both allow the connection; return traffic is implicitly allowed. Ingress isolation also retains the documented node-traffic exception. A supporting CNI/network-policy implementation is a prerequisite—creating policy objects alone has no effect. Validate DNS and database connectivity after enforcement. Sources: `concepts/services-networking/network-policies.md:44–81`; `concepts/security/multi-tenancy.md:208–225,231–234`.

8. **Base64 is not Secret protection.** Reject base64-encoded credentials in Git: the documentation explicitly describes base64 credentials as obscured, not secret. Kubernetes Secrets are stored unencrypted in etcd by default. Enable encryption at rest, ensure previously stored Secrets are rewritten for encryption, restrict Secret access through least-privilege RBAC, and expose credentials only to containers needing them. Restrict workload-creation permissions too: someone authorized to create Pods in a namespace can read its Secrets through those Pods, including indirectly through Deployment creation. Encryption at rest therefore does not replace authorization controls or protect a readable Git copy. Sources: `concepts/configuration/secret.md:35–48,305–310`; `tasks/administer-cluster/encrypt-data.md:590–607`.

9. **PV reclamation and PVC retention are separate decisions.** A StorageClass supplies the reclaim policy when dynamic PVs are created; changing the class does not retrofit existing PVs—inspect and edit those PVs individually. The default is `Delete`. With supported plugins, `Delete` removes both the PV and backing storage; `Retain` leaves a released PV and its data requiring manual reclamation after PVC deletion. StatefulSet deletion or scale-down does not delete template-created PVCs by default. Its separate `whenDeleted` and `whenScaled` retention settings can request deletion, subject to the documented feature prerequisite. Those PVC deletions then expose storage to PV reclaim behavior. Do not assume the API’s Deployment provides database lifecycle protection. Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:179–210`; `concepts/workloads/controllers/statefulset.md:387–423`.

10. **Prioritize validation before rollout.** First remove Git credentials, verify encryption/RBAC and CNI enforcement, and inspect database PVC retention and actual PV reclaim policies. Second measure startup, CPU, memory, and shutdown behavior; configure probes, requests, HPA, and grace time accordingly. Third verify zone labels and surge capacity, deploy the revised rollout strategy, and exercise drain, rolling update, node failure, and zone loss separately. Finally test missing metrics, DNS restrictions, unauthorized connections, database recovery, and long requests during termination. Unproven limits include request-draining duration, adequate capacity after zone loss, CPU’s suitability as a demand signal, and database recovery/durability. The documents provide mechanisms, not those application-specific guarantees. Sources: `concepts/workloads/pods/disruptions.md:93–141`; `concepts/workloads/pods/pod-lifecycle.md:581–645`; `tasks/run-application/horizontal-pod-autoscale.md:129–218`; `concepts/storage/persistent-volumes.md:179–210`.
