**Decision: revise before production approval.** The proposed fields provide useful controls, but do not establish five-replica availability, successful request draining, or database durability. Recommendations below are configuration choices unless identified as documented behavior. All source paths are relative to the supplied `docs/` directory; citations include source line ranges.

1. **PDB and rollout availability.** A PDB cannot prevent involuntary node failures; their unavailable Pods nevertheless consume its budget. During an eviction-based drain, `minAvailable: 5` permits one healthy replica’s eviction when six are healthy, then blocks further disruptive evictions until availability recovers. This depends on using the Eviction API, not direct deletion, and does not protect against concurrent failures. Deployment rolling updates are not constrained by PDBs. Consequently, `maxUnavailable: 2` permits rollout availability to fall to four. Recommend `maxUnavailable: 1`, `maxSurge: 1`, with capacity for surge Pods; use `maxUnavailable: 0` if preserving all six during planned updates warrants additional waiting. Neither configuration guarantees availability through simultaneous failures.  
   Sources: `concepts/workloads/pods/disruptions.md:99–136`; `concepts/workloads/controllers/deployment.md:1189–1211`.

2. **Zone placement.** Configure topology spread using the API’s Pod selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, targeting two replicas per zone. The topology key identifies node labels whose equal values form domains. With `DoNotSchedule`, skew bounds the difference between the target domain’s matching-Pod count and the global minimum; violating placements remain unscheduled. `ScheduleAnyway` instead prefers reduced skew without enforcing the bound. For this API, prefer the latter if restoring serving capacity during zone loss outweighs strict balance. With strict placement, explicitly decide `minDomains`: setting three makes the global minimum zero when fewer than three eligible domains remain, potentially blocking replacements. Zone unavailability does not necessarily mean domain disappearance; eligibility and existing nodes matter. Constraints also do not guarantee continued balance after removals.  
   Sources: `concepts/scheduling-eviction/topology-spread-constraints.md:82–130,527–529,605–623`.

3. **Probes for slow startup.** Use a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case initialization. Readiness and liveness begin only after startup succeeds. Configure readiness to reflect whether the API can serve requests, including indispensable database dependencies; readiness failure removes the Pod from matching Service endpoints without itself restarting the container. Use liveness for conditions such as deadlock that restarting can remedy, rather than a temporary database outage. Startup or liveness failure reaching the configured threshold kills the container, with subsequent restart governed by its restart policy. These mechanisms do not prove that the chosen health checks accurately represent application health.  
   Sources: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:311–318,342–358`; `concepts/workloads/pods/pod-lifecycle.md:479–497`.

4. **Termination and long requests.** The grace-period countdown starts **before** `preStop`; hook execution consumes that budget. Normally, the hook runs before the runtime sends TERM to the container’s main process. The kubelet requests a small, one-off two-second extension if the hook overruns; remaining processes face SIGKILL when termination expires. Endpoint updates occur concurrently with shutdown: terminating endpoints are not immediately removed from EndpointSlices, but have `ready: false` and are excluded from regular traffic; `serving` supports draining-aware consumers. Thirty seconds is a default, not a request-completion guarantee. Measure hook duration, request duration, and routing behavior, then configure sufficient grace and application signal handling.  
   Sources: `reference/kubernetes-api/workload-resources/pod-v1.md:1008`; `concepts/workloads/pods/pod-lifecycle.md:581–639`.

5. **Resource sizing and CPU HPA.** Set explicit, measured CPU requests for every relevant container. Requests drive scheduling capacity checks and typically determine relative CPU allocation under contention; they are not usage ceilings. CPU limits impose throttling, potentially increasing request latency. Memory limits are enforced reactively through OOM killing, rather than equivalent CPU-style throttling; exceeding a memory limit need not trigger an immediate kill. Set memory requests and limits from measured workloads. Utilization-based HPA divides CPU usage by requested CPU: if relevant requests are missing from some containers, Pod CPU utilization is undefined and HPA cannot act on that metric.  
   Sources: `concepts/configuration/manage-resources-containers.md:27–53,230–265`; `tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **HPA’s conservative adjustments.** HPA sets aside missing metrics and, for CPU, certain not-yet-ready Pods or samples predating readiness. Default readiness and CPU-initialization windows are 30 seconds and five minutes. For missing metrics, recalculation assumes 100% of target during downscale and 0% during upscale. Not-yet-ready Pods also contribute an assumed 0% when considering upscale, damping expansion. If recalculation reverses direction or falls within tolerance, scaling stops; default tolerance is 0.1. Downscale stabilization chooses the highest recommendation within the preceding window, defaulting to five minutes. Reported utilization excludes these conservative adjustments, so replica changes can differ from the apparent raw ratio. Validate startup behavior against the controller’s actual settings.  
   Source: `tasks/run-application/horizontal-pod-autoscale.md:141–218`.

7. **Least-privilege networking.** Replace namespace default allowance with ingress and egress default-deny policies, then explicitly permit approved callers to the API port, API egress to the database port, and corresponding database ingress. Allow required DNS access to the cluster’s actual resolver endpoints and ports; Service-name discovery depends on DNS. Ingress and egress isolation are independent. Policies combine additively as a union, so an existing broad allow policy defeats a narrower intended restriction. Both source egress and destination ingress must permit a connection; reply traffic is implicitly allowed. A supporting CNI/network-policy implementation is a prerequisite: creating policy objects alone can have no effect. Test allowed and denied paths, including DNS.  
   Sources: `concepts/services-networking/network-policies.md:45–81,210–259`; `concepts/services-networking/dns-pod-service.md:15–26`.

8. **Secrets and Git.** Base64 is insufficient protection: the documentation describes a base64 credential as “obscured but not secret.” Do not commit usable credentials merely because their Secret representation is encoded. Enable Secret encryption at rest; Secrets are otherwise stored unencrypted in etcd. Apply least-privilege RBAC and expose each Secret only to containers that require it. Restrict workload creation permissions too: someone authorized to create Pods, including indirectly through Deployments, can read any Secret in that namespace by arranging its consumption. Encryption at rest therefore does not replace authorization controls or protect a separately exposed Git copy.  
   Source: `concepts/configuration/secret.md:35–48,286–306,455–456`.

9. **Storage lifecycle.** Changing a StorageClass reclaim policy does not retroactively change existing PVs: the class supplies provisioning-time settings, and existing PVs must be edited or patched separately. `Retain` leaves a released PV and its data for manual reclamation after PVC deletion. With a supporting plugin, `Delete` removes both the PV and backing storage; dynamically provisioned volumes default to this unless configured otherwise. Active-use protection postpones PVC removal, not eventual reclamation. StatefulSet deletion or scaling normally retains its PVCs; optional `whenDeleted` and `whenScaled` retention settings can instead delete them, subsequently invoking PV reclamation. The supplied StatefulSet page identifies the feature-gate prerequisite. Prefer deliberate retention for database data, backed by recovery procedures.  
   Sources: `concepts/storage/storage-classes.md:34–36,126–135`; `concepts/storage/persistent-volumes.md:123–136,179–210`; `concepts/workloads/controllers/statefulset.md:391–423`.

10. **Prioritized rollout and validation checklist.**

   - **Before deployment:** remove encoded credentials from the proposed Git workflow; verify encryption, RBAC, workload-creation permissions, CNI enforcement, existing PV reclaim policies, and StatefulSet retention settings. These controls have separate prerequisites and lifecycle effects, as documented in questions 7–9.
   - **Before traffic:** configure probes, measured resource requests, a conservative rollout, zone placement, and adequate grace. Reserve surge and failure-recovery capacity. For topology-constrained storage, consider supported `WaitForFirstConsumer` provisioning; immediate binding can leave Pods unschedulable (`concepts/storage/storage-classes.md:171–195`).
   - **Before approval:** exercise drain, rolling update, node/zone loss, cold startup, missing metrics, database outage, long-request termination, and restore scenarios. Validate at least four limits the cited mechanisms do not establish: application health-check accuracy, maximum successful drain duration, sufficient surviving-zone capacity, and database recovery correctness. Also establish whether CPU utilization predicts API demand. PDB scope, scheduling limitations, forced termination, and HPA adjustments explicitly prevent treating field configuration as an end-to-end availability guarantee (`concepts/workloads/pods/disruptions.md:130–136`; `concepts/scheduling-eviction/topology-spread-constraints.md:605–623`; `concepts/workloads/pods/pod-lifecycle.md:619–639`; `tasks/run-application/horizontal-pod-autoscale.md:183–218`).
