**Decision memo — revise before production.** The proposed fields do not establish end-to-end availability, request completion, or database durability. Adopt the following configuration choices and validate their prerequisites. Citations refer exclusively to supplied local documents; paths are relative to the corpus’s `docs/` directory.

1. **The PDB is not a universal five-replica guarantee.** During node failure, involuntary losses cannot be prevented by a PDB, although they count against its budget. During an eviction-based node drain, `minAvailable: 5` permits one healthy replica’s eviction from six; subsequent evictions can be rejected until availability recovers. This depends on tools using the Eviction API rather than directly deleting Pods. During Deployment rolling updates, unavailable Pods count against the budget, but the Deployment controller is not constrained by it.  
   **Recommendation:** replace `maxUnavailable: 2`, which permits four available replicas, with `maxUnavailable: 0, maxSurge: 1`; reserve surge capacity. `maxUnavailable: 1` is also compatible with a five-replica rollout floor, absent other failures. These settings govern rollout behavior, not simultaneous failures.  
   Sources: `concepts/workloads/pods/disruptions.md:99–143`; `concepts/workloads/controllers/deployment.md:1189–1206`.

2. **Spread explicitly, while choosing the outage tradeoff.** Use an API-specific selector, `topologyKey: topology.kubernetes.io/zone`, and `maxSkew: 1`, targeting two replicas per zone. `topologyKey` groups nodes by equal label values. With `DoNotSchedule`, skew bounds the target domain’s matching-Pod count relative to the global minimum; violating placements remain unscheduled. `ScheduleAnyway` instead prefers placements that reduce skew, without enforcing the bound.  
   I recommend strict spreading initially, with a tested outage procedure. An unavailable zone does not automatically imply redistribution: eligibility, remaining nodes, and `minDomains` matter. With `minDomains: 3`, fewer than three eligible domains makes the minimum zero and can block replacements in already populated zones. Soft spreading favors replacement capacity but sacrifices guaranteed balance. Neither option preserves balance after Pod removals.  
   Source: `concepts/scheduling-eviction/topology-spread-constraints.md:82–126,527–529,605–619`.

3. **Separate initialization, serving readiness, and unrecoverable failure.** Configure a startup probe whose `failureThreshold × periodSeconds` covers measured worst-case startup. Readiness and liveness probes begin only after startup succeeds. Exhausting startup failures kills the container, with restart governed by its restart policy. Use readiness to report whether the API can serve requests; becoming unready removes it from Service load balancers, rather than restarting it. Use liveness for failures a restart can remedy, such as deadlock.  
   Avoid making a transient database outage alone trigger liveness failure: this is a design recommendation consistent with the documented warning about cascading restarts. Probe thresholds and dependency checks require application testing.  
   Source: `tasks/configure-pod-container/configure-liveness-readiness-startup-probes.md:14–46,311–347`.

4. **Thirty seconds is a shutdown allowance, not a completion guarantee.** The grace period encompasses shutdown, including `preStop`; it is not a fresh allowance after the hook. The kubelet runs `preStop` before asking the runtime to signal the container’s main process with TERM. A still-running hook can receive a one-off two-second extension. At grace expiry, remaining processes receive SIGKILL.  
   Endpoint processing happens concurrently with local shutdown. Terminating endpoints remain temporarily in EndpointSlices but have `ready: false`, excluding them from regular load balancing; `serving` supports draining-aware consumers. This does not establish that existing long requests finish or that traffic changes propagate instantaneously. Measure hook duration, request duration, connection draining, and database cleanup, then set a sufficient grace period.  
   Source: `concepts/workloads/pods/pod-lifecycle.md:567–577,581–639`.

5. **Size requests and limits independently.** CPU requests inform scheduling and provide the denominator for utilization-based HPA; they are not CPU ceilings. Containers can exceed requests when resources permit. CPU limits enforce a ceiling through throttling. Memory limits use reactive OOM killing: exceeding a limit can terminate the container, rather than merely slow it, and enforcement need not be immediate.  
   Set realistic CPU requests for every relevant container and test limits against latency and memory peaks. If some containers lack CPU requests, Pod CPU utilization is undefined and HPA takes no action for that metric. Inspect admitted configuration: when a limit exists without a request or admission default, Kubernetes copies the limit into the request.  
   Sources: `concepts/configuration/manage-resources-containers.md:18–53,64–66`; `tasks/run-application/horizontal-pod-autoscale.md:89–102`.

6. **Expect HPA decisions to differ from the raw ratio.** The starting calculation is current replicas multiplied by current/desired metric, rounded up, with default tolerance of 0.1. Missing metrics are set aside, then conservatively treated as 100% of target during downscale and 0% during upscale. Not-yet-ready Pods also dampen CPU-based upscale through a 0% assumption. If recomputation reverses direction or falls within tolerance, scaling stops.  
   Readiness classification uses configurable defaults of 30 seconds for initial readiness delay and five minutes for CPU initialization. Downscale stabilization defaults to five minutes and selects the highest recommendation within that window. Reported utilization excludes these conservative adjustments, so status alone need not reproduce the scaling decision.  
   Source: `tasks/run-application/horizontal-pod-autoscale.md:135–202,213–218`.

7. **Apply least privilege in both directions.** Establish namespace-wide default-deny ingress and egress, then allow intended clients to the API port, API egress to the database port, and corresponding database ingress. Permit other demonstrated dependencies explicitly. Allow DNS egress to the actual cluster resolver; the documented DNS Service example exposes both UDP and TCP port 53, but its address must be discovered locally.  
   Ingress and egress isolation are independent. Policies combine additively: a broad allow cannot be overridden by a later deny. Both source egress and destination ingress must permit a Pod-to-Pod connection; replies are implicitly allowed. A prerequisite is a CNI/network implementation enforcing NetworkPolicy—creating objects alone has no effect. Isolation also has documented exceptions, including node-origin ingress.  
   Sources: `concepts/services-networking/network-policies.md:45–81,254–262`; `tasks/administer-cluster/dns-debugging-resolution.md:158–170`.

8. **Base64 is not protection for credentials in Git.** Reject this proposal: the documentation explicitly describes base64-encoded credentials as obscured, not secret. Remove credential values from committed manifests and use a controlled secret-delivery process. Enable encryption at rest, since Secrets are stored unencrypted in etcd by default; configure least-privilege RBAC and restrict exposure to necessary containers.  
   Restrict workload creation as well as direct Secret reads. Permission to create a Pod in a namespace—including indirectly through a Deployment—allows reading that namespace’s Secrets. Encryption at rest does not address that authorized workload-access path or protect a Git copy.  
   Source: `concepts/configuration/secret.md:35–48,286–306`.

9. **Existing PVs require their own reclaim-policy review.** Dynamically provisioned PVs inherit the StorageClass policy, defaulting to `Delete`. Changing the class is not a retroactive repair: inspect and patch existing PVs individually. With `Retain`, deleting the PVC leaves the PV released, with data requiring manual reclamation. With supported `Delete` implementations, reclamation removes both the PV object and backing storage.  
   StatefulSet deletion or scale-down is a separate decision: template PVCs default to retention. Optional `whenDeleted` and `whenScaled` policies can delete the corresponding PVCs, after which PV reclaim behavior matters. Verify the documented `StatefulSetAutoDeletePVC` prerequisite. Dynamic provisioning alone establishes neither backups nor database recovery.  
   Sources: `concepts/storage/storage-classes.md:126–135`; `concepts/storage/persistent-volumes.md:180–209`; `concepts/workloads/controllers/statefulset.md:391–421`.

10. **Prioritize validation before widening rollout.** First, remove Git credentials, verify encryption/RBAC, enforce and test network isolation, and inventory existing PV policies. Second, measure startup and shutdown, set probes/resources/grace periods, reserve surge capacity, and adopt the revised rollout settings. Third, exercise a canary through drain, node/zone loss, long-request termination, missing metrics, and database recovery; inspect availability, EndpointSlices, HPA decisions, and retained storage before expanding. These checks follow the mechanisms and prerequisites cited above, especially `concepts/workloads/pods/disruptions.md:108–143`, `concepts/services-networking/network-policies.md:45–81`, and `concepts/storage/persistent-volumes.md:180–209`.

   Unresolved limits requiring application or cluster evidence include worst-case request completion, truthful probe behavior under database failure, spare capacity during zone loss, actual CNI enforcement, and database restore correctness. The supplied mechanisms do not guarantee any of these outcomes.
